上一章我们已经实现了完整的时间轮管理延迟消息功能了，这就意味着时间轮已经可以严格按照时间刻度来处理延迟消息，那接下来我们就要一起来看看，所谓的处理消息，这里面要执行的操作究竟是什么了。当然，这一块的内容我也早就跟大家简单讲解过了，在处理延迟消息的时候，这条消息的主题信息肯定是系统内置的延迟消息主题，那这个时候就要把消息的主题信息更改为它的原始主题信息， 然后再重新把它投递到 CommitLog 本地文件中即可。在这个过程中，这条消息也就会被写入到真正主题的消费队列中，等待被消费者客户端消费。这个逻辑大家应该还有印象吧？



而且我还记得之前跟大家提到过，因为处理每一条延迟消息的操作都相同，所以倒不如定义一个公共方法，只要时间轮要处理延迟消息了，就把消息交给这个公共方法处理，而公共方法的内容也就是刚才分析的那些操作。这些都很容易理解吧？当然，我们都是在没实现时间轮之前讨论的这些内容，现在时间轮组件已经定义完了，我们也为消息引入了滚动属性，并且也剖析了本地消息过期带来的问题，以及解决该问题的方式，了解了这些之后，那么这个公共方法就要做一点小小的改动。



也就是说，**当时间轮要真正处理延迟消息的时候，必须在公共方法中判断消息的魔术信息，如果是滚动属性，那么这条消息就要重新被投递到 CommitLog 本地文件中，并且消息的主题仍然是延迟消息主题，以防本地消息被过期删除；假如消息的魔术信息是默认信息，那就可以把消息的主题更改为原始主题信息，然后再把消息投递到 CommitLog 本地文件中即可**。这个逻辑大家都可以理解吧？如果这个逻辑大家都理解了，那接下来我们就要执行一个重要的操作，那就是启动一个新的线程，开始处理时间轮中到期的延迟消息。



既然要启动新的线程了，那这个时候就要更仔细一些，把这个线程要执行的工作给明确了。线程一旦启动，首先就得根据当前系统时间定位到对应的时间轮刻度，然后得到该刻度的所有消息。那得到这些消息之后呢？别忘了时间轮中存储的只是消息的关键信息，这个时候显然还要根据消息的关键信息到 CommitLog 文件中查询对应的完整消息。执行到这里还没完，查询到消息的完整消息之后，接下来就要判断这条消息是需要滚动还是真正被处理，如果需要滚动，则直接投递该消息到 CommitLog 文件中，如果需要真正被处理，则更换消息主题信息，然后投递消息到 CommitLog 文件中。这就是新线程要执行的大概操作。



看到这里，大家肯定会觉得，新启动的线程要执行的操作是不是太多了？如果某个时间刻度存储的消息不多，那么一个线程干这些活还算可以，如果这个时刻存储了巨量的待处理的消息，要让一个线程把这些消息全处理完了，又要从 CommitLog 文件中查数据，又要重新投递消息，那这个线程显然忙不过来。这个时候，**启动多个线程处理这些消息似乎是更有效率的方法**。没错，实际上 RocketMq 源码中也正是这么做的，在源码中，**时间轮处理消息的时候确实只启动了一个线程，但这个线程所执行的操作仅仅是根据时间轮指针刻度把对应刻度的消息取出来，然后放到一个新定义的队列中，只要放到这个队列中的消息，就都是到了延迟时间，要被立刻处理的消息。**在执行了这些操作之后，时间轮线程的工作也就完成了。这个时候，要被处理的消息已经从时间轮中存放到新定义的队列中了。然后，**RocketMq 源码又执行了一些新的操作，那就是又定义了多个线程，让这些线程同时到新定义的队列中获取消息，然后处理消息，而处理消息的逻辑和刚才我们一起分析的一样**。这样一来，也就是多个线程同时处理到期的延迟消息，效率自然就提高了。这个逻辑应该也很好理解吧？



如果大家理解了以上逻辑，那接下来我们就可以仿照源码，先把从时间轮取出消息的那个线程定义出来，然后再定义一个新的队列，以便存放从时间轮中取出的消息。当然，这两个我也早就定义好了，**线程就被我定义为了 TimerDequeueGetService 对象，队列仍然是 JDK 的原生阻塞队列，也就是 BlockingQueue 队列，并且这些内容都被我定义在了 TimerMessageStore 类中**，具体内容请看下面代码块。

从上面代码块中可以看到，我们已经定义了新的线程对象，也就是 TimerDequeueGetService 对象，这个线程一旦启动之后，按照我们之前分析的内容来看，它就会从时间轮中取出对应刻度的延迟消息，然后把消息放到新定义的 dequeueGetQueue 任务队列中。核心操作就是在上面代码块中的 dequeue() 方法中执行的，但是这个方法我并没有给大家实现。原因很简单，在具体实现该方法之前，还有一些细节问题需要讨论。



首先我们要明确一点，那就是时间轮处理延迟消息时，肯定是严格遵循指针刻度，也就是系统时间来处理的。**而我们之前也了解了，时间轮的写指针一般都是当前系统时间，所以在 dequeue() 方法中，程序首先就应该判断一下时间轮的读指针是否在合理范围之内，也就是说，时间轮的读指针必须要小于写指针，也就是要小于系统时间；如果时间轮的读指针大于或者等于当前系统时间了，那么这个线程就不能取出时间轮中的消息，而应该直接退出操作**。当然，我能想到有些朋友肯定对这一点有些困惑，当读指针大于写指针的时候，确实应该取消后续操作，但是读指针等于写指针的时候，为什么也要取消操作呢？这里我就要给大家解释一下，**写指针毕竟还代表提交到时间轮种数据的最新时间，如果读指针和写指针相等，就意味着时间轮写数据和读数据可能处于同一时刻，同时操作可能出现并发问题，所以两个指针相等的时候也退出，避免出现两个线程竞争的情况**。大家可以仔细品味品味这个逻辑。



好了，在分析了上面的细节之后，接下来 TimerDequeueGetService 线程对象要执行的操作就很简单了，无非就是根据时间轮读指针刻度定位到时间轮的具体槽位，然后再得到槽位链表中的所有消息，把这些消息再存储到 dequeueGetQueue 队列中即可。当然，存储的时候也不是存储消息本身，自然还要对消息做一层包装，仍然包装成 TimerRequest 对象即可。这一点应该也容易理解吧？最后，在执行完了这些操作之后，还要执行一个非常重要的操作：**那就是把时间轮读指针的刻度向前推移一个精度**，毕竟当前刻度的消息已经处理完毕了。其他的就没什么可分析的了，接下来，就请大家看一下我实现完毕的 dequeue() 方法吧，请看下面代码块。

```java
package org.apache.rocketmq.store.timer;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/10/31
 * @方法描述：定时消息存储引擎
 */
public class TimerMessageStore {


    private static final Logger LOGGER = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //省略该类部分内容

    //新定义的队列，注意，这个队列存储的每一个数据是一个list集合
    //这一点大家一定要看清楚，很快我就会跟大家解释为什么要这么做
    protected final BlockingQueue<List<TimerRequest>> dequeueGetQueue;

    //新定义的时间轮线程，这个也是当前类的内部类
    private TimerDequeueGetService dequeueGetService;

    //当前时间轮的数据读取时间，也就是说，现在时间轮的数据被处理到哪个时间段了
    protected volatile long currReadTimeMs;

    //时间轮写入数据的最新时间
    protected volatile long currWriteTimeMs;
   


    //构造方法
    public TimerMessageStore(final MessageStore messageStore, final MessageStoreConfig storeConfig) throws IOException {

        //省略该方法其他内容
        
        dequeueGetQueue = new LinkedBlockingDeque<>(DEFAULT_CAPACITY);
    }

    //初始化定时消息存储器的方法
    public void initService() {
        //省略该方法其他内容
        dequeueGetService = new TimerDequeueGetService();
    }

    
    //省略该类部分内容

    
    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：退役时间轮读取时间的方法
     */
    private void moveReadTime() {
        //推移到下一个刻度
        currReadTimeMs = currReadTimeMs + precisionMs;
        commitReadTimeMs = currReadTimeMs;
    }

    
    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：时间轮中的消息出队的方法，所谓出队其实就是把时间轮中达到延迟时间的消息取出来，放到dequeueGetQueue队列中等待处理
     */
    public int dequeue() throws Exception {

        //判断程序是否可以执行消息出队操作
        if (!isRunningDequeue()) {
            return -1;
        }
        
        //时间轮的写指针一般都是当前系统时间，所以在当前方法中，程序首先就应该判断一下时间轮的读指针是否在合理范围之内
        //也就是说，时间轮的读指针必须要小于写指针，也就是要小于系统时间；如果时间轮的读指针大于或者等于当前系统时间了，那么这个线程就不能取出时间轮中的消息，而应该直接退出操作
        //这里肯定有朋友疑惑，为什么等于的时候也要退出呢？原因很简单，currWriteTimeMs毕竟还代表了提交时间轮数据的最新时间
        //如果相等了，就意味着写数据和读数据可能处于同一时刻，同时操作可能出现并发问题，所以相等的时候也退出，避免出现两个线程竞争的情况
        if (currReadTimeMs >= currWriteTimeMs) {
            return -1;
        }

        
        //根据最新的消息读取时间得到对应的时间轮槽位，表示此刻要处理这个槽位的消息了
        Slot slot = timerWheel.getSlot(currReadTimeMs);
        //判断当前得到的槽位有没有要被处理的消息
        if (-1 == slot.timeMs) {
            //如果没有消息，那就说明这个时刻没有要被处理的消息，接下来就可以把时间轮时间向后推移，推移到下一个刻度
            //然后退出即可
            moveReadTime();
            return 0;
        }

        
        try {
           
            //得到时间轮槽位存储的条消息在TimerLog文件中的全局偏移量
            long currOffsetPy = slot.lastPos;
           
            //存放要处理的消息的集合
            LinkedList<TimerRequest> normalMsgStack = new LinkedList<>();
            LinkedList<SelectMappedBufferResult> sbrs = new LinkedList<>();
            SelectMappedBufferResult timeSbr = null;

            //接下来就要开始从TimerLog文件中读取消息了
            //因为指定槽位的消息是以链表的形式连接的，现在知道了链表最后一条消息，接下来就可以向前遍历，得到该槽位的所有消息了
            while (currOffsetPy != -1) {

                if (null == timeSbr || timeSbr.getStartOffset() > currOffsetPy) {
                    //根据指定偏移量获取TimerLog文件中对应的缓冲区
                    timeSbr = timerLog.getWholeBuffer(currOffsetPy);
                    if (null != timeSbr) {
                        //成功获取后则把缓冲区添加到集合中
                        sbrs.add(timeSbr);
                    }
                }
                //没有获取到缓冲区则退出循环
                if (null == timeSbr) {
                    break;
                }

                
                //用来记录前一个消息在TimerLog文件中全局偏移量的变量
                long prevPos = -1;
                try {

                    //根据消息全局偏移量和TimerLog单个文件大小计算消息在文件中的相对位置
                    //这里是取模操作
                    int position = (int) (currOffsetPy % timerLogFileSize);
                    //设置读指针位置
                    timeSbr.getByteBuffer().position(position);
                    //读取TimerLog文件中单条消息的大小，这里只是读取，移动指针而已，并不使用读取到的数据
                    timeSbr.getByteBuffer().getInt();
                    //得到前一个消息在TimerLog文件中的全局偏移量
                    prevPos = timeSbr.getByteBuffer().getLong();
                    //得到消息的魔数标志
                    int magic = timeSbr.getByteBuffer().getInt();
                    //得到消息提交到时间轮中的时间
                    long enqueueTime = timeSbr.getByteBuffer().getLong();
                    //得到消息具体的延迟时间
                    long delayedTime = timeSbr.getByteBuffer().getInt() + enqueueTime;
                    //得到消息在CommitLog文件中的全局偏移量
                    long offsetPy = timeSbr.getByteBuffer().getLong();
                    //得到消息完整内容的大小
                    int sizePy = timeSbr.getByteBuffer().getInt();
                    //把这些内容再次封装成一个TimerRequest对象
                    TimerRequest timerRequest = new TimerRequest(offsetPy, sizePy, delayedTime, enqueueTime, magic);
                    //把消息添加到消息集合中
                    normalMsgStack.addFirst(timerRequest);
                }catch (Exception e) {
                    LOGGER.error("Error in dequeue_read_timerlog", e);
                } finally {
                    //在这里更新currOffsetPy，这样一来，进入下一次循环时，就可以得到上一条消息了
                    currOffsetPy = prevPos;
                }
            }



            //执行到这里意味着循环结束了
            if (normalMsgStack.size() == 0) {
                //记录集合为空则记录告警日志
                LOGGER.warn("dequeue time:{} but read nothing from timerLog", currReadTimeMs);
            }

            //释放所有缓冲区资源
            for (SelectMappedBufferResult sbr : sbrs) {
                if (null != sbr) {
                    sbr.release();
                }
            }


            //接下来就是把消息存放到dequeueGetQueue队列的操作
            
            //这里在splitIntoLists()方法中对原集合中的数据重新处理，把原数据切割成多个小集合了
            //这里有一个细节，那就是每一个集合中的数据都属于同一个CommitLog本地文件
            //这里执行这个操作的目的很简单，因为接下来就要根据消息关键信息从CommitLog本地文件中
            //获取消息的完整内容了，把同一个文件中的消息归类到一起有利于提高读效率
            //这也就是dequeueGetQueue队列中存储的是List集合的原因
            for (List<TimerRequest> normalList : splitIntoLists(normalMsgStack)) {
                dequeueGetQueue.put(normalList);
            }

            //在这里更新时间轮刻度，接下来就可以处理下一个刻度的消息了
            moveReadTime();
            
        } catch (Throwable t) {
            LOGGER.error("Unknown error in dequeue process", t);
        }
        return 1;
        
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：将数据切割成多个集合的方法
     */
    private List<List<TimerRequest>> splitIntoLists(List<TimerRequest> origin) {

        List<List<TimerRequest>> lists = new LinkedList<>();

        //判断原集合大小，如果数据小于100条则无需切割
        if (origin.size() < 100) {
            lists.add(origin);
            return lists;
        }


        List<TimerRequest> currList = null;
        int fileIndexPy = -1;
        int msgIndex = 0;

        for (TimerRequest tr : origin) {
            //这里有一个很重要的细节，那就是判断遍历到的消息，是否属于同一个CommitLog文件
            if (fileIndexPy != tr.getOffsetPy() / commitLogFileSize) {
                //重置本批次存储的消息的数量
                msgIndex = 0;
                //如果本批次数据不为空，则把本批次集合添加到结果列表中
                if (null != currList && currList.size() > 0) {
                    lists.add(currList);
                }
                //执行到这里意味着当前消息和之前的消息不属于同一个文件，那就创建新的集合对象
                currList = new LinkedList<>();
                //把当前遍历到的消息添加到本批次集合中
                currList.add(tr);
                //更新当前消息所在文件的索引
                fileIndexPy = (int) (tr.getOffsetPy() / commitLogFileSize);
            } else {
                //执行到这里意味着当前消息和前一条消息在同一个文件中
                //那就直接添加到本批次集合中即可
                currList.add(tr);
                //判断本批次集合的大小，如果达到2000条消息，则创建新的批次集合
                if (++msgIndex % 2000 == 0) {
                    lists.add(currList);
                    currList = new ArrayList<>();
                }
            }
        }
        if (null != currList && currList.size() > 0) {
            lists.add(currList);
        }
        return lists;
    }

}
```

在 RocketMq 源码中是这么做的：**首先定义了一个线程组，然后又定义了一个新的阻塞队列。这个线程组中的每一个线程负责从 dequeueGetQueue 队列中解析每一条消息，然后从本地 CommitLog 文件中查询到完整的消息，然后再把完整消息投递到新定义的阻塞队列中**。到这个时候，新定义的线程组的工作就结束了。也许大家还是稍微感到困惑，不明白为什么到这里就戛然而止了，原因其实很简单，无非就是让线程的职责范围更明确一些，专门的线程负责专门的工作，假如仍然是一个线程来做这些工作，那么这个线程既要从本地查询完整的消息内容，又要把消息重新投递到 CommitLog 文件中，负责的内容稍微多一点。而 RocketMq 源码则让读写操作分离了，当然，这就意味着过一会儿我们还要仿照 RocketMq 源码，再定义一个新的线程组，这个线程组就会从新定义的队列中取出消息，然后判断消失是要滚动还是真正重新投递，接下来执行对应操作即可。

```java
        //省略该方法其他内容

        //省略该方法其他内容

     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * @方法描述：定时消息从时间轮入队服务，这个组件会把dequeueGetQueue队列中的消息存放到dequeuePutQueue队列中

         @Override

            TimerMessageStore.LOGGER.info(this.getServiceName() + " service start");
            while (!this.isStopped()) {
                //从队列中取出要处理的请求集合
                List<TimerRequest> trs = dequeueGetQueue.poll(100L * precisionMs / 1000, TimeUnit.MILLISECONDS);
                if (null == trs || trs.size() == 0) {
                    continue;
                }

                for (int i = 0; i < trs.size(); ) {
                    TimerRequest tr = trs.get(i);
                    //设置消息是否成功添加到dequeuePutQueue队列的标志
                    //只有成功添加了，才执行i++操作，也就是说，本地消息添加失败
                    //下一次进行重试
                    boolean doRes = false;
                    //根据请求封装的信息从CommitLog文件中查找消息的完整内容
                    MessageExt msgExt = getMessageByCommitOffset(tr.getOffsetPy(), tr.getSizePy());
                    if (null != msgExt) {
                        //把完整的消息设置到TimerRequest对象中
                        tr.setMsg(msgExt);
                        while (!isStopped() && !doRes) {
                            //在这里把请求存储到dequeuePutQueue队列中
                            doRes = dequeuePutQueue.offer(tr, 3, TimeUnit.SECONDS);
                        }
                    }else {
                        //没有得到消息则直接更新doRes为true
                        //表示在下次循环寻找新的消息
                        doRes = true;
                    }
                    if (doRes) {
                        i++;
                    }
                }
                //释放资源
                trs.clear();
            }
            TimerMessageStore.LOGGER.info(this.getServiceName() + " service end");
        }
    }
```

好了，那接下来就差最后一步，也就是判断消息是否需要滚动，然后执行不同的操作，如果需要滚动，那就不需要对消息的完整内容进行任何修改，直接把消息重新投递到 CommitLog 文件中即可；假如消息需要被消费，那么就需要更改消息的主题信息为它的原始主题，然后把消息重新投递到 CommitLog 文件中即可。这些操作仍然被交给一个线程组来执行，也就是接下来我们要定义的 TimerDequeuePutMessageService 线程组，这个 TimerDequeuePutMessageService 类仍然是 TimerMessageStore 的内部类，具体内容请看下面代码块。

```java
package org.apache.rocketmq.store.timer;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/10/31
 * @方法描述：定时消息存储引擎
 */
public class TimerMessageStore {


    private static final Logger LOGGER = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);
    
    //省略该类部分内容

    private TimerDequeueGetMessageService[] dequeueGetMessageServices;

    protected final BlockingQueue<TimerRequest> dequeuePutQueue;

    private TimerDequeuePutMessageService[] dequeuePutMessageServices;
   


    //构造方法
    public TimerMessageStore(final MessageStore messageStore, final MessageStoreConfig storeConfig) throws IOException {

        //省略该方法其他内容
        dequeuePutQueue = new LinkedBlockingDeque<>(DEFAULT_CAPACITY);
    }

    //初始化定时消息存储器的方法
    public void initService() {
        //省略该方法其他内容
        int getThreadNum = Math.max(storeConfig.getTimerGetMessageThreadNum(), 1);
        dequeueGetMessageServices = new TimerDequeueGetMessageService[getThreadNum];
        for (int i = 0; i < dequeueGetMessageServices.length; i++) {
            dequeueGetMessageServices[i] = new TimerDequeueGetMessageService();
        }
        
        int putThreadNum = Math.max(storeConfig.getTimerPutMessageThreadNum(), 1);
        dequeuePutMessageServices = new TimerDequeuePutMessageService[putThreadNum];
        for (int i = 0; i < dequeuePutMessageServices.length; i++) {
            dequeuePutMessageServices[i] = new TimerDequeuePutMessageService();
        }
    }

    
    //省略该类部分内容


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：判断消息是否为滚动消息
     */
    public boolean needRoll(int magic) {
        return (magic & MAGIC_ROLL) != 0;
    }


    //以下就是TimerDequeuePutMessageService内部类的内容
    

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：定时消息从时间轮出队服务，这个组件会把dequeuePutQueue队列中的消息重新投递到目标主题下
     */
    public class TimerDequeuePutMessageService extends ServiceThread{

        @Override
        public String getServiceName() {
            return getServiceThreadName() + this.getClass().getSimpleName();
        }
    
    
        @Override
        public void run() {
            
            TimerMessageStore.LOGGER.info(this.getServiceName() + " service start");
            //判断dequeuePutQueue队列中是否有待处理的数据
            //这里的判断也有一个细节，那就是就算服务组件停止工作了，但是队列中仍然有数据
            //那么也不能立刻停止，而是要把队列中的数据处理完毕才能停止工作
            while (!this.isStopped() || dequeuePutQueue.size() != 0) {

                try {
                    //从dequeuePutQueue队列中阻塞获取请求
                    TimerRequest tr = dequeuePutQueue.poll(10, TimeUnit.MILLISECONDS);
                    if (null == tr) {
                        continue;
                    }
                    //初始化消息处理结果
                    boolean doRes = false;

                    //在循环中处理消息
                    while (!isStopped() && !doRes) {
                        //从请求中得到消息本身内容
                        MessageExt msgExt = tr.getMsg();
                        //把消息转换为Broker内部的消息对象
                        //这里有一个needRoll(tr.getMagic())很重要的判断，如果消息需要滚动
                        //那么在转换消息内容的时候就不会替换消息主题信息，不是滚动消息则会替换消息主题信息
                        MessageExtBrokerInner msg = convert(msgExt, tr.getEnqueueTime(), needRoll(tr.getMagic()));
                        //执行消息重新投递操作，在这个操作中可能会把消息投递到目标主题下，当然，也肯能还是投递到定时消息主题下
                        doRes = PUT_NEED_RETRY != doPut(msg, needRoll(tr.getMagic()));

                        //投递失败则进行重试
                        while (!doRes && !isStopped()) {
                            //在这里执行重试操作，重试到成功或者服务停止工作为止
                            doRes = PUT_NEED_RETRY != doPut(msg, needRoll(tr.getMagic()));
                            //重试间隔
                            Thread.sleep(500L * precisionMs / 1000);
                        }
                        
                    }

                }catch (Throwable e) {
                    TimerMessageStore.LOGGER.error("Error occurred in " + getServiceName(), e);
                }   
            }
            TimerMessageStore.LOGGER.info(this.getServiceName() + " service end");
        }
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：将定时消息转换为MessageExtBrokerInner消息的方法
     */
    public MessageExtBrokerInner convert(MessageExt messageExt, long enqueueTime, boolean needRoll) {
        if (enqueueTime != -1) {
            //如果消息的入队时间有效，则把这个时间设置为消息本身的属性
            MessageAccessor.putProperty(messageExt, TIMER_ENQUEUE_MS, enqueueTime + "");
        }

        //判断消息是否需要滚动
        if (needRoll) {
            //如果消息需要滚动，则得到消息滚动次数
            if (messageExt.getProperty(TIMER_ROLL_TIMES) != null) {
                //因为本次仍然需要滚动，所以在这里更新消息的滚动次数
                MessageAccessor.putProperty(messageExt, TIMER_ROLL_TIMES, Integer.parseInt(messageExt.getProperty(TIMER_ROLL_TIMES)) + 1 + "");
            } else {
                //消息第一次滚动，则直接设置滚动次数为1次
                MessageAccessor.putProperty(messageExt, TIMER_ROLL_TIMES, 1 + "");
            }
        }
        //设置消息出队时间信息
        MessageAccessor.putProperty(messageExt, TIMER_DEQUEUE_MS, System.currentTimeMillis() + "");
        //在这里执行消息的转换操作
        MessageExtBrokerInner message = convertMessage(messageExt, needRoll);
        return message;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：转换消息的方法，在该方法中就会根据消息是否需要滚动来设置消息的主题信息
     */
    public MessageExtBrokerInner convertMessage(MessageExt msgExt, boolean needRoll) {
        MessageExtBrokerInner msgInner = new MessageExtBrokerInner();
        //设置消息体
        msgInner.setBody(msgExt.getBody());
        //设置消息标志位
        msgInner.setFlag(msgExt.getFlag());
        //设置消息属性
        MessageAccessor.setProperties(msgInner, MessageAccessor.deepCopyProperties(msgExt.getProperties()));
        //得到消息的主题过滤类型，tag或sql92
        TopicFilterType topicFilterType = MessageExt.parseTopicFilterType(msgInner.getSysFlag());
        //编码消息标签
        long tagsCodeValue = MessageExtBrokerInner.tagsString2tagsCode(topicFilterType, msgInner.getTags());
        //设置消息过滤信息
        msgInner.setTagsCode(tagsCodeValue);
        //将消息属性转换为字符串
        msgInner.setPropertiesString(MessageDecoder.messageProperties2String(msgExt.getProperties()));
        //设置系统标志位
        msgInner.setSysFlag(msgExt.getSysFlag());
        //设置消息生产时间
        msgInner.setBornTimestamp(msgExt.getBornTimestamp());
        //设置消息生产服务器信息
        msgInner.setBornHost(msgExt.getBornHost());
        //设置存储消息的服务器信息
        msgInner.setStoreHost(msgExt.getStoreHost());
        //设置消息重试次数
        msgInner.setReconsumeTimes(msgExt.getReconsumeTimes());
        //设置无需等待消息存储成功标志
        msgInner.setWaitStoreMsgOK(false);

        //接下来就是重点，判断消息是否需要滚动
        if (needRoll) {
            //如果消息需要滚动，也就意味着消息还不需要真正投递
            //那就还使用定时消息主题作为该消息的主题，把消息重新投递到定时消息主题下
            msgInner.setTopic(msgExt.getTopic());
            //设置消费队列Id，这里就是0
            msgInner.setQueueId(msgExt.getQueueId());
        } else {
            //如果不需要滚动，也就意味着消息要被真正消费了，那就要把消息投递到原始主题下
            //所以这里给消息设置了它的原始主题
            msgInner.setTopic(msgInner.getProperty(MessageConst.PROPERTY_REAL_TOPIC));
            //设置队列Id
            msgInner.setQueueId(Integer.parseInt(msgInner.getProperty(MessageConst.PROPERTY_REAL_QUEUE_ID)));
            //清理之前使用的主题和队列Id
            MessageAccessor.clearProperty(msgInner, MessageConst.PROPERTY_REAL_TOPIC);
            MessageAccessor.clearProperty(msgInner, MessageConst.PROPERTY_REAL_QUEUE_ID);
        }
        return msgInner;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：投递消息的方法，在该方法中消息就会被消息存储引擎重新存储
     */
    public int doPut(MessageExtBrokerInner message, boolean roll) throws Exception {

        //接收消息存储结果的对象
        PutMessageResult putMessageResult = null;
        if (escapeBridgeHook != null) {
            //如果escapeBridgeHook回调方法不为空，则使用该回调方法重新存储消息
            //这个回调对象并不为空，其实这里就是使用EscapeBridge对象的putMessage()方法重新存储消息
            putMessageResult = escapeBridgeHook.apply(message);
        } else {
            putMessageResult = messageStore.putMessage(message);
        }


        //初始化操作重试次数
        int retryNum = 0;
        //最多重试三次
        while (retryNum < 3) {
            //判断消息存储结果是否为空，为空则存储失败，需要重试
            if (null == putMessageResult || null == putMessageResult.getPutMessageStatus()) {
                retryNum++;
            } else {
                return PUT_OK;
            }

            //休眠50毫秒后重试
            Thread.sleep(50);
            if (escapeBridgeHook != null) {
                putMessageResult = escapeBridgeHook.apply(message);
            } else {
                putMessageResult = messageStore.putMessage(message);
            }
            LOGGER.warn("Retrying to do put timer msg retryNum:{} putRes:{} msg:{}", retryNum, putMessageResult, message);
        }
        
        //返回不需要重试的结果
        return PUT_NO_RETRY;
    }
}
```
