

## 实现顺序消费消息功能


谈到顺序消费消息，对大家来说，涌现脑海的第一个念头是什么呢？这不用说，肯定是要按照顺序一条一条消费消息，前一条消息没有消费完毕，那么消费者客户端就不能消费后面的消息。那怎么样就算是前一条消息被消费完毕了呢？这个也很简单，只要前一条消息被成功 ack 了，那就意味着前一条消息被消费完毕了。这样一来，其它的消费者客户端就可以消费后面的消息了。这个逻辑很好理解吧？



好了，现在我们都清楚了消费者客户端从 Broker 节点获取消息时都是批量获取的，那在顺序消费消息的情况中，这个时候就变成了必须等待前一批被 Pop 出的消息被消费完毕了，也就是全部被 ack 了，在其之后的消息才能被消费者客户端继续消费。这个逻辑也很容易理解吧？



我相信对大家来说，上面的内容理解起来肯定非常简单，因为这就是顺序消费消息功操作的本质，就算没有学过任何编程知识的朋友也能理解上面内容的意思。但话说回来，顺序消费消息并不是一个单一的功能，仅仅知道了消费者客户端怎么顺序消费消息还不够，消费者客户端只知道从消费队列中获取消息，等到前一批被消费的消息都 ack 完毕了，才能消费之后的消息，这么一来，消费者客户端就保证了消费消息的顺序性；但是，消息本身的顺序性该怎么保证呢？换句话说，已经储存到消费队列中的消息是不是按照顺序存储的呢？分析到这里，这一点就显得至关重要了。



比如说现在有一个生产者客户端，这个生产者客户端都要向 Test 主题下发送生产消息，而主题下有 8 个写队列和读队列，这就意味着这个生产者生产的消息会按照设定的负载均衡策略分布在各个队列中。假如说这些消息最终分散存储在了 8 个消费队列中，当消息这样被存储的时候，就会造成一种情况：第 1、3、5 消息被存储到了 Id 为 1 的消费队列中，2、4、6 被存储到了 Id 为 2 的消费队列中，**而我们目前实现的是 Pop 模式的消费者客户端，该客户端并不会只消费某个指定队列中的消息，而是会在循环中消费这 8 个队列中的所有消息。并且每次消费的时候，会根据一个随机值得到要消费的消费队列的 Id**。也就是说，消费者客户端可能并不会直接从 Id 为 1 的消费队列中获取消息，如果从 Id 为 2 的队列中消费消息，那么就会首先消费第 2 条消息了，这显然就没有按照严格的顺序消费消息。就像下面代码块展示的这样，请看下面代码块。

那以上这个问题该怎么解决呢？很简单，如果在真实的生产过程中，我们已经设定了某些消息必须要严格按照顺序来消费，**那么在生产这些消息的时候，就可以把这些消息都存储到同一个主题下的同一个消费队列中**。这样一来，就算是 Pop 消费者客户端前来消费，那从这个队列中获取消息时肯定也是按照顺序获取的。也就是说，现在我们要为生产者实现消息顺序存储功能，把顺序消息都存储到同一个消费队列中。而这个功能其实已经被我们实现了，也许大家对之前的内容没什么印象了，所以接下来就让我为大家简单回顾一下。



当生产者客户端想生产顺序消息时，就可以在生产消息的时候为这条消息设置一个 MessageGroup 信息，也就是消息分组信息，就行下面代码块展示的这样，请看下面代码块。

好了，有了这个消息分组标签之后，接下来就可以发送这条消息了。这条消息首先就会被发送给 Proxy 节点，Proxy 节点在接收到这条消息之后，就会在一系列操作中处理这条消息，最后把这条消息转发给 Broker 节点，交给 Broker 节点存储到本地的 CommitLog 文件中。而在 Proxy 节点把这条消息转发给 Broker 节点之前，会执行一个非常重要的操作，**那就是为这条消息选择具体的目标队列，一旦选定了目标队列，那么队列 Id 也就明确了，到了 Broker 节点内部，这条消息就会存储到对应 Id 的消费队列中**。这个操作就被定义在了 Proxy 节点的 SendMessageActivity 活动器中，我把相关代码也搬运过来了，请看下面代码块。

```java
        public SendMessageQueueSelector(SendMessageRequest request) {
            this.request = request;

        /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

                //得到请求中的第一条消息
                apache.rocketmq.v2.Message message = request.getMessages(0);
                String shardingKey = null;
                //如果请求中只有一条消息，获取其消息分组作为分片键
                if (request.getMessagesCount() == 1) {
                    shardingKey = message.getSystemProperties().getMessageGroup();

                AddressableMessageQueue targetMessageQueue;
                //判断消息是否存在分片键，这里的分片key其实就是生产者组名称

                    targetMessageQueue = messageQueueView.getWriteSelector().selectOneByPipeline(false);
                }
                //返回选择的目标队列
                return targetMessageQueue;
            } catch (Exception e) {
                return null;
            }
        }
    }
```

从上面代码块的第 52 行可以看到，为了给这条消息选择具体的目标队列，在处理消息的过程中为这条消息创建了一个 SendMessageQueueSelector 队列选择器。这个 SendMessageQueueSelector 队列选择器就是 SendMessageActivity 活动器的内部类，相关内容也展示在上面代码块中了。而在 SendMessageQueueSelector 队列选择器的核心方法，也就是 select() 方法中，我们可以看到，**在为这条消息选择具体的目标队列时，只要这条消息被设置了 MessageGroup 消息分组信息，那么这个消息就会被投递到指定的目标消费队列中**。看到这里大家应该回忆起来了，**如果为所有顺序消息都设置同一个 MessageGroup 消息分组信息，那么这些消息就会按照顺序被投递到同一个目标队列中。这样一来，Pop 消费者客户端在消费消息的时候就可以按照顺序消费了**。好了，看来顺序生产消息的功能真的早就被我们实现了，那接下来我们就可以把注意力再集中到顺序消费消息功能上了。



按照我们之前的分析，当消费者客户端要到 Broker 节点中顺序获取消息时，必须要等待指定队列的前一批消息全部被 ack 完了，只有全部 ack 完了，才能获取下一批消息，这个逻辑非常简单吧。这样分析下来，代码似乎不必执行什么重构，因为之前我们已经实现了消息 ck 和 ack 功能，每从 Broker 节点 Pop 出一批消息，都会为这批消息创建一个 PopCheckPoint 对象，这个对象内部封装了所有待 ack 的消息的额外信息，以及这批消息的更新位图信息，并且这个对象会被缓存到 PopBufferMergeService 对象中。如果是这样的话，**那当消费者客户端要顺序消费消息时，只需要在获取消息之前，先从 PopBufferMergeService 中得到该消费队列最新被 Pop 的消息对应的 PopCheckPoint 对象，然后判断该对象中的消息位图是否全被更新了即可。如果全被更新了，那么当前消费者客户端就可以到目标队列中获取消息，如果没有被完全更新，那么当前消费者客户端就无法从队列中获取消息**。这个逻辑很容易理解吧？如果大家理解了这个逻辑，那接下来就很好说了。



实际上，在 RocketMq 源码中并不是像我们刚才分析的那样，在消费者客户端顺序消费之前，判断上一批消息对应的 PopCheckPoint 对象的消息位图。源码中引入了一个新的类，**那就是 ConsumerOrderInfoManager 类，从名字上就能看出来，这个 ConsumerOrderInfoManager 类的对象就是顺序消费信息管理器，负责管理的也就是顺序消费消息的过程中，被获取的消息是否被消费成功的信息**。换句话说，顺序消费消息和普通消费消息的消息 ack 使用的是两个系统，普通消息被 Pop 出之后，就会为这批消息创建对应的 PopCheckPoint 对象，然后把 PopCheckPoint 对象缓存在 PopBufferMergeService 对象中；而在顺序消费消息的时候，每一批消息被 Pop 出之后，这些消息的信息就会交给 ConsumerOrderInfoManager 管理器管理。当然，二者的本质是一样的，这两个组件都会封装每批消息对应的 ack 位图，并且最终也都是根据位图是否完全更新完毕来判断这批消息是否被成功消费了。这么说大家可能不太理解，接下来我就把相关代码展示给大家，请看下面代码块。

```java
            return;

            //而顺序消费的ConsumerOrderInfoManager管理器只是用来让线程判断这个顺序队列是不是能继续消费消息，如果可以消费，那就从队列消费偏移量管理器中得到消费偏移量
            //然后开始消费
            this.brokerController.getConsumerOffsetManager().commitOffset(channel.remoteAddress().toString(), consumeGroup, topic, qId, nextOffset);
        
            //省略之后的内容
        }

    }
```

```java
        //但是被消费失败了，也就是说重试主题中的消息消费失败了，那这个消息又要被投递到重试主题中了
        //因为它的重试主题已经构建完毕了，所以直接使用构建好的充实主题即可
        if (!popCheckPoint.getTopic().startsWith(MixAll.RETRY_GROUP_TOPIC_PREFIX)) {
            //执行到这里意味着消息还没被投递到重试主题中，所以这里要构建一个重试主题
            msgInner.setTopic(KeyBuilder.buildPopRetryTopic(popCheckPoint.getTopic(), popCheckPoint.getCId(), brokerController.getBrokerConfig().isEnableRetryTopicV2()));
        } else {
            //执行到这里意味着已经被投递过了，所以这里直接使用重试主题即可
            //重试队列中的消息要是也被消费失败了还是会投递到真正的重试主题队列中，等待被再次消费，重试消息同样会被ck和ack
            //如果失败，则直接放到构建好的重试队列中即可
            msgInner.setTopic(popCheckPoint.getTopic());
        }

        //设置消息的原始消息体
        msgInner.setBody(messageExt.getBody());
        //设置消息队列Id，这里设置为0，表示真正的重试队列只有一个队列
        msgInner.setQueueId(0);
        //检查原始消息是否有tag
        if (messageExt.getTags() != null) {
            msgInner.setTags(messageExt.getTags());
        } else {
            MessageAccessor.setProperties(msgInner, new HashMap<>());
        }


        //省略部分内容
        
        //这里的操作非常关键，消息每重新投递到重试队列中，都会使重试次数加1，重试次数达到阈值之后
        //就会被转发到死信队列中
        msgInner.setReconsumeTimes(messageExt.getReconsumeTimes() + 1);

        //省略部分内容
        
        return true;
    }


     //省略该类其他内容
}
```

上面代码块展示的内容很清晰，那就是当一条消息被消费失败了，ack 响应超时，并且达到消息重新投递时间之后，这条消息就要被重新投递。假如这条消息重新投递到重试主题之后仍然被消费失败，那么这条消息仍然会被继续重新投递，而在每一次投递的时候，都会执行一个操作，也就是上面代码块第 57 行操作，**每次重新投递时，都给消息的重试次数加 1**，这个操作非常重要。



好了，知道了这个之后，那加入我们规定重新投递次数超过了 10 次，这条消息就要被转发到死信队列中，那这个功能该怎么实现呢？其实很简单，**只需要在消费者客户端每次获取到消息之后，判断一下这条消息的重新投递次数是否超过了 10 次，如果超过了 10 次，就把这条消息转发到死信队列中即可**。这个功能我也实现了，**在 ConsumerProcessor 处理器中，注意，这个时候程序已经从 Broker 节点返回到 Proxy 节点了！在每次从 Broker 节点获得了消息之后，我都让程序对消息执行了一个过滤器操作**，就像下面代码块展示的这样，请看下面代码块。

```java
/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
```

```java
public class PopMessageResultFilterImpl implements PopMessageResultFilter {

    //最大失败重试次数
    private final int maxAttempts;

    public PopMessageResultFilterImpl(int maxAttempts) {
        this.maxAttempts = maxAttempts;
    }

    @Override
    public FilterResult filterMessage(ProxyContext ctx, String consumerGroup, SubscriptionData subscriptionData, MessageExt messageExt) {
        //标签是否匹配，匹配才能通过
        if (!FilterUtils.isTagMatched(subscriptionData.getTagsSet(), messageExt.getTags())) {
            return FilterResult.NO_MATCH;
        }//是否重试超过最大次数，超过则进入死信队列
        if (messageExt.getReconsumeTimes() >= maxAttempts) {
            return FilterResult.TO_DLQ;
        }//匹配通过
        return FilterResult.MATCH;
    }
}
```
