上一章我已经为我们的程序引入了预重试主题与真正失败重试的主题，大家也都清楚了，当缓存在内存中的某个 PopCheckPointWrapper 对象过期之后，其持有的 PopCheckPoint 对象就会被持久化到本地，也就是持久化到对应的预重试主题下；而当预重试主题中的 PopCheckPoint 对象封装的消息依旧迟迟没有被 ack，那么达到重新投递时间的消息就会被重新投递到真正的失败重试主题下，这样一来消费者客户端就可以到真正的失败重试队列中消费这些消息，这些内容大家应该都还有印象。当然，随着以上这些内容的展开，大家也逐渐思考了更多的问题。



比如说预重试主题下的消息该怎么被 ack 呢？也就是说，已经持久化了的 PopCheckPoint 对象对应的消息该怎么被 ack 呢？还有，在预重试队列中达到了重新投递时间的消息，这些消息要怎么被投递到真正的消费失败重试队列中呢？除此之外，还有一个最重要的问题，那就是消费者客户端怎么才能到真正的失败重试队列中消费消息呢？这些问题至今都还没有被我们解决，那接下来，我们就逐一分析，一起寻找这些问题的答案。



## 引入 PopReviveService 类


其实面对刚才分析的几个问题，我们也不是毫无头绪，就比如说怎么把预重试主题下未被 ack 的消息投递到真正的失败重试队列中这个问题吧，实际上在上一章我们已经分析过了，预重试队列中存储的虽然是 MessageExtBrokerInner 消息，但是每一条消息封装的都是一个 PopCheckPoint 对象，而每一个 PopCheckPoint 对象又都封装了一批消息是否被 ack 的信息，如果达到了某条消息的重新投递时间，而这条消息却仍未被 ack，那这个时候，就可以把这条消息投递到真正失败重试的主题下了。这个逻辑在上一章我就为大家分析过，大家应该很清楚了。



但是，我们目前也仅仅是有这样一个设计思路，很多细节问题都还没有讨论，就比如说未被 ack 的消息怎么被重新投递到真正的失败重试队列中呢？按照之前的分析，**那肯定就是先确定这条未被 ack 的消息，然后再从 CommitLog 文件中找到这条消息本身的内容，接着再把查询到的完整消息投递到真正的失败重试主题下(至于真正的失败重试主题是怎么定义的，这个在上一章也讲解了，大家应该很清楚)**。这么做的原因很明确，PopCheckPoint 对象封装的仅仅是每一条消息是否被 ack 的信息，并没有封装每一条消息本身的内容，所以肯定要先从 CommitLog 文件中查询到这条消息本身的内容，然后再重新投递这条消息。



而我们设计的消息队列框架并不会直接从 CommitLog 文件中查询某条消息的具体内容，因为 CommitLog 文件中存储了所有主题下消息的信息，根本就没有便捷的查找方式。**在查找某条消息时，通常会根据这条消息所属的主题信息、以及主题下消费队列的 Id 和这条消息在消费队列中的具体偏移量，先从指定的消费队列中查询到这条消息的信息，然后得到该条消息的大小以及在 CommitLog 文件中的具体偏移量，这个时候就可以根据这些信息从 CommitLog 文件中获取这条消息本身的内容了**。这也就是说，**要想把预重试队列中没有被 ack 的消息重新投递到真正的失败重试主题下，必须要知道未被 ack 的消息所属主题信息、所在消费队列 Id、在消费队列中的具体偏移量**，这样才能先从消费队列中查询到这条消息的信息，然后再从 CommitLog 文件中或者这条消息的真正信息，这个逻辑大家可以理解吧？



如果大家理解了以上逻辑，那接下来就很好说了，因为在每一个 PopCheckPoint 对象中，都封装着待 ack 的每一条消息的主题信息、所在消费队列 Id 信息、以及在消费队列具体偏移量的信息，既然这些信息都可以直接从 PopCheckPoint 对象中获得，那么只要哪条未被 ack 的消息达到重新投递时间了，就可以直接根据 PopCheckPoint 对象封装的相关信息从 CommitLog 文件中查询到这条消息本身的内容，然后把这条消息重新投递到对应的重试主题下即可，而所谓重新投递，无非就是把消息交给消息存储引擎去存储而已，这之后的逻辑就不必我再展开分析了吧？



好了，这样分析下来，上面提出的第二个问题似乎就快解决了，反正只要判断出预重试主题下的哪些消息还没有被 ack，并且这些消息到达重试投递的时刻了，那就可以执行刚才分析的操作，对吧？那这样一来，似乎就回到了老地方，之前我们重构 PopBufferMergeService 时为该对象实现了一个功能，那就是把缓存在内存中的，但是已经超时过期的 PopCheckPoint 对象持久化到本地，而现在我们要实现的则是把与重试队列中达到重新投递时间的，未被 ack 的消息投递到真正的失败重试主题中，这两个功能除了最后执行的操作不同，前面的操作可谓是几乎一样。因为不管怎样，程序都要从一堆数据中找到需要处理的数据，对吧？PopBufferMergeService 对象处理超时未被 ack 的 PopCheckPoint 对象的方法非常简单，那就是在循环中定期判断是否有数据达到要被处理的条件，并且 PopBufferMergeService 本身就是一个线程。**那现在我们要把预重试主题下的未被 ack 的消息重新投递了，那显然也应该启动一个线程，在循环中定期判断哪些未被 ack 的消息到达了重新投递时间，满足条件则重新投递这些消息即可**。这个逻辑大家可以理解吧？如果大家理解了这个逻辑，那接下来我就想引入一个新的类，也就是 PopReviveService 类，这个类的对象就负责把预重试队列中的消息重新投递到失败重试主题下，当然，根据刚才的分析，**这个 PopReviveService 类显然也要继承 ServiceThread 类，本身就是一个线程**，然后把要执行的操作定义在 run() 方法中，这样该类的对象一旦启动就可以执行相应的操作了。

    protected void mergeAndRevive(ConsumeReviveObj consumeReviveObj) throws Throwable {

        //得到之前从队列中获取到的要重新投递的消息，当然，这些消息中有的可能已经被ack了
        //consumeReviveObj的genSortList()方法就是把map成员变量中的value存储到集合中
        //也就是把所有PopCheckPoint对象存储到集合中，并且按照消息的重新投递时间排好顺序
        ArrayList<PopCheckPoint> sortList = consumeReviveObj.genSortList();


        //遍历ck对象
        for (PopCheckPoint popCheckPoint : sortList) {
            if (!shouldRunPopRevive) {

                break;

            //因为最先的都没有超时，后面的肯定更没有超时了
            if (consumeReviveObj.endTime - popCheckPoint.getReviveTime() <= (PopAckConstants.ackTimeInterval + PopAckConstants.SECOND)) {
                break;
            }

            //执行到这里意味着可以重新投递消息了，那这里就是重新投递消息的操作
            reviveMsgFromCk(popCheckPoint);

    private void reviveMsgFromCk(PopCheckPoint popCheckPoint) {
        if (!shouldRunPopRevive) {
            POP_LOGGER.info("slave skip retry, revive topic={}, reviveQueueId={}", reviveTopic, queueId);
            return;
        }

        //既然要重新投递消息了，那么就要看看PopCheckPoint中的每一条消息是否被ack了，只有未被ack的消息才需要被重新投递
        //遍历ck对象中的每一个位
        for (int j = 0; j < popCheckPoint.getNum(); j++) {
            //判断当前遍历到的位是否已经被ack了
            //如果ack就不需要处理
            if (DataConverter.getBit(popCheckPoint.getBitMap(), j)) {
                continue;

            long msgOffset = popCheckPoint.ackOffsetByIndex((byte) j);

            //从预重试主题的消费队列中查询消息本身的内容
            MessageExt message = getBizMessage(popCheckPoint.getTopic(), msgOffset, popCheckPoint.getQueueId(), popCheckPoint.getBrokerName());
            //在这里把查询到的消息投递到该消息真正的重试队列中，等待被重新消费
            boolean result = reviveRetry(popCheckPoint, message);
        }
    }

    private boolean reviveRetry(PopCheckPoint popCheckPoint, MessageExt messageExt) {

        //构建一个新的msg对象
        MessageExtBrokerInner msgInner = new MessageExtBrokerInner();

        //因为消息要被投递到真正的重试主题下，所以肯定构建重试主题
        //并且把主题信息设置到MessageExtBrokerInner消息对象中
        msgInner.setTopic(KeyBuilder.buildPopRetryTopic(popCheckPoint.getTopic(), popCheckPoint.getCId(), brokerController.getBrokerConfig().isEnableRetryTopicV2()));

        //设置消息的原始消息体
        msgInner.setBody(messageExt.getBody());
        //设置消息队列Id，这里设置为0，表示真正的重试队列只有一个队列

        //检查原始消息是否有tag

            msgInner.setTags(messageExt.getTags());
        } else {
            MessageAccessor.setProperties(msgInner, new HashMap<>());
        }
        //以下设置的这些参数都见过很多次了，我就不重复添加注释了
        msgInner.setBornTimestamp(messageExt.getBornTimestamp());
        msgInner.setFlag(messageExt.getFlag());
        msgInner.setSysFlag(messageExt.getSysFlag());
        msgInner.setBornHost(brokerController.getStoreHost());
        msgInner.setStoreHost(brokerController.getStoreHost());
        //这里的操作非常关键，消息每重新投递到重试队列中，都会使重试次数加1，重试次数达到阈值之后
        //就会被转发到死信队列中
        msgInner.setReconsumeTimes(messageExt.getReconsumeTimes() + 1);
        msgInner.getProperties().putAll(messageExt.getProperties());
        if (messageExt.getReconsumeTimes() == 0 || msgInner.getProperties().get(MessageConst.PROPERTY_FIRST_POP_TIME) == null) {
            //设置消息第一次被pop弹出的时间
            msgInner.getProperties().put(MessageConst.PROPERTY_FIRST_POP_TIME, String.valueOf(popCheckPoint.getPopTime()));
        }
        msgInner.setPropertiesString(MessageDecoder.messageProperties2String(msgInner.getProperties()));
        //将重试主题配置信息存储到Broker节点中
        addRetryTopicIfNoExit(msgInner.getTopic(), popCheckPoint.getCId());
        
        //在这里构建完毕的msg对象投递到重试队列中
        PutMessageResult putMessageResult = putMessageToSpecificQueue(msgInner);

        //判断消息是否投递成功了
        if (putMessageResult.getAppendMessageResult() == null || putMessageResult.getAppendMessageResult().getStatus() != AppendMessageStatus.PUT_OK) {
            //不成功则记录错误日志
            POP_LOGGER.error("reviveQueueId={}, revive error, msg is: {}", queueId, msgInner);
            return false;
        }
        
        return true;
    }

    public PutMessageResult putMessageToSpecificQueue(MessageExtBrokerInner messageExt) {
        //获取集群主节点
        //判断当前Broker节点是不是集群主节点，如果是集群主节点，直接把消息存储到本地即可
        BrokerController masterBroker = this.brokerController.peekMasterBroker();
        if (masterBroker != null) {
            //执行到这里就意味着当前节点就是集群主节点，那么直接存储消息即可
            return masterBroker.getMessageStore().putMessage(messageExt);
        }else {
            LOG.warn("Put message to specific queue failed, enableSlaveActingMaster={}, enableRemoteEscape={}.",
                    this.brokerController.getBrokerConfig().isEnableSlaveActingMaster(), this.brokerController.getBrokerConfig().isEnableRemoteEscape());
            return new PutMessageResult(PutMessageStatus.SERVICE_NOT_AVAILABLE, null);
        }
    }

            startOffset = ExtraInfoUtil.getCkQueueOffset(extraInfo);
            //得到要确认消息的在本批消息中的偏移量
            ackOffset = requestHeader.getOffset();
            //得到消息的额外信息
            popTime = ExtraInfoUtil.getPopTime(extraInfo);
            //得到消息的不可见时间
            invisibleTime = ExtraInfoUtil.getInvisibleTime(extraInfo);
            
            //创建封装消息唯一信息的ack对象
            ackMsg = new AckMsg();
           
        } else {

             //这个分支就是批量ack消息的操作，这部分内容大家也可以直接忽略
        }

        //执行到这里就要开始真正ack消息了
        //把刚才得到的各个参数设置到ackMsg对象中
        ackMsg.setConsumerGroup(consumeGroup);
        ackMsg.setTopic(topic);
        ackMsg.setQueueId(qId);
        ackMsg.setStartOffset(startOffset);
        ackMsg.setAckOffset(ackOffset);
        ackMsg.setPopTime(popTime);
        ackMsg.setBrokerName(brokerName);

        //在这里把创建完毕的AckMsg对象交给PopBufferMergeService对象去处理
        //在这里ack消息，注意，这里就是在内存中，也就是缓冲区中ack消息的操作
        if (this.brokerController.getPopMessageProcessor().getPopBufferMergeService().addAk(rqId, ackMsg)) {
            //ack成功直接推出当前方法
            return;
        }

       
        //执行到这里意味着这条消息ack失败了，这就意味着要被确认的消息可能已经不在缓冲区中了，那这个时候
        //就要把ack消息包装成一条内部消息，然后把这条消息持久化到重试队列中，重试主题就是reviveTopic
        MessageExtBrokerInner msgInner = new MessageExtBrokerInner();
        //设置消息的重试主题
        msgInner.setTopic(reviveTopic);
        //设置消息体，起始就是这条ack信息
        msgInner.setBody(JSON.toJSONString(ackMsg).getBytes(DataConverter.CHARSET_UTF8));
        //设置重试队列Id
        //这个重试Id非常重要，大家可以看一下，这个重试队列Id是从ack请求中得到的
        //这就会让ack消息和未被ack的消息持久化到预重试主题下的同一消费队列中
        //这样一来，只负责单个消费队列数据处理的PopReviveService对象才能执行ack操作
        msgInner.setQueueId(rqId);
        if (ackMsg instanceof BatchAckMsg) {
            msgInner.setTags(PopAckConstants.BATCH_ACK_TAG);
            msgInner.getProperties().put(MessageConst.PROPERTY_UNIQ_CLIENT_MESSAGE_ID_KEYIDX, PopMessageProcessor.genBatchAckUniqueId((BatchAckMsg) ackMsg));
        } else {
            //设置单条ack消息标签
            msgInner.setTags(PopAckConstants.ACK_TAG);
            //设置ack消息的唯一Id，注意，这个是程序内部定义的，并非是一开始的消息唯一Id
            msgInner.getProperties().put(MessageConst.PROPERTY_UNIQ_CLIENT_MESSAGE_ID_KEYIDX, PopMessageProcessor.genAckUniqueId(ackMsg));
        }
        //设置消息生成时间
        msgInner.setBornTimestamp(System.currentTimeMillis());
        //设置消息生成服务器为当前Broker节点的信息
        msgInner.setBornHost(this.brokerController.getStoreHost());
        //设置存储消息的服务器信息
        msgInner.setStoreHost(this.brokerController.getStoreHost());
        //设置消息的不可见时间，超过不可见时间，消息未被处理，那么消息就可以被重新投递了
        msgInner.setDeliverTimeMs(popTime + invisibleTime);
        //设置消息ack唯一Id，为什么又设置一遍？
        msgInner.getProperties().put(MessageConst.PROPERTY_UNIQ_CLIENT_MESSAGE_ID_KEYIDX, PopMessageProcessor.genAckUniqueId(ackMsg));
        //设置消息属性
        msgInner.setPropertiesString(MessageDecoder.messageProperties2String(msgInner.getProperties()));
        //在这里把消息存放到重试主题的队列中，其实就是存放到本地CommitLog文件中，然后被构建到重试主题的消费队列中
        this.brokerController.getEscapeBridge().putMessageToSpecificQueue(msgInner);
    }

}

上面代码块的内容非常简单，就是简单的持久化 AckMsg 对象的操作，我相信每个朋友都能看懂。但是，就算看明白了上面代码块中的内容，大家可能也不清楚持久化 AckMsg 对象到预重试主题下的用意，接下来就让我来为大家解释一下。实际上是这样的，上面代码块的操作，**会把 AckMsg 对象持久化到预重试主题下，并且一定会把该对象持久化到和自己对应匹配的，等待 ack 的消息的同一消费队列中，这样一来，当 PopReviveService 线程在处理数据时，就会从本地把消费队列的数据加载到内存，然后根据 MessageExtBrokerInner 消息的标签判断当前消息封装的是 ack 对象还是 ck 对象，如果是 ack 对象，那就可以使用这个 ack 对象去以加载到内存的 ck 对象中匹配唯一消息，匹配成功则更新消息标志位**。这就是持久化到预重试主题下的消息被 ack 的整个过程，**而这些内容就被定义在了 PopReviveService 对象的 consumeReviveMessage() 方法中**，但是我并不会在文章中再次重构该方法了，否则要展示的内容就太多了。我想说的是，虽然这些内容很多，操作琐碎，但是逻辑都很简单，都是在循环中判断、处理数据，都是很常规的流程，所以这些内容就留给大家去我提供的第二十三版本代码中查看吧。

/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

 */
public class PopMessageProcessor implements NettyRequestProcessor {

    private static final Logger POP_LOGGER = LoggerFactory.getLogger(LoggerName.ROCKETMQ_POP_LOGGER_NAME);


    //省略该类其他内容


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * @方法描述：处理消费者客户端消费消息请求的方法
     */
    @Override
    public RemotingCommand processRequest(ChannelHandlerContext ctx, RemotingCommand request)  throws RemotingCommandException {

        //省略该方法部分内容

        
        //以下就是开始获取消息的操作了

        //得到一个随机数，后面拉取消息的时候会用到
        int randomQ = random.nextInt(100);

        //重试消息Id
        int reviveQid;
        //如果是顺序消息，那么消息被重试的时候，都要被投递到同一个队列中
        //这样在被消费的时候才能保证顺序性
        if (requestHeader.isOrder()) {
            //这个就是系统内置的顺序消息的重试队列Id
            reviveQid = KeyBuilder.POP_ORDER_REVIVE_QUEUE;
        } else {
            //非顺序消息就是随机分配队列Id
            reviveQid = (int) Math.abs(ckMessageNumber.getAndIncrement() % this.brokerController.getBrokerConfig().getReviveQueueNum());
        }

        
        //这里有一个操作很重要，这里的操作返回true的概率为百分之20
        //这个就是消费失败重试主题消息的概率
        boolean needRetry = randomQ % 5 == 0;

        
        //记录弹出消息的时间
        long popTime = System.currentTimeMillis();
        CompletableFuture<Long> getMessageFuture = CompletableFuture.completedFuture(0L);



        //判断当前请求是不是需要消费重试主题中的消息，并且当前请求不能是顺序消息请求
        //从这里就能看出来，每次pop消息的时候，都有五分之一的概率获取重试主题中的消息
        if (needRetry && !requestHeader.isOrder()) {
            
            //构建重试主题名称
            String retryTopic = KeyBuilder.buildPopRetryTopic(requestHeader.getTopic(), requestHeader.getConsumerGroup(), brokerConfig.isEnableRetryTopicV2());
            //在这里执行消费失败重试主题消息的操作
            getMessageFuture = popMsgFromTopic(retryTopic, true, getMessageResult, requestHeader, reviveQid, channel,
                    popTime, finalMessageFilter, startOffsetInfo, msgOffsetInfo, orderCountInfo, randomQ, getMessageFuture);
        }
        

        
        //判断请求中是否指定了队列Id，注意，这里队列Id一定是-1，pop模式下队列Id肯定是-1
        //只有是-1，pop模式才能从该主题下的每个队列中获取消息
        if (requestHeader.getQueueId() < 0) {
            //从选中主题的所有队列中弹出消息
            //第二个参数false表示这不是从重试主题队列中获取消息，而是从普通主题队列中获取消息
            //弹出的消息会被封装到getMessageResult对象中，而剩余的可消费消息数量则存储在getMessageFuture中
            getMessageFuture = popMsgFromTopic(topicConfig, false, getMessageResult, requestHeader, reviveQid, channel,
                    popTime, finalMessageFilter, startOffsetInfo, msgOffsetInfo, null, randomQ, getMessageFuture);
        } else {
            //执行到这里意味着指定了队列Id，那这种情况下就要从被选中主题的指定队列中pop消息了，在pop模式下不会进入该分支
            int queueId = requestHeader.getQueueId();
            getMessageFuture = getMessageFuture.thenCompose(restNum ->
                    //从指定队列中弹出消息
                    popMsgFromQueue(topicConfig.getTopicName(), requestHeader.getAttemptId(), false,
                            getMessageResult, requestHeader, queueId, restNum, reviveQid, channel, popTime, finalMessageFilter,
                            startOffsetInfo, msgOffsetInfo, null));
        }



        //下面这个操作也很重要，那就是判断本次是否pop出了足够的消息，如果消息不够，则去重试主题中获取消息
        //尽可能让消费者客户端多获取消息
        if (!needRetry && getMessageResult.getMessageMapedList().size() < requestHeader.getMaxMsgNums() && !requestHeader.isOrder()) {
            //构建重试主题名称
