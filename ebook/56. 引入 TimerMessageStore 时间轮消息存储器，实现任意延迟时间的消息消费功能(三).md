一旦我们开始思考时间轮的消息为什么要滚动，那就意味着 RocketMq 框架时间轮的面纱就要被我们解开了。请大家想一想，我们不可能把延迟消息主题中完整消息内容提交到时间轮中，而随着时间流逝，存储在本地的消息就会被过期删除，那有没有一个完美的方法，既能让时间轮存储消息的少量信息，又能防止本地消息被删除呢？这样一来，等过了消息的延迟时间，那么时间轮就可以根据消息的关键信息到 CommitLog 文件中查询到消息的完整内容，然后再重新投递这条消息即可。



方法肯定是有的，只是操作起来有些麻烦，但即便是麻烦一些，在我看来，这也算是个两全其美的好方法了。首先我们应该认识到一点，RocketMq 框架的 CommitLog 文件中的数据，肯定会被定期过期删除，这是无法更改的设定，否则整个程序将不能正常运转，所以我们就不要在这方面动脑筋了。但这并不就意味着事情没有回转的余地，请大家想一想，CommitLog 文件中的数据是怎么来的？还不是 Broker 节点把一条条消息写入到本地文件中？当然，在我们过去实现的功能中，Broker 节点肯定是接收到生产者生产的每一条消息，然后再把消息写入到 CommitLog 文件中。这一点大家都能理解吧？好了，那既然是这样，我就开始思考，**Broker 节点内部能不能产生消息呢，这些节点内部产生的消息也能写入到本地 CommitLog 文件中吗**？显然是可以的，我么们都知道，Broker 节点拥有一个消息存储引擎，这个存储引擎负责把消息写入到本地 CommitLog 文件中，并且，这个存储引擎并不会关心消息是从哪里来的，它只负责纯粹的存储消息的工作。



想到了这一点，那我就有了一个主意，**在处理延迟时间过长的消息时，我们为何不在这条消息即将过期之前，再把它重新写入到 CommitLog 文件中呢？这样一来，这条消息的关键信息也会被重新写入到延迟消息主题的消费队列中，那时间轮不就能重新处理这条消息了吗**？虽然过期的消息被删除了，但是这条消息又被重新写入到本地文件中，当然可以被重新处理。也许大家不明白这个操作具体是什么意思，那接下来让我举一个具体的例子来为大家解释说明吧。



假设我们现在有一个时间轮，这个时间轮可以处理 7 天以内的所有延迟消息，而延迟主题的消费队列中也存储了延迟时间为 7 天以内的消息。那么时间轮刚刚启动，线程开始工作，就会把延迟消息主题的消费队列中的消息都提交到时间轮中，当然，提交的都是每一条消息的关键信息，并不是消息的完整内容。接下来，时间轮就会随着时间的推移，处理每一个刻度的延迟消息。当时间轮的指针来到第三天即将结束的时刻，最关键的部分就要来了，第三天一过，延迟主题消息队列中的内容就会被过期删除，再也找不到了，已经被处理过的消息没什么可说的，但是还没处理过的消息一旦被删除，这就意味着数据丢失了。那这个时候，我们就可以让时间轮执行一个操作，**那就是把时间轮上尚未被处理过的消息重新投递一遍，也就是说，要根据时间轮中存储的消息的关键信息，到 CommitLog 文件中查询出消息的完整信息，然后再把这些完整消息重新交给消息存储引擎去存储，而在存储的过程中，这些消息的关键信息又会被写入到延迟主题的消费队列中**。这样一来，过期的消息被删除了，但是新的消息又被写入了，仍然可以被继续处理。大家可以品味一下这个逻辑。



如果大家理解了以上逻辑，那肯定就能从上面的逻辑中发现两个问题，而且这两个问题一个比一个严重。首先是第一个问题：**延迟主题消费队列中的消息并不是按照延迟时间来排序的，可能排在后面的消息，反而要先执行。而已经提交到时间轮种的消息肯定是严格按照延迟时间在刻度上排好了顺序，只要沿着指针前进的方向，就能依次处理这些消息。但是，我们都知道，时间轮本身就是一个随着时间推移来工作的组件，它必须严格遵守指针刻度，怎么可能在第三天结束的时候，就提前得到了之后所有刻度存储的消息呢**？



第二个问题也很明显，那就是就算时间轮能提前把剩余的消息重新写入到本地 CommitLog 文件中，也就是说，时间轮在走到第三天的时候，提前把后面四天的消息重新写入到本地 CommitLog 文件中，那么这个操作执行了之后，时间轮后四天的消息还要继续保留在时间轮中吗？**如果继续保留，而延迟主题消费队列中又来了一批相同的消费信息，这些消息也要被再次提交到时间轮中，这样一来不就重复处理相同的消息了吗**？可见，时间轮后四天的消息不应该被继续保存了，对吧？



这么分析下来，我感觉稍微有点眉目了，我意识到我们要执行的操作要满足几个条件，**首先时间轮肯定要提前把即将过期的消息重新写入到本地 CommitLog 文件中；其次时间轮还要严格按照指针的移动来处理消息；最后时间轮中即将过期的消息一旦被重新存储了，那就意味着这条消息被处理过了，就要从时间轮中移除**。反正它后面还会重新被提交到时间轮中，等待延迟时间一过，就会被真正处理。



既然是这样的话，我决定对时间轮执行一个操作，那就是我想把时间轮划分一下，**假设有一个时间轮只能处理 7 天以内的延迟消息，那么当程序向时间轮中提交延迟消息时，只能正常提交两天以内的延迟消息信息，超过两天以内的消息，就要重新计算这个消息的延迟时间，然后把消息放在对应的刻度，并且，给这个消息设置滚动属性**！好了，这就是我们的计划，我知道大家现在对这个计划还不清楚，但没关系，请大家先记住这个计划，然后再看我接下来的具体例子。



时间轮的调度总时间为 7 天，但是我们规定时间轮只能正常处理 2 天以内的延迟消息，很好，假如现在系统时间还是第一天的 0 点，也就是时间轮刚刚启动，延迟消息主题消费队列中有 5 条消息，前 4 条消息都是 2 天以内就要延迟消费，最后一条消息要在第 5 天被延迟消费。在把消息提交到时间轮的时候，前四条消息就能正常提交到时间轮中，并且放在正确的刻度，等待被处理就行。在提交最后一条消息的时候，就要执行一个非常重要的操作：**那就是让第五条消息的延迟时间，减去系统当前时间，发现这条消息要在五天后才能被处理，那么这个时候就要把这个消息在时间轮中的延迟时间修改为当前时间加上两天的时间，而当前时间是第一天 0 点，那么这条消息在时间轮中的延迟时间就成了 2 天之后的 0 点，这条消息就会被放到时间轮的这个刻度位置，并且给这个消息设置一个滚动的属性**。注意，这里修改的只是这条消息在时间轮中的延迟时间，并不是消息真正的延迟时间，消息真正的延迟时间还在消息完整内容中存储着呢，还有一点，消息一旦被提交到时间轮，就意味着延迟主题消费队列中的消息就被消费了。大家要记住这些内容。



那执行了以上操作就会怎样呢？很简单，时间轮的指针会继续向前推移，依次处理消息，前四条消息正常处理，等到处理第五条消息的时候，这个时候时间已经过去两天了，再过一天，本地消息就要被过期删除了，这个时候时间轮发现正在处理的第五条消息有一个滚动属性，那么这个时候时间轮就会认为这条消息需要重新写入到本地 CommitLog 文件中，否则就会被过期删除。接下来，时间轮就会根据这条消息的关键信息到 CommitLog 文件中查询到消息的完整内容，然后把消息再次写入到 CommitLog 文件中，这样一来，就算第三天过去了，旧的数据删除了，但是这条消息又被新写入了一份，所以数据依然没有丢失；而在写入的过程中，延迟消息主题的消费队列也会重新写入这条消息的关键信息。执行了这些操作之后，第五条消息就会从时间轮中移除，表示处理过了，而重新写入到延迟主题消费队列中的消息，又会被重新提交到时间轮中。这条消息在被又一次提交到时间轮时，仍然会执行消息延迟时间减去系统当前时间的操作，因为系统时间已经走了两天了，这个时候就会发现这条消息要在三天后被处理，而我们设置的时间轮处理正常消息的时间窗口为 2 天，所以这一次仍然要把消息在时间轮的延迟时间设置为当前时间加上两天之后的时间，也就是第 4 天 0 点，并且还要给消息设置滚动属性。接下来的逻辑就不用我再详细重复了吧？依然是消息被重新写入到 CommitLog 文件中的逻辑，然后消息又会再一次被处理，直到发现消息的延迟时间在当前系统时间之后的两天以内，这个时候才会把消息放到时间轮的正常刻度，然后正常处理消息，也就是把消息重新投递到它真正主题的消费队列中。大家一定要仔细品味品味这个逻辑！



如果大家理解了以上逻辑，那我就可以为大家总结一下：**在我们为 RocketMq 框架设计的时间轮组件中，实际上给时间轮定义了一个滑动窗口，这个滑动窗口的时间总量就是 2 天，当消息被提交到时间轮中时，都要先执行一个判断，那就是让消息延迟时间(这里说的延迟时间指的就是精准的执行时间，并不是相对延迟时间)减去系统当前时间，只有延迟时间在 2 天以内延迟执行的消息才会被正常提交，而超过 2 天的消息，都要重新计算该消息的延迟时间，并且设置滚动属性，这么做就是为了防止本地文件中的消息被过期删除，导致数据丢失，遗漏重要操作**！了解了这一点，现在大家应该知道消息的滚动属性有多重要了吧？

```java
                //也就是说在经过当前时间窗口之后，不到五分钟这条消息就要被处理了
```

其实时间轮就是一个缓冲区，它可以是一个数组，也可以直接就是一个 ByteBuffer，当然， 在 ByteBuffer 内部仍然是一个数组，只不过是字节数组而已。时间轮的总时长确定了，时间精度也确定了，那么时间轮缓冲区的长度也就确定了。比如说时间轮一共有 7 秒，每个刻度为 1 秒，那么时间轮就要有 7 个刻度，也就对应着 7 个槽位，我们只要明确了每一个槽位的大小，然后再乘以 7，这样就得到了时间轮缓冲区的总长度。而所谓槽位，也就是 Slot 对象。这一点可以理解吧？



好了，那现在问题来了，时间轮的每一个刻度都对应着一个槽位，那就意味着每一个刻度对应的众多消息都要存储到槽位中，是这样吗？实际上并不是这样，在 RocketMq 中是这么做的：**首先定义了一个 TimerLog 对象，这个对象也有对应的本地文件，并且以内存映射的方式操纵本地文件写入数据和读取数据。所有被提交到时间轮中的消息的信息都会按照提交顺序被写入到 TimerLog 文件中**。好了，现在我们知道了时间轮中的所有消息实际上都要写入到 TimerLog 文件中，那么每一条消息在 TimerLog 文件中的格式是什么样的呢？也就是说，TimerLog 文件的消息单元是怎样的呢？这一点源码已经展示得很清楚了，我就直接把对应的代码展示给大家看吧，请看下面代码块。

```java

/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

public class TimerLog {

    private static Logger log = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //文件空白区的标记码
    public final static int BLANK_MAGIC_CODE = 0xBBCCDDEE ^ 1880681586 + 8;

    //文件空白区域的字节长度，前四个字节记录的是当前文件剩余容量的大小
    //中间8字节写入0，最后四个字节写入空白标识码
    private final static int MIN_BLANK_LEN = 4 + 8 + 4;

    //TimerLog文件的消息单元大小
    public final static int UNIT_SIZE = 4  //这里的4字节表示消息单元的大小
            + 8 //prev pos 前一条消息在TimerLog文件中的偏移量
            + 4 //magic value 消息魔术值
            + 8 //curr write time, for trace 当前消息写入时间
            + 4 //delayed time, for check 消息的延迟投递时间
            + 8 //offsetPy 消息在commitLog中的全局偏移量
            + 4 //sizePy 消息在commitLog文件中的大小
            + 4 //hash code of real topic 消息实际主题的hash值
            + 8; //reserved value, just in case of 保留值，在程序中还没有发挥作用

    //这28个字节用来记录消息单元的大小、消息在TimerLog文件的偏移量、消息的魔术值、消息的写入时间、消息的延迟时间
    //其实就是为了快速得到消息单元中offsetPy和sizePy的值，所以引入了这个前置大小成员变量
    public final static int UNIT_PRE_SIZE_FOR_MSG = 28;

    //映射文件队列，映射文件会存储定时消息信息
    private final MappedFileQueue mappedFileQueue;

    //每个映射文件的大小，默认为100MB
    private final int fileSize;


    //省略该类其他内容

    //追加消息信息到TimerLog文件中的方法
    public long append(byte[] data) {
        return append(data, 0, data.length);
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * @方法描述：追加消息信息到TimerLog文件中的方法
     */
    public long append(byte[] data, int pos, int len) {
        //得到内存映射文件队列的最后一个文件
        MappedFile mappedFile = this.mappedFileQueue.getLastMappedFile();
        //如果映射文件已满，或者没有内存映射文件，则创建新的内存映射文件
        if (null == mappedFile || mappedFile.isFull()) {
            mappedFile = this.mappedFileQueue.getLastMappedFile(0);
        }
        if (null == mappedFile) {
            //仍然得不到内存映射文件，则返回追加失败结果
            log.error("Create mapped file1 error for timer log");
            return -1;
        }
        //先判断当前得到的内存映射文件是否还有足够的空间够写入数据，也就是判断一下要写入的数据加上文件结尾留白的字节长度是否超过了文件剩余容量
        if (len + MIN_BLANK_LEN > mappedFile.getFileSize() - mappedFile.getWrotePosition()) {
            //如果当前文件容量已经不够，则给当前文件写入结尾内容
            //分配留白内容的缓冲区
            ByteBuffer byteBuffer = ByteBuffer.allocate(MIN_BLANK_LEN);
            //写入当前文件剩余空间大小
            byteBuffer.putInt(mappedFile.getFileSize() - mappedFile.getWrotePosition());
            byteBuffer.putLong(0);
            //写入文件结尾标志魔数
            byteBuffer.putInt(BLANK_MAGIC_CODE);
            //把文件留白内容写入到文件中
            if (mappedFile.appendMessage(byteBuffer.array())) {
                //写入成功后，把文件写入位置设置为文件末尾，表示文件写满了
                mappedFile.setWrotePosition(mappedFile.getFileSize());
            } else {
                log.error("Append blank error for timer log");
                return -1;
            }
            //因为当前文件写满了，那就再创建一个新的内存映射文件
            mappedFile = this.mappedFileQueue.getLastMappedFile(0);
            if (null == mappedFile) {
                log.error("create mapped file2 error for timer log");
                return -1;
            }
        }
        
        //得到当前内存映射文件的写入位置，这里得到的其实就是要被写入的本地文件的消息信息在TimerLog文件中的全局偏移量
        long currPosition = mappedFile.getFileFromOffset() + mappedFile.getWrotePosition();
        //把消息信息写入到TimerLog文件中
        if (!mappedFile.appendMessage(data, pos, len)) {
            log.error("Append error for timer log");
            return -1;
        }
        //返回这条消息在TimerLog文件中的全局偏移量
        return currPosition;
    }
```

我想理解以上逻辑并不困难，那现在新的问题就来了，时间轮怎么就知道刻度 1 的第三条消息在 TimerLog 文件中的全局偏移量呢？还有一点，每一条消息写入 TimerLog 文件中的时候，怎么就知道前一条消息在 TimerLog 文件中的全局偏移量呢？我相信这个问题一定困扰着大家，那这个时候就轮到时间轮的槽位登场了。



实际上是这样的**，时间轮中每一个刻度都存储着一个槽位，也就是 Slot 对象，这个 Slot 对象存储着该刻度对应链表的第一条延迟消息在 TimerLog 文件中全局偏移量，还有链表最后一条消息在 TimerLog 文件中的全局偏移量，以及这个槽位对应的消息总数量**。每次向时间轮的指定刻度提交消息时，都会更新槽位的信息，这样一来，每向 TimerLog 文件中写入一条消息时，总能从 Slot 对象中找到上一条消息在 TimerLog 文件中的全局偏移量，于是链表就这么构成了。 Slot 的内容我也实现了，请看下面代码块。

```java
 * ├────────────┼───────────┼───────────┼───────────┼───────────┤
```

```java
package org.apache.rocketmq.store.timer;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @方法描述：时间轮实现类
 */
public class TimerWheel {

    private static final Logger log = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //BLANK表示槽位为空，没有任务
    //IGNORE表示该槽位的任务需要被忽略，不必执行
    public static final int BLANK = -1, IGNORE = -2;

    //时间轮中的所有槽位数量
    public final int slotsTotal;

    //时间轮每两个刻度之间的时间间隔，也就是时间轮精度，精度默认为1秒
    public final int precisionMs;

    //时间轮文件名称，时间轮数据会持久化到该本地文件中
    private String fileName;

    private final RandomAccessFile randomAccessFile;

    private final FileChannel fileChannel;

    private final MappedByteBuffer mappedByteBuffer;

    private final ByteBuffer byteBuffer;

    private final ThreadLocal<ByteBuffer> localBuffer = new ThreadLocal<ByteBuffer>() {
        @Override
        protected ByteBuffer initialValue() {
            return byteBuffer.duplicate();
        }
    };

    //时间轮总长度
    private final int wheelLength;


    //构造方法
    public TimerWheel(String fileName, int slotsTotal, int precisionMs) throws IOException {
        this.slotsTotal = slotsTotal;
        this.precisionMs = precisionMs;
        this.fileName = fileName;
        //这里给时间轮的总长度赋值，这里大家可以看到，时间轮总长度等于时间轮槽位总数乘以2乘以每个槽位的大小
        //之所以成乘以2，则代表时间轮其实有两圈
        //那为什么要有两圈呢？也就是14天时间，为什么这么设计呢？其实非常简单
        //我们定义的时间轮能调度的消息的最大延迟时间为7天，也就是说，超过7天之后的任务是不能被提交到时间轮种的
        //只能随着时间推移，慢慢向时间轮中提交任务。而时间轮又是一个循环，写完一圈之后就要写第二圈
        //这里定义为14天就是让最新写数据和读数据的间隔永远差半圈，也就是差7天，不会出现数据覆盖的问题
        this.wheelLength = this.slotsTotal * 2 * Slot.SIZE;

        //创建时间轮本地文件
        File file = new File(fileName);
        UtilAll.ensureDirOK(file.getParent());

        try {
            //创建随机访问文件，设置为读写模式
            randomAccessFile = new RandomAccessFile(this.fileName, "rw");
            //检查文件一致性：如果文件已存在且不为空，但长度与计算的时间轮长度不匹配，则抛出异常
            if (file.exists() && randomAccessFile.length() != 0 &&
                    randomAccessFile.length() != wheelLength) {
                throw new RuntimeException(String.format("Timer wheel length:%d != expected:%s",
                        randomAccessFile.length(), wheelLength));
            }
            //设置文件长度为刚才得到的时间轮长度
            randomAccessFile.setLength(wheelLength);
            fileChannel = randomAccessFile.getChannel();
            //将时间轮文件映射到内存
            mappedByteBuffer = fileChannel.map(FileChannel.MapMode.READ_WRITE, 0, wheelLength);
            assert wheelLength == mappedByteBuffer.remaining();
            //分配一个直接内存缓冲区，注意，这个直接缓冲区的大小和内存映射文件一模一样
            //后面大家就会看到，实际上时间轮中的数据会先写入到这个直接缓冲区，读取的时候也是从这个缓冲区中读取
            //等数据刷新到本地的时候，就会把直接缓冲区中的数据复制到内存映射文件中，然后再刷新到本地
            this.byteBuffer = ByteBuffer.allocateDirect(wheelLength);
            //这里可以看到，刚才的内存映射缓冲区的内容被复制到了直接内存缓冲区
            //到这里，时间轮的数据就恢复到byteBuffer中了
            this.byteBuffer.put(mappedByteBuffer);
        } catch (FileNotFoundException e) {
            log.error("create file channel " + this.fileName + " Failed. ", e);
            throw e;
        } catch (IOException e) {
            log.error("map file " + this.fileName + " Failed. ", e);
            throw e;
        }
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：得到指定时间戳对应的时间轮槽位
     */
    public Slot getSlot(long timeMs) {
        //得到时间戳对应的槽位
        Slot slot = getRawSlot(timeMs);
        //判断槽位记录的时间戳和指定时间戳是否一致，不一致则返回无效槽位
        //这里虽然返回无效槽位，但是作用很大，当时间不一致说明什么？说明时间轮又过了一轮
        //有数据要被覆盖了，这里返回一个无效槽位，槽位记录的上一条消息的偏移量无效
        //这正好切断了新数据和就数据的连接，大家一定要梳理清楚这个逻辑
        if (slot.timeMs != timeMs / precisionMs * precisionMs) {
            return new Slot(-1, -1, -1);
        }
        return slot;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

    public Slot getRawSlot(long timeMs) {
        //getSlotIndex(timeMs)得到的是时间戳对应的槽位索引，乘以槽位大小得到的则是槽位的起始位置
        localBuffer.get().position(getSlotIndex(timeMs) * Slot.SIZE);
        //在这里创建了对应的槽位对象，槽位的起始位置有了，而槽位中的各个字节代表什么含义，请查看Slot类中的注释
        //这里就会把各个字节内容读取出来，创建一个Slot对象返回
        return new Slot(localBuffer.get().getLong() * precisionMs,
                localBuffer.get().getLong(), localBuffer.get().getLong(), localBuffer.get().getInt(), localBuffer.get().getInt());
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：根据时间戳计算对应槽位索引的方法
     */
    public int getSlotIndex(long timeMs) {
        //本来只要时间戳除以精度得到时间单元数，再对总槽位数取模得到循环索引
        //但刚才我们分析了，时间轮一共有两轮，所以这里需要对总槽位数乘以两倍
        return (int) (timeMs / precisionMs % (slotsTotal * 2));
    }

     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

        localBuffer.get().position(getSlotIndex(timeMs) * Slot.SIZE);

        localBuffer.get().putLong(timeMs / precisionMs);
```

```java
package org.apache.rocketmq.store.timer;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/10/31
 * @方法描述：定时消息存储引擎
 */
public class TimerMessageStore {


    private static final Logger LOGGER = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //省略该类部分内容

    //消息魔术信息，分别是默认消息，需要滚动的消息，需要删除的消息
    public static final int MAGIC_DEFAULT = 1;
    public static final int MAGIC_ROLL = 1 << 1;
    public static final int MAGIC_DELETE = 1 << 2;

    //时间轮滚动窗口槽数，这里我要对这个滚动窗口解释一下，所谓时间轮滚动窗口
    //就是时间轮能处理的定时消息时间的最大范围
    //虽然时间轮的总槽数是七天的时间，也就是说可以存储七天之内要被定时执行的消息
    //但是在时间轮真正处理消息时，最多只能处理两天内的消息，这个两天，就是所谓的滑动窗口
    //而延迟时间超过滑动窗口的消息，就需要被滚动，所谓滚动，我也在文章中跟大家解释了
    private final int timerRollWindowSlots;
    //时间轮总槽位数，这个槽数其实就是7天时间的意思，每个槽都对应1秒
    private final int slotsTotal;
    //时间轮精度，每个精度为1秒，也就是1000毫秒
    protected final int precisionMs;

    //时间轮对象
    private final TimerWheel timerWheel;

    //存储定时消息信息的成员变量
    private final TimerLog timerLog;


    //构造方法
    public TimerMessageStore(final MessageStore messageStore, final MessageStoreConfig storeConfig) throws IOException {

        this.messageStore = messageStore;
        this.storeConfig = storeConfig;
        //给当前Broker节点赋值，在我们的程序中，当前Broker节点肯定是主节点
        this.lastBrokerRole = storeConfig.getBrokerRole();
        enqueuePutQueue = new LinkedBlockingDeque<>(DEFAULT_CAPACITY);

         //时间轮精度，精度是1秒
        this.precisionMs = storeConfig.getTimerPrecisionMs();
        //时间轮总槽数赋值，总共是 7天
        this.slotsTotal = TIMER_WHEEL_TTL_DAY * DAY_SECS;
        //这里得到的就是2天
        this.timerRollWindowSlots = storeConfig.getTimerRollWindowSlot();

         //创建时间轮对象
        this.timerWheel = new TimerWheel(getTimerWheelPath(storeConfig.getStorePathRootDir()), this.slotsTotal, precisionMs);
        //创建定时消息存储对象
        this.timerLog = new TimerLog(getTimerLogPath(storeConfig.getStorePathRootDir()), timerLogFileSize);
    }

    
    //省略该类部分内容




    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：消息被提交到时间轮的方法
     */
    public boolean doEnqueue(long offsetPy, int sizePy, long delayedTime, MessageExt messageExt) {
        LOGGER.debug("Do enqueue [{}] [{}]", new Timestamp(delayedTime), messageExt);
        long tmpWriteTimeMs = currWriteTimeMs;
        boolean needRoll = delayedTime - tmpWriteTimeMs >= (long) timerRollWindowSlots * precisionMs;
        int magic = MAGIC_DEFAULT;
        if (needRoll) {
            magic = magic | MAGIC_ROLL;
            if (delayedTime - tmpWriteTimeMs - (long) timerRollWindowSlots * precisionMs < (long) timerRollWindowSlots / 3 * precisionMs) {
                delayedTime = tmpWriteTimeMs + (long) (timerRollWindowSlots / 2) * precisionMs;
            } else {
                delayedTime = tmpWriteTimeMs + (long) timerRollWindowSlots * precisionMs;
            }
        }

        
        //以下则是重构后添加的内容
        
        //接下来就是把消息提交到时间轮的操作了，当然并不会提交消息本身完整的内容，而是提交消息的核心信息
        //这里得到的消息所属的原始主题信息，消息被时间轮处理，也就是重新投递时，就会把消息投递到真正的主题下
        //这样消息才能被订阅了该主题的消费者消费
        String realTopic = messageExt.getProperty(MessageConst.PROPERTY_REAL_TOPIC);
        //根据消息要被时间轮处理的延迟时间，得到消息在时间轮中的槽位
        Slot slot = timerWheel.getSlot(delayedTime);
        //接下来就要把消息数据写入到TimerLog文件中了
        ByteBuffer tmpBuffer = timerLogBuffer;
        //清空缓冲区
        tmpBuffer.clear();
        //写入TimerLog文件中的消息单元大小
        tmpBuffer.putInt(TimerLog.UNIT_SIZE);
        //记录该槽位记录的上一条消息在TimerLog文件中的偏移量
        tmpBuffer.putLong(slot.lastPos);
        //写入消息魔数
        tmpBuffer.putInt(magic);
        //写入消息写入时间轮的时间
        tmpBuffer.putLong(tmpWriteTimeMs);
        //写入消息要被延迟投递的时间，这里记录的其实是时间差值
        tmpBuffer.putInt((int) (delayedTime - tmpWriteTimeMs));
        //写入消息在CommitLog文件中的全局偏移量
        tmpBuffer.putLong(offsetPy);
        //写入消息的完整大小
        tmpBuffer.putInt(sizePy);
        //写入消息原始主题的哈希值信息
        tmpBuffer.putInt(hashTopicForMetrics(realTopic));
        // reserved value, just set to 0 now
        //写入保留值，该信息并没有被用上，算是一个预留值
        tmpBuffer.putLong(0);
        //把以上数据追加到TimerLog文件中，这里返回的是写入的这条消息在TimerLog文件中的全局偏移量
        long ret = timerLog.append(tmpBuffer.array(), 0, TimerLog.UNIT_SIZE);
        //判断数据是否追加成功
        if (-1 != ret) {
            //追加成功则更新时间轮槽位信息，看到这里大家就应该意识到，实际上时间轮槽位只会存储一条消息的信息
            //会存储这条消息在TimerLog文件中的全局偏移量，但是这条消息中存储着上一条消息在TimerLog文件中的全局偏移量
            //这样串联起来，就成了一个链表，就可以得到这个时间轮槽位管理的所有消息
            timerWheel.putSlot(delayedTime, slot.firstPos == -1 ? ret : slot.firstPos, ret,
                    isDelete ? slot.num - 1 : slot.num + 1, slot.magic);
            //更新性能信息
            addMetric(messageExt, isDelete ? -1 : 1);
        }
        return -1 != ret;
    }
    

}
```
