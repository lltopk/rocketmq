

## 分析客户端和服务端消息的 ck 和 ack 流程细节


上一章结尾我为大家匆匆分析了消费者消费消息过程中的 ck 和 ack 流程，大家应该也清楚了所谓消息的 ck 和 ack 是什么意思。但是，我能想到看完上一章结尾的内容，大家可能脑袋更懵了，这其中肯定有我很大一部分责任，是我在上一章结尾讲解得太快，根本就没有把消息 ck 和 ack 的整个流程展开讲解，所有细节都没有铺展开，那这就导致了一个结果，对于消息的 ck 和 ack 功能，大家也只是了解一个很模糊的概念，看完了我讲解得内容，非但没有解决老问题，反而在脑海里产生了很多新的问题。



就比如说，大家肯定会困惑，一个 ck 对象怎么能匹配多个 ack 响应呢？还有一点，那就是 ck 对象会在那里创建呢？而且 Broker 节点内部还要保存 ck 对象，那又该怎么保存这个 ck 对象呢？这些新的问题肯定困扰着大家，所以我才说旧的问题没被解决，新的问题反而全来了。当然，还有最重要的一个问题，那就是我们说了很久的 ck 对象，提到过很多次的 ck 对象，这个对象该怎么定义呢？



在上一章我已经为大家分析了：**每当消费者客户端从 Broker 节点获取了一批消息，Broker 节点就会为这一批消息创建一个对应的 CheckPoint 对象，也就是检查点对象，这个对象内部封装了这批消息被消费的消费组信息，消息所属主题，队列 Id，被消费时队列的消息起始偏移量，各个消息在队列中的偏移量，以及消息被 Pop 出去的时间**，按照这种分析，那们我们就可以先定义一个 CheckPoint 类，然后把上述信息定义为该类的成员变量，当然，现在我们实现的是 Pop 模式的消费消息功能，那就可以把 CheckPoint 类的名称修改为 PopCheckPoint，接下来就请大家看一看初步定义完毕的 PopCheckPoint 类，请看下面代码块。

```java
package org.apache.rocketmq.store.pop;


public class PopCheckPoint implements Comparable<PopCheckPoint> {
    
    //检查点对象对应的这批待确认消息的起始偏移量
    private long startOffset;

    //消息被弹出的时间
    private long popTime;

    //ck对象对应的待确认消息的数量
    private byte num;

    //消息原本所在队列的Id
    private int queueId;

    //消息的主题信息
    private String topic;

    //消费者组信息
    private String cid;

    //Broker节点名称
    String brokerName;


    //省略get、set方法
}
```

上面的代码块展示的内容非常简单，每一位朋友应该都能看懂，但是看懂这个类只会让大家更加茫然，这个 PopCheckPoint 类定义得根本没有一点水准啊，就定义这些内容能干成什么事呢？没错，这个 PopCheckPoint 类的对象确实封装了消息的很多额外信息，但是从它现有的内容上看，它封装的内容似乎和一批消息根本没有关系啊。之前我们不是已经明确了吗？一个 PopCheckPoint 对象会封装一批消息的额外信息，假如消费者客户端从 Broker 节点获取的一批消息的数量为 32 条，那么这一个 PopCheckPoint 对象就会被 32 个 ack 响应匹配，都匹配完毕后，才意味着这 32 条消息被消费者客户端成功消费了，可在我们目前定义的 PopCheckPoint 对象中根本体现不出匹配多个 ack 响应的功能呀。显然，我们目前定义的 PopCheckPoint 类存在很严重的缺陷，接下来就让我们耐心对其进行重构吧。



我相信大家肯定能意识到，所谓的消息 ck 和 ack 操作，在操作的整个流程中，其实并不需要每一条消息本身参与，因为消息被消费者客户端获得之后，就在本地消费了，完整的消息并不会再从消费者客户端传输到 Broker 节点了，如果真这么做那也太蠢了。所以，在消息 ck 和 ack 的整个过程中，其实一直是这些消息的额外信息在发挥作用。比如说消费者客户端从 Broker 节点获取了 32 条消息，这批消息在消费队列中的起始偏移量为 200，也就是说消费者客户端是从消费队列偏移量为 200 字节的位置开始查询消息，每一个消息单元为 20 字节，那这批消息的第二条消息在消息队列的起始偏移量肯定是 200 + 20 字节，也就是 220 字节，这个大家可以理解吧？那当这批消息的第二条消息被消费成功了，要为这条消息回复一个消费成功响应，也就是 ack 响应，那在回复响应的时候，是不是只需要把消费组信息，消息所属主题，消息所在消费队列 Id，这批消息在消费队列的起始偏移量，以及这条消息，也就是第二条消息在队列的偏移量，也就是 220 字节，还有这批消息被 Pop 出的时间，也就是弹出时间，返回给 Broker 节点，那么肯定就能在 Broker 节点内部确定这条消息，因为这些信息组合到一起就是一条被消费的消息的唯一信息。这个逻辑大家可以理解吧？



既然是这样的话，那我已经想到了，**只要我在 PopCheckPoint 类中再定义一个成员变量，这个成员变量是一个集合，专门用来存储本批待确认的消息中每一条消息在消费队列中的具体偏移量，而Broker 节点每接收一个 ack 响应，都可以从响应中得到要 ack 的消息在消费队列中的具体偏移量**，这样一来，每一条消息不就对应上了吗？然后 Broker 节点只需要确认这条消费被成功消费即可，这个逻辑可以理解吧？很好，那接下来我们就按照这个分析对 PopCheckPoint 类进行重构，请看下面重构之后的代码块。

```java
package org.apache.rocketmq.store.pop;


public class PopCheckPoint implements Comparable<PopCheckPoint> {
    
    //检查点对象对应的这批待确认消息的起始偏移量
    private long startOffset;

    //消息被弹出的时间
    private long popTime;

    //ck对象对应的待确认消息的数量
    private byte num;

    //消息原本所在队列的Id
    private int queueId;

    //消息的主题信息
    private String topic;

    //消费者组信息
    private String cid;

    //存储待确认的每一条消息相对于本批消息的起始偏移量的的偏移量差值
    private List<Integer> queueOffsetDiff;

    //Broker节点名称
    String brokerName;

    //添加每一条消息距本批消息起始偏移量差值到queueOffsetDiff成员变量中的方法
    public void addDiff(int diff) {
        if (this.queueOffsetDiff == null) {
            this.queueOffsetDiff = new ArrayList<>(8);
        }
        this.queueOffsetDiff.add(diff);
    }

    
    //省略get、set方法
}
```

从上面代码块中可以看到，**我给 PopCheckPoint 类定义了一个 queueOffsetDiff 成员变量，但这个成员变量存储的并不是待确认的每一条消息在消费队列中的具体偏移量，而是每一条消息在消费队列中的具体偏移量和这批消息起始偏移量的差值**，这可能会让大家有些不解，没关系，让我为大家举一个简单的例子大家就知道是怎么回事了。假如消费者客户端从 Broker 节点获取了 32 条消息，这批消息在消费队列的起始偏移量为 200 字节，消息单元为 20 字节，那么第一条消息在消费队列的偏移量相对于这批消息的起始偏移量的差值肯定是 0，第二条消息的差值肯定是 20 字节，第三条则是 40 字节，这个逻辑大家清楚吧？而刚才定义的 queueOffsetDiff 成员变量存储的就是每条消息的偏移量距离这批消息的起始偏移量的差值，PopCheckPoint 对象的 startOffset 成员变量已经存储了这批消息的起始偏移量，**那根据起始偏移量和每一条消息相对于起始偏移量的差值的和，不就得到了每一条消息在消费队列中的具体偏移量吗，这样依然可以确认唯一一条消息**。大家可以仔细品味品味这个逻辑，我知道这种设计方式可能和大家预想的有点不一样，但是我必须指出来我为什么这么做，在 RocketMq 源码中就是这么设计的，所以我也照搬过来了，所以我们也就这样接受吧。总之，现在我们已经可以在 PopCheckPoint 对象中确定唯一一条消息了，这一点大家应该都认同吧？



很好很好，事情进展得非常不错，但与此同时我们也不得不承认，我们又面临了一个新的问题，那就是当 Broker 节点要表示某一条消息被消费成功了，只需要等待 ack 响应和待确认的消息匹配成功即可，但迄今为止，**我们也没有定义什么标志能够表示一条消息被成功了**。也就是说，Broker 节点的某一条消息被消费成功了，至少得做点什么吧，得让程序知道这条消息被消费成功了，这个大家可以理解吧？而我们之前也说了，在消息的整个 ck 和 ack 的操作流程中，消息本身并不参与进来，那怎么表示一条消息被消费成功了呢？**最简单的方式就是直接为每一条待确认的消息定义一个标志，比如说一批消息的数量为 32，那就定义一个存储 Boolean 对象的集合，集合的每一个索引都对应一条消息，也就是说每一个 Boolean 对象对应一条消息，哪一条消息被消费成功了，就根据消息对应的索引更新 Boolean 对象的值，直到集合中所有 Boolean 对象都被设置为 true，那就意味着这一批消息被成功消费完毕了**。这个逻辑可以立即吧？



没错，我们确实可以这么做，但是，还是回到 RocketMq 源码中，看看源码是怎么做的吧。在源码中并不是定义了一个存储 Boolean 对象的集合，而是使用了位图。**当然，说是位图，实际上就是使用了一个 AtomicInteger 对象，int 整数有 32 位，正好对应一批的 32 条消息。也就是说，每一位都对应一条消息，如果 Broker 节点收到了某一条消息的 ack 响应，那么就可以找到与这条消息对应的 bit 位，然后把使用 CAS 把这一 bit 更新为 1，如果是没有收到 ack 响应的消息，那么这个消息对应的 bit 位就是 0**。这就是 RocketMq 源码执行的操作，那现在我们清楚了源码是怎么做的，接下来当然可以仿照源码把这个功能复刻到我们自己的程序中。这一点大家可以理解吧？很好，说干就干，文字分析已经够多了，是时候把分析的这些内容落实到代码层面了。



但是，没错，又是一个但是，等到真正编写代码的时候，我越想越不对劲，总觉得还缺点什么东西。请大家想一想，一旦这个位图更新的功能实现完毕，位图的每一个 bit 和每一条待确认的消息对应了，这就意味着 ck 和 ack 功能就更加完善了，但现在我们的注意力都放到了消息被客户端成功消费的情况下，Broker 节点成功接收到了消息的 ack 响应，事情总有两面，我们也别高兴得太早，那假如 Broker 节点迟迟接收不到消费者客户端为消息回复的 ack 响应呢？想到这里，上一章结尾我留下的诸多问题中的第四个问题忽然涌现在我脑海中：**那就是不管出于什么原因，反正 Broker 节点一直没有接收到对应的 ack 响应，那 Broker 节点应该怎么办呢？考虑到这个问题，我们是不是应该给消费者客户端回复 Broker 节点 ack 响应定义一个超时时间呢？Broker 节点肯定不能无期限等待下去，如果我们定义一个时间阈值，那么只要 Broker 节点等待响应的时间超过这个阈值则视为消费者客户端消费失败**。这个问题是不是很合乎情理？心跳检测都还有超时时间呢，更别说如此重要的 ack 响应了。想通了这一点，我认为给 Broker 节点接收 ack 响应定义超时时间是很有必要的，那么这个超时时间该怎么定义呢？这个时候就轮到消息不可见时间登场了。



## 分析消息不可见时间的作用


我相信大家对 Pop 模式消费者客户端消费消息的操作还有印象，如果忘记了也没关系，我把 Pop 消费者客户端消费消息的部分代码搬运到下面了，帮助大家简单回顾一下，请看下面代码块。

```java
package org.apache.rocketmq.client.java.example;


/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/7/17
 * @方法描述：Pop模式的消费者客户端
 */
public class SimpleConsumerExample {

    private static final Logger LOGGER = LoggerFactory.getLogger(SimpleConsumerExample.class);

    private SimpleConsumerExample() {
    }

    public static void main(String[] args) throws ClientException, IOException {
        
        //省略部分内容
        
        // Max message num for each long polling.
        //设置本次从服务端拉取消息的最大条数
        int maxMessageNum = 16;
        // Set message invisible duration after it is received.
        //设置消息的不可见时间，至于不可见时间是什么，以及如何发挥作用，请大家阅读文章即可
        Duration invisibleDuration = Duration.ofSeconds(10);
        final List<MessageView> messages = consumer.receive(maxMessageNum, invisibleDuration);
        for (MessageView message : messages) {
            try {
                System.out.println("收到消息了" + message.getTopic() + message.getMessageId());
                consumer.ack(message);
            } catch (Throwable t) {
                LOGGER.error("Failed to acknowledge message, messageId={}", message.getMessageId(), t);
            }
        }
        // Close the simple consumer when you don't need it anymore.
        //consumer.close();

    }
}
```

从上面代码块中可以看到，Pop 消费者客户端在执行 receive() 方法，也就是从 Broker 节点获取可消费的消息时，向 receive() 方法中传入的第二个参数，就是消息的不可见时间。当时我没有跟大家解释消息的不可见时间的作用，现在时机成熟了，就让我来告诉大家，**所谓的消息不可见时间，其实就是 Broker 节点等待消息 ack 响应的超时时间**！也就是说从一开始，我们就把消息 ack 响应的超时时间定义完毕了，只要 Broker 节点在这个时间内没有接收到消息的 ack 响应，那就可以认为等待超时，消息没有被成功消费。当然，消费者从 Broker 节点获取消息时都是批量获取的，每次获取一批消息，这也就意味着消息不可见时间的作用范围是一批消息，这一批消息中的每一条消息的 ack 响应超时时间都是一样的。那这样正好，**我们刚才不是定义了一个 PopCheckPoint 类吗？这个类的对象封装了消息的 Pop 时间，也就是弹出 Broker 节点的时间，那 Pop 时间加上消息的不可见时间，这不就得到了这批消息 ack 响应的超时时间吗**？也就是说，只要在超过了 ack 响应时间，这批消息中的某一条消息还没有被 ack 的话，那就可以认定这条消息没有被消费成功，这个逻辑应该很清晰了吧？



很好，现在消息的不可见时间也分析完毕了，那接下来总该轮到在代码层面实现这些内容了吧，给 PopCheckPoint 类再定义一个消息不可见时间成员变量，这样它就可以加上消息被 Pop 出的时间，最终得到 ack 响应超时时间，与此同时也应该把消息确认消费成功的位图功能实现了，对吧？没错，确实应该实现这些功能了，但是大家有没有考虑过，为什么要把 ack 响应超时时间称为消息不可见时间呢？按照字面的意思来理解，消息的不可见时间好像就是消息不能被看见的时间，那什么时候不能被看见呢？**显然是刚被一个消费者客户端获取了，那么这个消息在规定的时间内，就不能被其他消费者客户端看到，这样一来消息就不会被其他客户端重复消费。而过了这个不可见时间，如果接收到 ack 响应，就意味着消息被消费成功了，如果没有接收到 ack 响应，就意味着消息消费失败了，在这之后，按照常规理解，那么这条消息是不是就可以再次被其他消费者客户端看到了？也就意味着这条消息可以被重新消费了，总之要确保没一条消息被消费成功**。这个逻辑可以理解吧？



如果大家理解了这个逻辑，我相信一定有朋友会感到疑惑，既然消息不可见时间还有这么一层意思，那是不是就意味着多个消费者客户端消费同一目标队列中的消息时，不管怎么样，反正必须得等到一段时间才能继续消费消息呢？要么是等待上一批消息被全部 ack，Broker 节点更新了最新的消费偏移量到管理器中，然后下一个消费者客户端才能继续消费；要么就是等待消息 ack 响应超时，也就是超过了消息的不可见时间，下一个客户端继续消费同一批消息，保证这批消息一定被消费成功。这个也是常规逻辑吧？但如果要按照这个逻辑思考，那假如一批消息里只有两条消息没有被成功 ack，那么这一批消息都要被重新消费吗？显然不能这么做的，这也太荒谬了。这些问题困扰着我，让我越来越理不清头绪。我总觉得程序不应该这么设计，**我觉得当前要消费的客户端不应该等待上一批消息消费完成**，还记得上一章结尾我列出的诸多问题中的前三个问题吗？



**1 如果消费者客户端从 Broker 节点获取了一批消息，不管是否在本地成功消费了这些消息，最终确实一条响应都没回复给 Broker 节点，那么 Broker 节点还能为这批消息更新消费偏移量吗？会不会出现一直不更新偏移量的情况？这样一来，其他消费者客户端还可以消费这一批消息，保证消息一定会被消费。**

**2 如果消费者消费了一批消息，并且消费者也逐一为这批消息的每一条都向 Broker 节点回复了消费成功的响应，但是，唯独中间有一条消息落下了，或者是别的什么原因，这条消息没有消费成功，自然也就没有回复成功响应，那这种情况下，Broker 节点还可以为这批消息更新消费偏移量吗？**

**3 抛开以上种情况，假设消费者客户端每次都能成功消费消息，也就意味着消费者客户端会把每条消息的成功响应回复给 Broker 节点，最终 Broker 节点才会更新这批消息的消费偏移量。这就意味着 Broker 节点必须等到消费者客户端成功消费了消息，才能更新消费偏移量，而更新了消费偏移量，Pop 模式的消费者客户端才能从同一消费队列中继续获取消息，那这样的话，消息被消费的效率显然很低啊。如果遇到网络波动，Broker 节点接收客户端响应慢了一点，那更新消费偏移量显然就会慢一点，那其他消费客户端要等到什么时候才能继续消费消息呢**？



现在浏览这三个问题，我认为这三个问题提得非常好，之前我就觉得多个消费者客户端消费消息的时候不必互相等待，尤其是在 Pop 消费模式下，如果互相等待，那么 Pop 模式也就失去了它存在的意义，这么做消费消息简直是太低了。而且刚才我们也梳理了消息不可见时间的意思，既然刚刚被消费的消息都不可见了，那其他消费者客户端还等个屁啊，再说了，**Broker 节点怎么保证刚被消费的消息在这个时间内不可见呢？最简单最直接的方法摆在眼前，那就是直接把这批消息的消费偏移量更新到管理器中，这样一来其他消费者客户端肯定就不会消费到这一批消息了，而是直接消费之后的消息，这不就做到了消息不可见吗**？



那这个时候显然就有朋友提出新的问题，如果每从 Broker 节点内部 Pop 出一批消息给客户端，就立刻更新这批消息的消费偏移量，那这批消息被消费失败了，但是偏移量已经被更新了，那它们就不能被同一个消费组内的其他客户端再次消费了呀？就算是这批消息中只有某一条消息被消费失败了，也不能更新消费偏移量啊，这么做未免太武断了。这时候，我就想起了上一章结尾为大家展示的第五个问题：

**5** **假如消费者客户端消费消息失败了，不管是消费所有消息都失败了，还是只失败了其中几条消息，那抛开更新消费偏移量，Broker 节点还可以执行什么操作呢？我能想到的是让这批消息被其他消费者客户端消费，保证数据的完整性，但这个功能该怎么实现呢**？



现在我们就可以思考这种情况了，有两个选择摆在我们面前：**第一个选择就是延迟更新消息队列的消费偏移量，每当有消费者客户端到队列消费消息的时候，都得等到前面的消息被消费成功了，更新了最新的消费偏移量，然后消费者客户端才能消费消息，这种选择会导致程序工作效率非常低！第二个选择就是实时更新消费队列的消费偏移量，那就是每当一批消息被 Pop 出去，直接就把这批消息的偏移量更新到消费偏移量管理器中，这样一来这批消息就对其他消费者客户端不可见了，其他消费者客户端也可以直接消费新的消息，程序工作效率肯定非常高；这种选择也会导致一个问题，那就是消息 ack 失败了，似乎无法被重新消费，可能会造成数据丢失**。那这两种情况我们应该选择哪一种呢？



现在就让我来揭晓答案吧，如果消费者客户端执行的是顺序消费消息操作，那么就选择第一种情况，如果消费者客户端执行的普通消费消息的操作，那么就选择第二种情况。当然，顺序消费功能并不是我们目前要关注的重点，目前大家的所有疑问肯定还是围绕着第二种情况产生的，因为我们目前实现的就是 Pop 消费者客户端消费普通消息的功能。好了，现在我们已经知道了第二种情况无法保证消费失败的消息被重新消费，那这个问题该怎么解决呢？其实解决方式非常简单：**只要不是顺序消费的情况，那么每当 Broker 节点被 Pop 出去一批消息，那就为这个消费队列更新一个临时的最新消费偏移量，其他消费者客户端就可以获得这个最新的临时消费偏移量去队列中消费消息，只有当消息被消费成功了才更新消费偏移量管理器中的对应信息；如果消息消费失败了，不管是这一批全部失败了，还是只有几条失败了，这都无所谓，反正哪些消息消费失败了，只要超过了消息 ack 的响应超时时间，就可以把消费失败的消息投递到消息重试队列中，而消息重试队列中的消息也会被消费者客户端消费，直到消费成功**。这样一来，以上全部问题不就迎刃而解了吗？**Pop 消费者客户端既可以无限制消费最新的消息，又不会消费同一条消息，而消费失败的消息也会被重新消费**。当然，消息重试队列目前也不是我们关注的重点，大家先知道程序内部有这个功能组件即可。大家可以仔细品味品味这个逻辑，如果理解了以上内容，大家就会清楚，消息的 popTime + 消息不可见时间最终得到的信息既可以成为消息 ack 响应超时时间，又可以被称为消息重新投递时间，这里的重新投递，自然是投递到重试队列中。

                        //如果获取到了消息，并且是顺序消费消息模式则进入下面分支
                        if (isOrder) {
                            //这里的代码大家先有个了解就行，因为刚才我在文章中提到了
                            //顺序消息和普通消息处理的不同逻辑，所以尽管还没有实现顺序消费消息功能

                            // this.brokerController.getConsumerOrderInfoManager().update(requestHeader.getAttemptId(), isRetry, topic,
                            //         requestHeader.getConsumerGroup(),
                            //         queueId, popTime, requestHeader.getInvisibleTime(), result.getMessageQueueOffset(),
                            //         orderCountInfo);
                            // this.brokerController.getConsumerOffsetManager().commitOffset(channel.remoteAddress().toString(), requestHeader.getConsumerGroup(), topic, queueId, finalOffset);
                        } else {
                            //如果不是顺序模式，就可以构建ck对象，添加检查点了，检查点添加了之后，当消费者客户端消费完消息，就可以回复服务端消息被消费成功了，如果一直没有回复
                            //就意味着消息没有被消费成功，那么消息就可能会被放到重试队列中，甚至最后进入死信队列
                            //下面方法中的reviveQid重试队列Id参数大家可以暂时忽略
                            if (!appendCheckPoint(requestHeader, topic, reviveQid, queueId, finalOffset, result, popTime, this.brokerController.getBrokerConfig().getBrokerName())) {
                                return atomicRestNum.get() + result.getMessageCount();
                            }
                        }
                    }


                    //省略之后的内容
                    
                    
                }).whenComplete((result, throwable) -> {
                    if (throwable != null) {
                        POP_LOGGER.error("Pop message error, {}", lockKey, throwable);
                    }
                    //最后还要把锁释放了
                    queueLockManager.unLock(lockKey);
                });
    }

     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * @方法描述：追加ck消息到popBufferMergeService缓冲区的方法
     */
    private boolean appendCheckPoint(final PopMessageRequestHeader requestHeader,
                                     final String topic, final int reviveQid, final int queueId, final long offset,
                                     final GetMessageResult getMessageTmpResult, final long popTime, final String brokerName) {

        
        //创建一个ck检查点对象
        final PopCheckPoint ck = new PopCheckPoint();
        //初始化位图为0，用于标记哪些消息已经被确认
        ck.setBitMap(0);
        //设置本次弹出消息的数量
        ck.setNum((byte) getMessageTmpResult.getMessageMapedList().size());
        //设置消息弹出时间
        ck.setPopTime(popTime);
        //设置消息的不可见时间
        ck.setInvisibleTime(requestHeader.getInvisibleTime());
        //设置本批消息在队列的起始偏移量
        ck.setStartOffset(offset);
        //设置消费者组信息
        ck.setCId(requestHeader.getConsumerGroup());
        //设置消息主题
        ck.setTopic(topic);
        //设置队列Id
        ck.setQueueId(queueId);
        //设置Broker名称
        ck.setBrokerName(brokerName);
        //得到并设置每一条消息相对于本批消息的起始偏移量的的偏移量差值
        for (Long msgQueueOffset : getMessageTmpResult.getMessageQueueOffset()) {
            ck.addDiff((int) (msgQueueOffset - offset));
        }
        //把创建完毕的ck对象添加到pop缓冲区组件中
        //这里传进去了一个getMessageTmpResult.getNextBeginOffset()，大家可以往前翻一翻，一定要弄清楚这里传进去的参数有什么意义
        //下面方法中的reviveQid, -1两个参数大家先不必关注，后面真正用到的时候我会对其展开讲解
        this.popBufferMergeService.addCk(ck, reviveQid, -1, getMessageTmpResult.getNextBeginOffset());
        return true;
    }

}

    public boolean addCk(PopCheckPoint point, int reviveQueueId, long reviveQueueOffset, long nextBeginOffset) {
        
        //判断是否启用了缓冲区功能，没有启用则直接返回添加失败
        //注意，在源码中默认并没有启动这个功能，但是你可以自己配置启用
        //没有启用的后果很直接，那就是PopCheckPoint对象会被持久化到本地
        if (!brokerController.getBrokerConfig().isEnablePopBufferMerge()) {
            return false;
        }
        //判断当前服务是否可以正常工作
        if (!serving) {
            return false;
        }
        
        //得到系统当前时间
        long now = System.currentTimeMillis();
        //判断要被存放的消息是否快超时了，也就是不可见时间已经快到期了，快到期则默认来不及ack处理
        //这里多出来的1500就是留给ack的操作时间，防止ack刚到，结果也超时了
        if (point.getReviveTime() - now < brokerController.getBrokerConfig().getPopCkStayBufferTimeOut() + 1500) {
            if (brokerController.getBrokerConfig().isEnablePopLog()) {
                POP_LOGGER.warn("[PopBuffer]add ck, timeout, {}, {}", point, now);
            }
            //直接返回失败结果
            return false;
        }
        
        //判断缓冲区是否已经存满数据了，存满则直接返回失败结果
        if (this.counter.get() > brokerController.getBrokerConfig().getPopCkMaxBufferSize()) {
            POP_LOGGER.warn("[PopBuffer]add ck, max size, {}, {}", point, this.counter.get());
            return false;
        }
        
        
        //创建ck检查点包装器对象，这里的操作很重要，本批消息的唯一key就会在这个过程中创建
        PopCheckPointWrapper pointWrapper = new PopCheckPointWrapper(reviveQueueId, reviveQueueOffset, point, nextBeginOffset);
        
        //检查是否存在key冲突
        if (this.buffer.containsKey(pointWrapper.getMergeKey())) {
            POP_LOGGER.warn("[PopBuffer]mergeKey conflict when add ck. ck:{}, mergeKey:{}", pointWrapper, pointWrapper.getMergeKey());
            return false;
        }

        //在这里把消息缓存到buffer成员变量中
        this.buffer.put(pointWrapper.getMergeKey(), pointWrapper);
        this.counter.incrementAndGet();
        return true;
    }
