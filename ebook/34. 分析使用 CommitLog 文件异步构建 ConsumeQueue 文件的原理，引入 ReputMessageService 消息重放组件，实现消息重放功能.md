## 引入 ReputMessageService 组件，实现消息存储引擎消息重放功能


很好，终于要开始实现消息重放功能了，那在最开始请大家先思考一个小问题，那就是应该怎么从 CommitLog 文件的内存缓冲区中解析消息呢？也许大家一上来就很关心消息重放的后台线程应该如何定义，但在我看来这个问题很容易解决，线程其实就是一个 Thread 对象，创建 Thread 线程对象并非重点，定义好线程要执行的 run() 方法才是重点。也就是说，创建线程启动线程是非常简单的操作，关键是线程启动之后做什么，这个才是我们要重点关注的内容。当然，现在不用思考就知道，线程启动之后肯定是解析 CommitLog 文件夹中的新消息，那问题就来了，CommitLog 文件夹中的消息内容那么多，应该从哪里开始解析呢？而一旦开始解析之后，会不会重复解析同一条消息呢？也就是说要防止同一条消息被重放两次，还有一点，消息重放后台线程怎么就知道有新的消息到达 CommitLog 文件缓冲区了呢？最后，还有最重要的一个问题，那就是消息重放后台线程知道了要解析的消息了，那应该怎么解析呢？按照什么格式解析呢？



一下子提出这么多问题，大家肯定有点懵，但我相信给大家一点时间，大家思考几秒钟就会意识到，以上几个问题其实都很好解决，在解析消息时，要保证完全正确、不重复、不遗漏 CommitLog 文件缓冲区任何一条消息其实非常简单，**只需要给负责重放消息的后台线程定义一个初始解析偏移量即可，这个偏移量可以定义为 0，每当线程从 CommitLog 文件缓冲区中解析了一些消息，这些消息的大小为多少，就为后台线程的解析偏移量增加多少值即可**。而通过前面章节的学习我们已经知道了，**当消息被写入到 CommitLog 文件缓冲区时，内存映射文件对象内部有一个 wrotePosition 成员变量记录消息写入的最新位置，那么只要让 CommitLog 得到它内部最新的内存映射文件对象的 wrotePosition，再和消息重放线程的解析偏移量做对比，不就知道解析偏移量解析了多少消息了吗？也就知道还剩下多少消息没有被解析，当然，如果这两个偏移量一致，那就意味着在那个时刻，CommitLog 文件缓冲区中的消息都被重放完毕了**。只要实现了这个功能，消息重放线程肯定就不会遗漏 CommitLog 文件缓冲区的任何一条消息，也不会重复解析同一条消息，大家可以品味品味这个逻辑。



当然，到这里还没有分析完毕，还有最后一个问题需要分析，那就是消息重放线程知道了要解析的消息后，应该怎么解析呢？我之所以提出这个问题，是因为考虑到了消息的存储方式，在 CommitLog 文件缓冲区中，消息都是存放带 ByteBuffer 中，而要解析每一条消息，肯定就要从这个 ByteBuffer 中读取消息，然后再解析消息，**那这就意味着在从 ByteBuffer 中读取消息的时候，肯定要按照生产消息的编码格式，先读取缓冲区的前 4 个字节，的到整条消息的长度，然后再读区整条消息，解析这条消息即可；并且读取到这里之后，大家可以想一想，ByteBuffer 缓冲区的读指针是不是已经向后移动了，这个时候读指针已经移动到第二条消息的位置了，那么再读区 4 个字节，就得到了第二条消息的总长度，然后再读区第二条消息解析即可**。这个逻辑大家可以理解吧？这就是消息重放后台线程从 CommitLog 文件缓冲区中读取并解析消息的核心逻辑。好了，这些逻辑分析完毕之后，接下来我就想先编写一部分代码，加强大家对消息重放功能的理解。



我之前说了定义后台线程是最简单的事，而事实也正是这样，因为在程序中已经有了一个线程对象，那就是 ServiceThread 对象，在之前实现的各种数据提交和刷新功能中，我们也都用到了这个 ServiceThread 对象。那现在要定义消息重放线程了，我们也知道消息重放操作会在消息队列程序运行期间一直工作，显然这个线程启动之后就会在一个循环中不断执行消息重放的操作，**那我们可以把这个消息重放线程定义为 ReputMessageService 类，并且让这个类继承 ServiceThread 类，这样一来消息重放线程就被定义完毕了**。当然，接下来你还要为这个线程定义 run() 方法，而 run() 方法的逻辑刚才我们已经分析了，就是在一个循环中不断执行消息重放操作，除此之外，我们还需要给这个线程对象定义一个消息解析偏移量，这么分析下来，这个 ReputMessageService 线程对象可以先定义成下面这样，请看下面代码块。

以上代码块中的逻辑都很简单吧？我相信每一位朋友都能看懂，那定义好了 ReputMessageService 类之后，这个消息重放线程该怎么被创建，以及怎么启动呢？创建和启动其实都很好说，无非就是创建一个 ReputMessageService 对象，然后调用其父类的 start() 方法启动线程即可，之后消息重放线程就会执行 run() 方法，开始执行消息重放的操作，这些都很好实现，现在我们要明确的是，这个 ReputMessageService 对象该在哪里创建和启动呢？在 **RocketMq 源码中，其实是把 ReputMessageService 定义为 DefaultMessageStore 默认消息存储引擎的内部类了，并且 ReputMessageService 对象的创建和启动都是在消息存储引擎中进行的，在消息存储引擎的构造方法中创建线程对象，在消息存储引擎的 start() 方法中启动线程对象**。这么做的原因很简单，因为 ReputMessageService  消息重放线程需要从 CommitLog 文件缓冲区中读取并解析消息，而把线程对象定义在默认消息存储引擎中就可以直接使用 CommitLog 对象，因为 CommitLog 对象是默认消息存储引擎的成员变量。那么我们不如就放照源码，也把 ReputMessageService 消息重放线程对象定义为 DefaultMessageStore 默认存储引擎的内部类吧，具体实现请看下面代码块。

好了，阅读完以上代码块之后，大家应该清楚了，CommitLog 对象的 getConfirmOffset() 方法得到的就是目前写入到 CommitLog 文件夹的本地文件中的所有可读取数据的总容量，那还是回到之前，在 DefaultMessageStore 消息存储引擎的 start() 方法中，执行的 this.reputMessageService.setReputFromOffset(this.commitLog.getConfirmOffset()) 这行代码，把写入到 CommitLog 文件夹的本地文件中的所有可读取数据的总容量赋值给了消息重放线程的消息解析偏移量，为什么这么做呢？接下来请大家听我解释：**假如消息队列框架是第一次启动，本地文件还没有存储任何数据的时候，那么 CommitLog 对象的 getConfirmOffset() 方法得到的肯定是 0，这一点没有问题吧？只有不断写入数据，CommitLog 对象的 getConfirmOffset() 方法才会得到最新的可读消息偏移量；如果是程序第一次启动，那使用 CommitLog 对象的 getConfirmOffset() 方法得到的 0 给重放线程的消息解析偏移量赋值，这个时候就意味着消息重放线程在重放消息时，应该从 CommitLog 文件缓冲区的起始位置，也就是偏移量为 0 的位置开始解析并重放消息，这一点大家也可以理解吧？而消息队列框架在运行了一段时间之后可能出现重新启动的情况，重新启动的时候，CommitLog 文件夹中的本地文件可能已经存储了很多数据了，所以程序每次重启的时候，要执行加载数据的方法，也就是 load() 方法，在执行这个方法的过程中，会把数据的各个关键信息都加载到内存中，比如说最新写入消息的偏移量等等，而这个时候 CommitLog 对象的 getConfirmOffset() 方法得到的肯定就是本地文件最新的可读消息偏移量。当程序内部各个组件的 load() 方法执行完毕之后，各个组件的 start() 方法才会被执行(这一点在后面版本代码中实现 load() 方法时就会得到印证，大家先记住即可)，也就是说这个时候各个组件才会真正启动，消息重放线程的消息解析偏移量才会被赋值，如果服务器重启之后CommitLog 对象的 getConfirmOffset() 方法得到偏移量为 700，然后把 700 赋值给消息重放线程的消息解析偏移量，就意味着消息线程开始工作时，就要从 CommitLog 文件缓冲区偏移量为 700 的位置开始执行消息重放操作，之前的消息已经被重放完了，不需要再次被重放**。大家可以仔细品味品味这个逻辑，如果这个逻辑清楚了，那接下来我们就可以继续重构 ReputMessageService 类，实现该类的 doReput() 方法，也就是真正重放消息的方法。



而消息重放的核心逻辑非常简单，**其实就是给 doReput() 方法内部定义一个循环，让线程在一个循环中，不断从消息解析偏移量的位置从 CommitLog 中开始读取并解析消息，解析出消息的关键信息，然后把重放消息存放到目标消费队列中即可，如果一个本地文件解析完了，就换下一个文件继续解析，如果 CommitLog 文件缓冲区都解析完了，那就退出循环，等待 run() 方法进入下一次循环再继续工作**。这些逻辑我之前已经为大家分析过了，怎么解析消息也分析过了，所以接下来我就直接展示相关代码了，更多的细节我在代码注释中写得非常清楚，我就不再详细解释了，如果每一个细节，每一个类都讲解，那么五万字的篇幅也无法讲完消息重放的功能。当然，大家现在其实也已经可以阅读第十五版本代码了，如果看文章中的源码比较吃力，那么直接结合文章阅读第十五版本代码中的相关内容也可以，请看下面代码块。

            //循环执行操作
            while (!this.isStopped()) {
                try {
                    //每次让线程休息1毫秒，避免没有可重放数据时线程空转
                    TimeUnit.MILLISECONDS.sleep(1);
                    //执行消息重放操作
                    this.doReput();
                } catch (Exception e) {
                    DefaultMessageStore.LOGGER.warn(this.getServiceName() + " service has exception. ", e);
                }

            DefaultMessageStore.LOGGER.info(this.getServiceName() + " service end");

        /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

         * @方法描述：终止消息重放组件工作的方法

            //循环50次，每次都判断是否还有未重放的消息
            for (int i = 0; i < 50 && this.isCommitLogAvailable(); i++) {
                try {
                    //每次循环睡100ms，这里就是给够消息重放组件重放消息时间
                    //尽可能在停止工作之前把CommitLog中的消息重放完毕
                    Thread.sleep(100);
                } catch (InterruptedException ignored) {

                }
            }
            //判断组件终止之前是否仍有未重放的CommitLog消息
            if (this.isCommitLogAvailable()) {

                LOGGER.warn("shutdown ReputMessageService, but CommitLog have not finish to be dispatched, CommitLog max" +
                                " offset={}, reputFromOffset={}", DefaultMessageStore.this.commitLog.getMaxOffset(),
                        this.reputFromOffset);
            }
            //调用父类关闭方法终止线程工作
            super.shutdown();
        }



        /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
         * @author：陈清风扬，个人微信号：chenqingfengyangjj。
         * @方法描述：判断CommitLog文件中是否还有待重放的数据的方法
         */
        public boolean isCommitLogAvailable() {
            return this.reputFromOffset < DefaultMessageStore.this.getConfirmOffset();
        }



         /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
         * @author：陈清风扬，个人微信号：chenqingfengyangjj。
         * @方法描述：重放CommitLog中数据的方法，也是消息重放组件中最核心的方法
         */
        public void doReput() {
            //判断消息重放的偏移量是否小于CommitLog文件消息的最小偏移量，这里我要解释一下为什么要做这个判断
            //假如那么CommitLog文件的最小偏移量就是1000，而消息重放才重放到500，这就意味着CommitLog文件中前1000的数据已经被过期删除了
            //消息重放都没来得及重放，数据就被过期删除了，可能是消息重放的太慢，也可能是其他原因，导致CommitLog文件数据过期了消息重放还没处理完毕
            //所以这个时候要记录一下告警日志，然后更新消息重放的偏移量
            if (this.reputFromOffset < DefaultMessageStore.this.commitLog.getMinOffset()) {
                //在这里记录告警日志
                LOGGER.warn("The reputFromOffset={} is smaller than minPyOffset={}, this usually indicate that the dispatch behind too much and the commitlog has expired.",
                        this.reputFromOffset, DefaultMessageStore.this.commitLog.getMinOffset());
                //把消息重放偏移量设置为CommitLog文件最新的的最小偏移量
                this.reputFromOffset = DefaultMessageStore.this.commitLog.getMinOffset();
            }


            //下面就是在循环中根据消息解析偏移量不断从CommitLog文件缓冲区中读取解析消息的操作
            
            //在循环中执行消息重放操作，循环的时候一直判断CommitLog文件中是否还有待重放的数据
            //如果没有则退出循环
            for (boolean doNext = true; this.isCommitLogAvailable() && doNext; ) {
                //从要重访的位置得到封装了后面所有消息数据的缓冲区对象，我把CommitLog类的getData()方法也展示在当前代码块中了
                //大家可以看一看，这里可以看到，每次都会直接从CommitLog文件缓冲区中得到消息解析偏移量之后的所有缓冲区内容
                //当然，只要有新的生产消息不断写入到CommitLog文件缓冲区中，那么在每次循环的时候，总能从CommitLog中读取到新的消息
                SelectMappedBufferResult result = DefaultMessageStore.this.commitLog.getData(reputFromOffset);
                //如果没有得到缓冲区对象，则直接退出循环
                if (result == null) {
                    break;
                }
                try {
                    //在循环中，每次循环都会更新消息重放起始位置为当前获取到的数据起始位置
                    this.reputFromOffset = result.getStartOffset();


                    //以下就是读取缓冲区中每一条消息，然后解析每一条消息的内容

                    
                    //result.getSize()就是刚才从CommitLog文件中读取到的要重放的数据的总大小
                    //接下来要执行消息重放操作，所以这里会判断消息重放的大小如果超过刚才获得的数据总大小了，就会退出循环
                    for (int readSize = 0; readSize < result.getSize() && reputFromOffset < DefaultMessageStore.this.getConfirmOffset() && doNext; ) {
                        
                        //这里会从CommitLog文件中真正解析消息，但是并不是解析消息的内容，而是得到消息在CommitLog中的全局偏移量，消息的大小，消息的目标队列Id
                        //消息的tag过滤标签信息等等，这些信息都会封装到dispatchRequest对象中，我把DispatchRequest类的部分内容也展示在当前代码块中了
                        //commitLog.checkMessageAndReturnSize()方法我也展示在当前代码块中了
                        DispatchRequest dispatchRequest = DefaultMessageStore.this.commitLog.checkMessageAndReturnSize(result.getByteBuffer(), false, false, false);
                        
                        
                        //得到本次解析到的消息的大小
                        int size = dispatchRequest.getBufferSize() == -1 ? dispatchRequest.getMsgSize() : dispatchRequest.getBufferSize();
                        
                        //如果当前解析到的消息的大小加上消息重放位置，超过了CommitLog文件的消息确认位置，非集群模式下其实就是CommitLog文件的消息最大偏移量
                        if (reputFromOffset + size > DefaultMessageStore.this.getConfirmOffset()) {
                            //这个时候就会直接退出循环
                            doNext = false;
                            break;
                        }

                        
                        //判断消息是否解析成功了
                        if (dispatchRequest.isSuccess()) {
                            if (size > 0) {

                                //下面就是真正重放消息的操作
                                
                                //如果消息解析成功了，那就可以在这里把消息交给消息重放器去重放
                                //这个时候消息就会被存储到消费队列和index文件队列中了
                                //这行代码大家先记住，马上我就会为大家实现这个doDispatch方法
                                DefaultMessageStore.this.doDispatch(dispatchRequest);


                                
                                //更新消息重放偏移量，增加当前重放的消息大小
                                this.reputFromOffset += size;
                                //更新已重放的消息大小
                                readSize += size;
                            }

                                
                            //如果这次解析到的消息大小为0，说明本次得到的SelectMappedBufferResult缓冲区对象中的消息已经解析完毕了
                            //意味着需要切换到下一个文件开始解析了
                            else if (size == 0) {
                                //这里得到下一个内存映射文件的起始偏移量，把这个偏移量更新给消息重放偏移量
                                this.reputFromOffset = DefaultMessageStore.this.commitLog.rollNextFile(this.reputFromOffset);
                                //设置已读大小为当前SelectMappedBufferResult缓冲区数据大小，表示当前文件已处理完
                                readSize = result.getSize();
                            }
                        }
                            
                        else {//执行到这里意味着消息没有解析成功
                            
                             //记录错误日志，日志信息为读取的消息总数与消息总大小不匹配
                             LOGGER.error("[BUG]read total count not equals msg total size. reputFromOffset={}", reputFromOffset);
                             //更新消息重放偏移量
                             this.reputFromOffset += size;
                        }
                    }
                } catch (RocksDBException e) {
                    ERROR_LOG.info("dispatch message to cq exception. reputFromOffset: {}", this.reputFromOffset, e);
                    return;
                } finally {
                    //释放映射缓冲区资源
                    result.release();
                }
                //在消息重放操作执行完毕后，执行回调方法
                finishCommitLogDispatch();
            }
        }

                return DefaultMessageStore.this.getBrokerIdentity().getIdentifier() + ReputMessageService.class.getSimpleName();
            }
            return ReputMessageService.class.getSimpleName();
        }

                    return new DispatchRequest(-1, false /* success */);
            }
            //根据魔术得到消息版本
            MessageVersion messageVersion = MessageVersion.valueOfMagicCode(magicCode);

package org.apache.rocketmq.store;




/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

public class ConsumeQueue implements ConsumeQueueInterface {


    private static final Logger log = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //消费队列内存映射文件存储的每条消息的字节，也就是存储单元为20字节
    //前8字节为物理偏移量，后4字节为消息长度，后8字节为消息的Tag哈希值
    public static final int CQ_STORE_UNIT_SIZE = 20;

    //消息tag标签在存储单元中的偏移量为12字节
    public static final int MSG_TAG_OFFSET_INDEX = 12;

    private static final Logger LOG_ERROR = LoggerFactory.getLogger(LoggerName.STORE_ERROR_LOGGER_NAME);

    //消息存储引擎
    private final MessageStore messageStore;

    //内存映射文件队列
    private final MappedFileQueue mappedFileQueue;

    //当前消费队列存储消息所属的主题信息
    private final String topic;

    //当前消费队列的队列Id
    private final int queueId;

    //存储消息的缓冲区对象，其实是这样的，当消息重放的时候，会先把消息的关键信息写入到这个缓冲区中
    //然后再把内容从这个缓冲区存储到内存映射文件中，至于为什么这么做，原因也很简单，那就是先对消息按照固定格式编码
    //编码完毕之后，就可以直接把消息写入到pagecache中了
    private final ByteBuffer byteBufferIndex;

    //ConsumeQueue消费队列文件的存储路径
    private final String storePath;

    //单个内存映射文件的大小
    private final int mappedFileSize;

    //消费队列映射文件中的最大消息物理偏移量，注意这个最大偏移量指的是消息队列文件中
    //存储的最新的消息在CommitLog文件中的全局偏移量，这个偏移量是消息的结尾偏移量
    //所谓结尾偏移量就是消息结尾的全局偏移量，比如说一条消息有5个字节，它在CommitLog文件中
    //的全局偏移量是200，表示是从200字节的位置开始存储这条消息，消息总大小为5字节
    //那么消息的结尾偏移量就是205字节，这就是当前成员变量表示的含义，一会大家就知道是怎么回事了
    private long maxPhysicOffset = -1;


    //构造方法
    public ConsumeQueue(
            final String topic,
            final int queueId,
            final String storePath,
            final int mappedFileSize,
            final MessageStore messageStore) {
        this.storePath = storePath;
        this.mappedFileSize = mappedFileSize;

        this.byteBufferIndex = ByteBuffer.allocate(CQ_STORE_UNIT_SIZE);
    }




    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

    @Override
    public boolean flush(final int flushLeastPages) {
        //调用映射文件队列的flush方法，刷新指定页数的数据
        boolean result = this.mappedFileQueue.flush(flushLeastPages);

    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

    @Override
    public void putMessagePositionInfoWrapper(DispatchRequest request) {
        //定义失败重试的最大次数
        final int maxRetries = 30;
        //判断当前消息存储引擎是否可写，可写的情况下才允许消息重放到消费队列
        boolean canWrite = this.messageStore.getRunningFlags().isCQWriteable();
        //循环写入消息，这里虽然是循环，但只要写入成功一次就会退出当前方法了
        for (int i = 0; i < maxRetries && canWrite; i++) {
            //得到消息的tag哈希值
            long tagsCode = request.getTagsCode();
            //在这里执行真正的消息重放操作，把消息存储到ConsumeQueue消费队列中了，这里可以看到，消息的全局偏移量

            boolean result = this.putMessagePositionInfo(request.getCommitLogOffset(), request.getMsgSize(), tagsCode, request.getConsumeQueueOffset());

            //处理写入结果的操作我就省略了，都是很简单的代码
            
        }
        
        //程序执行到这里意味着循环了很多次依然没有写入成功，那就记录错误日志
        log.error("[BUG]consume queue can not write, {} {}", this.topic, this.queueId);
        //设置存储引擎当前的状态为逻辑队列错误状态
        this.messageStore.getRunningFlags().makeLogicsQueueError();
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：该方法就是把消息真正重放到消费队列中的方法，该方法在文章中做了简化
     * 但实际上源码和我提供的第十五版本中的内容也不难，无非就是添加了一点消息偏移量范围的合法校验操作
     */
    private boolean putMessagePositionInfo(final long offset, final int size, final long tagsCode) {

        //该方法的内容依然保持简化处理
        
        //判断要存入的消息的全局偏移量加上消息的大小是否小于消费队列的最大消息偏移量
        //如果小于的话则记录告警日志，因为要存入新的消息了，新消息存储之后的消费队列的最大消息偏移量肯定要比之前的大呀
        //但存储之后反而还小就意味着当前要存储的消息是旧的，可能重复处理同一条消息了，直接退出当前方法即可
        if (offset + size <= this.getMaxPhysicOffset()) {
            log.warn("Maybe try to build consume queue repeatedly maxPhysicOffset={} phyOffset={}", this.getMaxPhysicOffset(), offset);
            //直接退出当前方法
            return true;
        }
        //将缓冲区的当前位置设置为0，准备写入数据
        this.byteBufferIndex.flip();
        //设置缓冲区的大小限制，设置为存储单元的长度，保证后续写入的数据不会超过这个长度
        this.byteBufferIndex.limit(CQ_STORE_UNIT_SIZE);
        //把消息全局偏移量写入到缓冲区中
        this.byteBufferIndex.putLong(offset);
        //把消息的大小写入到缓冲区中
        this.byteBufferIndex.putInt(size);
        //把消息的tag哈希值写入到缓冲区中
        this.byteBufferIndex.putLong(tagsCode);
        //得到消费队列内存映射文件中的最后一个映射文件
        MappedFile mappedFile = this.mappedFileQueue.getLastMappedFile();
        //更新消费队列最大的消息偏移量，其实就是消息的全局偏移量加上消息的大小
        //这个结果表示消息结尾在CommitLog文件中的位置
        this.setMaxPhysicOffset(offset + size);
        //在这里把缓冲区中的数据存放到内存映射文件的缓冲区中，返回true意味着消息写入成功了
        return mappedFile.appendMessage(this.byteBufferIndex.array());
        return true;
    }

    

    //其他get、set方法省略
    
}

## 实现 ConsumeQueue 消费队列数据刷盘功能


其实本章内容到这里就可以结束了，但还有最后一个小功能没有实现，那就是把 ConsumeQueue 消费队列中的数据刷新到本地硬盘，现在来看，这个功能应该非常容易实现了吧？和之前实现刷新消息到 CommitLog 文件夹的功能几乎一样，只要定期调用相关管理器的 flush() 方法即可。**要把 ConsumeQueue 消费队列中的数据刷新到本地硬盘，只需要定期调用消费队列管理器，也就是 ConsumeQueueStore 对象的 flush() 方法就可以了。当然，我们肯定还是得再定义一个后台线程，让这个线程继承 ServiceThread 类，然后创建该线程对象，再启动它即可。至于如何工作，那肯定还是在一个循环中不断执行刷新数据的操作，同时也要考虑到最少刷新页数的限制、以及最大刷新时间间隔的兜底等等情况**，这些内容我也就不展开细说了，毕竟之前实现 CommitLog 数据的刷新功能时，已经仔细分析过这种刷新数据功能的实现思路了，所以接下来我就直接为大家展示相关代码，**这个刷新消费队列数据的线程就被定义为了 FlushConsumeQueueService，也是 DefaultMessageStore 的内部类**，具体内容请看下面代码块。

     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：消费队列数据刷盘器，这个刷新器会定期把消费队列的数据刷新到本地硬盘文件中
     */
    class FlushConsumeQueueService extends ServiceThread {

        //消息刷盘重试次数
        private static final int RETRY_TIMES_OVER = 3;

        //最新刷盘的时间
        private long lastFlushTimestamp = 0;


        /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
         * @author：陈清风扬，个人微信号：chenqingfengyangjj。
         * @方法描述：把消费队列数据刷盘的方法
         */
        private void doFlush(int retryTimes) {

            //得到消费队列每次刷盘数据的最少页数
            int flushConsumeQueueLeastPages = DefaultMessageStore.this.getMessageStoreConfig().getFlushConsumeQueueLeastPages();
            //判断消息刷盘重试次数是否到达上线
            if (retryTimes == RETRY_TIMES_OVER) {
                //到达上限则意味着要强制刷盘，所以这里把最小刷新页数设置为0，意味着不管有多少数据，都要立即执行刷盘操作
                flushConsumeQueueLeastPages = 0;
            }
            long logicsMsgTimestamp = 0;
            //得到消费队列数据刷新的时间间隔
            int flushConsumeQueueThoroughInterval = DefaultMessageStore.this.getMessageStoreConfig().getFlushConsumeQueueThoroughInterval();
            //得到当前系统时间
            long currentTimeMillis = System.currentTimeMillis();
            //判断距离上一次刷新的时间，是否超过了规定的时间间隔
            if (currentTimeMillis >= (this.lastFlushTimestamp + flushConsumeQueueThoroughInterval)) {
                //如果超过了则更新最新刷新时间
                this.lastFlushTimestamp = currentTimeMillis;
                //设置最小刷新页数为0，意味着可以强制执行刷盘操作
                flushConsumeQueueLeastPages = 0;
            }
            //得消费队列映射表，key是主题，value是队列Id和队列本身
            ConcurrentMap<String, ConcurrentMap<Integer, ConsumeQueueInterface>> tables = DefaultMessageStore.this.getConsumeQueueTable();
            //遍历队列执行刷新操作
            for (ConcurrentMap<Integer, ConsumeQueueInterface> maps : tables.values()) {
                //得到每一个消费队列
                for (ConsumeQueueInterface cq : maps.values()) {
                    //是否刷新成功的标志
                    boolean result = false;
                    //循环重试
                    for (int i = 0; i < retryTimes && !result; i++) {
                        //在这里执行刷盘操作
                        result = DefaultMessageStore.this.consumeQueueStore.flush(cq, flushConsumeQueueLeastPages);
                    }
                }
            }
            //如果是强制刷盘，则更新存储检查点中的逻辑消息时间戳
            if (0 == flushConsumeQueueLeastPages) {
                if (logicsMsgTimestamp > 0) {
                    DefaultMessageStore.this.getStoreCheckpoint().setLogicsMsgTimestamp(logicsMsgTimestamp);
                }
                //将存储检查数据刷盘
                DefaultMessageStore.this.getStoreCheckpoint().flush();
            }
        }



        /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
         * @author：陈清风扬，个人微信号：chenqingfengyangjj。
         * @方法描述：消费队列刷盘器启动后要执行的方法
         */
        @Override
        public void run() {
            DefaultMessageStore.LOGGER.info(this.getServiceName() + " service started");
            while (!this.isStopped()) {
                try {
                    //得到消费队列数据刷盘间隔
                    int interval = DefaultMessageStore.this.getMessageStoreConfig().getFlushIntervalConsumeQueue();
                    this.waitForRunning(interval);
                    //执行刷盘操作
                    this.doFlush(1);
                } catch (Exception e) {
                    DefaultMessageStore.LOGGER.warn(this.getServiceName() + " service has exception. ", e);
                }
            }//程序关闭之前再执行一次刷盘操作
            this.doFlush(RETRY_TIMES_OVER);
            DefaultMessageStore.LOGGER.info(this.getServiceName() + " service end");
        }

        /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
         * @author：陈清风扬，个人微信号：chenqingfengyangjj。
         * @方法描述：得到服务名称的方法
         */
        @Override
