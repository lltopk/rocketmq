

## 重构 PopLongPollingService 长轮询组件


上一章结尾我跟大家提出了三个问题，分别是：

**1 被挂起的长轮询请求等待超时后，并不能被及时处理。**

**2 在生产者发送了消息之后，Broker 节点内部不能主动唤醒等待的长轮询请求。**

**3 从消息存储引擎中返回的诸多消息信息意义不明**。

我相信在阅读了部分二十二版本代码之后，大家对这几个问题的思考肯定会更全面。当然，我也不是忘记了之前章节遗留的一些问题，那就是尽管我们的代码已经更新到第二十二版本了，长轮询组件也引入了，**但是当消费者从 Broker 节点内部获取了一批新的消息之后，并没有及时更新目标队列最新的消费偏移量，如果这个时候有另外的消费者到同一个目标队列中获取消息，那么使用旧的消费偏移量，不就会消费同一批消息了吗**？大家应该对这个问题还有印象吧？反正这个问题还没有解决，就和刚才那几个问题归到一起，当作第四个问题吧。从现在开始，我们的任务就是依次解决上面的四个问题。



其实第一个问题很容易解决，在上一章实现了 PopLongPollingService 长轮询组件之后，所有要被挂起的请求都被存放到了长轮询对象内部，并且在存放的时候，已经把这个请求的过期时间计算出来了，就像下面代码块展示的这样，请看下面代码块。

从上面代码块的第 46-47 行可以看到，被挂起的请求的超时时间已经得到了，并且被封装在了 PopRequest 对象中，而在上面代码块的第 59 行可以看到，PopRequest 对象又被存放到了 pollingMap 成员变量中。既然是这样，接下来就很好办了，**反正所有被挂起的请求都存放在 pollingMap 成员变量中，而每一个被挂起的请求的超时时间也确定的，那就可以开启一个循环，在循环中不断取出 pollingMap 中的请求，查看每一个请求是否超时了，当然，只需使用请求的超时时间和当前系统时间做对比，就可以判断请求是否超时了**。这个逻辑理解起来没什么问题吧？很好，那现在新的问题就来了，那就是怎么开启循环呢？**是单独启动一个线程执行循环操作呢？还是说在 PopLongPollingService 长轮询组件内部执行循环操作呢**？还有一点，**假如在循环中找到一些已经超时了的长轮询请求，那该怎么处理这些请求呢**？大家可以自己先思考思考，然后再往后看。



其实在 RocketMq 源码中，解决以上两个问题的方法非常简单，既然要开启一个循环，在循环中不断查找被挂起的请求有没有超时，相比于新启动一个线程执行这些操作，**那倒不如直接把 PopLongPollingService 长轮询组件直接定义为一个线程，也就是让这个 PopLongPollingService 组件继承 ServiceThread 类**，这样一来，长轮询组件不就是一个线程了吗？**既然是线程那就要执行 run() 方法，只需要在 run() 方法中开启循环操作，只要存放被挂起的请求的 pollingMap 中有数据，就可以判断有没有请求超时，而接下来只要在 Broker 节点启动的时候，启动这个长轮询组件，也就是调用这个线程的 start() 方法，那么 PopLongPollingService 就可以执行它的 run() 方法了**。这个操作流程应该很容易理解吧？



至于查找到了超时的请求该怎么处理，那就更简单了，**不管 Broker 节点的主题下是否有消息，凡是超时的请求，直接立刻去获取一次消息就行，获取到了就返回客户端有效响应，获取不到则返回空响应**。这些内容也很容易理解吧？如果大家理解了这些内容，那接下来就请看一下我早就实现的代码，请看下面代码块。

```java
package org.apache.rocketmq.broker.longpolling;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/10/24
 * @方法描述：Pop模式长轮询组件，如果有客户端到服务端Pop消息，但是服务端没有可消费的消息
 * 那么客户端请求就会被长训论组件挂起，当前类的对象就是负责这些工作的组件
 */
public class PopLongPollingService extends ServiceThread {

    private static final Logger POP_LOGGER = LoggerFactory.getLogger(LoggerName.ROCKETMQ_POP_LOGGER_NAME);

    private final BrokerController brokerController;

    private final NettyRequestProcessor processor;

    //外层map的key是主题信息，value是一个map，value这个map的key是消费组信息，值为占位符Byte，没有什么实际意义
    //通过这个成员变量可以迅速定位某个主题被哪些消费者组订阅了
    private final ConcurrentHashMap<String, ConcurrentHashMap<String, Byte>> topicCidMap;

    //存放轮询请求的映射表，key是主题+消费组+队列Id的组合字符串，value是轮询请求集合
    private final ConcurrentLinkedHashMap<String, ConcurrentSkipListSet<PopRequest>> pollingMap;

    //上一次清理过期长轮询请求的时间
    private long lastCleanTime = 0;

    //长轮询请求计数器
    private final AtomicLong totalPollingNum = new AtomicLong(0);


    //省略该类其他内容


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：因为长轮询组件也是一个线程，所以线程启动之后就会执行run方法，而长轮询组件是在BrokerController启动的时候启动的
     * 这一点大家可以自己在代码中验证一下
     */
    @Override
    public void run() {
        //循环计数
        int i = 0;
        //长轮询启动之后，只要没有停止工作，就会一直在循环中执行操作
        while (!this.stopped) {
            try {
                //在循环中，每次循环都会等待20毫秒
                this.waitForRunning(20);
                //循环次数加1
                i++;
                //如果长轮询请求映射表为空，意味着没有要处理的长轮询请求，则跳过本次循环
                //这里我要跟大家解释一下，所谓的处理长轮询请求，其实就是判断哪个长轮询请求过期超时了
                //如果过期超时就要回复给客户端响应了，这就是处理长轮询请求的逻辑
                //因为长轮询请求没有超时，那么会有其他线程唤醒等待的长轮询，然后去继续消费消息
                if (pollingMap.isEmpty()) {
                    continue;
                }
                //记录所有主题消费者组队列对应的长轮询请求总数
                long tmpTotalPollingNum = 0;
                
                
                
                //遍历每个队列的长轮询请求
                for (Map.Entry<String, ConcurrentSkipListSet<PopRequest>> entry : pollingMap.entrySet()) {
                    //得到长轮询请求的key，也就是主题+消费者组+队列Id
                    String key = entry.getKey();
                    //得到该队列对应的长轮询请求集合
                    ConcurrentSkipListSet<PopRequest> popQ = entry.getValue();
                    //集合为空，跳过本次循环
                    if (popQ == null) {
                        continue;
                    }
                    
                    
                    //记录从队列中取出的第一个请求
                    PopRequest first;
                    do {
                        //取出队列中的首个请求，这个请求也就是最早要超时的长轮询请求
                        //注意，这里我强调一下，获取到的第一个请求肯定是最早被放进去的请求
                        //也就是说在集合中越靠前的数据肯定是快要超时的
                        first = popQ.pollFirst();
                        //没有请求则跳出循环
                        if (first == null) {
                            break;
                        }
                        //判断从集合中去除的第一个请求是否超时了
                        if (!first.isTimeout()) {
                            //没有超时则把请求重新放回队列中，这里就会把数据放到队尾
                            //注意，在循环中会把队列中的所有请求都取出来判断一次
                            //本次循环结束后，就会处理下一个主题+消费者组+队列Id对应的队列中的请求
                            if (popQ.add(first)) {
                                //添加成功则退出本次do while循环，因为队列首个请求没有超时，后面的更不可能超时了，不需要判断
                                break;
                            } else {
                                //添加失败则记录日志信息
                                POP_LOGGER.info("polling, add fail again: {}", first);
                            }
                        }

                        
                        //执行到这里意味着刚才从队列中取出的请求超时了，那就在这里处理超时长轮询请求
                        if (brokerController.getBrokerConfig().isEnablePopLog()) {
                            POP_LOGGER.info("timeout , wakeUp polling : {}", first);
                        }
                        //因为要处理一个长轮询请求了，所以对长轮询请求总数减1
                        totalPollingNum.decrementAndGet();
                        //在这里唤醒超时的长轮询请求，所谓唤醒就是让这个长轮询请求对应的客户端立即去队列中拉取一次消息
                        //不管有没有消息，都要把响应返回给客户端
                        wakeUp(first);
                    } while (true);
                    
                    
                    //执行到这里就跳出do while循环了
                    if (i >= 100) {
                        //判断外层循环是否超过100次了，超过100次则记录一些日志信息
                        //记录当前遍历到的队列存储的长轮询请求数量
                        long tmpPollingNum = popQ.size();
                        //累加到所有队列存储的总数量中
                        tmpTotalPollingNum = tmpTotalPollingNum + tmpPollingNum;
                        //如果单个队列存储的长轮询请求数量超过100，则记录日志信息，这对发现队列是否堆积有重要意义
                        if (tmpPollingNum > 100) {
                            POP_LOGGER.info("polling queue {} , size={} ", key, tmpPollingNum);
                        }
                    }
                }

                
                //再次判断外层循环是否超过100次了，超过100次则记录一些日志信息
                if (i >= 100) {
                    //记录详细的长轮询统计信息
                    POP_LOGGER.info("pollingMapSize={},tmpTotalSize={},atomicTotalSize={},diffSize={}",
                            pollingMap.size(), tmpTotalPollingNum, totalPollingNum.get(),
                            Math.abs(totalPollingNum.get() - tmpTotalPollingNum));
                    //更新存储的总的长轮询请求数量
                    totalPollingNum.set(tmpTotalPollingNum);
                    //重置循环计数器，再次循环到100次之后，再次记录相关信息
                    i = 0;
                }
            } catch (Throwable e) {
                POP_LOGGER.error("checkPolling error", e);
            }
        }

        
        try {
            //执行到这里意味着长轮询组件停止工作了，那么就可以把成员变量中的数据都清楚了
            for (Map.Entry<String, ConcurrentSkipListSet<PopRequest>> entry : pollingMap.entrySet()) {
                ConcurrentSkipListSet<PopRequest> popQ = entry.getValue();
                PopRequest first;
                //得到队列中的每一个长轮询请求
                while ((first = popQ.pollFirst()) != null) {
                    //唤醒该长轮询请求，其实就是在组件终止工作时，让所有长轮询请求对应的客户端立刻去获取一次消息，不管有没有消息
                    //直接回复客户端即可
                    wakeUp(first);
                }
            }
        } catch (Throwable e) {

        }
    }



    //省略该类其他内容

}
```

上面代码块中的内容非常详细，代码注释也很多，我就不再重复解释了。当然，大家可能还会关心这个 PopLongPollingService 长轮询组件在哪里启动，这个问题就留给大家去我提供的第二十二版本代码中查看吧，答案非常简单，其实就是在 BrokerController 中启动的，我就不在文章中展示这部分的内容了。好了，到此为止，我们就把 PopLongPollingService 长轮询组件重构完毕了，处理超时长轮询请求的功能也就完成了。那接下来我们就可以关注第二个问题，看看在生产者发送了消息之后，Broker 节点内部怎么主动唤醒等待的长轮询请求。要想实现这个功能，最常规的做法其实就是定义一个监听器，或者是定义一个回调方法，其实你怎么说都行，因为不管是监听器还是什么回调方法，其实本质都是关注它们被执行的时机。那执行时机是什么呢？这一点已经非常清楚了，**那就是当生产者向 Broker 节点内部某个主题生产了消息**。Broker 节点接收到生产者生产的消息后，这就意味着有了新的消息可以被消费，假如这个时候恰好有消费这个主题下消息的请求被挂起了，那么直接执行唤醒被挂起请求的操作不就行了？当然这些操作就可以定义成一个回调方法，或者是定义在一个监听器中。这样一来，不就实现了 Broker 节点自己唤醒被挂起请求的功能了？



**在 RocketMq 源码中就是定义了一个监听器，每当 Broker 节点接收到生产者发送过来的消息，也就是说，每当 DefaultMessageStore 消息存储引擎存储了新的消息，并且异步构建了消费队列，这个时候就可以执行监听器中的方法，也就是执行唤醒被挂起的请求的操作**。注意，大家一定要梳理清楚，**一定要在消费队列构建完毕之后才执行监听器方法**，因为消费者客户端肯定是到消费队列中消费消息，就算新的消息被存储到 CommitLog 文件中了，但是对应的消费队列的内容还没有构建好，那么消费者客户端也消费不到 CommitLog 文件中的消息，大家一定要弄清楚这一点。当然，在我之前为大家实现生产消息功能时，我已经仿照源码把这个监听器实现了，并且也在 DefaultMessageStore 消息存储引擎中执行了监听器中的方法，只不过我当时跟大家说了，让大家暂时别关注这些内容，等到后面才会用上。现在这些早就被我实现的内容要派上用场了，那接下来就请大家跟着我的思路，我们一起把程序的执行流程梳理一下。

```java
package org.apache.rocketmq.broker.longpolling;



/**
```

```java
 * 那么客户端请求就会被长训论组件挂起，当前类的对象就是负责这些工作的组件

public class PopLongPollingService extends ServiceThread {


    //省略该类其他内容



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * @方法描述：通知指定主题下指定队列的长轮询请求有消息到达的方法
     */
    public void notifyMessageArrivingWithRetryTopic(final String topic, final int queueId) {
        //执行通知消息到达的方法
        notifyMessageArriving(topic, queueId);
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：通知指定主题下指定队列的长轮询请求有消息到达的方法
     */
    public void notifyMessageArriving(final String topic, final int queueId) {
        //得到该主题下的所有消费组
        ConcurrentHashMap<String, Byte> cids = topicCidMap.get(topic);
        if (cids == null) {
            return;
        }
        //遍历消费者组
        for (Map.Entry<String, Byte> cid : cids.entrySet()) {
            if (queueId >= 0) {
                //在这里得到的主题+消费者组+队列Id，唤醒该队列下的长轮询请求即可
                //这里还判断了一下队列Id，如果Id大于0，则先设置为-1，这是因为有的消费者可能订阅了所有队列的消息
                //而设置为-1，就表示可以拉取所有队列的消息，pop模式其实就是默认队列为-1
                //长轮询组件是一个公共组件，这里这么做是为了兼容Pop消费模式
                notifyMessageArriving(topic, cid.getKey(), -1);
            }
            //这里就是通知订阅了指定队列的消费者有新消息到达了
            notifyMessageArriving(topic, cid.getKey(), queueId);
        }
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：通知指定主题下指定队列的长轮询请求有消息到达的方法
     */
    public boolean notifyMessageArriving(final String topic, final String cid, final int queueId) {
        //根据主题+消费者组+队列Id得到对应的长轮询请求集合
        ConcurrentSkipListSet<PopRequest> remotingCommands = pollingMap.get(KeyBuilder.buildPollingKey(topic, cid, queueId));
        if (remotingCommands == null || remotingCommands.isEmpty()) {
            return false;
        }
        //从集合中取出第一个长轮询请求
        PopRequest popRequest = remotingCommands.pollFirst();
        //判断请求不为空和请求对应的客户端通道是否不活跃了
        while (popRequest != null && !popRequest.getChannel().isActive()) {
            //如果不活跃意味着长轮询不需要再回复客户端了，这个长轮询直接被丢弃就行了，反正已经从队列中取出了
            //长轮询总数减1
            totalPollingNum.decrementAndGet();
            //获取下一个要处理的请求
            popRequest = remotingCommands.pollFirst();
        }
        //没有找到长轮询请求则返回false
        if (popRequest == null) {
            return false;
        }
        //找到有效的长轮询请求了，就可以唤醒该请求，那么长轮询请求总轮询数减1即可
        totalPollingNum.decrementAndGet();
        if (brokerController.getBrokerConfig().isEnablePopLog()) {
            POP_LOGGER.info("lock release , new msg arrive , wakeUp : {}", popRequest);
        }
        //唤醒该长轮询请求
        return wakeUp(popRequest);
    }




    //省略该类其他内容
    
}
```

```java
package org.apache.rocketmq.store;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/6/25
 * @方法描述：默认的消息存储引擎，这个消息存储就应就会把生产者客户端生产的消息提交给CommitLog对象，然后存储到CommitLog文件中
 * 可以说这个类的对象和CommitLog类的对象是rocketmq消息存储模块中最重要的两个功能对象
 */
public class DefaultMessageStore  implements MessageStore{


    //省略该类其他内容

    //把消息存储到CommitLog文件中的核心组件
    protected final CommitLog commitLog;
    
    //消息到达监听器
    private final MessageArrivingListener messageArrivingListener;

    //是否批量通知消息到达的标志
    protected boolean notifyMessageArriveInBatch = false;


    //省略该类其他内容

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：消息重放服务组件，就是这个组件负责把CommitLog文件中的消息异步投递到消费队列和index文件队列中
     */
    class ReputMessageService extends ServiceThread {

        //消息重放的偏移量，这个偏移量其实就是记录当前组件从CommitLog的哪个位置开始处理消息的
        protected volatile long reputFromOffset = 0;

        //省略该内部类其他内容

        /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
         * @author：陈清风扬，个人微信号：chenqingfengyangjj。
         * @方法描述：消息重放组件启动之后要运行的方法
         */
        @Override
        public void run() {
            DefaultMessageStore.LOGGER.info(this.getServiceName() + " service started");
            //循环执行操作
            while (!this.isStopped()) {
                try {
                    //每次让线程休息1毫秒，避免没有可重放数据时线程空转
                    TimeUnit.MILLISECONDS.sleep(1);
                    //执行消息重放操作
                    this.doReput();
                } catch (Exception e) {
                    DefaultMessageStore.LOGGER.warn(this.getServiceName() + " service has exception. ", e);
                }
            }
            DefaultMessageStore.LOGGER.info(this.getServiceName() + " service end");
        }



         /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
         * @author：陈清风扬，个人微信号：chenqingfengyangjj。
         * @方法描述：重放CommitLog中数据的方法，也是消息重放组件中最核心的方法
         */
        public void doReput() {

            //判断消息重放的偏移量是否小于CommitLog文件消息的最小偏移量
            if (this.reputFromOffset < DefaultMessageStore.this.commitLog.getMinOffset()) {
                //在这里记录告警日志
                LOGGER.warn("The reputFromOffset={} is smaller than minPyOffset={}, this usually indicate that the dispatch behind too much and the commitlog has expired.",
                        this.reputFromOffset, DefaultMessageStore.this.commitLog.getMinOffset());
                //把消息重放偏移量设置为CommitLog文件最新的的最小偏移量
                this.reputFromOffset = DefaultMessageStore.this.commitLog.getMinOffset();
            }

            //在循环中执行消息重放操作，循环的时候一直判断CommitLog文件中是否还有待重放的数据
            //如果没有则退出循环
            for (boolean doNext = true; this.isCommitLogAvailable() && doNext; ) {
                //从要重访的位置得到封装了后面所有消息数据的缓冲区对象
                SelectMappedBufferResult result = DefaultMessageStore.this.commitLog.getData(reputFromOffset);
                //如果没有得到缓冲区对象，则直接退出循环
                if (result == null) {
                    break;
                }
                try {
                    //在循环中，每次循环都会更新消息重放起始位置为当前获取到的数据起始位置
                    this.reputFromOffset = result.getStartOffset();
                    //result.getSize()就是刚才从CommitLog文件中读取到的要重访的数据的总大小
                    //接下来要执行消息重放操作，所以这里会判断消息重放的大小如果超过刚才获得的数据总大小了，就会退出循环
                    for (int readSize = 0; readSize < result.getSize() && reputFromOffset < DefaultMessageStore.this.getConfirmOffset() && doNext; ) {
                        //这里会从CommitLog文件中真正解析消息，但是并不是解析消息的内容，而是得到消息在CommitLog中的全局偏移量，消息的大小，消息的目标队列Id，消息的tag过滤标签信息等等，这些信息都会封装到dispatchRequest对象中
                        DispatchRequest dispatchRequest = DefaultMessageStore.this.commitLog.checkMessageAndReturnSize(result.getByteBuffer(), false, false, false);
                        //得到本次解析到的消息的大小
                        int size = dispatchRequest.getBufferSize() == -1 ? dispatchRequest.getMsgSize() : dispatchRequest.getBufferSize();
                        //如果当前解析到的消息的大小加上消息重放位置，超过了CommitLog文件的消息确认位置，非集群模式下其实就是CommitLog文件的消息最大偏移量
                        if (reputFromOffset + size > DefaultMessageStore.this.getConfirmOffset()) {
                            //这个时候就会直接退出循环
                            doNext = false;
                            break;
                        }
                        //判断消息是否解析成功了
                        if (dispatchRequest.isSuccess()) {
                            if (size > 0) {
                                //如果消息解析成功了，那就可以在这里把消息交给消息重放器去重放
                                //这个时候消息就会被存储到消费队列和index文件队列中了
                                DefaultMessageStore.this.doDispatch(dispatchRequest);
                                //如果不是批量通知模式，则单条消息到达后，也就是被重放到消费队列中了，就直接通知相关组件处理
                                //这里的操作就是来一条消息就处理一条消息，不会攒一批了再通知
                                if (!notifyMessageArriveInBatch) {
                                    notifyMessageArriveIfNecessary(dispatchRequest);
                                }
                                //更新消息重放偏移量，增加当前重放的消息大小
                                this.reputFromOffset += size;
                                //更新已重放的消息大小
                                readSize += size;

                                //省略该方法之后的内容
                            }
                        }
                    }
                }
            }
        }


        //省略该内部类其他内容
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：当消费队列中有消息到达时，就意味着有消息可以消费者，当前方法就是通知相关组件有新消息到达的方法
     * 该方法在第十五版本代码中根本发挥不了作用，等后面用到了我才为大家真正讲解这个方法是怎么发挥作用的
     */
    @Override
    public void notifyMessageArriveIfNecessary(DispatchRequest dispatchRequest) {
        if (DefaultMessageStore.this.brokerConfig.isLongPollingEnable()
                && DefaultMessageStore.this.messageArrivingListener != null) {
            DefaultMessageStore.this.messageArrivingListener.arriving(dispatchRequest.getTopic(),
                    dispatchRequest.getQueueId(), dispatchRequest.getConsumeQueueOffset() + 1,
                    dispatchRequest.getTagsCode(), dispatchRequest.getStoreTimestamp(),
                    dispatchRequest.getBitMap(), dispatchRequest.getPropertiesMap());
        }
    }


    //省略该类其他内容
}
```

## 分析客户端和服务端消息的 ck 和 ack 流程


朋友们，现在让我们再回过头看看文章开头列出的那几个问题，第 1、2 这两个问题已经被解决了，还剩下第 3、4 问题需要解决，**也就是我们还不清楚从消息存储引擎中返回的诸多消息信息的意义，并且当消费者从 Broker 节点内部获取了一批新的消息之后，并没有及时更新目标队列最新的消费偏移量**，我们现在要关注的就是这两个问题。那要先分析哪一个问题呢？也许已经有朋友意识到了，我之所以现在重新回顾这两个问题，并且是放到一起回顾，那很可能就意味着这两个问题的联系非常紧密，需要整合到一起来分析。没错，确实是这样，当然，我们也不急着分析这两个问题，现在我们还有很多时间，请允许我先岔开主题，跟大家讨论一种新的情况。



请大家思考一下，当一个 Pop 模式消费者到 Broker 节点的 Test 主题中消费了一条消息，就比如说是从 Test 主题下 Id 为 1 的队列中消费的，那么消费者客户端获取了这条消息，在本地消费完了之后应该执行什么操作呢？如果是你自己开发的消息队列框架，那么此时你会让你的消费者客户端执行什么操作呢？如果是我的话，我肯定会让消费者客户端向 Broker 节点回复一个消费成功的响应，告诉 Broker 节点刚才获取的这条消息被消费成功了。我这么做的原因非常简单，我的目的并不是说在消费成功这条消息之后就通知 Broker 节点可以让其他消费者消费这条消息了，肯定不是这样，我们之前就分析过了，实际上通常情况下同意消费组的不同客户端不能消费同一条消息，**而我之所以这么做是考虑到了消费失败的情况**。请大家想一想，如果消费者客户端从 Broker 节点获取了一条消息然后在本地消费，结果出于某种原因，一直没能成功消费这条消息，然后消费者客户端也不回复 Broker 节点响应，Broker 节点就不知道这条消息没有消费成功，但在 Broker 节点内部的消费队列的最新消费偏移量总会在某个时刻被更新，**如果一条消息并没有被成功消费，而它对应的消费偏移量却被更新了，这就意味着它不可能在被其他消费者客户端消费，也就意味着它不会被消费，那么在生产中可能就会出现数据丢失的问题**。这个逻辑大家可以理解吧？这样分析下来，看来确实应该让消费者客户端在成功消费了消息之后，向 Broker 节点回复一个消费成功响应，并且，现在我们应该也意识到了，**消费队列消息偏移量的更新，这个操作应该在 Broker 节点接收到消息消费成功的响应之后执行**。我想对于这一点，大家应该也没有异议。



但是，在我们之前实现的功能中，消费者客户端总是一批一批地从 Broker 节点获取消息啊，比如说一个消费者客户端从 Broker 节点的某个消费队列中获取了 32 条消息，然后在本地消费成功了，肯定会为这 32 条消息都回复成功响应。那 Broker 节点该怎么更新队列消费偏移量呢？显然，**Broker 节点肯定要接收到这 32 条消息的每一个消费成功响应，然后才能把这一批消息的偏移量更新到消费进度管理器中**，这一点，大家应该也能认同吧？如果大家理解了这个逻辑，那很快就有很多问题突然展现在我们面前。



我首先能想到的是，**如果消费者客户端从 Broker 节点获取了一批消息，不管是否在本地成功消费了这些消息，最终确实一条响应都没回复给 Broker 节点，那么 Broker 节点还能为这批消息更新消费偏移量吗**？会不会出现一直不更新偏移量的情况？这样一来，其他消费者客户端还可以消费这一批消息，保证消息一定会被消费。这是我能想到的第一个问题。

**2 如果消费者消费了一批消息，并且消费者也逐一为这批消息的每一条都向 Broker 节点回复了消费成功的响应，但是，唯独中间有一条消息落下了，或者是别的什么原因，这条消息没有消费成功，自然也就没有回复成功响应，那这种情况下，Broker 节点还可以为这批消息更新消费偏移量吗**？

**3 抛开以上种情况，假设消费者客户端每次都能成功消费消息，也就意味着消费者客户端会把每条消息的成功响应回复给 Broker 节点，最终 Broker 节点才会更新这批消息的消费偏移量。这就意味着 Broker 节点必须等到消费者客户端成功消费了消息，才能更新消费偏移量，而更新了消费偏移量，Pop 模式的消费者客户端才能从同一消费队列中继续获取消息，那这样的话，消息被消费的效率显然很低啊。如果遇到网络波动，Broker 节点接收客户端响应慢了一点，那更新消费偏移量显然就会慢一点，那其他消费客户端要等到什么时候才能继续消费消息呢**？

**4 刚才说到网络波动可能会对 Broker 节点接收客户端消费成功响应的实时性造成影响，那么考虑到这个问题，我们是不是应该给消费者客户端回复 Broker 节点消费成功响应定义一个超时时间呢？Broker 节点肯定不能无期限等待下去，如果我们定义一个时间阈值，那么只要 Broker 节点等待响应的时间超过这个阈值则视为消费者客户端消费失败**。

**5 好了，假如消费者客户端消费消息失败了，不管是消费所有消息都失败了，还是只失败了其中几条消息，那抛开更新消费偏移量，Broker 节点还可以执行什么操作呢？我能想到的是让这批消息被其他消费者客户端消费，保证数据的完整性，但这个功能该怎么实现呢**？

**6 最后一个问题，并且是最关键的一个问题，那就是消费者客户端回复 Broker 节点消费成功响应时，Broker 节点怎么就知道接收到的响应回复的是哪一条消息呢？也就是说，Broker 节点怎么确定消息和响应的匹配关系呢？只有正确的响应匹配到了正确的消息，Broker 节点才能确认是哪一条消息真的被消费成功了**。

从上面代码块中可以看到，当一个消费者从 Broker 节点中获取消息时，通常情况下消息总是批量返回的，而批量返回的这批消息就会先被封装到一个 GetMessageResult 对象中，除了消息本身，随着一起返回的还有消费队列中被消费的每一条消息在消费队列的偏移量，以及消费这一批消息时，消费队列的消费起始偏移量。大家以前还不明白这些信息的作用，那现在就让我解释给大家听，**这些信息就可以确定 Broker 节点中哪一条消息被消费了，也就是响应和消息匹配的关键信息，当然，还得把消息所属的主题以及队列信息加上，消费组信息也得明确**。这么说大家可能还是不理解，接下来让我来举一个简单的例子，假如某个消费组中的消费者客户端到 Broker 节点中获取了一批消息，当消费者获取消息的时候，是从 Test 主题下 Id 为 1 的队列中获取的，并且是从队列消费偏移量为 300 字节之后获取的，而获取的某一条消息在消费队列中的偏移量为 360，那只要 Broker 节点把这些信息都记录下来，当消费者客户端成功消费了消息，回复成功响应时，只要把消息组信息，消息所属主题信息，队列 Id 信息，消息被消费时队列的消息起始偏移量，消息在队列中的偏移量都回复过来，那么 Broker 节点就可以根据这些信息确认唯一一条消息。Broker 节点持续不断地接收消费成功响应，直到按照这个匹配关系把这一批消息全部确认了，就可以把这批消息对应的消费偏移量更新到偏移量管理器中。大家可以仔细品味品味这个逻辑。



如果大家理解了以上的逻辑，那接下来我就可以直接跟大家解释一下，在 RocketMq 源码中是怎么明确消息响应与消息的匹配关系的。实际上，每当消费者客户端从 Broker 节点获取了一批消息，Broker 节点就会为这一批消息创建一个对应的 CheckPoint 对象，也就是检查点对象，这个对象内部封装了这批消息被消费的消费组信息，消息所属主题，队列 Id，被消费时队列的消息起始偏移量，各个消息在队列中的偏移量，以及消息被 Pop 出去的时间(这一点大家可以在 PopMessageProcessor 请求处理器的 processRequest() 方法中看到，我就不在文章中展示了)，Broker 节点所在集群的名称，以及其他一些重要信息。最后，这个 CheckPoint 对象会被 Broker 节点缓存起来，当这批消息被消费者客户端获取到本地时，这个 CheckPoint 对象封装的信息也会被消费者客户端获取，当消费者客户端成功消费了消息，回复 Broker 节点成功响应时，响应中也会携带这些额外信息。而这些信息被 Broker 节点接收后，又会在 Broker 节点内部被封装为一个 Ack 对象，每一条消息的响应信息都会被封装为一个 Ack 对象，然后就用 Ack 对象去和之前 Broker 节点缓存的 CheckPoint 对象匹配，消费者一次可以获取 32 条消息，那这也就意味着直到 32 个 Ack 对象把 CheckPoint 中的所有消息都匹配完了，Broker 节点才能认为这一批消息被消费者客户端消费成功了。这个就是消息被消费时的 ck 和 ack 流程。
