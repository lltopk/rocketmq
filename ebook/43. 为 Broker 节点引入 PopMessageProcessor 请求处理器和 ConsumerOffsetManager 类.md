## 简单分析 PopMessageProcessor 处理器的工作内容


我不清楚正在阅读本篇文章的朋友们是否已经看完了前面更新的几个框架课程，也就是说，大家可能是一路看过来，直到看到目前正在更新的 RocketMq 框架。如果是这样的话，那么我相信诸位心里可能会有一种感觉——也许大家并没有这种感受——但我对自己曾阅读过的诸多框架感受颇深，那就是在很多框架中，要实现某种功能时，即便这个功能是整个框架最核心的功能，最复杂的功能，在实现它的时候编写的代码也并没有多少，可能真正核心的代码只有那么二十几行、十几行，甚至是五六行，其他大量的代码所做的都是重复性的校验工作，或者是保证并发安全的工作。我这么说并不是没有原因，就拿当下我们要实现的 Broker 节点返回消费者客户端可消费消息的功能来说吧，这个功能最核心的操作是什么？这不用说，肯定就是在 Broker 节点内部，**准确地说是在消息存储引擎中找到可以让消费者客户端消费的消息**，这个是最核心的工作，至于把消息返回给客户端，这个工作在核心程度上，层次就稍微低一些了，毕竟其中涉及到的网络通信的功能我们早就实现了，无非就是看看怎么定义响应对象，怎么封装消息内容而已。



那说回最刚才我们分析的最核心操作，Broker 节点要怎么在消息存储引擎中找到客户端要消费的消息呢？把这个逻辑梳理清楚对我们要实现的功能至关重要，当然，大家也别把这个逻辑想象得多么复杂，真正实现起来其实并没有什么难度。请大家想一想，当订阅了某个主题的消费者客户端——就比如说是 Test 主题吧——要到 Broker 节点中获取该主题下的消息，那接收到了请求的 Broker 节点应该执行什么操作呢？**是不是先根据客户端订阅的主题找到该主题下的所有消费队列呢**？显然应该是这样的，只有先得到该主题下的所有消费队列，然后才能消费消息呀。



那得到了所有消费队列之后呢？就比如说该主题下有 8 个消费队列，那接下来该怎么办呢？这没得说，肯定是直接开始消费消息了，如果说有什么操作必须注意，那就是我们目前实现的是 Pop 消费模式客户端，在这种模式下，**消费者客户端可以消费 Test 主题下 8 个消费队列中的所有消息。如果是这样的话，那在 Broker 节点内部就可以开启一个循环，遍历所有消费队列，依次从每一个消费队列中获取可消费的消息**。当然，这其中有一个很重要的细节，**那就是消费者客户端没必要每次都从所有队列中获取消息**，原因很简单，现在我们已经知道了，消费者客户端每次到 Broker 获取消息时，会获取一批消息，这批消息的数量是有限制的，不可能无限大。**假如消费者客户端一次可以从 Broker 节点获取 32 条消息，当消费者客户端从 Test 主题下 8 个消费队列获取消息时，会在循环中遍历各个队列，如果遍历第一个消费队列就从该队列中得到了 32 条消息，那就可以退出循环，不必再遍历之后的队列获取消息了**，这个逻辑大家应该可以理解吧？



如果上面的逻辑大家都理解了，那之后就更简单了，因为之前我们在实现 Broker 节点存储生产者消息功能，异步构建 ConsumeQueue 消费队列得时候，已经跟大家讲解得很清楚了，**只要从消费队列中得到了消息，就可以得到每一条消息在 CommitLog 文件中的全局偏移量和消息大小，然后根据全局偏移量和消息大小就可以从 CommitLog 文件中得到真正可消费的消息**，这一点大家应该还有印象吧？那这么分析下来，好像实现 Broker 节点在消息存储引擎中找到可以让消费者客户端消费的消息的功能好像真的没有那么难，对吧？这就是 PopMessageProcessor 请求处理器处理消费者客户端请求时要执行的最核心的操作了，只要把这个实现了，其它的都好说。



看起来好像真的没有那么复杂，那接下来我们就可以开始实现这个功能了吗？要我说，现在时机根本不成熟，因为我们遗漏了最关键的一个问题，这个问题不解决，刚才分析的内容全都无法实现，**那就是我们根本无法保证消费队列中的消息不被多个消费者客户端重复消费**。当然，这一点并不是揭露了程序存在并发安全方面的隐患，实际上从之前我们分析 Pop 消费模式的时候就已经明确了，当多个 Pop 模式消费者客户端到 Broker 节点消费消息时，从同一个消费队列中获取消息的时候会争抢同步锁，只有得到锁的消费者客户端才能获取消息，等该客户端获取消息释放锁之后，其它的消费者客户端才能继续争抢锁进入同一个队列获取消息，这么来看，在同步锁的帮助下，就算多个消费者客户端同时消费同一个消费队列中的消息，也不会出现什么并发问题，对吧？没错，看起来确实是这样，但是大家都忽略了最重要的一点，**那就是消费者客户端到消费队列中获取消息的时候，怎么就知道上一个消费者客户端消费了哪些消息呢**？这一点至关重要啊。就比如说，现在有两个 Pop 模式的消费者客户端到 Test 主题下 Id 为 1 的消费队列中消费消息，消费队列中一共有 42 条消息，客户端 a 先抢到了同步锁，然后到队列中得到了前 32 条消息；释放同步锁之后，轮到客户端 b 到队列中消费消息了，为了不让同一条消息被重复消费，那客户端 b 肯定只能消费队列中的后 10 条消息，在这种情况下，客户端 b 是不是显然就要知道 Id 为 1 的消费队列被消费到哪里了？**也就是说客户端 b 必须清楚地知道消费队列被消费的进度**，只有这样，客户端 b 才能从客户端 a 消费的位置开始消费，不至于和客户端 a 消费到同一条消息，这个逻辑大家可以理解吧？如果理解了这个逻辑，那现在问题就来了，**每一个消费者客户端怎么能够知道消费队列最新的消费进度呢**？



稍微想想其实就能意识到刚才的问题很容易解决，**我们可以专门定义一个消费进度管理器，这个消费进度管理器也可以称为消费偏移量管理器，Broker 节点内部所有主题下的所有消费队列的消费进度都可以被这个消费进度管理器管理**。有了这个消费进度管理器之后，消费者客户端到 Broker 节点获取消息的流程就变得更严谨了：**消费者客户端每次获取消息之前，都要先到消费进度管理器中查询要消费的队列的最新消费偏移量，然后从该偏移量之后开始消费队列的消息，而消费完毕之后，还要立刻把该队列最新的消费偏移量更新到消费进度管理器中**，这样一来，消费队列中的消息肯定就不会被重复消费了。到此为止，Broker 节点返回消费者客户端可消费消息核心功能的实现思路就分析完毕了，是不是非常简单？我们只需要稍微费点力气，把消费进度管理器定义出来就行，其它的就是常规操作了，怎么根据消费队列消息封装的消息全局偏移量从 CommitLog 文件中获得消息本身，这些操作我也都为大家分析过了，现在我们只需要把这个消费进度管理器实现了即可，那这个消费进度管理器该怎么实现呢？也许大家已经迫不及待想看我实现这个消费进度管理器了，但很遗憾，现在还不是实现它的最好时机，因为除了我们刚才分析的那些功能，这个 PopMessageProcessor 请求处理器还有很多额外的操作要执行。大家可以先记住待实现的消费进度管理器，然后继续听我往下分析。



接下来要讨论的内容可能非常简单，但是对程序的严谨程度起着决定性的作用。请大家思考一下，当 Broker 节点接收到消费者客户端想要获取消息的请求后，也就是说，Broker 节点的 PopMessageProcessor 请求处理器在执行自己内部的 processRequest() 方法时，直接就可以根据客户端订阅的主题去消息存储引擎中获取消息吗？就算再怎么直接，在执行这些操作之前，是不是应该先看一看，**当前 Broker 节点内部是否真的存在对应的主题呀**？也就是说，只要应该先对消费者客户端订阅的主题信息进行校验，Broker 节点内部真的存在这个主题，才能执行下一步操作，如果主题都不存在，那肯定就获取不了消息，这个操作可以理解吧？



那除了校验主题合法性，还需要执行什么操作呢？如果往细了说那可太多了，比如当前 Broker 节点是否具备读权限，也就是说当前 Broker 节点内部的消息是否可以被消费；还可以校验客户端本次拉取请求的条数是否超过了 32，如果超过了 32 则超过规定阈值；当然，还可以验证消费者客户端订阅的主题是否具备读权限，如果不具备读权限，也不能返回消费者客户端消息。除此之外还有一些校验操作，我就不一一列举了，总之，大家现在应该意识到了，**在 Broker 节点的 PopMessageProcessor 请求处理器执行自己内部的 processRequest() 方法时，不可能直接就去消息存储器中查找消息，然后返回给客户端，而是会先执行大量的参数校验操作**，接下来我就把这些操作的具体内容展示给大家，请看下面代码块。

```java
package org.apache.rocketmq.broker.processor;

/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/10/20
 * @方法描述：处理Pop模式消费者客户端消费消息请求的处理器
 */
public class PopMessageProcessor implements NettyRequestProcessor {


    private static final Logger POP_LOGGER = LoggerFactory.getLogger(LoggerName.ROCKETMQ_POP_LOGGER_NAME);

    private final BrokerController brokerController;

    public PopMessageProcessor(final BrokerController brokerController) {
        this.brokerController = brokerController;
    }

    @Override
    public RemotingCommand processRequest(ChannelHandlerContext ctx, RemotingCommand request) throws Exception {
        
        Channel channel = ctx.channel();
        //创建Pop消息响应对象
        RemotingCommand response = RemotingCommand.createResponseCommand(PopMessageResponseHeader.class);
        //创建响应头对象
        final PopMessageResponseHeader responseHeader = (PopMessageResponseHeader) response.readCustomHeader();
        //从请求对象中得到Pop消息请求头对象
        final PopMessageRequestHeader requestHeader = (PopMessageRequestHeader) request.decodeCommandCustomHeader(PopMessageRequestHeader.class, true);
        //给响应设置唯一标识
        response.setOpaque(request.getOpaque());



        //以下就是处理请求之前的一些必要校验

        //判断请求的超时次数是否过多
        //如果客户端报告过来的当前请求超时次数过多，则意味着客户端和服务端存在网络问题或者是服务器负载过高
        //这个时候就没必要处理请求了，直接回复客户端长轮询超时响应码即可
        if (requestHeader.isTimeoutTooMuch()) {
            response.setCode(ResponseCode.POLLING_TIMEOUT);
            //备注请求失败原因
            response.setRemark(String.format("the broker[%s] pop message is timeout too much", this.brokerController.getBrokerConfig().getBrokerIP1()));
            return response;
        }

        //判断当前处理请求的Broker是否具备读权限，只有具备读权限的Broker节点才能弹出消息
        if (!PermName.isReadable(this.brokerController.getBrokerConfig().getBrokerPermission())) {
            //如果不具备读权限则回复错误响应
            response.setCode(ResponseCode.NO_PERMISSION);
            response.setRemark(String.format("the broker[%s] pop message is forbidden", this.brokerController.getBrokerConfig().getBrokerIP1()));
            return response;
        }

        //判断客户端本次要拉取的最大消息数量是否超过了32条，超过则不处理请求，因为一次最多允许拉取32条消息
        if (requestHeader.getMaxMsgNums() > 32) {
            response.setCode(ResponseCode.SYSTEM_ERROR);
            response.setRemark(String.format("the broker[%s] pop message's num is greater than 32", this.brokerController.getBrokerConfig().getBrokerIP1()));
            return response;
        }

        //得到当前要拉取的消息所属主题的配置信息
        TopicConfig topicConfig = this.brokerController.getTopicConfigManager().selectTopicConfig(requestHeader.getTopic());
        //判断主题配置信息是否为空
        if (null == topicConfig) {
            //为空则意味着该主题不存在，那直接回复客户端错误响应即可
            POP_LOGGER.error("The topic {} not exist, consumer: {} ", requestHeader.getTopic(), RemotingHelper.parseChannelRemoteAddr(channel));
            response.setCode(ResponseCode.TOPIC_NOT_EXIST);
            response.setRemark(String.format("topic[%s] not exist, apply first please! %s", requestHeader.getTopic(), FAQUrl.suggestTodo(FAQUrl.APPLY_TOPIC_URL)));
            return response;
        }

        //判断消息所属主题是否具备读权限，没有读权限则直接回复客户端错误响应
        if (!PermName.isReadable(topicConfig.getPerm())) {
            response.setCode(ResponseCode.NO_PERMISSION);
            response.setRemark("the topic[" + requestHeader.getTopic() + "] peeking message is forbidden");
            return response;
        }

        //判断要消费的主题队列是否超过主题配置的读队列数量，超过则回复客户端错误响应
        if (requestHeader.getQueueId() >= topicConfig.getReadQueueNums()) {
            String errorInfo = String.format("queueId[%d] is illegal, topic:[%s] topicConfig.readQueueNums:[%d] " +
                            "consumer:[%s]",
                    requestHeader.getQueueId(), requestHeader.getTopic(), topicConfig.getReadQueueNums(),
                    channel.remoteAddress());
            POP_LOGGER.warn(errorInfo);
            response.setCode(ResponseCode.SYSTEM_ERROR);
            response.setRemark(errorInfo);
            return response;
        }


        //暂不实现后续内容
    }



    @Override
    public boolean rejectRequest() {
        return false;
    }
}
```

```java
    private static final Logger POP_LOGGER = LoggerFactory.getLogger(LoggerName.ROCKETMQ_POP_LOGGER_NAME);

    private final BrokerController brokerController;

    public PopMessageProcessor(final BrokerController brokerController) {
        this.brokerController = brokerController;
    }

    @Override
    public RemotingCommand processRequest(ChannelHandlerContext ctx, RemotingCommand request) throws Exception {

        //省略之前执行的一系列校验操作



        //定义一个消息过滤器表达式对象，在获取消息的时候要判断消息的tag，只有tag一样，才能弹出该消息
        //这里我要多补充一句，在rocketmq中实际上还有一种过滤类型，那就是根据sql对消息进行过滤
        //但是在我们的代码中，我把这个sql过滤功能省略了，因为实现这个功能要引入的组件太多了，光是一个sql语法解析器就有非常多的内容了
        //所以我就给省略了，等后面实现h2关系型数据库的时候，再为大家实现sql语法解析器吧
        ExpressionMessageFilter messageFilter = null;
        
        //判断请求中是否设置了过滤表达式，如果设置了则意味着要对消息进行过滤
        if (requestHeader.getExp() != null && requestHeader.getExp().length() > 0) {
            try {
                //构建客户端订阅数据对象，该对象封装了消费者组名称、主题名称、过滤表达式和表达式类型
                //这里的操作很重要，在构建SubscriptionData对象的时候，给该对象的codeSet成员变量添加了数据
                //这个数据就是消息tag的哈希值，后续在过滤消息的时候就会用到它了
                SubscriptionData subscriptionData = FilterAPI.build(requestHeader.getTopic(), requestHeader.getExp(), requestHeader.getExpType());
               
                //以下这几行代码其实不必关注，因为下面就是判断过滤表达式是否为sql类型的，如果是sql类型的
                //就要构建sql类型的消息过滤器，在我们的代码中，并没有引入sql类型的过滤器，所以下面几行代码大家直接忽略即可
                //我引入进来只是为了让大家尽可能多了解一下完整的源码是什么样的
                ConsumerFilterData consumerFilterData = null;
                //判断过滤表达式类型是否为tag类型，如果不是则进入下面分支，这也就意味着过滤器类型为sql类型
                if (!ExpressionType.isTagType(subscriptionData.getExpressionType())) {
                    //构建消费者过滤数据
                    consumerFilterData = ConsumerFilterManager.build(
                            requestHeader.getTopic(), requestHeader.getConsumerGroup(), requestHeader.getExp(),
                            requestHeader.getExpType(), System.currentTimeMillis()
                    );
                    //构建失败则返回客户端错误响应
                    if (consumerFilterData == null) {
                        POP_LOGGER.warn("Parse the consumer's subscription[{}] failed, group: {}",
                                requestHeader.getExp(), requestHeader.getConsumerGroup());
                        response.setCode(ResponseCode.SUBSCRIPTION_PARSE_FAILED);
                        response.setRemark("parse the consumer's subscription failed");
                        return response;
                    }
                }

                //执行到这里意味着是tag过滤类型，直接构建tag类型的消息过滤器对象即可
                //在这里创建了真正的消息过滤器，从消费队列获取消息的时候就会用到这个消息过滤器了
                messageFilter = new ExpressionMessageFilter(subscriptionData, consumerFilterData, brokerController.getConsumerFilterManager());
            } catch (Exception e) {
                //有异常则回复客户端错误响应
                POP_LOGGER.warn("Parse the consumer's subscription[{}] error, group: {}", requestHeader.getExp(), requestHeader.getConsumerGroup());
                response.setCode(ResponseCode.SUBSCRIPTION_PARSE_FAILED);
                response.setRemark("parse the consumer's subscription failed");
                return response;
            }
        } else {
            try {
                //执行到这里意味着消费消息时并没有设置过滤表达式，也就是订阅了所有消息
                //并不会构建消息过滤器，这里的操作只是记录并存储了一些信息，内容很少，也很简单，我就不在文章中展示了
                
            } catch (Exception e) {
                POP_LOGGER.warn("Build default subscription error, group: {}", requestHeader.getConsumerGroup());
            }
        }


        //后续内容暂时不做实现
    }



    @Override
    public boolean rejectRequest() {
        return false;
    }
}
```

好了，既然要开始实现从消息存储器中获取消息的核心功能了，那接下来我们就一起来讨论一下该功能的实现细节，现在我们肯定已经知道了消费者客户端要获取的消息所属的主题，因为使用的是 Pop 消费模式，所以不需要关注目标消费队列的 Id，消费者客户端会在一个循环中遍历主题下的所有队列，直到获取到 32 条可消费的消息才会停止操作。既然是这样的话，那请大家想一想，如果多个客户端都来 Broker 节点获取同一主题下的消息，这也就意味着多个消费者客户端都会同时遍历主题下的所有队列，**如果严格按照队列 Id 的顺序来遍历，那么多个消费者客户端显然就会同时消费队列 Id 为 0 的消费队列中的消息，肯定就会争抢该队列的同步锁了**。为了防止这种情况出现，我们可以执行一个简单的优化操作，**那就是定义一个随机数，多个客户端遍历队列的时候可以随机开始遍历**，如果都从不同 Id 的队列中获取消息，那显然就不会争抢每个队列的同步锁了。这样分析下来，我想我们可以直接把这部分内容重构到 PopMessageProcessor 类的 processRequest() 方法中，就像下面代码块展示的这样，请看下面代码块。

## 引入 ConsumerOffsetManager  消费偏移量管理器


请大家想一想，现在我们已经可以从遍历到的消费队列中获取消息了，这也就意味着消费队列的 Id 明确了，消费队列所属的主题也明确了，那很好办，直接根据主题和队列 Id 找到对应的消费队列，然后从该队列中获取消息不就行了？核心逻辑就是这么简单，但是还是回到之前的问题，我们必须保证客户端在队列中消费的消息进度是最新的，这样才不会出现同一条消息被重复消费的问题，所以，这个时候就要先把消费偏移量管理器实现了，然后才能执行后续操作。**只有消费偏移量管理器先实现了，消费者到队列中获取消息时，就可以先从消费偏移量管理器中查询该队列最新的消费进度了**，这个逻辑很容易理解吧？



那这个消费管理器该怎么实现呢？其实实现思路分析起来很简单，**说白了它就是个管理器，只负责各个主题下消费队列消息进度的查询和更新**，这就是它最主要的工作，**我想把它定义为 ConsumerOffsetManager  类，然后再给它定义两个负责查询和更新队列消费进度的核心方法**，就像下面代码块展示的这样，请看下面代码块。

```java
package org.apache.rocketmq.broker.offset;


/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/10/22
 * @方法描述：消费偏移量管理器
 */
public class ConsumerOffsetManager extends ConfigManager {


    protected static final Logger LOG = LoggerFactory.getLogger(LoggerName.BROKER_LOGGER_NAME);
```

```java
    public static final String TOPIC_GROUP_SEPARATOR = "@";

    //各个主题下所有队列的消费偏移量就存储在这个map中
    //这里我要跟大家解释一下，ConcurrentMap<Integer, Long>中的value表示消费队列的最新消费偏移量
    //这个偏移量并不是记录的队列中消息的逻辑偏移量，而是逻辑偏移量/消息单元大小
    //比如说一个消费队列中存储了400 字节数据，而一个消息单元是20字节，那么这个队列中就存储了20条消息
    //现在被消费到了第8条消息，那么ConcurrentMap<Integer, Long>的value就会存储9这个数值，表示
    //下一次要从第九条消息开始消费，真正消费的时候，直接用9*20，就得到要消费的消息在消费队列中的
    //具体偏移量了，大家要理解这个逻辑
    protected ConcurrentMap<String/* topic@group */, ConcurrentMap<Integer, Long>> offsetTable = new ConcurrentHashMap<>(512);


    //省略该类其他内容
    

    //更新指定队列最新消费偏移量的方法
    public void commitOffset(final String clientHost, final String group, final String topic, final int queueId, final long offset) {
        String key = topic + TOPIC_GROUP_SEPARATOR + group;
        this.commitOffset(clientHost, key, queueId, offset);
    }


    //真正更新指定队列最新消费偏移量的方法
    private void commitOffset(final String clientHost, final String key, final int queueId, final long offset) {
        ConcurrentMap<Integer, Long> map = this.offsetTable.get(key);
        if (null == map) {
            map = new ConcurrentHashMap<>(32);
            map.put(queueId, offset);
            this.offsetTable.put(key, map);
        } else {
            Long storeOffset = map.put(queueId, offset);
            if (storeOffset != null && offset < storeOffset) {
                LOG.warn("[NOTIFYME]update consumer offset less than store. clientHost={}, key={}, queueId={}, requestOffset={}, storeOffset={}", clientHost, key, queueId, offset, storeOffset);
            }
        }
    }


    //查询指定主题消费队列的最新消费偏移量的方法
    public long queryOffset(final String group, final String topic, final int queueId) {
        String key = topic + TOPIC_GROUP_SEPARATOR + group;
        ConcurrentMap<Integer, Long> map = this.offsetTable.get(key);
        if (null != map) {
            Long offset = map.get(queueId);
            if (offset != null) {
                return offset;
            }
        }//执行到这里意味着队列没有被消费呢，返回—1
        //表示消费偏移量无效
        return -1L;
    }


    //省略该类其他内容

}
```
