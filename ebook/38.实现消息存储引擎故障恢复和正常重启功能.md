

## 实现 Broker 节点数据加载功能


这一章要讲解的内容也不多，确切地说，这一章要为大家分析的内容并不多，基本上都是很简单的内容，和过期文件删除功能一样，只要简单分析一下代码逻辑，然后直接展示代码即可。这倒不是因为我写文章写累了，不想再把每一个功能的实现思路都分析得特别详细，而是本章要实现的功能确实没什么可分析的。还有一点就是本章要展示的全部功能，其实在之前的版本代码中已经呈现给大家了，也许有的朋友已经结合代码注释都看完了，当然，肯定还有很多朋友没有从之前的版本代码中阅读过那些内容，这么关系，只要接下来跟着我的思路，也可以完全掌握本章讲解的所有内容。



在我们之前展示的版本代码中，大家肯定已经在各个组件中看见过 load() 方法了，比如说在 DefaultMessageStore 默认消息存储引擎中，大家肯定注意到了该类定义了一个 load() 方法，而在 CommitLog 类中，也定义了一个 load() 方法，除此之外，在 ConsumeQueueStore 消费队列管理器，以及 IndexService 类中都被定义了 load() 方法。在之前的代码版本中，我只是把这些方法展示出来了，并没有在文章中给大家讲解，原因我之前也解释过，因为 load() 方法就是在程序启动的过程中，加载本地数据到内存的方法，而我们最开始实现的是生产消息存储到本地文件中的功能，也就是说，在数据存储功能还没实现之前，根本没有数据可以从本地被加载到内存，那么 load() 方法自然也就无法真正实现，就算我强行实现了，把源码中的内容搬运到我们自己的版本代码中，那大家也不会理解这些内容究竟有什么作用。



但现在不同了，现在我们已经把 Broker 节点存储数据的功能实现完毕了，也构建好了本地的各个文件，数据也都可以存入到本地文件中了，那现在 Broker 节点启动的时候，自然就可以执行 load() 方法，把本地文件中的数据加载到内存中。**因为现在本地有三类重要的文件，分别是 CommitLog 文件夹中的文件、ConsumeQueueStore 消费队列管理器管理的消费队列的文件，以及 Index 文件夹中的所有文件，所以当 Broker 节点启动的时候，我们就可以执行 DefaultMessageStore 默认消息存储引擎的 load() 方法，然后在该方法中执行 CommitLog、ConsumeQueueStore、IndexService 这三个对象的 load() 方法，把各个组件的本地文件中的数据加载到内存中**。这个逻辑应该很顺畅吧？所以大家才会在 DefaultMessageStore 默认消息存储引擎中看到，在它内部的 load() 方法中又调用了 CommitLog、ConsumeQueueStore、IndexService 这三个对象的 load() 方法，就像下面代码块展示的这样，请看下面代码块。

从上面代码块中可以看到 DefaultMessageStore 消息存储引擎的 load() 方法的具体内容，当然，目前这个方法的内容跟我提供的第十六版本代码中的内容还不完全一样，我在文章中对它做了部分简化，后面还会继续重构。不管怎么说，只要程序在启动的时候，DefaultMessageStore 消息存储引擎的 load() 方法将就会被调用，那么本地文件中的数据就会被加载到内存中。现在大家关心的问题可能是 DefaultMessageStore 消息存储引擎的 load() 方法会在什么时候被调用，对吧？这个问题很简单，就是在 BrokerController 对象的 initialize() 方法中，调用逻辑非常简单，我就不在文章中展示具体内容了。我接下来想说的是，我关注的问题可能和大家关注的问题并不一样，我关注的是，**当 CommitLog、ConsumeQueueStore、IndexService 这三个对象要执行自己的 load() 方法时，究竟会执行什么操作呢**？



我刚才一直跟大家说，当程序内部各个组件执行 load() 方法时，会把各自本地文件中的数据加载到内存中，我这么说是因为这似乎是流行框架的通用逻辑，也可以称为常规逻辑，就比如说 sofajraft、nacos 在启动的时候，会从本地加载一些元信息到内存中。但是，在目前的消息队列框架中面临的是什么呢？是 CommitLog、ConsumeQueueStore、IndexService 这三类本地文件中的全部数据啊，如果执行 load() 方法之后就要把这三类本地文件中的所有数据都加载到内存中，那内存不就直接被挤爆了吗？所以，**当 CommitLog、ConsumeQueueStore、IndexService 执行它们的 load() 方法时，显然不能把本地文件的所有数据都加载到内存中**。大家一定要理解这一个逻辑，那既然不把本地数据加载到内存中，那么 load() 方法究竟会执行什么操作呢？这就需要从源码中寻找答案了。



实际上在 RocketMq 源码中是这么做的，当 CommitLog、ConsumeQueueStore、IndexService 执行了它们的 load() 方法之后，只不过是给本地文件在内存中创建了对应的内存映射文件对象，具体解释一下，**就比如说 CommitLog 文件夹下有 5 个本地文件存储了生产消息数据，那么在 CommitLog 对象了执行了它的 load() 方法之后，就会为这 5 个本地文件分别创建 DefaultMappedFile 内存映射文件对象，然后把这些 DefaultMappedFile 对象存放到集合成员变量中以便管理**。到此为止，CommitLog 对象 load() 方法执行的操作就结束了。注意，**整个 load() 方法所做的仅仅是为每一个本地文件创建了对应的 DefaultMappedFile 内存映射文件对象，只是实现了本地文件到虚拟内存的映射，并没有真的把本地文件的数据加载到内存中**，大家一定要记住这一点。那这样分析下来之后，大家就能在 CommitLog、ConsumeQueueStore、IndexService 这三个类中看到下面代码块中展示的 load() 方法，请看下面代码块。

```java
package org.apache.rocketmq.store;


/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
```
```java
 * @date:2025/6/29
 * @方法描述：内存映射文件管理器
 */
public class MappedFileQueue implements Swappable {


    private static final Logger log = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    private static final Logger LOG_ERROR = LoggerFactory.getLogger(LoggerName.STORE_ERROR_LOGGER_NAME);

    //CommitLog或ConsumeQueue文件的存储目录
    protected final String storePath;

    //单个内存映射文件的大小
    protected final int mappedFileSize;

    //存放所有内存映射文件都西昂的集合
    protected final CopyOnWriteArrayList<MappedFile> mappedFiles = new CopyOnWriteArrayList<>();

    //消息最后刷盘位置
    protected long flushedWhere = 0;

    //消息最新提交到操作系统缓存的位置
    protected long committedWhere = 0;

    //消息最后的存储时间
    protected volatile long storeTimestamp = 0;


    //省略该类其他内容

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：加载存储路径下的本地文件到内存映射队列中的方法
     */
    public boolean load() {
        //创建存储目录文件对象，文件路径就是：/store/commitlog
        File dir = new File(this.storePath);
        //获取文件夹下的所有文件
        File[] ls = dir.listFiles();
        if (ls != null) {
            //那文件加载到内存映射文件中
            return doLoad(Arrays.asList(ls));
        }
        return true;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：加载本地文件到内存映射队列的方法
     */
    public boolean doLoad(List<File> files) {
        //根据内存映射文件名称从小到大排序
        files.sort(Comparator.comparing(File::getName));
        //遍历所有内存映射文件
        for (int i = 0; i < files.size(); i++) {
            //得到文件本身
            File file = files.get(i);
            //如果当前文件是文件夹则跳过本次循环
            if (file.isDirectory()) {
                continue;
            }
            //这里就是判断当前遍历到的文件是不是文件队列的最后一个文件
            if (file.length() == 0 && i == files.size() - 1) {
                //如果是队列最后一个文件，并且是空文件，那就删除这个文件
                boolean ok = file.delete();
                //记录告警日志
                log.warn("{} size is 0, auto delete. is_ok: {}", file, ok);
                continue;
            }
            //校验文件大小是否等于用户配置的大小
            if (file.length() != this.mappedFileSize) {
                //不符合则记录告警日志
                log.warn(file + "\t" + file.length()
                        + " length not matched message store config value, please check it manually");
                //并且返回false，终止加载内存映射文件操作
                return false;
            }
            try {
                //在这里创建内存映射文件对象，创建对象的过程会执行初始化操作，完成内存映射操作
                MappedFile mappedFile = new DefaultMappedFile(file.getPath(), mappedFileSize);
                //设置内存映射文件的写入位置
                mappedFile.setWrotePosition(this.mappedFileSize);
                //设置刷盘位置
                mappedFile.setFlushedPosition(this.mappedFileSize);
                //设置消息已提交位置
                mappedFile.setCommittedPosition(this.mappedFileSize);
                //把文件加入内存映射队列，这里大家可能会困惑，为什么从本地加载的内存映射文件的消息写入位置，消息刷盘位置，消息提交位置
                //都设置成最满呢？如果本地最后一个文件没有写满数据，但是设置成最满了，那后续还怎么向该文件写入新数据呢？这不是浪费吗？
                //我知道大家肯定会有这个困惑，别急朋友们，请大家先记住这个问题，等后面
                //大家就知道究竟是怎么回事了，到时候功能就更加完善，大家的困惑也就消除了
                this.mappedFiles.add(mappedFile);
                log.info("load " + file.getPath() + " OK");
            } catch (IOException e) {
                log.error("load file " + file + " error", e);
                return false;
            }
        }
        return true;
    }


    //省略该类其他内容
}
```

上面代码块展示的内容非常简单，不管是对 CommitLog 文件夹中本地文件执行 load() 操作，还是对 ConsumeQueueStore 消费队列管理器管理的各个消费队列的本地文件执行 load() 操作，最终只不过是为每一个本地文件创建了对应的 DefaultMappedFile 内存映射文件对象，这一点从上面的代码块中已经被印证了。而这也正和我们之前说的一样：**在 RocketMq 源码中，每个组件的 load() 方法所做的仅仅是为每一个本地文件创建了对应的 DefaultMappedFile 内存映射文件对象，只是实现了本地文件到虚拟内存的映射，并没有真的把本地文件的数据加载到内存中**。阅读了上面的代码之后，现在大家应该理解了这些内容了吧？



当然，在阅读了上面的代码块之后，现在大家肯定更加困惑，这么做有什么意义呢？就算为各个组件的本地文件创建了对应的 DefaultMappedFile 内存映射文件也没用啊？因为从一开始，我们创建 DefaultMappedFile 内存映射文件对象的初衷就是为了更方便、快速的处理数据，能快速持久化数据和读取数据，但现在我们仅仅是为本地文件创建了对应的内存映射文件对象，建立了内存映射关系而已，本地文件中的数据并没有真的被加载到内存中，并没有被真的加载到 pagecache 中；我们的想法肯定是把本地文件的数据加载到 pagecache 中，这样一来，当消费者客户端来消费消息时，就可以直接从 pagecache 中获取数据，可以提高消费效率。但我们并没有这么做，那忙了一场好像根本没什么用啊。而且，上面代码块中还有一个非常令人困惑的地方，**那就是在为每一个本地文件创建了 DefaultMappedFile 内存映射文件对象之后，直接就把这个 DefaultMappedFile 内存映射文件被设置为写满状态了，这一点从上面代码块的 91～96 行能体现出来**。这么做似乎很没道理，如果一个本地文件已经写满数据了，那确实可以直接把于它对应的 DefaultMappedFile 对象设置为满状态，但如果这个本地文件是最新的，比如说是 CommitLog 文件夹中最新的本地文件，并且这个本地文件还没写满数据，那把与它对应的 DefaultMappedFile 对象设置为满状态，这显然就有点荒漠了，以后还怎么往这个本地文件中写入数据呢？我相信这也是令大家感到困惑的问题之一。那这究竟是怎么回事呢？别着急，这个时候，就该轮到数据恢复功能登场了。



## 实现 Broker 节点数据恢复功能


请大家再次思考一下，当一个已经运行了一段时间的 Broker 节点重新启动了，这个时候这个 Broker 节点应该执行什么操作呢？也就是说，这个 Broker 节点已经持久化了一批数据了，那这个时候，我认为 Broker 节点在启动的过程中，**肯定要把持久化的这批数据使用内存映射机制加载到内存中，也就是加载到 pagecache 中**，原因很简单，在这批被持久化的数据中，也许有些数据还没有被消费者客户端消费呢，所以要加载到内存中等待被消费。但与此同时，我还认为不应该把本地所有的数据都加载到内存中，因为很多数据可能已经被客户端消费了，只是在等待被过期删除了而已。就比如说 CommtiLog 文件夹下有 10 个本地文件，可能前八个本地文件存储的数据都已经被消费完毕了，只剩下后两个文件的数据待消费，那这个时候只需要把后两个本地文件的数据加载到内存即可，这一点大家可以理解吧？既然是这样，那我索性就对 Broker 节点加载本地文件到内存的功能设置一个阈值，那就是当 Broker 节点重新启动时，如果发现本地存在各个组件的本地文件，**那么就只会把各个组件最后三个本地文件加载到内存中，也就是说，默认认为这三个本地文件存储的数据是比较新的，只把较新的数据加载到内存中即可**，比如说对于 CommitLog 文件夹中的本地文件，只会把最后三个文件加载到内存中，而消费队列文件也是一样。我把这个操作称为 Broker 节点的数据恢复，当然，仅仅是这么做还不够，原因很简单，Broker 节点一旦启动之后除了可以让消费者客户端到自己内部消费消息，还需要接收生产者客户端发送过来的新消息。



既然 Broker 节点还需要接收生产者客户端发送过来的新消息，这也就意味着有新的数据要被写入到 CommitLog 文件夹本地文件中最新的文件中，也就意味着要写入到与其对应的 DefaultMappedFile 内存映射文件对象中，既然是这样，那当写入新消息的时候，肯定得知道要写入的位置吧？**也就是要知道写入的 CommitLog 全局文件的偏移量，还有刷新数据的位置，或者是提交数据的位置等等信息，这些信息必须和之前 Broker 服务停机时的位置信息是连续的**，就比如说 Broker 节点停机之前，CommitLog 文件缓冲区的写入偏移量为 300 字节，那么重新启动之后，要写入新消息的时候，也要从 300 偏移量之后开始写入，以此保证数据的连续性。 那怎么就能在 Broker 节点重新启动的过程中知道这些位置信息呢？方法很简单，毫无技巧可言，**那就是在把本地最新三个文件加载到内存的过程中，对每次读取到的数据进行累加，最终得到最终的数据信息**。因为在 CommitLog 本地文件中，文件名称代表了该文件存储数据的起始全局偏移量，那么根据最新三个本地文件的名称以及最后一个文件存储的数据容量，就能得到 CommitLog 本地文件存储的最后一条消息的全局偏移量，假如说这个全局偏移量是 1000 字节，那这个时候就可以把 CommitLog 内存映射文件写入最新数据的全局偏移量、刷新数据的偏移量、提交数据的偏移量都设置为 1000，接下来写入新消息的时候，就可以从这个偏移量之后开始写入。这个逻辑理解起来也不难吧？整个这部分功能都可以称为 Broker 节点数据恢复功能。



我把数据恢复功能定义为了一个方法，也就是 recover() 方法，在 CommitLog 和 ConsumeQueue 消费队列中，大家都可以看到这个方法。接下来我就为大家具体展示一下各个组件的 recover() 方法。当然，在具体展示之前，我还要再补充一点，那就是我想先为大家展示 ConsumeQueue 消费队列的数据恢复方法，我这么做的原因很简单，我们都知道，消费队列是由消费队列管理器管理的，当我们要执行数据恢复操作时，肯定也是通过消费队列管理器来执行的，当消费队列管理器执行了它的数据恢复方法后，就会在方法内部执行它管理的每一个消费队列的 recover() 方法，执行完毕之后，每一个消费队列存储的最新数据的偏移量也就可以确定的，而知道了它存储的最新数据，也就是最新重放消息的偏移量，根据重放消息封装的消息全局偏移量，肯定就能得到消费队列存储的全局消息的最大偏移量。这一点可以理解吧？



而我们都很清楚，不管消费队列管理器管理了多少消费队列，消费队列存储的又都是什么主题的重放消息，这些重放消息在各个消费队列中都是按照顺序存储的，越晚存储的重放消息，它封装的消息全局偏移量肯定就越大，假如现在有 4 个消费队列，这 4 个消费队列存储了很多重放消息，对于这 4 个消费队列来说，它们存储的最新的重放消息封装的消息全局偏移量分别为 100、500、1000、400，那这是不是就意味着第三个消费队列存储的最新重放消息封装的消息全局偏移量是最大的？那这是不是也就意味着根据消费队列存储的所有重放消息来看，存储在 CommitLog 文件中的消息的全局偏移量最大应该为 1000？这个逻辑可以理解吧？既然是这样，**那么当后面恢复 CommitLog 文件中的数据时，就可以使用这个从消费队列中得到的最大全局消息偏移量去 CommitLog 文件中做对比，如果最后恢复完 CommitLog 文件的所有数据，发现 CommitLog 文件存储的消息的最大全局偏移量是 900，那这个时候就要执行一个操作，那就是要再回到消费队列中，把消费对类中封装了消息全局偏移量大于 900 的重放消息全部截掉，以保证数据和 CommitLog 文件的一致性**。这个是 RocketMq 源码中的操作，由此也可以看到，在执行数据恢复的时候，一切都应该以 CommitLog 文件中的数据为准，毕竟其他文件中的数据都是由 CommitLog 文件的数据构建而来的。



好了，说了这么多，接下来还是给大家先展示消费队列的 recover() 方法把，因为消费队列会被消费队列管理器管理，各个消费队列数据恢复操作的入口其实在消费队列管理器中，所以我先为大家展示消费队列管理器，也就是 ConsumeQueueStore 类的 recover() 方法，请看下面代码块。

```java
package org.apache.rocketmq.store;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @方法描述：消费队列文件对象
 */
public class ConsumeQueue implements ConsumeQueueInterface, FileQueueLifeCycle {


    //省略该类其他内容

    //内存映射文件队列
    private final MappedFileQueue mappedFileQueue;

    //消费队列映射文件中的最大消息偏移量，注意，这个偏移量并不是重放消息的最大偏移量
    //而是最新的重放消息封装的消息全局偏移量
    private long maxPhysicOffset = -1;
    
    
    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：加载消费队列内存映射文件的方法
     */
    @Override
    public boolean load() {
        //在这里加载消费队列内存映射文件
        boolean result = this.mappedFileQueue.load();
        log.info("load consume queue " + this.topic + "-" + this.queueId + " " + (result ? "OK" : "Failed"));
        return result;
    }





    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：消费队列冲新回复的方法
     */
    @Override
    public void recover() {
        //得到映射文件队列中的所有映射文件
        final List<MappedFile> mappedFiles = this.mappedFileQueue.getMappedFiles();
        //判断映射文件集合是否不为空
        if (!mappedFiles.isEmpty()) {
            //不为空则计算开始恢复数据的文件索引，默认从倒数第三个文件开始恢复数据
            //也就是从倒数第三个文件开始向后遍历，根据后三个文件存储的数据恢复消费队列本身的相关数据信息
            //这样设计是为了提高恢复效率，因为最新的几个文件更可能包含有效数据
            int index = mappedFiles.size() - 3;
            //如果内存映射文件总数小于3，则从第一个文件开始恢复
            if (index < 0) {
                //所以这里把开始恢复的索引设置为0
                index = 0;
            }
            //得到单个内存映射文件的最大容量
            int mappedFileSizeLogics = this.mappedFileSize;
            //根据索引得到开始恢复数据的内存映射文件
            MappedFile mappedFile = mappedFiles.get(index);
            //得到内存映射文件的读视图，用来读取数据
            ByteBuffer byteBuffer = mappedFile.sliceByteBuffer();
            //得到刚才获得的内存映射文件的起始偏移量，这个就是当前消息队列已处理的数据的偏移量
            long processOffset = mappedFile.getFileFromOffset();
            //初始化映射文件内的当前偏移量为0
            long mappedFileOffset = 0;
            //在循环中恢复消费队列数据
            while (true) {
                //以存储单元为步长，遍历映射文件内的所有消息条目
                for (int i = 0; i < mappedFileSizeLogics; i += CQ_STORE_UNIT_SIZE) {
                    //得到当前读取的消息的CommitLog文件全局偏移量
                    long offset = byteBuffer.getLong();
                    //得到当前消息的大小
                    int size = byteBuffer.getInt();
                    //得到该消息的哈希值
                    long tagsCode = byteBuffer.getLong();
                    //判断读取到的消息是否有效
                    if (offset >= 0 && size > 0) {
                        //如果有效则移动到下一个消息条目的起始位置
                        mappedFileOffset = i + CQ_STORE_UNIT_SIZE;
                        //在这里更新当前消费队列的最大物理偏移量
                        //也就是当前读取到的消息的CommitLog文件全局偏移量加上消息的大小
                        //注意，随着不断循环，当前消费队列的maxPhysicOffset会不断增加，直到没有数据位置
                        this.setMaxPhysicOffset(offset + size);
                    } else {
                        //如果读取到的消息是无效的，则记录日志信息，退出当前循环
                        //这里之所以会有这个分支，是因为在程序启动的过程中会执行load方法，在该方法中会创建和本地文件对应的内存映射文件
                        //并且把内存映射文件默认设置为写满消息的状态，这样一来在后续恢复数据的时候，如果内存映射文件真的有数据，那就读取数据即可
                        //如果没有数据，读取到的就是0，也就是无效数据，这个时候就说明这个内存映射文件读取完了，可以退出循环了
                        log.info("recover current consume queue file over,  " + mappedFile.getFileName() + " "
                                + offset + " " + size + " " + tagsCode);
                        break;
                    }
                }
                //判断当前遍历的内存映射文件是否读取完毕了
                if (mappedFileOffset == mappedFileSizeLogics) {
                    //读取完毕则增加索引，开始读取下一个文件进行数据恢复操作
                    index++;
                    //判断是否是读取完了最后一个内存映射文件，文件最大索引肯定要比文件数量少1，所以这里一旦等于就意味着最后一个文件读取完了
                    if (index >= mappedFiles.size()) {
                        //记录恢复操作执行完毕的日志信息
                        log.info("recover last consume queue file over, last mapped file " + mappedFile.getFileName());
                        //退出while循环
                        break;
                    } else {
                        //如果还有文件需要处理，则获取下一个内存映射文件
                        mappedFile = mappedFiles.get(index);
                        //得到内存映射文件的读视图，用来读取数据
                        byteBuffer = mappedFile.sliceByteBuffer();
                        //更新要处理的偏移量为新文件的起始偏移量
                        processOffset = mappedFile.getFileFromOffset();
                        //重置文件内偏移量为0，准备从文件头开始处理
                        mappedFileOffset = 0;
                        //记录开始处理下一个文件的日志信息
                        log.info("recover next consume queue file, " + mappedFile.getFileName());
                    }
                } else {
                    //如果文件未处理完但遇到了无效数据，说明已到达文件的有效数据末尾
                    //记录当前恢复位置的日志信息
                    log.info("recover current consume queue over " + mappedFile.getFileName() + " " + (processOffset + mappedFileOffset));
                    break;
                }
            }
            //得到当前消费队列最终处理到的数据的偏移量，mappedFileOffset是读取到当前文件中的实际数据的偏移量
            //二者相加就是消费队列最终拥有的数据的实际最大偏移量
            processOffset += mappedFileOffset;
            //使用消费队列最终拥有的数据的实际最大偏移量更新映射文件队列的刷盘位置
            this.mappedFileQueue.setFlushedWhere(processOffset);
            //使用消费队列最终拥有的数据的实际最大偏移量更新映射文件队列的提交位置
            this.mappedFileQueue.setCommittedWhere(processOffset);
            //截断脏数据，也就是删除消费队列中processOffset之后的所有数据，因为这些数据可能是不完整或损坏的，确保消费队列数据的一致性和完整性
            this.mappedFileQueue.truncateDirtyFiles(processOffset);
        }
    }



    @Override
    public long getMaxPhysicOffset() {
        return maxPhysicOffset;
    }


    public void setMaxPhysicOffset(long maxPhysicOffset) {
        this.maxPhysicOffset = maxPhysicOffset;
    }

}
```

从 ConsumeQueue 对象的 recover() 方法中确实可以看到，正如我们之前分析的那样，**在恢复数据的过程中，执行的操作就是把消费队列本地最新三个文件的数据读取到内存中，然后累计数据的大小，也就是重放消息的大小，最终得到存储的重放消息的最大偏移量，然后再给消费队列的数据刷新偏移量、数据提交偏移量赋值**。这个逻辑应该很清楚了吧？当然，在这个过程中还得到了最新重放消息封装的消息全局偏移量，得到这个全局消息偏移量很有意义，因为等多个消费队列都执行完毕数据恢复操作后，就可以对比各个消费队列的 maxPhysicOffset 成员变量，然后就能得到消费队列存储的最新的重放消息，对应的消息全局偏移量是多少了，这样一来，**也就得到了 CommitLog 文件中应该存储的消息的最大全局偏移量**。大家可以仔细品味品味这个逻辑，也许还有一个问题我应该再补充一下，因为看到这里，大家可能会觉得很奇怪，明明已经得到了消费队列存储的最新重放消息的偏移量，怎么没有把这个偏移量设置给消费队列呢？这样一来，再写入新的消息时，就知道应该从哪个位置开始写入消息了，对吧？



实际上是有这个操作的，上面代码块的第 135 行执行了 this.mappedFileQueue.truncateDirtyFiles(processOffset) 这样一行代码，也就是根据消费队列存储的最新重放消息的全局偏移量去截断内部后续的脏数据，这里我想给大家解释一下，为什么要这么操作一下。大家应该还记得在执行 load() 方法的时候，给本地最新文件创建的内存映射文件对象直接设置为写满状态了，而我们都知道，本地最新文件可能并没有写满数据，因此在执行了数据恢复操作之后，就要在 ecover() 方法结尾执行 truncateDirtyFiles() 方法，把所谓的脏数据都截断，而在这个过程中，就会把消费队列存储的最新重放消息的偏移量给更新了，也就是把消费队列最新本地文件的数据偏移量给更新了，接下来，就让我为大家展示一下 MappedFileQueue 对象的 truncateDirtyFiles() 方法，请看下面代码块。

```java
     * @方法描述：截断内存映射文件脏数据的方法
     */
    public void truncateDirtyFiles(long offset) {
        //创建一个列表，用于存储需要被删除的映射文件
        //这些文件的数据通常是完全在最大有效偏移量之后，被认为包含无效数据，所以应该被删除
        //而最大有效偏移量就是方法参数传进来的offset
        List<MappedFile> willRemoveFiles = new ArrayList<>();
        //遍历当前所有的映射文件
        for (MappedFile file : this.mappedFiles) {
            //计算当前遍历的文件的尾部偏移量
            long fileTailOffset = file.getFileFromOffset() + this.mappedFileSize;
            //判断文件尾部偏移量是否超过了有效数据的截止偏移量
            //如果超过，说明文件中可能包含脏数据需要处理
            if (fileTailOffset > offset) {
                //判断有效数据的截止偏移量是否在当前文件范围内
                //如果在文件范围内，说明文件的一部分是有效的，一部分是脏数据
                if (offset >= file.getFileFromOffset()) {
                    //如果在当前文件中，那就计算文件内的有效写入位置，先计算offset % this.mappedFileSize这个，也就是有效最大偏移量在当前文件中的相对偏移量
                    //因为已经确定有效偏移量在当前文件中了，所以可以直接取模
                    //设置当前文件的写入位置，表示文件中只有这个位置之前的数据是有效的，这样一来，之后写入数据，就可以直接从这个位置往后写
                    //覆盖脏数据了
                    file.setWrotePosition((int) (offset % this.mappedFileSize));
                    //同时更新提交位置和刷盘位置，保证数据一致性
                    file.setCommittedPosition((int) (offset % this.mappedFileSize));
                    file.setFlushedPosition((int) (offset % this.mappedFileSize));
                }
                else { //如果有效数据的截止偏移量小于文件的起始偏移量，说明整个文件都是无效的，需要被删除
                    //销毁物理文件，设置等待时间为1秒
                    file.destroy(1000);
                    //将要删除的内存映射文件添加到待删除列表中
                    willRemoveFiles.add(file);
                }
            }
        }
        //执行删除内存映射文件操作
        this.deleteExpiredFile(willRemoveFiles);
    }

}
```

接下来就是 CommitLog 类的数据恢复方法，当然，从上面代码块中可以看到，当执行 CommitLog 对象的数据恢复方法时，把数据恢复分为了两种情况，一种是服务器正常停机，正常启动的情况，也就是正常恢复数据的情况；另一种就是服务器故障重启的情况，我在文章中只给大家展示正常恢复数据的代码，并不会展示故障重启的代码，因为故障重启的数据恢复功能和正常重启数据恢复功能没什么本质区别，**在故障重启情况下，会默认 CommtiLog 本地文件中存储的数据是残缺的、不完整的，执行数据恢复的时候不能只恢复最新三个本地文件的数据，而是会从后往前，对 CommitLog 文件夹中的本地文件进行遍历查询，直到找到第一个内容连续完整，可以作为数据恢复起始文件的本地文件，然后从该文件开始进行数据恢复，而且在这个工程中还有一个非常重要的操作，那就是每从 CommitLog 文件中恢复了一条消息，就要把这条消息在消费队列文件和 Index 文件中的重放消息也重新构建出来，以保证在 Broker 节点异常恢复情况下，消费队列数据和 Index 文件数据和 CommitLog 文件数据的绝对一致性**。大家只需要记住这个逻辑即可，其他的就没什么可分析的了，大家直接去第十六版本代码中阅读即可，好了，请看下面代码块。

```java
     * @方法描述：正常退出程序，重启程序之后恢复CommitLog数据的方法，在正常恢复数据方法中认为每一个文件的结构是完整的，数据也是连续的，所以直接从倒数第三个文件开始恢复即可
     */
    public void recoverNormally(long maxPhyOffsetOfConsumeQueue) throws RocksDBException {
        //判断是否启用了恢复数据时的CRC校验功能
        boolean checkCRCOnRecover = this.defaultMessageStore.getMessageStoreConfig().isCheckCRCOnRecover();
        //判断是否启用了消息去重功能
        boolean checkDupInfo = this.defaultMessageStore.getMessageStoreConfig().isDuplicationEnable();
        //得到当前CommitLog文件所有的内存映射文件
        final List<MappedFile> mappedFiles = this.mappedFileQueue.getMappedFiles();
        //判断映射文件集合是否不为空
        if (!mappedFiles.isEmpty()) {
            //不为空则计算开始恢复数据的文件索引，默认从倒数第三个文件开始恢复数据
            //也就是从倒数第三个文件开始向后遍历，根据后三个文件存储的数据恢复消费队列本身的相关数据信息
            //这样设计是为了提高恢复效率，因为最新的几个文件更可能包含有效数据
            int index = mappedFiles.size() - 3;
            //如果内存映射文件总数小于3，则从第一个文件开始恢复
            if (index < 0) {
                index = 0;
            }
            //根据索引得到内存映射文件
            MappedFile mappedFile = mappedFiles.get(index);
            //得到内存映射文件视，用来读取数据图
            ByteBuffer byteBuffer = mappedFile.sliceByteBuffer();
            //得到当前得到的内存映射文件的起始偏移量，这个局部变量记录的其实就是当前消息队列已处理的数据的偏移量
            long processOffset = mappedFile.getFileFromOffset();
            //初始化映射文件内的当前偏移量为0
            long mappedFileOffset = 0;
            //得到当前内存映射文件已确认消息的最大偏移量，这里得到的其实是当前文件的总容量
            //因为程序启动执行load方法的过程中，会把所有内存映射文件默认设置成满状态
            //后面只要根据恢复后的数据截断脏数据即可
            long lastValidMsgPhyOffset = this.getConfirmOffset();
            //消息分发标志设置为false，因为消费队列中已经有消息了，现在只是恢复CommitLog文件数据，所以没必要执行消息分发操作
            boolean doDispatch = false;
            //在循环中恢复CommitLog数据
            while (true) {
                //在这里得到当前文件存储的消息的重放请求对象，注意，这里得到消息重放请求对象不是真的要重放消息，而是要获取消息的关键信息，比如消息总长度
                DispatchRequest dispatchRequest = this.checkMessageAndReturnSize(byteBuffer, checkCRCOnRecover, checkDupInfo);
                //得到当前解析出来的消息的长度
                int size = dispatchRequest.getMsgSize();
                //判断消息是否真的解析成功
                if (dispatchRequest.isSuccess() && size > 0) {
                    //解析成功则更新CommitLog文件最大有效的消息全局偏移量
                    //如果解析的是第一条消息，那么这个值就会被更新为mappedFile.getFileFromOffset() + 0,因为第一条消息在当前文件中的偏移量为0
                    lastValidMsgPhyOffset = processOffset + mappedFileOffset;
                    //更新当前文件处理的偏移量，也就是读取到当前文件哪一部分了
                    mappedFileOffset += size;
                    //这里就是消息重放的操作，但并不会真的执行，因为doDispatch是false
                    //如果是异常数据恢复，那么就会在这里执行消息重放操作
                    this.getMessageStore().onCommitLogDispatch(dispatchRequest, doDispatch, mappedFile, true, false);
                }
                else if (dispatchRequest.isSuccess() && size == 0) {
                    //如果消息解析成功，但是消息长度是0，就意味着已经读取到文件末尾了，这个时候就应该切换下一个内存映射文件，读取下一个文件的数据，继续恢复CommitLog相关信息
                    this.getMessageStore().onCommitLogDispatch(dispatchRequest, doDispatch, mappedFile, true, true);
                    //增加索引，准备读取下一个文件的数据
                    index++;
                    //判断是否是读取完了最后一个内存映射文件，文件最大索引肯定要比文件数量少1，所以这里一旦等于就意味着最后一个文件读取完了
                    if (index >= mappedFiles.size()) {
                        //记录恢复操作执行完毕的日志信息
                        log.info("recover last 3 physics file over, last mapped file " + mappedFile.getFileName());
                        break;
                    }  else {
                        //如果还有文件需要处理，则获取下一个内存映射文件
                        mappedFile = mappedFiles.get(index);
                        //得到内存映射文件的读视图，用来读取数据
                        byteBuffer = mappedFile.sliceByteBuffer();
                        //更新要处理的偏移量为新文件的起始偏移量
                        processOffset = mappedFile.getFileFromOffset();
                        //重置文件内偏移量为0，准备从文件头开始处理
                        mappedFileOffset = 0;
                        //记录开始处理下一个文件的日志信息
                        log.info("recover next physics file, " + mappedFile.getFileName());
                    }
                }
                else if (!dispatchRequest.isSuccess()) {
                    //执行到这里意味着消息没有解析成功
                    if (size > 0) {
                        //size>0表示存在不完整的消息数据，该数据将被截断，这里记录错误日志信息
                        log.warn("found a half message at {}, it will be truncated.", processOffset + mappedFileOffset);
                    }
                    //记录当前文件恢复结束日志信息
                    log.info("recover physics file end, " + mappedFile.getFileName());
                    break;
                }
            }


            
            //执行到这里意味着文件恢复完毕了
            //得到当前消费队列最终处理到的数据的偏移量，mappedFileOffset是读取到当前文件中的实际数据的偏移量
            //二者相加就是CommitLog最终拥有的数据的实际最大偏移量
            processOffset += mappedFileOffset;
            //控制器模式下的代码暂时忽略
            if (this.defaultMessageStore.getBrokerConfig().isEnableControllerMode()) {
                // if (this.defaultMessageStore.getConfirmOffset() < this.defaultMessageStore.getMinPhyOffset()) {
                //     log.error("confirmOffset {} is less than minPhyOffset {}, correct confirmOffset to minPhyOffset", this.defaultMessageStore.getConfirmOffset(), this.defaultMessageStore.getMinPhyOffset());
                //     this.defaultMessageStore.setConfirmOffset(this.defaultMessageStore.getMinPhyOffset());
                // }
                // else if (this.defaultMessageStore.getConfirmOffset() > processOffset) {
                //     log.error("confirmOffset {} is larger than processOffset {}, correct confirmOffset to processOffset", this.defaultMessageStore.getConfirmOffset(), processOffset);
                //     this.defaultMessageStore.setConfirmOffset(processOffset);
                // }
            }
            else {//在这里更新数据恢复完毕之后的CommitLog文件最大有效的消息全局偏移量
                this.setConfirmOffset(lastValidMsgPhyOffset);
            }



            
            //maxPhyOffsetOfConsumeQueue这个可是从消费队列中传过来的参数，代表消费队列存储的消息的最大全局偏移量
            //现在CommitLog数据恢复了，CommitLog文件中存储的最大数据偏移量肯定是有效数据，如果消费中存储的消息全局偏移量超过了CommitLog文件的最大偏移量
            //就意味着消费队列中多余出来的数据是脏数据，需要截断，一切应该以CommitLog文件的内容为准则
            if (maxPhyOffsetOfConsumeQueue >= processOffset) {
                log.warn("maxPhyOffsetOfConsumeQueue({}) >= processOffset({}), truncate dirty logic files", maxPhyOffsetOfConsumeQueue, processOffset);
                 //执行消费队列脏数据截断操作
                this.defaultMessageStore.truncateDirtyLogicFiles(processOffset);
            }
            //使用最后得到的CommitLog最终拥有的数据的实际最大偏移量更新映射文件队列的刷盘位置
            this.mappedFileQueue.setFlushedWhere(processOffset);
            //使用最后得到的CommitLog最终拥有数据的实际最大偏移量更新映射文件队列的提交位置
            this.mappedFileQueue.setCommittedWhere(processOffset);
            //截断文件脏数据
            this.mappedFileQueue.truncateDirtyFiles(processOffset);
        } else {
            //执行到这里意味着文件集合为空，这时候记录CommitLog文件被删除告警日志
            log.warn("The commitlog files are deleted, and delete the consume queue files");
            this.mappedFileQueue.setFlushedWhere(0);
            this.mappedFileQueue.setCommittedWhere(0);
            //销毁现有消费队列存储器
            this.defaultMessageStore.getQueueStore().destroy();
            //重新初始化消费队列存储器
            this.defaultMessageStore.getQueueStore().loadAfterDestroy();
        }
    }

}
```
