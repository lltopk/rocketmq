事务这个基本概念，我相信不用我再给大家解释了吧？在我的理解中，有两个操作，操作一和操作二，这两个操作彼此独立但是又有无法分割的联系，这个时候我们就可以称这两个操作存在事务关系，只有两个操作都同时成功了，那么我们就可以认为事务操作成功了。就比如说现在有两个服务，一个是订单服务，一个是库存服务。用户先下了一个订单，订单服务执行了对应的操作，接下来就应该根据订单信息去库存服务中执行扣减库存的操作。只有当这两个操作都成功了，那么整个下订单，扣库存的程序才算执行完毕。如果仅仅是下单成功，但是库存扣减失败了，那程序运行显然就出现问题。我们接下来要实现的功能，就是防止这种情况出现。



那这个事务和 RocketMq 框架有什么关系呢？要说关系其实也没那么大，在我看来，事务消息并不是 RocketMq 框架的核心功能，因为除了这个框架，还有很多其他的方式可以为事务操作提供完善的保障。只不过 RocketMq 框架提供了完美的消息队列机制，因此也可以用来实现事务消息功能。好了，说了这么多，那么在 RocketMq 框架中，这个事务功能究竟该怎么实现呢？梳理清楚这一点非常重要，我想大家多少都有一些工作经验，知道事务操作成功的前提是事务内的所有操作都要执行成功，那还是回到刚才举得例子上，**当用户下订单之后，就要执行扣减库存操作，为了让这两个操作都成功。那这个时候就可以在用户下订单之后向 RocketMq 框架发送一条订单消息，这个时候订单服务就是消息生产者；当然，这条订单消息对消费者客户端，也就是库存服务是不可见的，等到消息生产者本地的事务操作执行完毕了，比如说订单信息已经持久化到数据库中了，这个时候 Broker 节点中的事务消息就变成可见的了，然后库存服务就可以消费这条消息，执行对应的扣减库存的操作**。从这个过程中大家可以看到，只有当订单服务的操作执行成功之后，库存服务才能开始执行，这也就在一定程度上保证了两个服务都成功执行的概率。等库存服务执行完毕了，那么订单，扣减库存的事务操作也就成功结束了。这个逻辑大家应该可以理解吧？



这个时候我已经想到了，大家肯定有一个问题，那就是假如订单服务执行成功了，发送到 Broker 节点中的消息也对库存服务可见了，但是库存服务根据订单消息扣减库存的操作却执行失败了，这样一来，事务操作不也没有成功吗？那这个时候该怎么办呢？我必须要提前对这一点做解释说明：实际上 RocketMq 框架的事务功能并不能完美解决这个问题，RocketMq 框架本身提供了消息重试功能，当消息消费失败的时候可以多次重试，重新消费，也许多次重试，总有一次可以执行成功。但多次重试都没有执行成功，那这时候就没办法了，只能人为来解决，可能是程序出现并发问题了，导致库存没有了，无法扣减成功。这时候就要具体问题具体分析了，大家清楚这一点就行。



好了，现在大家应该清楚了 RocketMq 事务消息功能的实现原理，**其实就是暂时隐藏生产者发送的事务消息，等到生产者操作执行成功了，再放开这条消息，让消费者能消费这条事务消息**。那这个功能我们其实已经实现过了，非常简单，我们完全可以仿照任意级别的延迟消息，在系统内部再定义一个事务消息主题，生产者如果发送的是事务消息，那么当 Broker 节点接收到事务消息之后，就可以更改这个消息的主题信息，把消息投递到事务消息主题队列中；等到生产者客户端的事务操作执行成功了，那就可以向 Broker 节点发送一个事务消息提交请求，Broker 节点接收到这个请求之后，就可以从事务主题队列中找到对应的消息信息，然后更改消息主题信息为原始主题，最后重新投递这条消息到原始主题队列中即可。这个时候，消费者客户端就可以消费这条消息了。大家可以品味一下这个逻辑，如果大家理解这个逻辑了，那接下来我就先为大家展示生产者客户端向 Broker 节点发送事务消息的代码，请看下面代码块。

```java
package org.apache.rocketmq.client.java.impl.producer;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/11/9
 * @方法描述：事务消息实现类
 */
class TransactionImpl implements Transaction {

    //生产者客户端
    private final ProducerImpl producerImpl;

    //存放生产的事务消息的集合
    private final Set<PublishingMessageImpl> messages;

    //存放待提交或者回滚的消息的Map，这里的PublishingMessageImpl对象和messages成员变量中的是同一个对象
    private final ConcurrentMap<PublishingMessageImpl, SendReceiptImpl> messageSendReceiptMap;

    //构造方法我就省略了


    //存储事务消息的方法
    public PublishingMessageImpl tryAddMessage(Message message) throws IOException {
        final PublishingMessageImpl publishingMessage = new PublishingMessageImpl(message, producerImpl.producerSettings, true);
        messages.add(publishingMessage);
        return publishingMessage;
    }

    //存储事务消息和发送回执映射关系的方法
    public void tryAddReceipt(PublishingMessageImpl publishingMessage, SendReceiptImpl sendReceipt) {
        messageSendReceiptMap.put(publishingMessage, sendReceipt);
    }

    //提交事务消息的方法
    @Override
    public void commit() throws ClientException {
        if (messageSendReceiptMap.isEmpty()) {
            throw new IllegalStateException("Transactional message has not been sent yet");
        }
        for (Map.Entry<PublishingMessageImpl, SendReceiptImpl> entry : messageSendReceiptMap.entrySet()) {
            final PublishingMessageImpl publishingMessage = entry.getKey();
            final SendReceiptImpl sendReceipt = entry.getValue();
            //根据消息发送回执结束事务关系
            producerImpl.endTransaction(sendReceipt.getEndpoints(), publishingMessage.getMessageCommon(),
                    sendReceipt.getMessageId(), sendReceipt.getTransactionId(), TransactionResolution.COMMIT);
        }
    }

    //回滚事务消息的方法
    @Override
    public void rollback() throws ClientException {
        if (messageSendReceiptMap.isEmpty()) {
            throw new IllegalStateException("Transactional message has not been sent yet");
        }
        for (Map.Entry<PublishingMessageImpl, SendReceiptImpl> entry : messageSendReceiptMap.entrySet()) {
            final PublishingMessageImpl publishingMessage = entry.getKey();
            final SendReceiptImpl sendReceipt = entry.getValue();
            producerImpl.endTransaction(sendReceipt.getEndpoints(), publishingMessage.getMessageCommon(),
                    sendReceipt.getMessageId(), sendReceipt.getTransactionId(), TransactionResolution.ROLLBACK);
        }
    }
}
```

```java
class ProducerImpl extends ClientImpl implements Producer {


    //省略该类其他内容


    //开启事务消息的方法，其实就是创建一个TransactionImpl对象
    @Override
    public Transaction beginTransaction() {
        checkNotNull(checker, "Transaction checker should not be null");
        if (!this.isRunning()) {
            LOGGER.error("Unable to begin a transaction because producer is not running, state={}, clientId={}",

    //发送事务消息的方法
    @Override
    public SendReceipt send(Message message, Transaction transaction) throws ClientException {

        if (!(transaction instanceof TransactionImpl)) {
            throw new IllegalArgumentException("Failed downcasting for transaction");
        }//得到事务消息对象
        TransactionImpl transactionImpl = (TransactionImpl) transaction;
        final PublishingMessageImpl publishingMessage;
        try {//创建并存储要发布的事务消息
            publishingMessage = transactionImpl.tryAddMessage(message);
        } catch (Throwable t) {
            throw new ClientException(t);
        }//在这里执行了发送事务消息的操作
        final ListenableFuture<List<SendReceiptImpl>> future = send0(
                Collections.singletonList(publishingMessage),
                true
        );
        final List<SendReceiptImpl> receipts = handleClientFuture(future);
        //得到发送消息的回执对象
        final SendReceiptImpl sendReceipt = receipts.iterator().next();
        //存储消息和回执对象，后续提交或者回滚事务消息时会用到这个回执对象
        ((TransactionImpl) transaction).tryAddReceipt(publishingMessage, sendReceipt);
        return sendReceipt;
    }


    //结束事务消息的方法，这里就是向服务端发送提交事务请求，或者是回滚事务请求
    //和之前我们见过的向服务端发送各种请求的流程一样，我就不天下注释了，大家自己看看就行
    public void endTransaction(Endpoints endpoints, MessageCommon messageCommon, MessageId messageId,
                               String transactionId, final TransactionResolution resolution) throws ClientException {
        Metadata metadata;
        try {
            metadata = sign();
        } catch (Throwable t) {
            throw new ClientException(t);
        }
        final EndTransactionRequest.Builder builder = EndTransactionRequest.newBuilder()
                .setMessageId(messageId.toString()).setTransactionId(transactionId)
                .setTopic(apache.rocketmq.v2.Resource.newBuilder().setName(messageCommon.getTopic()).build());
        switch (resolution) {
            case COMMIT:
                builder.setResolution(apache.rocketmq.v2.TransactionResolution.COMMIT);
                break;
            case ROLLBACK:
            default:
                builder.setResolution(apache.rocketmq.v2.TransactionResolution.ROLLBACK);
        }
        final Duration requestTimeout = clientConfiguration.getRequestTimeout();
        //创建了结束事务操作的请求对象
        final EndTransactionRequest request = builder.build();

        final Stopwatch stopwatch = Stopwatch.createStarted();
        final List<MessageCommon> messageCommons = Collections.singletonList(messageCommon);
        MessageHookPoints messageHookPoints = TransactionResolution.COMMIT.equals(resolution) ?
                MessageHookPoints.COMMIT_TRANSACTION : MessageHookPoints.ROLLBACK_TRANSACTION;
        doBefore(messageHookPoints, messageCommons);

        //在这里发送了结束事务的请求
        final ListenableFuture<RpcInvocation<EndTransactionResponse>> future =
                clientManager.endTransaction(endpoints, metadata, request, requestTimeout);
        Futures.addCallback(future, new FutureCallback<RpcInvocation<EndTransactionResponse>>() {
            @Override
            public void onSuccess(RpcInvocation<EndTransactionResponse> invocation) {
                final Duration duration = stopwatch.elapsed();
                final EndTransactionResponse response = invocation.getResponse();
                final Status status = response.getStatus();
                final Code code = status.getCode();
                MessageHookPointsStatus messageHookPointsStatus = Code.OK.equals(code) ? MessageHookPointsStatus.OK :
                        MessageHookPointsStatus.ERROR;
                doAfter(messageHookPoints, messageCommons, duration, messageHookPointsStatus);
            }

            @Override
            public void onFailure(Throwable t) {
                final Duration duration = stopwatch.elapsed();
                doAfter(messageHookPoints, messageCommons, duration, MessageHookPointsStatus.ERROR);
            }
        }, MoreExecutors.directExecutor());
        final RpcInvocation<EndTransactionResponse> invocation = handleClientFuture(future);
        final EndTransactionResponse response = invocation.getResponse();
        final Status status = response.getStatus();
        final Code code = status.getCode();
        if (!Code.OK.equals(code)) {
            throw new ClientException(code.getNumber(), invocation.getContext().getRequestId(), status.getMessage());
        }
    }

    //省略该类其他内容
}
```

```java
        //设置消息存储到的服务器的网络地址
        msgInner.setStoreHost(this.getStoreHost());
        //设置消息重试次数
        msgInner.setReconsumeTimes(requestHeader.getReconsumeTimes() == null ? 0 : requestHeader.getReconsumeTimes());

        //设置集群名称

        //将消息属性转换为字符串格式
        msgInner.setPropertiesString(MessageDecoder.messageProperties2String(msgInner.getProperties()));
    

        //得到消息类型标志
        String traFlag = oriProps.get(MessageConst.PROPERTY_TRANSACTION_PREPARED);
        boolean sendTransactionPrepareMessage;
        if (Boolean.parseBoolean(traFlag)
                //执行到这这里意味着消息是事务消息，那接下来就判断一下当前Broker节点是否支持处理事务消息
                && !(msgInner.getReconsumeTimes() > 0 && msgInner.getDelayTimeLevel() > 0)) {
            if (this.brokerController.getBrokerConfig().isRejectTransactionMessage()) {
                //不支持处理事务消息则直接返回响应
                response.setCode(ResponseCode.NO_PERMISSION);
                response.setRemark(
                        "the broker[" + this.brokerController.getBrokerConfig().getBrokerIP1()
                                + "] sending transaction message is forbidden");
                return response;
            }
            //设置事务消息标志
            sendTransactionPrepareMessage = true;
        } else {
            //设置当前消息为非事务消息标志
            sendTransactionPrepareMessage = false;
        }


        //判断是否启用异步存储
        if (brokerController.getBrokerConfig().isAsyncSendEnable()) {
            //省略该方法部分内容
        }
        
        else {
            //执行到这里就意味着是同步发送消息操作，在这里把消息交给存储引擎存储，同步等待结果返回
            PutMessageResult putMessageResult = null;
            if (sendTransactionPrepareMessage) {
                //同步存储事务消息
                putMessageResult = this.brokerController.getTransactionalMessageService().prepareMessage(msgInner);
            } else {
                //同步存储普通消息
                putMessageResult = this.brokerController.getMessageStore().putMessage(msgInner);
            }
            //处理消息存储结果，并设置响应对象
            handlePutMessageResult(putMessageResult, response, request, msgInner, responseHeader, sendMessageContext, ctx, queueIdInt, beginTimeMillis, mappingContext, BrokerMetricsManager.getMessageType(requestHeader));

            sendMessageCallback.onComplete(sendMessageContext, response);
            //返回响应对象
            return response;
        }
    }
```

```java
/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
```

```java
 */
public class EndTransactionProcessor implements NettyRequestProcessor {

    private static final Logger LOGGER = LoggerFactory.getLogger(LoggerName.TRANSACTION_LOGGER_NAME);

    private final BrokerController brokerController;


    public EndTransactionProcessor(final BrokerController brokerController) {
        this.brokerController = brokerController;
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：处理事务消息请求的方法
     */
    @Override
    public RemotingCommand processRequest(ChannelHandlerContext ctx, RemotingCommand request) throwsRemotingCommandException {

        //得到响应对象
        final RemotingCommand response = RemotingCommand.createResponseCommand(null);
        //从请求中解析请求头
        final EndTransactionRequestHeader requestHeader = (EndTransactionRequestHeader) request.decodeCommandCustomHeader(EndTransactionRequestHeader.class);
        LOGGER.debug("Transaction request:{}", requestHeader);
        //判断当前节点是否为从节点，如果是从节点则不能处理事务消息请求，该请求通常是主节点处理的，因此这里要返回从节点无法处理请求的响应码
        if (BrokerRole.SLAVE == brokerController.getMessageStoreConfig().getBrokerRole()) {
            response.setCode(ResponseCode.SLAVE_NOT_AVAILABLE);
            LOGGER.warn("Message store is slave mode, so end transaction is forbidden. ");
            return response;
        }

        //创建事务消息操作结果对象
        OperationResult result = new OperationResult();
        
        //接下来就是真正处理事务消息的操作了，先判断是不是提交事务消息的请求
        if (MessageSysFlag.TRANSACTION_COMMIT_TYPE == requestHeader.getCommitOrRollback()) {
            //如果是，则在这里执行提交事务消息的操作
            //注意，这里并没有执行把办消息重新投递到原始主题队列中的操作，而是仅仅得到了这条半消息的内容
            result = this.brokerController.getTransactionalMessageService().commitMessage(requestHeader);
            //判断刚才是否得到了完整的办消息内容
            if (result.getResponseCode() == ResponseCode.SUCCESS) {
                //执行到这里意味着消息可以被提交或者回滚，而刚才已经得到这条半消息了，不管接下来要执行什么操作
                //都要先对这条消息进行有效性校验
                RemotingCommand res = checkPrepareMessage(result.getPrepareMessage(), requestHeader);
                //判断消息是否有效
                if (res.getCode() == ResponseCode.SUCCESS) {
                    //有效则接下来就可以真正处理这条消息了，因为是消息提交操作，那么在这里就可以把这条半消息提交到原始主题队列中
                    //endMessageTransaction()方法中执行的操作很简单，就是更换半消息的主题信息
                    MessageExtBrokerInner msgInner = endMessageTransaction(result.getPrepareMessage());
                    //设置消息的事务标志位，表示事务已提交
                    msgInner.setSysFlag(MessageSysFlag.resetTransactionValue(msgInner.getSysFlag(), requestHeader.getCommitOrRollback()));
                    //设置消息在消费队列中的逻辑偏移量
                    msgInner.setQueueOffset(requestHeader.getTranStateTableOffset());
                    //设置半消息在CommitLog文件中的全局偏移量
                    msgInner.setPreparedTransactionOffset(requestHeader.getCommitLogOffset());
                    //设置消息的存储时间戳
                    msgInner.setStoreTimestamp(result.getPrepareMessage().getStoreTimestamp());
                    //清除消息属性中的事务消息标志
                    MessageAccessor.clearProperty(msgInner, MessageConst.PROPERTY_TRANSACTION_PREPARED);
                    //在这里把消息投递到它的原始主题队列中，其实就是把消息写入到CommitLog文件中的操作
                    RemotingCommand sendResult = sendFinalMessage(msgInner);
                    return sendResult;
                }
                return res;
            }
        }

        //执行到这里意味着是事务消息回滚操作
        //回滚操作和提交操作逻辑几乎一样，只不过回滚操作最关键地方什么都不做，也就是不必重新投递消息，既然不重新投递
        //那么消费者就消费不到这条消息，这也就意味着消息回滚成功了
        else if (MessageSysFlag.TRANSACTION_ROLLBACK_TYPE == requestHeader.getCommitOrRollback()) {
            //这里虽然执行了消息回滚操作，其实就是从事务消息主题中得到了半消息的完整内容
            result = this.brokerController.getTransactionalMessageService().rollbackMessage(requestHeader);
            //一下执行的操作和COMMIT分支一样，都是对半消息进行有效性校验我就不再添加注释了
            //大家简单看看就行
            if (result.getResponseCode() == ResponseCode.SUCCESS) {
                RemotingCommand res = checkPrepareMessage(result.getPrepareMessage(), requestHeader);
                return res;
            }
        }
        response.setCode(result.getResponseCode());
        response.setRemark(result.getResponseRemark());
        return response;
    }
```

现在我可以跟大家解释清楚了，**当 Broker 节点主动向生产者客户端执行事务回查操作时，生产者客户端接收到事务回查请求后，就会调用 TransactionChecker 事务检查器中的方法，判断本地事务的执行情况**。当然，在测试类中我写得内容很简单，实际上这个 TransactionChecker 事务检查器的内容是由程序员根据实际业务自己定义的，大家理解这个意思即可。这个逻辑也很简单。



说完客户端，还是再回到 Broker 节点吧，现在我们要关心的是，Broker 节点该怎么执行所谓的事务回查操作呢？我能想到的就是首先应该定义一个超时时间，B**roker 节点可以在自己内部判断，哪一条事务消息存在的时间已经超时了，如果超时了，那就要对这条事务消息执行回查操作；很好，既然要根据事务消息存在时间判断消息是否超时，那么当一条事务消息被提交或者回滚后，显然应该立刻从消息队列中删除**，这一点可以理解吧？当然，这里说的删除并不是真正物理意义上的删除，我们都知道，CommitLog 文件中的数据只能被过期删除，在程序运行过程中，我们很少会对本地文件中的数据手动进行操作。那这个时候大家肯定就会有新的疑问，所谓的删除究竟是什么呢？



接下来让我为大家解释一下源码中的设计思想：在源码中，内置了一个事务消息主题，那就是 RMQ_SYS_TRANS_HALF_TOPIC 主题信息，翻译过来就是半消息主题，并且这个主题下只有一个 Id 为 0 的消息队列。也就是说，所有事务消息都会被投递到同一个消费队列中。当定义好了这一切之后，源码中还内置了一个系统级别的主题，就是 RMQ_SYS_TRANS_OP_HALF_TOPIC 主题，翻译过来就是已处理半消息主题，所谓处理就是已经被提交或者被回滚的意思。刚才我已经跟大家说了，事务消息主题下只有一个消费队列，那实际上，这个 RMQ_SYS_TRANS_OP_HALF_TOPIC 主题下也是如此，或者说在程序中存在一个消费队列与 RMQ_SYS_TRANS_HALF_TOPIC 事务主题的消费队列对应，并且这个消费队列所属主题为 RMQ_SYS_TRANS_OP_HALF_TOPIC。可能说的有点绕口，但我相信大家可以理解我的意思。



好了，这两个主题和主题下的队列定义完毕了之后，应该怎么做呢？这个时候就很简单了，那就是每当事务消息主题中一条消息被处理了，也就是被提交或者回滚了，那么就会把这条消息在消费队列中的偏移量写入到 OP 主题的消费队列中。**比如说事务消息主题中有一条偏移量为 100 的消息，这条消息被提交了，那么在提交之后，就要把 100 这个偏移量写入到 OP 主题的消费队列中。这样一来，只要 Broker 节点定时扫描 OP 主题消费队列中存储的消息偏移量，只要存储了哪个偏移量，就意味着事务消息主题队列中的哪条消息被处理了，那么这条消息就不必被回查了。而一旦发现哪条消息没有被处理，并且这条消息已经超时了，那这个时候就要对这条消息执行回查操作了**。大家可以仔细品味品味这个逻辑。



如果大家理解了这个逻辑，那接下来就很好说了，那我们只需要让 Broker 节点提交或者回滚消息之后，执行对应的操作即可。也就是得到被处理的消息在事务主题队列中的偏移量，然后把偏移量写进 OP 主题消费队列中。因为这两个队列是一一对应的，而消息的偏移量又是唯一的，所以只需要根据消息偏移量就能确定事务主题消费队列中唯一一条消息。当然，我知道看到这里肯定有朋友还是有疑问，就算可以定期扫描 OP 消费队列的数据，然后判断事务主题消费队列的消息是否被处理，那么每次扫描对比的时候具体要怎么执行呢？难道要扫描队列全部内容，然后对比事务消息队列全部内容？这么做岂不是太麻烦，也太费事了吗？



是的，显然不能这么做，正确的做法应该是这样：**每次扫描 OP 消息队列中的数据肯定是有限的，扫描了多少就意味着在队列中消费了多少消息，更新队列消费偏移量即可，下一次扫描时，就从最新的消费偏移量开始扫描即可；而每一次到事务主题消费队列中对比消息，对比了多少消息就意味着消费了多少消息，这个队列的消费偏移量也应该被记录下来，并且每次对比都要从最新的消费偏移量开始对比**。我想这个逻辑也不难理解吧？如果大家理解了这个逻辑，那大家肯定还会接着思考，如果按照队列消费偏移量来扫描对比消息，那假如事务消费队列偏移量为 200 的消息被回查了，而这个 200 偏移量已经被消费了，那么下一次对比消息的时候，这个 200 偏移量的消息不就再也无法对比了吗？没错，确实存在这个问题，但这个问题并不是没办法解决，实际上解决方法非常简单，**那就是每次回查消息的时候，只要把这条消息重新再重新投递到事务消息主题中，那它就会被重新构建到消费队列中，消费偏移量也是新的，自然就会被再次查询到了**。这么说大家可能还是觉得很模糊，所以接下来我会给大家展示相关代码，大家只要先把这个大概逻辑记住，一会儿就可以到代码中印证我所说的逻辑了。

当然，接下来展示的代码的内容可能跟我们之前分析的有些不同，之前我们分析一条消息被处理了，那么就要立刻把它的事务消费队列偏移量写入 OP 队列中，对吧？其实也不必这么着急，**IO 操作本就会消耗资源，频繁的 IO 操作也会拖累程序执行的性能，最好的方法是先把数据写到缓冲区里，等到缓冲区积攒的数据达到阈值了，再一口气把缓冲区中的数据写入到 OP 消费队列中**。这一点大家应该也可以理解吧？如果大家理解了这些逻辑，那接下来我就可以为大家展示对应的代码了，大家也可以直接阅读第 27 版本代码，请看下面你代码块。

```java
package org.apache.rocketmq.broker.transaction.queue;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @方法描述：事务消息服务组件，这个组件对象提供了很多处理事务消息的方法，其中最核心的方法就是回查事务消息方法，以及把已提交或者回滚的消息写入到OP主题的方法。
 */
public class TransactionalMessageServiceImpl implements TransactionalMessageService {

    //存放缓冲队列的Map，注意，这里虽然是一个Map，但根据我们之前的了解
    //事务主题下只有一个队列，所以这里只会存储一个键值对
    //MessageQueueOpContext对象内部持有了一个队列，队列中存储的都是字符串，已被处理的事务消息的偏移量就会先写进这个队列中
    //MessageQueueOpContext的内容我就不在文章中展示了，内容真的很简单
    private final ConcurrentHashMap<Integer, MessageQueueOpContext> deleteContext = new ConcurrentHashMap<>();
    
    //省略该类其他内容

    //这个对象就是专门用来执行事务消息解析、获取、存储操作的
    //我把这个对象的内容也展示在当前代码块中了，大家可以简单看一看
    //内容非常简单
    private TransactionalMessageBridge transactionalMessageBridge;

    private ServiceThread transactionalOpBatchService;


    public TransactionalMessageServiceImpl(TransactionalMessageBridge transactionBridge) {
        this.transactionalMessageBridge = transactionBridge;
        transactionalOpBatchService = new TransactionalOpBatchService(transactionalMessageBridge.getBrokerController(), this);
        transactionalOpBatchService.start();
    }

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：同步存储半消息的方法
     */
    @Override
    public PutMessageResult prepareMessage(MessageExtBrokerInner messageInner) {
        return transactionalMessageBridge.putHalfMessage(messageInner);
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：删除本消息队列中办消息的方法，这里虽然是删除，但其实就是为这些半消息向对应的OP队列中写入一条决议消息
     */
    @Override
    public boolean deletePrepareMessage(MessageExt messageExt) {
        //得到消息所在队列Id，这里得到的就是Id0
        Integer queueId = messageExt.getQueueId();
        //得到OP消息的内存缓冲队列
        MessageQueueOpContext mqContext = deleteContext.get(queueId);
        //没有则创建 一个MessageQueueOpContext对象，然后缓存在deleteContext中
        if (mqContext == null) {
            mqContext = new MessageQueueOpContext(System.currentTimeMillis(), 20000);
            MessageQueueOpContext old = deleteContext.putIfAbsent(queueId, mqContext);
            if (old != null) {
                mqContext = old;
            }
        }
        
        //得到半消息在消费队列中的逻辑偏移量，TransactionalMessageUtil.OFFSET_SEPARATOR是分隔符，因为一条OP消息可以存储多个半消息偏移量
        //也就是说，偏移量200，220，240的消息都被处理了，那么它们也可以合并成同一条OP消息里
        String data = messageExt.getQueueOffset() + TransactionalMessageUtil.OFFSET_SEPARATOR;
        try {
            //把数据写入到缓冲队列中，这里大家就可以看出来，当有一条半消息被提交或者回滚后，就会向对应的OP队列中写入一条决议消息
            //但是决议消息并不是立刻就写到OP队列中，而是先写到缓冲区里，等到恰当的时机，再唤醒TransactionalOpBatchService对象
            //让TransactionalOpBatchService对象批量把决议消息写入到OP队列中
            boolean res = mqContext.getContextQueue().offer(data, 100, TimeUnit.MILLISECONDS);
            //判断数据是否成功写到缓存队列中了
            if (res) {
                //成功写入则更新缓存队列中累计数据大小
                int totalSize = mqContext.getTotalSize().addAndGet(data.length());
                //如果累计数据超过了阈值，那么就意味着写满了，这个时候就要唤醒TransactionalOpBatchService对象，让TransactionalOpBatchService对象批量写入OP消息到本地文件中
                if (totalSize > transactionalMessageBridge.getBrokerController().getBrokerConfig().getTransactionOpMsgMaxSize()) {
                    this.transactionalOpBatchService.wakeup();
                }
                return true;
            } else {
                //没写入成功，那就意味着内存缓冲队列可能写满了，堆积的数据太多
                //这个时候也要唤醒TransactionalOpBatchService对象，让TransactionalOpBatchService对象批量写入OP消息到本地文件中
                this.transactionalOpBatchService.wakeup();
            }
        } catch (InterruptedException ignore) {

        }
        //执行到这里意味着消息写入缓冲区失败了，如果成功则刚才就应该退出当前方法了
        //这个时候程序执行了一个操作，那就是把缓冲队列中的半消息偏移量拼接成了一条OP消息
        //然后把这一条OP消息写入到本地文件中了，getOpMessage()方法执行的就是拼接半消息，得到一条OP消息的操作
        Message msg = getOpMessage(queueId, data);
        //在这里把刚才得到的一条OP消息写入到本地文件中
        if (this.transactionalMessageBridge.writeOp(queueId, msg)) {
            log.warn("Force add remove op data. queueId={}", queueId);
            return true;
        } else {
            log.error("Transaction op message write failed. messageId is {}, queueId is {}", messageExt.getMsgId(), messageExt.getQueueId());
            return false;
        }
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：拼接半消息，得到一条OP消息的方法
     */
    public Message getOpMessage(int queueId, String moreData) {
        //得到OP消息的主题信息
        String opTopic = TransactionalMessageUtil.buildOpTopic();
        //得到对应的缓冲队列
        MessageQueueOpContext mqContext = deleteContext.get(queueId);
        //计算传进来的moreData数据的长度
        int moreDataLength = moreData != null ? moreData.length() : 0;
        int length = moreDataLength;
        //得到一条OP消息的最大字节长度
        int maxSize = transactionalMessageBridge.getBrokerController().getBrokerConfig().getTransactionOpMsgMaxSize();
        //判断现在构建的OP消息的字节长度是否超过了规定阈值
        if (length < maxSize) {
            //没有超过则得到缓冲队列中已累积的数据总大小
            int sz = mqContext.getTotalSize().get();
            //判断加上缓冲队列中已累积的数据长度是否超过了阈值
            if (sz > maxSize || length + sz > maxSize) {
                //如果超过了则更新length为最大字节+100的长度
                length = maxSize + 100;
            } else {
                //没有超过则直接使用精准的字节长度
                length += sz;
            }
        }
        //接下来就是拼接一条OP消息的操作了
        StringBuilder sb = new StringBuilder(length);
        if (moreData != null) {
            //把moreData数据拼接到OP消息中
            sb.append(moreData);
        }
        //判断缓冲队列内容是否不为空
        while (!mqContext.getContextQueue().isEmpty()) {
            if (sb.length() >= maxSize) {
                //数据不能超过上限
                break;
            }
            //不为空则取出每一条消息
            String data = mqContext.getContextQueue().poll();
            if (data != null) {
                //在这里拼接
                sb.append(data);
            }
        }
        if (sb.length() == 0) {
            return null;
        }
        //判断本次拼接操作从缓冲队列中获取的数据长度
        int l = sb.length() - moreDataLength;
        //更新缓冲队列存储的数据大小
        mqContext.getTotalSize().addAndGet(-l);
        mqContext.setLastWriteTimestamp(System.currentTimeMillis());
        //这里可以清楚的看到，OP消息的标签为d
        //在这里，大家也肯到了OP消息的具体格式和内容
        return new Message(opTopic, TransactionalMessageUtil.REMOVE_TAG,
                sb.toString().getBytes(TransactionalMessageUtil.CHARSET));
    }

    //大家可以先看一看具体的逻辑

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：把deleteContext中的消息批量写入到OP主题队列中的方法，这个方法的逻辑非常简单，我就不添加详细注释了，大家简单看看就行
     */
    public long batchSendOpMessage() {
        //得到操作开始执行时间
        long startTime = System.currentTimeMillis();
        try {
            long firstTimestamp = startTime;
            Map<Integer, Message> sendMap = null;
            //得到操作间隔
            long interval = transactionalMessageBridge.getBrokerController().getBrokerConfig().getTransactionOpBatchInterval();
            //得到可刷新最大数量
            int maxSize = transactionalMessageBridge.getBrokerController().getBrokerConfig().getTransactionOpMsgMaxSize();
            boolean overSize = false;
            //遍历缓冲区
            for (Map.Entry<Integer, MessageQueueOpContext> entry : deleteContext.entrySet()) {
                MessageQueueOpContext mqContext = entry.getValue();
                if (mqContext.getTotalSize().get() <= 0 || mqContext.getContextQueue().size() == 0 ||
                        mqContext.getTotalSize().get() < maxSize &&
                                startTime - mqContext.getLastWriteTimestamp() < interval) {
                    continue;
                }
                if (sendMap == null) {
                    sendMap = new HashMap<>();
                }//在这里，大家会看到又得到一个OP消息
                Message opMsg = getOpMessage(entry.getKey(), null);
                if (opMsg == null) {
                    continue;
                }
                sendMap.put(entry.getKey(), opMsg);
                firstTimestamp = Math.min(firstTimestamp, mqContext.getLastWriteTimestamp());
                if (mqContext.getTotalSize().get() >= maxSize) {
                    overSize = true;
                }
            }

            if (sendMap != null) {
                for (Map.Entry<Integer, Message> entry : sendMap.entrySet()) {
                    //在这里调用writeOp方法写入OP消息
                    if (!this.transactionalMessageBridge.writeOp(entry.getKey(), entry.getValue())) {
                        log.error("Transaction batch op message write failed. body is {}, queueId is {}",
                                new String(entry.getValue().getBody(), TransactionalMessageUtil.CHARSET), entry.getKey());
                    }
                }
            }
            log.debug("Send op message queueIds={}", sendMap == null ? null : sendMap.keySet());
            long wakeupTimestamp = firstTimestamp + interval;
            if (!overSize && wakeupTimestamp > startTime) {
                return wakeupTimestamp;
            }
        } catch (Throwable t) {
            log.error("batchSendOp error.", t);
        }
        return 0L;
    }

}
```

```java
public class TransactionalMessageServiceImpl implements TransactionalMessageService {

    //存放缓冲队列的Map，注意，这里虽然是一个Map，但根据我们之前的了解
    //事务主题下只有一个队列，所以这里只会存储一个键值对
    //MessageQueueOpContext对象内部持有了一个队列，队列中存储的都是字符串，已被处理的事务消息的偏移量就会先写进这个队列中

    //内容非常简单

    private ServiceThread transactionalOpBatchService;


    public TransactionalMessageServiceImpl(TransactionalMessageBridge transactionBridge) {
        this.transactionalMessageBridge = transactionBridge;
        transactionalOpBatchService = new TransactionalOpBatchService(transactionalMessageBridge.getBrokerController(), this);
        transactionalOpBatchService.start();
    }

    
    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：本类最核心的方法，也就是事务消息回查的方法
     */
    @Override
    public void check(long transactionTimeout, int transactionCheckMax,
                      AbstractTransactionalMessageCheckListener listener) {
        try {
            //得到事务消息的主题信息
            String topic = TopicValidator.RMQ_SYS_TRANS_HALF_TOPIC;
            //得到该主题下的所有队列，这里虽然得到的是一个集合，但是我们都知道，事务消息主题下只有一个消费队列，所以这里得到的集合中只有一个元素
            Set<MessageQueue> msgQueues = transactionalMessageBridge.fetchMessageQueues(topic);
            if (msgQueues == null || msgQueues.size() == 0) {
                log.warn("The queue of topic is empty :" + topic);
                return;
            }
            log.debug("Check topic={}, queues={}", topic, msgQueues);
            
            
            
            //遍历所有消费队列
            for (MessageQueue messageQueue : msgQueues) {
                //得到操作开始执行的时间
                long startTime = System.currentTimeMillis();
                //根据事务主题队列的信息得到与该队列对应的OP消息队列
                MessageQueue opQueue = getOpQueue(messageQueue);
                //得到事务消息主题队列的消费进度，也就是消费偏移量
                long halfOffset = transactionalMessageBridge.fetchConsumeOffset(messageQueue);
                //得到OP消息的消费偏移量
                long opOffset = transactionalMessageBridge.fetchConsumeOffset(opQueue);
                log.info("Before check, the queue={} msgOffset={} opOffset={}", messageQueue, halfOffset, opOffset);
                //校验消费偏移量的合法性
                if (halfOffset < 0 || opOffset < 0) {
                    log.error("MessageQueue: {} illegal offset read: {}, op offset: {},skip this queue", messageQueue, halfOffset, opOffset);
                    continue;
                }
                //下面这三个局部变量的作用很重要，尤其是removeMap变量的作用非常重要
                List<Long> doneOpOffset = new ArrayList<>();
                //大家应该清楚了已经被决议的消息在OP主题队列中的存储格式，比如说事务消息主题队列中，逻辑偏移量为1的消息被决议了
                //那么就会被这个偏移量1存储在对应的OP队列中，比如说存储在OP队列的偏移量为2，那么键值对1——2也就意味着是OP队列偏移量为2的位置存储了事务主题队列偏移量为1的消息的偏移量
                //并且这个偏移量出的事务消息已经被决议了
                //如果大家还是不清楚，那么我就举一个具体的例子
                //op队列中偏移量为10的位置存储了一条消息，这条消息解析之后得到了三个便宜量，分别是20、40、60
                //也就是说事物消息队列中，20、40、60这三个便宜量位置的消息已经被处理了
                //那么op队列的便宜量10和它存储的三个便宜量就会被存放到这个map中
                //并且以三条消息的方式存放，分别是20——10，40——10，60——10
                //当开始扫描事务消息队列时，从有效消费便宜量之后开始扫描，只要发现有哪个便宜量能在这个map
                //找到对应的值，就意味着这个便宜量对应的消息被处理了，找不到则意味着没被处理，那就需要看情况判断是否需要回查
                HashMap<Long, Long> removeMap = new HashMap<>();
                HashMap<Long, HashSet<Long>> opMsgMap = new HashMap<Long, HashSet<Long>>();
                //这里的操作非常重要，fillOpRemoveMap()方法所执行的操作就是从op队列中获取数据
                //然后把数据分别存放到刚才定义的三个局部变量中，存放到removeMap中的数据最为重要
                PullResult pullResult = fillOpRemoveMap(removeMap, opQueue, opOffset, halfOffset, opMsgMap, doneOpOffset);
                if (null == pullResult) {
                    log.error("The queue={} check msgOffset={} with opOffset={} failed, pullResult is null",
                            messageQueue, halfOffset, opOffset);
                    continue;
                }
                int getMessageNullCount = 1;
                long newOffset = halfOffset;
                //得到要继续遍历的事务主题队列的位置
                long i = halfOffset;
                //得到OP队列中的下一条要被消费的消息的偏移量
                long nextOpOffset = pullResult.getNextBeginOffset();
                int putInQueueCount = 0;
                int escapeFailCnt = 0;


                //下面就是根据从op中获得数据，判断事物消息队列中的数据是否需要回查的操作
                
                //在循环中判断事务消息主题中有哪些消息没有被决议，然后对这些消息执行回查操作
                while (true) {
                    //判断check操作是否超时了，也就是说当前方法每次执行的时候，最多执行60000毫秒，超过指定时间则要退出循环
                    if (System.currentTimeMillis() - startTime > MAX_PROCESS_TIME_LIMIT) {
                        log.info("Queue={} process time reach max={}", messageQueue, MAX_PROCESS_TIME_LIMIT);
                        break;
                    }//判断便利到的消息便宜量是否在removeMap中，在的话意味着消息已经被处理了
                    if (removeMap.containsKey(i)) {
                        //这里就是判断当前遍历到的事务消息主题中的半消息是否在removeMap中，如果在map中，就意味着当前遍历到的偏移量的事务半消息已经被决议了
                        //那就可以不必处理这条消息，直接跳过本次循环即可
                        log.debug("Half offset {} has been committed/rolled back", i);
                        //从map中删除对应的消息
                        Long removedOpOffset = removeMap.remove(i);
                        opMsgMap.get(removedOpOffset).remove(i);
                        //判断OP队列中该偏移量存储的所有半消息偏移量的消息是否都处理完毕了
                        if (opMsgMap.get(removedOpOffset).size() == 0) {
                            //如果处理完毕则从opMsgMap中移除对应消息
                            opMsgMap.remove(removedOpOffset);
                            //然后把OP队列的这个偏移量添加到doneOpOffset中
                            doneOpOffset.add(removedOpOffset);
                        }
                    } else {
                        //执行到这里意味着当前遍历到的事务半消息的偏移量并不在removeMap中，这就意味着这条消息并没有被决议，那就要对这条消息执行回查操作
                        //这里就是从事务消息主题中根据消息偏移量得到这条半消息
                        GetResult getResult = getHalfMsg(messageQueue, i);
                        MessageExt msgExt = getResult.getMsg();
                        if (msgExt == null) {
                            //如果半消息为空，那接下来就要执行重试操作，这里判断一下重新获取消息的次数超过了最大阈值，那就要退出循环了
                            if (getMessageNullCount++ > MAX_RETRY_COUNT_WHEN_HALF_NULL) {
                                break;
                            }
                            //这里就是判断一下看看队列中是否没有消息了，如果没有消息也就要退出循环
                            if (getResult.getPullResult().getPullStatus() == PullStatus.NO_NEW_MSG) {
                                log.debug("No new msg, the miss offset={} in={}, continue check={}, pull result={}", i,
                                        messageQueue, getMessageNullCount, getResult.getPullResult());
                                break;
                            } else {
                                //执行到这里意味着拉去消息的偏移量不合规，可能是数据出现丢失，不连续
                                log.info("Illegal offset, the miss offset={} in={}, continue check={}, pull result={}",
                                        i, messageQueue, getMessageNullCount, getResult.getPullResult());
                                //这里就得到半消息队列的下一个有效的消费偏移量
                                i = getResult.getPullResult().getNextBeginOffset();
                                newOffset = i;
                                continue;
                            }
                        }

                        //执行到这里意味着消息需要回查，并且消息本身内容也没有问题，那接下来就要判断一下这条消息是否需要
                        //丢弃或者被跳过，如果都不需要，那就可以对这条消息执行回查操作，至于为什么丢弃和被跳过，大家直接去对应的
                        //方法中查看逻辑即可
                        if (needDiscard(msgExt, transactionCheckMax) || needSkip(msgExt)) {
                            //如果需要被丢弃，那就把消息重新投递到RMQ_SYS_TRANS_CHECK_MAX_TIME_TOPIC系统内置的主题中，等待被处理
                            listener.resolveDiscardMsg(msgExt);
                            //更新半消息消费队列的消费进度
                            newOffset = i + 1;
                            //更新遍历位置
                            i++;
                            //进入下一次循环
                            continue;
                        }
                        //执行到这里意味着消息不应该被丢弃，那就判断一下消息的存储时间是否大于操作开始时间
                        //如果超过则意味着本次检查操作开始之后，这条消息才被存储Broker节点，这种情况也不能处理这条消息
                        //因为生产者客户端的事务操作可能根本就没有结束呢，那就退出当前循环
                        if (msgExt.getStoreTimestamp() >= startTime) {
                            log.debug("Fresh stored. the miss offset={}, check it later, store={}", i,
                                    new Date(msgExt.getStoreTimestamp()));
                            break;
                        }

                        //接下来就是判断一下，消息是否过了首次回查时间阈值，如果没有超过，那就不能回差
                        //这里得到的就是消息的存活时长
                        long valueOfCurrentMinusBorn = System.currentTimeMillis() - msgExt.getBornTimestamp();
                        //这里得到的就是默认的消息回查时间
                        long checkImmunityTime = transactionTimeout;
                        //判断用户是否设置了消息首次回查时间，如果设置了，那就是用用户设置的这个时间
                        String checkImmunityTimeStr = msgExt.getUserProperty(MessageConst.PROPERTY_CHECK_IMMUNITY_TIME_IN_SECONDS);
                        if (null != checkImmunityTimeStr) {
                            //得到最终要使用的首次回查时间
                            checkImmunityTime = getImmunityTime(checkImmunityTimeStr, transactionTimeout);
                            //判断消息存活时间是否小于回查时间，如果小于，则意味着消息本地事务可能还没结束
                            //那就先不回查这条消息
                            if (valueOfCurrentMinusBorn < checkImmunityTime) {
                                //这里再次判断一下，这条消息是否已经被决议了，其实就是判断一下消息的偏移量是否存储在removeMap中
                                //如果已经决议了，那就更不用关心这条消息，直接更新相关信息，进入下一次循环即可
                                if (checkPrepareQueueOffset(removeMap, doneOpOffset, msgExt, checkImmunityTimeStr)) {
                                    newOffset = i + 1;
                                    i++;
                                    continue;
                                }
                            }
                        } else {
                            //如果用户没有设置回查时间，那就判断一下消息的存活时长是否小于默认的回查时长，如果小于，则意味着消息本地事务可能还没结束
                            if (0 <= valueOfCurrentMinusBorn && valueOfCurrentMinusBorn < checkImmunityTime) {
                                log.debug("New arrived, the miss offset={}, check it later checkImmunity={}, born={}", i,
                                        checkImmunityTime, new Date(msgExt.getBornTimestamp()));
                                //退出循环即可，这里直接退出循环的原因也很简单，消费对类中的消息肯定是按照生产时间顺序存储的，前面的消息存活时间还不够呢
                                //后面的消息存活时间只会更短，那就都不必判断了
                                break;
                            }
                        }


                        
                        //接下来就要执行消息回查操作了，先得到从OP队列中拉取的本批次消息
                        List<MessageExt> opMsg = pullResult == null ? null : pullResult.getMsgFoundList();
                        //下面这些判断中，我只分析opMsg.get(opMsg.size() - 1).getBornTimestamp() - startTime > transactionTimeout这个判断，其他的逻辑都很简单，大家自己看看就行
                        //在opMsg.get(opMsg.size() - 1).getBornTimestamp() - startTime > transactionTimeout判断中，大家可以看到首先得到了本批获取的OP消息的最后一条消息
                        //然后用最后一条消息的诞生时间减去本批次检查操作的开始时间，这样就得到了本批次消息中最新消息存活时长，如果最新消息的存储时长都大于事务超时时间
                        //那就意味着这一批消息的存活时长都超过了事务超时阈值，那么就可以发起回查了
                        boolean isNeedCheck = opMsg == null && valueOfCurrentMinusBorn > checkImmunityTime
                                || opMsg != null && opMsg.get(opMsg.size() - 1).getBornTimestamp() - startTime > transactionTimeout
                                || valueOfCurrentMinusBorn <= -1;

                        if (isNeedCheck) {
                            //可以执行消息回查之后，那就可以在这里把这条半消息写回到CommitLog文件中，因为这条办消息中的属性已经更新了
                            //也就是回查次数更新了，所以必须要重新写回到CommitLog文件中
                            if (!putBackHalfMsgQueue(msgExt, i)) {
                               //写入失败则跳过这条消息
                                continue;
                            }
                            //写入成功则更新回查消息计数器
                            putInQueueCount++;
                            log.info("Check transaction. real_topic={},uniqKey={},offset={},commitLogOffset={}",
                                    msgExt.getUserProperty(MessageConst.PROPERTY_REAL_TOPIC),
                                    msgExt.getUserProperty(MessageConst.PROPERTY_UNIQ_CLIENT_MESSAGE_ID_KEYIDX),
                                    msgExt.getQueueOffset(), msgExt.getCommitLogOffset());
                            //在这里执行消息回查操作
                            listener.resolveHalfMsg(msgExt);
                        } else {
                            //如果不需要回查，则更新下次从Op队列拉取消息的起始偏移量
                            nextOpOffset = pullResult != null ? pullResult.getNextBeginOffset() : nextOpOffset;
                            pullResult = fillOpRemoveMap(removeMap, opQueue, nextOpOffset, halfOffset, opMsgMap, doneOpOffset);
                            if (pullResult == null || pullResult.getPullStatus() == PullStatus.NO_NEW_MSG
                                    || pullResult.getPullStatus() == PullStatus.OFFSET_ILLEGAL
                                    || pullResult.getPullStatus() == PullStatus.NO_MATCHED_MSG) {
                                try {
                                    Thread.sleep(SLEEP_WHILE_NO_OP);
                                } catch (Throwable ignored) {
                                }
                            } else {
                                log.info("The miss message offset:{}, pullOffsetOfOp:{}, miniOffset:{} get more opMsg.", i, nextOpOffset, halfOffset);
                            }
                            continue;
                        }
                    }
                    newOffset = i + 1;
                    i++;
                }


                
                //执行到这里意味着循环结束了，那接下来就该把半消息主题队列和OP消息主题队列的消费偏移量更新一下，其他的也就没什么重要操作了
                //下面的代码我就不添加注释了，大家自己看看吧
                if (newOffset != halfOffset) {
                    transactionalMessageBridge.updateConsumeOffset(messageQueue, newOffset);
                }
                long newOpOffset = calculateOpOffset(doneOpOffset, opOffset);
                if (newOpOffset != opOffset) {
                    transactionalMessageBridge.updateConsumeOffset(opQueue, newOpOffset);
                }
                //以下就是记录日志信息的操作，我也不添加注释了
                GetResult getResult = getHalfMsg(messageQueue, newOffset);
                pullResult = pullOpMsg(opQueue, newOpOffset, 1);
                long maxMsgOffset = getResult.getPullResult() == null ? newOffset : getResult.getPullResult().getMaxOffset();
                long maxOpOffset = pullResult == null ? newOpOffset : pullResult.getMaxOffset();
                long msgTime = getResult.getMsg() == null ? System.currentTimeMillis() : getResult.getMsg().getStoreTimestamp();
                log.info("After check, {} opOffset={} opOffsetDiff={} msgOffset={} msgOffsetDiff={} msgTime={} msgTimeDelayInMs={} putInQueueCount={}",
                        messageQueue,
                        newOpOffset,
                        maxOpOffset - newOpOffset,
                        newOffset,
                        maxMsgOffset - newOffset,
                        new Date(msgTime),
                        System.currentTimeMillis() - msgTime,
                        putInQueueCount);
            }
        } catch (Throwable e) {
            log.error("Check error", e);
        }

    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：从OP主题队列中获取消息的方法，这里我再强调一下，只要是写入到OP主题队列中的消息，都是已经被决议的消息
     */
    private PullResult fillOpRemoveMap(HashMap<Long, Long> removeMap, MessageQueue opQueue,
                                       long pullOffsetOfOp, long miniOffset, Map<Long, HashSet<Long>> opMsgMap, List<Long> doneOpOffset) {

        //根据队列消费偏移量和最大可获取条目数，从OP队列中获取一批消息
        PullResult pullResult = pullOpMsg(opQueue, pullOffsetOfOp, OP_MSG_PULL_NUMS);
        if (null == pullResult) {
            return null;
        }
        //判断拉取消息的状态是否正常
        if (pullResult.getPullStatus() == PullStatus.OFFSET_ILLEGAL || pullResult.getPullStatus() == PullStatus.NO_MATCHED_MSG) {
            log.warn("The miss op offset={} in queue={} is illegal, pullResult={}", pullOffsetOfOp, opQueue, pullResult);
            transactionalMessageBridge.updateConsumeOffset(opQueue, pullResult.getNextBeginOffset());
            return pullResult;
        } else if (pullResult.getPullStatus() == PullStatus.NO_NEW_MSG) {
            //执行到这里意味着OP主题队列中已经没有消息了
            log.warn("The miss op offset={} in queue={} is NO_NEW_MSG, pullResult={}", pullOffsetOfOp, opQueue, pullResult);
            return pullResult;
        }
        //得到获取的这批消息
        List<MessageExt> opMsg = pullResult.getMsgFoundList();
        if (opMsg == null) {
            log.warn("The miss op offset={} in queue={} is empty, pullResult={}", pullOffsetOfOp, opQueue, pullResult);
            return pullResult;
        }
        //遍历这批消息，然后解析每一条消息的内容，消息的内容存储的就是已被决议的半消息在它的队列中的逻辑偏移量
        for (MessageExt opMessageExt : opMsg) {
            if (opMessageExt.getBody() == null) {
                log.error("op message body is null. queueId={}, offset={}", opMessageExt.getQueueId(), opMessageExt.getQueueOffset());
                doneOpOffset.add(opMessageExt.getQueueOffset());
                continue;
            }
            //用来存放当前OP消息存储的所有半消息偏移量的集合
            HashSet<Long> set = new HashSet<Long>();
            //解析得到遍历到的消息的消息体，这个消息体中可能存储了多个半消息的偏移量
            String queueOffsetBody = new String(opMessageExt.getBody(), TransactionalMessageUtil.CHARSET);
            log.debug("Topic: {} tags: {}, OpOffset: {}, HalfOffset: {}", opMessageExt.getTopic(), opMessageExt.getTags(), opMessageExt.getQueueOffset(), queueOffsetBody);
            //判断OP消息的标签，只要是被写入到OP主题队列中的消息，标签都是d，这个是默认的
            if (TransactionalMessageUtil.REMOVE_TAG.equals(opMessageExt.getTags())) {
                //标签正确则解析当前消息存储的所有半消息偏移量，把偏移量存放到数组中
                String[] offsetArray = queueOffsetBody.split(TransactionalMessageUtil.OFFSET_SEPARATOR);
                for (String offset : offsetArray) {
                    //遍历每一个半消息偏移量
                    //得到办消息的偏移量数值
                    Long offsetValue = getLong(offset);
                    //判断半消息偏移量是否小于传进来的半消息队列的最小偏移量
                    //小于的话就说明当前遍历的半消息已经被处理过了
                    if (offsetValue < miniOffset) {
                        continue;
                    }
                    //版消息没有被处理，则把半消息存放到removeMap中
                    //注意，removeMap中的key是半消息偏移量，value是存储半消息偏移量的OP队列消息的偏移量
                    removeMap.put(offsetValue, opMessageExt.getQueueOffset());
                    //把半消息的偏移量存放到set中
                    set.add(offsetValue);
                }
            } else {
                log.error("Found a illegal tag in opMessageExt= {} ", opMessageExt);
            }
            //如果set集合中有数据，那就意味着这条OP消息确实存储了半消息偏移量
            if (set.size() > 0) {
                //那就把当前OP消息的队列偏移量作为key，存储半消息偏移量的集合set作为value存放到opMsgMap中
                opMsgMap.put(opMessageExt.getQueueOffset(), set);
            } else {
                doneOpOffset.add(opMessageExt.getQueueOffset());
            }
        }
        log.debug("Remove map: {}", removeMap);
        log.debug("Done op list: {}", doneOpOffset);
        log.debug("opMsg map: {}", opMsgMap);
        return pullResult;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：判断指定的半消息是否超过了最大的回查次数，达到最大回查次数之后，半消息仍然没有被决议，那么这条消息就要被丢弃了
     */
    private boolean needDiscard(MessageExt msgExt, int transactionCheckMax) {
        //消息每被回查一次，它的回查次数属性就会加1，这里就得到了消息的回查次数
        String checkTimes = msgExt.getProperty(MessageConst.PROPERTY_TRANSACTION_CHECK_TIMES);
        int checkTime = 1;
        if (null != checkTimes) {
            //这里得到消息真正的回查次数，如果没有，那么回查次数就是默认1次
            checkTime = getInt(checkTimes);
            if (checkTime >= transactionCheckMax) {
                //超过最大回查次数意味着消息应该被丢弃了
                return true;
            } else {
                //没有超过则自增回查次数
                checkTime++;
            }
        }
        //更新消息回查次数属性
        msgExt.putUserProperty(MessageConst.PROPERTY_TRANSACTION_CHECK_TIMES, String.valueOf(checkTime));
        return false;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：判断消息是否应该被跳过的方法，如果这条半消息存在的时间过久，那就会认为这条消息可能已经过期了
     * 就不再处理了
     */
    private boolean needSkip(MessageExt msgExt) {
        long valueOfCurrentMinusBorn = System.currentTimeMillis() - msgExt.getBornTimestamp();
        if (valueOfCurrentMinusBorn > transactionalMessageBridge.getBrokerController().getMessageStoreConfig().getFileReservedTime() * 3600L * 1000) {
            log.info("Half message exceed file reserved time ,so skip it.messageId {},bornTime {}",
                    msgExt.getMsgId(), msgExt.getBornTimestamp());
            return true;
        }
        return false;
    }

}
```
