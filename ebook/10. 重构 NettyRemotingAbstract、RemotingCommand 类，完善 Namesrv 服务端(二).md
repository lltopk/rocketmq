好了，在简单回顾了上一章的内容之后，接下来我们就应该开始定义 RemotingCommand 消息对象的传输格式了。那这个传输格式该怎么定义呢？按照我们过去的编程经验，或者使用任何 RPC 框架的经验，我们应该很清楚：**客户端在给服务端发送一条消息时，要使用某种方式对这条消息进行序列化，然后计算序列化之后的字节长度，也就是消息长度，接着就可以把消息发送给服务端了；那服务端在接收客户端的消息时，肯定也要知道客户端发送过来的消息长度，只有知道客户端发送的消息的总长度，服务端才能获取到完整的消息，不至于解码到一半才发现接收到的消息并不完整，当然，服务端读取到完整的消息后，还需要知道客户端序列化消息的方式，然后才能对这条消息进行反序列化，最终得到还原后的消息**。这个流程大家应该都很熟悉了吧？这样分析下来，我们很容易就能发现：**客户端和服务端要想顺利通信，客户端在向服务端发送消息的时候，就应该发送消息的序列化方式，以及这条消息的总字节数，也就是长度告诉服务端**。这样一来，服务端才能顺利获得这条消息。这一点大家没有异议吧？



好了，现在让我们回到 RemotingCommand 消息对象中，上一章我已经为大家讲解了，Namesrv 客户端向服务端发送 RemotingCommand 消息时，会在一条 RemotingCommand 消息中封装请求头、请求体，然后把 RemotingCommand 消息对象发送给服务端(为了简化逻辑，我们暂且把消息的请求类型，也就是请求码，以及请求唯一标识给省略，后面重构消息发送格式时会重新加上)，请求头和请求体分别代表什么，这个我也为大家解释清楚了。**按照之前的分析来看，一条 RemotingCommand 消息的长度其实就是请求头加上请求体的长度，当然，序列化方式肯定也要发送给服务端**。如果一条已经序列化了的 RemotingCommand 消息的请求头和请求体总长度为 300 个字节，再加上需要额外补充的序列化方式，加入序列化方式为 4 个字节，那么客户端要发送给服务端的消息总长度就为 304 个字节，我们可以定义这样一种格式：那就是整条消息的前 4 个字节存放消息的序列化方式，后面的字节就是消息的真正内容。这样的话服务端就可以通过这条消息得到消息的序列化方式和消息内容本身了。



按照刚才那样分析当然没什么问题，但大家千万别忘了，还有最重要的消息总长度呢，客户端肯定要把自己发送的消息总长度告诉服务端呀，不然服务端不知道究竟要从消息缓冲区中读取多少字节才能读取到一条完整的消息。所以一条 RemotingCommand 消息序列化之后的总字节数也要存放在消息本身中发送给服务端，假如用 4 个字节存储一条 RemotingCommand 消息的总长度，那么现在要发送一条 RemotingCommand 消息给服务端，要发送的消息格式就成为了下面这样，请看下面代码块。

```java
|4字节消息总长度 |4字节序列化方式|消息本身| = 4 + 4 + 300 = 308字节
```

上面代码块展示的就是我们目前分析出来的一条 RemotingCommand 消息的发送格式，这个理解起来应该没什么难度吧？如果大家理解了 RemotingCommand 消息的发送格式，那我现在有一个问题想问问大家，在上面代码块中的 4 字节消息总长度中，这个 4 个字节应该用什么呢填充呢？我们都知道消息的总长度是 300 字节，那么就直接用 300 填充整条消息的前 4 个字节吗？稍微想一想就知道肯定不能这么做，原因很简单，**如果只用 300 填充 4 个字节的消息总长度，那么序列化方式就漏掉了**。这样一来，服务端接收到客户端发送过来的消息后读取了消息的前 4 个字节，发现消息总长度是 300 字节，于是只向后读取了 300 个字节的长度，300 个字节减去存放序列化信息的 4 个字节的长度，还剩下 296 个字节，但 RemotingCommand 消息的完整长度是 300 个字节，这样一来就漏掉了 4 个字节，这条消息显然就不完整了。所以，4 字节的消息总长度不应该只填冲消息的完整长度，还应该把消息的序列化方式填充进去，也就是说，4 字节的消息总长度应该被 304 填充。这个逻辑应该也能理解吧？



如果上面的逻辑大家都理解了，那么下面就让我再为大家补充一些信息，在上一章结尾我们仿照 RocketMq 源码为 RemotingCommand 类引入了一些额外的成员变量，比如协议版本号、使用的编程语言类型等等，实际上在源码中，客户端与服务端通信时，也会把这些信息封装到消息中一起发送给对方，在执行某些操作的时候，会用到这些信息。这一点在后面的代码中也会有所展示，现在我想跟大家进一步解释的是，当这些额外的信息也要随着消息发送时，客户端向服务端发送一条 RemotingCommand 消息的格式就发生了变化，或者说按照源码的方式来发送消息时，那么我们刚才定义的 RemotingCommand 消息发送格式就需要重构了。



实际上在源码中是这么做的，RocketMq 把要发送的 RemotingCommand 请求分成了两个部分，当然，之前我们分析的时候也是两部分，一部分是请求头，一部分是请求体；但现在加上了一些额外信息，**要发送的 RemotingCommand 消息就分成了消息头和请求体，其中消息头包含了附加的额外信息和请求头内容，当然还有非常重要的请求类型，现在我们就可以把 RemotingCommand 代表的请求类型添加回来了，至于请求体仍然是请求体**。就像下面展示的这样，请看下面代码块。

这些都很好理解吧？但我接下来要说的是，在 RocketMq 源码中把 RemotingCommand 消息的消息头和消息体的序列化分开了，实际上是这样的：**消息头包含的内容比较少，在 RocketMq 源码中提供了两种序列化消息头的方式，一种是 ROCKETMQ 模式，一种是 JSON 模式，用户配置了哪一种，就可以使用哪一种方式序列化消息头；至于消息体的序列化，现在大家可以先理解为消息体的序列化是固定的，也就是说不管是客户端还是服务端，都是用同一种方式对消息体进行序列化和反序列化，并且消息体在设置的那一刻就被序列化完成了，然后赋值给 RemotingCommand 对象的 body 成员变量，因此消息体的序列化信息不必随消息发送**。这样分析下来之后，要发送的消息格式就要发生一些变化了，因为消息头和消息体不会采用相同的序列化方式，那么消息头的长度以及消息头的序列化信息就要被填充到消息中，所以 RemotingCommand 消息的发送格式应该重构成下面这样，请看下面代码块。

```java
|4字节消息总长度|消息头长度信息和消息头序列化方式信息，这两个信息总共占用4字节|消息头+消息体，也就是消息本身| = 4 + 4 + 300 = 308字节
```

这样一来，**当服务端接收到客户端发送的一条消息之后，首先就会从消息的前 4 个字节中得到整条消息的长度，当然了，这个时候解析到的整条消息的长度除了包含消息总长度之外，肯定还包含了消息头长度和序列化方式那 4 个字节，也就是说，服务端读取到的消息总长度为 304 字节，然后又会读取第二个 4 字节，从这 4 个字节中得到消息头长度和消息头序列化方式，然后解析后 300 个字节，先从后 300 个字节中读取消息头长度，读取消息头的信息，然后反序列化得到消息头中包含的所有信息，接着让 300 字节减去消息头长度，这时候就得到了消息体，然后再反序列化消息体即可**。这就是 Namesrv 客户端和服务端通信的过程中，消息的传输和解析流程，大家可以再品味品味这个流程。

        int headerLength = getHeaderLength(oriHeaderLen);
        //判断消息头长度是否正确，不正确则抛出异常
        if (headerLength > length - 4) {
            throw new RemotingCommandException("decode error, bad header length: " + headerLength);

        int bodyLength = length - 4 - headerLength;

        if (bodyLength > 0) {
            bodyData = new byte[bodyLength];
            //从缓冲区中把有效消息的数据写入到字节数组中
            byteBuffer.readBytes(bodyData);
        }

        cmd.body = bodyData;
        return cmd;
