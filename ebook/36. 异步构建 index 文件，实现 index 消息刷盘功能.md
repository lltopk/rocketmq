

## 分析 index 文件存储数据的方式


朋友们，在上一章我们已经实现了消息重放功能，也就是对 CommitLog 文件夹中的消息进行解析，得到消息的关键信息之后，然后把这些关键信息封装为一条重放消息，再把重放消息写入到 ConsumeQueue 消息队列中。在实现这个功能的过程中，我们定义了一个重放消息线程对象，让这个线程对象负责消息重放工作。也许有朋友认为到这里消息重放的功能就全部实现完毕了，但我想说的是，在 RocketMq 源码中，消息重放其实包含了两部分内容，一部分是把 CommitLog 文件夹中解析后的消息存储到 ConsumeQueue 消费队列文件中，这样消费者客户端才能准确又迅速地从 Broker 节点消费消息；**而另一部分就是把消息的 key 信息存放到本地的 index 文件中，只要用户给消息定义了 key 信息，那么在线程重放消息的时候，就会从 CommtiLog 文件夹的消息中把消息的 key 信息解析出来，然后存放到本地的 index 文件中，这个操作也属于消息重放的范围**。至于为什么要存储消息的 key 信息，这个愿意按也很简单，有时候用户可能希望根据消息的 key，也就是消息的唯一标记迅速定位并从 Broker 节点得到这条消息，所以消息的 key 信息显然也要被存储起来，以便后续在查询消息的时候使用。



上一章我们只实现了消息重放的一部分功能，在这一章，我将紧接着上一章的内容，为大家实现 index 文件数据的重放功能。当然，在实现这个功能之前，照例还是先分析一下 index 文件中究竟要存储什么数据。我们都知道，生产者客户端在生产消息的时候，可能会给消息定义业务 key，可能会定义一个 key，也可能会定义一个 key 集合，总之，**用户希望能根据这个消息的 key 直接从 Broker 节点查询到这条消息本身。那消息的 key 信息显然是要存储到 index 文件中，如果消息有多个 key，那么这些 key 都要存储到 index 文件中**。当然，**我们最终希望的是能够根据消息的 key 定位到这条完整的消息，那么这条消息在 CommitLog 文件中的全局偏移量肯定也要被存储到 index 文件中吧**？也就是说，就目前分析的情况来看，**index 文件要存的每一条重放消息肯定要包含两部分内容，一部分是消息的 key 信息，另一部分就是消息在 CommitLog 文件中的全局偏移量**，这个逻辑大家可以理解吧？当消费者客户端需要根据消息的 key 来定位消息时，那么在 Broker 节点内部，就可以先从 index 本地文件中查看，看看 index 文件中的哪条重放消息包含了同样的 key，得到了包含相同 key 信息的重放消息后，再根据重放消息中的消息全局偏移量到 CommitLog 文件夹中定位对应的消息即可，这个逻辑大家应该也可以理解吧？都是前面章节已经讲解过的旧知识了。



当然，讲到这里，我相信大家肯定也意识到了，要把消息存储到本地的 index 文件夹中，那这个过程肯定还是用到了老一套功能，也就是内存映射机制。**而 index 文件实际上是一个文件夹，所有重放消息，不管是什么主题，都会存放到这个 index 文件夹中，文件夹中有多个本地文件，每一个文件都对应程序内部的一个 DefaultMappedFile 内存映射文件，重放消息会首先被写入到 DefaultMappedFile 内存映射文件的缓冲区中，然后被操作系统刷新到对应的本地文件中，如果一个本地文件写满了，那么就创建新的本地文件存储消息即可**。这些逻辑打击也能理解吧？因为我们在实现消费队列消息重放功能时就是这么做的，index 文件消息重放也是如此。



好了，看到这里，大家肯定会觉得本章内容非常简单，只需要按照刚才的思路，按部就班把 index 文件消息重放的功能从代码层面上实现即可，根据上一章的内容，我们已经知道了 CommitLog 中的消息被解析后的内容都会被封装到一个 DispatchRequest 请求中，在实现消费队列消息重放功能时，我们定义了一个 CommitLogDispatcherBuildConsumeQueue 重放消息分发器，这个分发器会接收 DispatchRequest 请求，把请求中的相关内容写入到对应的 ConsumeQueue 消费队列对象中；**那现在我们要实现 index 文件消息重放功能了，那我们不妨就再定义一个 index 消息分发器，就定义成 CommitLogDispatcherBuildIndex 类，它也是 DefaultMessageStore 的内部类，这个 CommitLogDispatcherBuildIndex 类的对象就会专门接收 DispatchRequest 请求，然后把 DispatchRequest 请求中的相关内容写入到 index 文件中**。当然，index 消息重放器接收请求只是个开始，得把这个请求交给真正的服务组件处理才行，就像 CommitLogDispatcherBuildConsumeQueue 消费队列消息重放器在接收到 DispatchRequest 请求后，会把请求交给 ConsumeQueueStore 消费队列管理器处理；那么 index 文件的消息重放器在接收到请求后，也要把请求交给 index 文件的相关组件处理才行。



这样分析下来，**我决定再定义一个新的类，就定义为 IndexService 类，这个类的对象就是 index 文件的服务组件，用来把 index 文件的重放消息存放到本地**。**我可以给这个类定义一个 buildIndex() 方法，这个方法就是专门用来接收 DispatchRequest 请求，并处理 DispatchRequest 请求的**；那除了 buildIndex() 方法，还可以给 IndexService 定义什么内容呢？我认为还有一个非常重要的成员变量需要定义，那就是一个文件集合，因为 index 重放消息肯定要写入到本地文件中啊，而 IndexService 对应的只是本地的 index 文件夹，这个文件夹中的本地文件才是真正存储数据的。而每一个本地文件都对应一个 DefaultMappedFile 内存映射文件，这就意味着 IndexService 内部会管理多个内存映射文件对象，所以我就定义一个文件集合好了。当然，我们也可以对 DefaultMappedFile 内存映射文件做一层包装，比如说我们可以定义一个 IndexFile 类，这个类内部持有 DefaultMappedFile 内存映射文件对象，这样一来，每一个 IndexFile 对象不就代表一个内存映射文件对象吗？至于为什么要对 DefaultMappedFile 内存映射文件做包装，大家可以先记住这个问题，再往下看就清楚了。

好了， 从上面两个代码块中，大家应该也清楚了 index 文件消息分配器 CommitLogDispatcherBuildIndex 的工作逻辑，只要这个消息分配器把消息 DispatchRequest 请求交给 IndexService 的 buildIndex() 方法之后，index 文件的重放消息怎么存储到本地就完全是 IndexService 对象的事了，所以接下来我们的重点就要来到 IndexService 类中，逐渐完善这个类的内容。



那面度现在的局面，我首先想到的就是当 IndexService 得到 DispatchRequest 请求对象之后应该做什么。这个很简单，**肯定就是从 DispatchRequest 请求中得到消息的关键信息，比如说消息的 key 信息，还有消息在 CommitLog 中的全局偏移量，然后再得到 IndexService 内部管理的最新的 IndexFile 文件，接下来把重放消息写入到 IndexFile 文件中即可**。这个逻辑很清晰吧？很好，终于进行到这一步了，到了这里，我们就要正式考虑如何存储消息了，换句话说，我们就要开始正式分析，index 重放消息在 IndexFile 本地文件中的存储格式。说个更具体一点，**那就是我们得明确 IndexFile 文件中的消息存储单元吧？重放消息的每个信息占用多少字节必须得明确吧？只有把重放消息变成定长的，那么当 IndexFile 中的消息被查询时，才知道每次读取多少字节就能得到一条完整的消息**。这个逻辑想必大家也很清楚了，那要把 IndexFile 文件中的存储单元定义为多少字节呢？



接下来我们就该认真思考一下了 IndexFile 文件的内容格式了，其实我早就有一个问题想跟大家讨论，那就是当我们把 index 的重放消息存储到 IndexFile 文件中后，或者说写入到 IndexFile 文件对应的内存映射缓冲区后，假如需要根据 key 从 IndexFile 文件中查询消息，应该怎么查询呢？**我们的目标是希望直接使用 key 就能定位到消息本身，确切地说，是直接使用 key 就定位到重放消息本身，然后再从重放消息中得到消息在 CommitLog 中的全局偏移量，然后再去 CommitLog 中根据全局偏移量查询消息的全部内容**。但不管我们给 IndexFile 文件的存储单元定义为多少字节，就目前来看，只要我们把重放消息存放到 IndexFile 文件中，那么要从 IndexFile 文件中根据 key 查询消息的时候，似乎只能读取 IndexFile 文件中的每一条消息，然后对比 key 是否相同，以此获得对应的重放消息。这显然是错误的执行流程，因为 IndexFile 文件存储的消息是不区分主题信息的，所有消息都存储在 Index 本地文件夹中，这就意味着有的消息的 key 和要查询的消息的 key 肯定不一致，那从 IndexFile 文件中读取 key 不一致的重放消息显然是在浪费时间啊。在消费队列中读取每一条重放消息是因为消费队列是按主题来存放重放消息的，只要主题和队列 Id 对应，那么消费队列文件中的所有消息都是要被消费的消息。那这种情况该怎么办呢？也就是说，怎么能根据 key 快速定位到 IndexFile 文件中的重放消息呢？而不是对比 IndexFile 文件中每一条消息来筛选过滤匹配正确的重放消息。



要解决这个问题其实很简单，只要找到正确的突破口。按照我们的理解，根据 key 迅速定位到对应的消息，这显然是传统的键值对数据结构能够提供的便利功能，也就是说定义一个 Map 就好了。但是我们现在要把数据写入到 IndexFile 文件中啊，并且很重放消息都会被写入到 IndexFile 文件中，那这个时候还怎么定义 Map 呢？根本没办法定义啊，总不能一个 key 对应一个 IndexFile 文件吧？那成千上万个 key 就要定义成千上万个 IndexFile 文件吗？这也太荒谬了，对吧？确实是这样，我们确实无法给文件定义 Map 数据结构，但是我们可以对文件中存储重放消息的格式进行设计。



现在请大家思考一下，假如说我们有一个 IndexFile 文件，这个文件最多只能存储 500 个字节，而 IndexFile 文件中的存储单元为 10 字节，这 10 个字节中前五个用来存储消息的 key 信息，当然，按照惯例，这里存储的肯定是 key 的哈希值，后五个字节存储的就是这条消息在 CommitLog 文件夹中的全局偏移量。这样一来，这个 IndexFile 文件最多就可以存储 50 条重放消息。这个理解起来没什么问题吧？很好，那现在来了一批重放消息，要存储到 IndexFile 文件中了，如果我们按照顺序把这些消息依次写入到 IndexFile 文件中，那么这个文件能存储 50 条重放消息，但根据 key 查询对应消息的时候，需要把 IndexFile 文件中的 50 条消息全部读取了，判断重放消息的 key 是否和要查找的消息的 key 匹配，这么做显然非常麻烦，我们现在要做的就是摒弃这种做法。很好，既然我们不想这么麻烦，那接下来我提出了一个设想，**那就是把总容量为 500 字节的 IndexFile 文件从内容上分成了两半，IndexFile 文件的前 20 字节并不存储重放消息了，后 480 字节才真正存储重放消息，这样一来，整个 IndexFile 文件只能存储 48 条重放消息了**。当然，看到这里大家肯定有一个疑问，那就是 IndexFile 文件的前 20 字节存储什么内容呢？不存储别的，**只存储重放消息在 IndexFile 文件后 480 字节的索引**。这就是我给出的设计答案。



我知道看了我刚才提出的解决问题的方法，很多朋友肯定更懵了，不用担心，接下来就让我为大家举一个非常直接的例子，阐述一下 IndexFile 文件前 20 字节存储的重放消息在 IndexFile 文件后 480 字节的索引究竟是什么意思。假如现在 IndexFile 本地文件是空的，有三条重放消息要写入到 IndexFile 文件中，每个消息的 key 都不相同，那这个时候我可以执行这样一个操作：先得到第一条重放消息的 key，然后计算 key 的哈希值，得到了 key 的哈希值之后，就用这个哈希值和 20 做 % 运算，得到一个数值为 3 的结果。那为什么是和 20 做运算呢？原因很简单，因为 IndexFile 文件前 20 个字节并不存储重放消息，**这空出来的 20 个字节就被我定义为了哈希槽**，每个哈希槽为 1 字节，刚才 key 的哈希值和 20 做运算得到的结果为 3，那么就可以找到 IndexFile 文件前 20 个字节的区域，也就是哈希槽的第 3 个槽位，在这个槽位存储数值 1，**表示当前要存储的重放消息是 IndexFile 文件后 480 字节，也就是消息重放区的第一条消息，既然是消息重放区的第一条消息，那么这条消息在消息重放区的偏移量就应该为 0，当然，我们也可以使用 1 作为第一条消息的偏移量(源码中使用的就是 1)，这样一来消息偏爱量和消息重放区消息的消息数量就一一对应了，如果是第二条消息，那么这条消息在消息重放区的偏移量就是 2，或者说索引就是 2；当然，真正的偏移量肯定还得再乘以存储单元**，就是存储单元 * 1，也就是 10，那这样一来，前面 20 个字节哈希槽加上刚刚计算出来的 10 偏移量，就得到了偏移量 30，这就意味着第一条重放消息要从 IndexFile 文件偏移量为 30 字节的位置开始写入。大家可以仔细品味这个逻辑，要知道 IndexFile 文件的哪部分是哈希槽区，哪部分是消息重放区，如果梳理清楚了，那么大家就明白了，**当把第一条重放消息放到一个空的 IndexFile 文件中时，那么在这个 IndexFile 文件的哈希槽区的第三个槽位，会记录这条重放消息在 IndexFile 文件消息重放区的索引，第一条消息的索引就是 1，第二条消息的索引就是 2，以此类推，而在 IndexFile 文件消息重放区的偏移量为 10 的位置，在 IndexFile 文件总偏移量为 30 的位置，会开始写入第一条重放消息，这条重放消息占用 10 个字节的空间**。大家可以仔细品味品味这个逻辑，然后结合我为大家提供的这幅简图，加深一下 IndexFile 文件存储重放消息的格式的理解，请看下面图片。

看了上面的图片之后，我相信大家对 IndexFile 文件存储重放消息的格式已经有所了解了，那么还是在我们提出的这个设想之上，假如现在要从 IndexFile 文件中根据 key 查询第一条重放消息，应该怎么查询呢？这个时候就很简单了，现在我们已经知道了 IndexFile 文件的存储单元为 10，并且整个 IndexFile 文件分为哈希槽区和消息重放区，要根据第一个消息的 key 查找第一条重放消息了，那就可以使用 key 的哈希值和哈希槽区的槽数，也就是 20 做 % 运算，得到哈希槽的位置，然后取出该位置的重放消息索引值，这个时候就得到了重放消息在消息重放区的索引，索引为 1，这就意味着它是 IndexFile 文件存储的第一条消息，也就是消息重放区存储的第一条消息，那接下来就很好做了，既然是第一条消息，那么 1 * 10 就得到了这条消息在消息重放区的偏移量，再加上前面的哈希槽区的 20 个字节，就得到了第一条重放消息在整个 IndexFile 文件中的偏移量，也就是 30，那么接下来就可以从 30 字节偏移量的位置读取第一条重放消息，读取 10 个字节就可以得到这条完整的重放消息，然后从这条重放消息中得到完整消息在 CommitLog 中的全局偏移量，再去 CommitLog 文件夹中得到指定消息的内容即可。大家可以仔细品味品味这个逻辑，一定要梳理清楚。



很好，现在第一条重放消息已经被写入到 IndexFile 文件中了，那接下来我们就可以根据之前写入第一条重放消息的逻辑，把第二条重放消息写入到 IndexFile 文件中。前面我们已经说过了，第二条重放消息的 key 和第一条消息不一致，要存放第二条消息，首先就要计算消息 key 的哈希值，然后用它的哈希值和哈希槽区的容量做 % 运算，假如运算后得到的结果是 2，这也就意味着要在 IndexFile 文件的哈希槽区的第二个槽位，把第二条重放消息的索引放在哈希槽区的第二个槽位中，第二条重放消息的索引当然是 2，所以就可以直接在 IndexFile 文件哈希槽区的第二个槽位存储 2 这个数值，然后就可以把这条重放消息写入到 IndexFile 文件的消息重放区了；那接下来就要计算第二条重放消息在 IndexFile 文件中的偏移量，直接让哈希槽区的总大小，加上消息在消息重放区的偏移量，也就是 2 * 10，就得到了值为 40 的偏移量，这样一来，就可以从 IndexFile 文件偏移量为 40 的位置，开始写入第二条重放消息了，第二条消息存放完毕后，IndexFile 文件存储的内容就变成了下面这样，请看下面图片。

![画板](https://cdn.nlark.com/yuque/0/2025/jpeg/26725125/1757481392144-34943fb0-9611-4967-89ba-cd96812d1c18.jpeg)

好了，当第二条重放消息存储完毕之后，假如要根据消息的 key 从 IndexFile 文件中查询第二条重放消息，那么就可以先计算 key 的哈希值，然后得到存储第二条消息索引的哈希槽位置，再从这个位置中得到第二条消息的索引，接着根据索引以及哈希槽区的总大小计算第二条重放消息在 IndexFile 文件中的整体偏移量，最后就可以从这个偏移量位置读取 10 个字节，得到完整的第二条重放消息了。当然，得到第二条重放消息之后，还要从消息内部得到完整消息在 CommitLog 文件中的全局偏移量，这样才能从 CommitLog 文件中定位并查询到到完整的消息。梳理到这个程度，我相信大家应该已经彻底理解了 IndexFile 文件存储重放消息和查询重放消息的逻辑。



总结下来其实就是这样：**重放消息其实就是按顺序写入 IndexFile 文件中的，每一条消息被写入的时候都有一个索引，而索引就是消息被写入的顺序值。但我们要做的是根据 key 从 IndexFile 文件中查询消息，而根据 key 查询的时候，我们并不知道这个消息是第几条消息，并不知道消息的索引，所以要把重放消息的索引值记录下来，也就是这条消息的 key 对应第几条消息的信息，也就是消息索引记录下来，这个索引就记录在哈希槽中**。这样一来，**消息的 key 就和重放消息的索引构成了一个键值对关系**，而得到了重放消息的索引就可以得到消息在 IndexFile 文件中的偏移量，而得到了偏移量则可以直接操作文件缓冲区，从内存映射文件缓冲区中读取消息，这样不就可以根据消息的 key 迅速定位并查询到每一条消息了吗？到此为止，IndexFile 文件存储重放消息的核心逻辑，我就为大家分析完毕了。



当然，看到这里大家肯定会有两个问题，第一个问题很简单，也很直接，那就是当重放消息不断被写入到 IndexFile 文件中时，怎么就知道当前写入的重放消息是第几条呢？我的意思是，**要记录当前存放的消息是第几条消息，肯定得有一个全局的消息序号，或者说消息索引记录器吧，用来记录当前 IndexFile 文件一共存储的多少条消息，每存储一条新的消息，就使用这个记录器为消息分配索引，当然，记录器的值肯定也要自增**。这样分析下来，第一个问题就被解决了。但第二个问题就稍微复杂一点了，那就是根据我们刚才的例子可以看到，一个 IndexFile 文件总大小为 500 字节，前 20 个字节为哈希槽，也就是说哈希槽可以记录 20 条消息在消息重放区的索引，但是消息重放区有 480 个字节，每个消息为定长 10 字节，那么消息重放区总共可以存储 48 条消息，但现在用来记录消息的哈希槽槽位只有 20 个，那多余的 28 条消息的索引该怎么记录呢？



这个时候其实就面临一个问题，**那就是不管我们给 IndexFile 文件的哈希槽区分配多少字节，就算分配 50 个字节，也就是有 50 个槽位，但成百上千的重放消息存放到同一个 IndexFile 文件中时，就算这些消息的 key 各不相同，但最后计算每个 key 的哈希值和 50 个槽位数量做 % 运算后，总会有结果相同的情况，这种情况其实我们也可以称为哈希冲突的情况**。如果成百上千条消息的 key 经过哈希计算后，有几条消息的哈希值结果一样，然后这些哈希值和 50 做 % 运算得到的结果肯定相同，这种情况是我们常见的哈希冲突的情况。但是，我们目前面临的结果是，这两种哈希冲突的情况都有可能出现，哈希槽的位数是有限的，但消息的数量可能远多于哈希槽的数量，那么不同的 key 都和 50 做 % 运算，肯定会得到一些相同的结果；或者某些消息的 key 是一样的，这种情况下这些消息得到的哈希槽结果肯定也是一致的。比如说第一条重放消息和第三条、第五条重放消息的哈希槽位置一样，经过计算后，都要在第二个哈希槽存放各自消息的索引，那这个时候该怎么办呢？



这个时候就要想想 HashMap 是怎么解决哈希冲突问题了，如果是 HashMap 遇到哈希冲突，那么直接在同一个位置使用链表或者红黑树连接各个数据，这个知识大家肯定很熟悉吧？那会到 IndexFile 文件中，如果第 1、3、5 条重放消息都定位到第二个哈希槽记录重放消息索引，那我们是不是可以在第二个哈希槽处定义一个链表，记录这三条消息的消息重放区的索引呢？当然可以这么做，实际上，RocketMq 源码中也就是这么做的，当然，在源码中并不是直接在哈希槽定义了链表，而是给 IndexFile 文件的存储单元做了一个设计，巧妙的构建了一个索引链表。



实际上是这样的，**在 RocketMq 源码中给 IndexFile 文件的消息存储单元定义为了 20 字节，这 20 个字节中的最后 4 个字节存储的就是上一条哈希槽位置相同的重放消息的索引**，我这么说大家可能根本不理解是什么意思，接下来让我为大家举一个具体的例子讲解一下。**首先我们先把 IndexFile 文件存储单元存储的内容明确了，根据源码来看，存储单元为 20 个字节，前 4 个字节存储的是消息 key 的哈希值，后 8 个字节存储的是消息在 CommitLog 中的全局偏移量，再往后的 4 个字节存储的是当前这条重放消息的存储时间和当前 IndexFile 文件存储的第一条重放消息的存储时间的差值，这个差值的作用大家先不必关心，也不用在意，等后面实现具体代码的时候大家就清楚是怎么回事了，反正这个也不是重点；很好，还剩下最后 4 个字节，而最后 4 个字节存储的就是当前重放消息所定位的哈希槽记录的上一条重放消息的索引**。这样分析下来，IndexFile 文件存储单元的具体格式就变成了下面代码块中展示的这样，请看下面代码块。

```java
//消息索引的大小，实际上就是索引文件存储消息key的存储单元大小
//一共是20个字节
//┌───────────────┬───────────────────────────────┬───────────────┬
//│ Key HashCode  │ Physical Offset   │ Time Diff │ Next Index Pos│
//│ (4 Bytes)     │ (8 Bytes)         │ (4 Bytes) │ (4 Bytes) │
//├───────────────┴───────────────────────────────┴───────────────┴
//从上图可以看到，前4个字节存储的是消息的key的哈希值，后面8个字节是这条消息在CommitLog文件中的全局偏移量，后面4个字节是这条消息
//存储的时间和索引文件中第一条消息存储时间的差值，如果差值小于0则意味着该索引条目无效
//最后4个字节存储的是哈希槽中上一条消息的索引，现在大家可能还不清楚这一切是什么意思，别着急，再往下看就全明白了
```

好了，存储单元的格式梳理清楚了，接下来就可以使用具体的例子解释了，假如现在有一个空的 IndexFile 文件，这个文件哈希槽区的槽位一共有 20 个，消息重放区为 480 字节，存储单元变成了 20 字节，也就意味着这个 IndexFile 文件总共可以存储 24 条消息。现在有 10 条重放消息要存储到这个 IndexFile 文件中，经过计算之后，发现简直是太巧了，第 1、2、3 条重放消息的 key 和哈希槽执行 % 运算之后结果都是一样的，得到的结果是 2，也就是说，这三条消息都要定位到哈希槽区的第 2 个槽位，把自己在消息重放区的索引记录到哈希槽 2 的位置。这三条消息的索引都很好说，因为是按存储顺序来定义的，那索引自然就对应它们的顺序，分别是 1、2、3，存储肯定也是按照顺序来，那么第一条消息先被写入到 IndexFile 文件中，这个时候 IndexFile 文件中的内容就变成了下面这样，请看下面图片。

到此为止，大家应该就清楚了在 IndexFile 文件中存储重放消息的全部逻辑了吧，这部分内容讲解完毕，也就意味着本章核心内容结束了，剩下的都是非常简单内容，无非就是展示一下代码，梳理一下流程而已。当然，我还得再补充一句，如果 IndexFile 文件中哈希冲突的情况非常多，哈希冲突非常严重，那么查询 IndexFile 文件中的重放消息效率肯定会特别低，这一点大家可以立即吧？所以我们要要尽量避免哈希冲突，那怎么避免哈希冲突呢？答案很简单，无非就是扩大 IndexFile 文件中哈希槽区的槽数，**所以在 RocketMq 源码中是这么设计的，每一个 IndexFile 文件的哈希槽被定义了 500 万个槽位，而 IndexFile 文件的消息重放区则做多可存放 2千万条消息**，在我提供的代码中，大家就会看到这些设定了。



即然我们又一次说到 RocketMq 源码，那么索性就一次补充完整，实际上在 RocketMq 中，IndexFile 文件并非只有哈希槽区和消息重放区，其实 IndexFile 文件被分成了三部分，第一部分是文件头，第二部分是哈希槽区，第三部分才是消息重放区，文件头记录的是当前的 IndexFile 文件的一些元信息，比如该文件存储的第一条消息的 CommitLog 存储时间戳，存储的最后一条消息的 CommitLog 存储时间戳，每一条消息被存储到 CommitLog 文件的时候都会有一个存储时间戳，而在执行消息重放操作时，这个时间戳就会被封装到 DispatchRequest 请求中，根据这个时间戳可以判断要存储到 IndexFile 文件中的消息是否已经过期，如果消息的存储时间戳小于 IndexFile 文件第一条消息的存储时间戳，那么当前要被重放的消息显然就过期了，不需要对其执行重放操作。当然，除了消息时间戳，IndexFile 文件的文件头还定义了 IndexFile 文件存储的消息的数量，以及第一条和最后一条消息在 CommitLog 文件中的全局偏移量等等信息；这些内容我就不具体展开了，大家阅读我提供的第十七版本代码时就全清楚了。还有一点要补充的是，**IndexFile 文件的文件头要被写入到 IndexFile 对应的内存映射文件缓冲区的头部，然后才是哈希槽区，最后是消息重放区，所以在根据消息索引计算重放消息在 IndexFile 文件的整体偏移量时，不仅要把哈希槽的容量加上，还要把文件头的大小也加上**。在源码中，文件头总大小为 40 字节，接下来就让我把文件头，也就是 IndexHeader 类的内容展示给大家，请看下面代码块。

```java
package org.apache.rocketmq.store.index;


/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/7/14
 * @方法描述：封装索引文件的头部信息的类
 */
public class IndexHeader {

    //文件头大小
    public static final int INDEX_HEADER_SIZE = 40;

    //存储的第一条消息的时间戳在文件缓冲区中的写入和读取位置
    private static int beginTimestampIndex = 0;

    //存储的最后一条消息的时间戳在文件缓冲区中的写入和读取位置
    private static int endTimestampIndex = 8;

    //存储的第一条消息在CommitLog的全局偏移量在文件缓冲区中的写入和读取位置
    private static int beginPhyoffsetIndex = 16;

    //存储的最后一条消息在CommitLog的全局偏移量在文件缓冲区中的写入和读取位置
    private static int endPhyoffsetIndex = 24;

    //哈希槽使用数量在文件缓冲区中的写入和读取位置
    private static int hashSlotcountIndex = 32;

    //索引文件存储的索引条目在文件缓冲区中的写入和读取位置
    private static int indexCountIndex = 36;

    //内存映射文件缓冲区，因为文件头其实就是IndexFile对象的成员变量
    //这个byteBuffer其实就是IndexFile对象内部mappedByteBuffer内存映射
    //缓冲区的副本视图而已
    private final ByteBuffer byteBuffer;

    private final AtomicLong beginTimestamp = new AtomicLong(0);

    private final AtomicLong endTimestamp = new AtomicLong(0);

    private final AtomicLong beginPhyOffset = new AtomicLong(0);

    private final AtomicLong endPhyOffset = new AtomicLong(0);

    private final AtomicInteger hashSlotCount = new AtomicInteger(0);

    //消息索引被初始化为1，也就是说第一条被写入的消息的索引直接就是1，而不是0，这一点大家要注意
    private final AtomicInteger indexCount = new AtomicInteger(1);

    public IndexHeader(final ByteBuffer byteBuffer) {
        this.byteBuffer = byteBuffer;
    }


    //把文件头的数据写入到IndexFile本地文件中的方法
    //在执行数据刷新操作时，就会先调用这个方法，首先把文件头的数据写入到本地文件
    //然后再刷新后面的重放消息的数据
    public void updateByteBuffer() {

        this.byteBuffer.putLong(beginTimestampIndex, this.beginTimestamp.get());
        this.byteBuffer.putLong(endTimestampIndex, this.endTimestamp.get());
        this.byteBuffer.putLong(beginPhyoffsetIndex, this.beginPhyOffset.get());
        this.byteBuffer.putLong(endPhyoffsetIndex, this.endPhyOffset.get());
        this.byteBuffer.putInt(hashSlotcountIndex, this.hashSlotCount.get());
        this.byteBuffer.putInt(indexCountIndex, this.indexCount.get());
    }

    //其他get、set方法省略

}
```

接下来就该重构 IndexService 类了，这个类的重构逻辑非常简单，**当该类的 buildIndex() 方法要执行重放消息的操作时，无非就是找到最新的 IndexFile 文件，如果整个 Index 文件夹中还没有文件，或者最新的 IndexFile 文件已经写满数据了，那就创建新的 IndexFile 文件，然后把重放消息写入到 IndexFile 文件中即可**。这就是 IndexService 类重构的核心逻辑，当然还有一些具体的细节需要注意，但我就不在文章中讲解了代码的注释非常详细，所有细节问题我都写在代码注释中了，大家只需要按照顺序阅读以下代码块中的内容，就能掌握 IndexService 类的全部内容，请看下面代码块。

```java
package org.apache.rocketmq.store.index;


/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/7/14
 * @方法描述：索引数据服务组件
 */
public class IndexService {

    private static final Logger LOGGER = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //创建索引文件的最大尝试次数
    private static final int MAX_TRY_IDX_CREATE = 3;

    //默认消息存储引擎
    private final DefaultMessageStore defaultMessageStore;

    //索引文件可以使用的最大哈希槽数量
    private final int hashSlotNum;

    //索引文件可以存储的最大条目数
    private final int indexNum;

    //索引文件存储路径
    private final String storePath;

    //索引文件集合
    private final ArrayList<IndexFile> indexFileList = new ArrayList<>();

    private final ReadWriteLock readWriteLock = new ReentrantReadWriteLock();

    //构造方法
    public IndexService(final DefaultMessageStore store) {
        this.defaultMessageStore = store;
        this.hashSlotNum = store.getMessageStoreConfig().getMaxHashSlotNum();
        this.indexNum = store.getMessageStoreConfig().getMaxIndexNum();
        this.storePath = StorePathConfigHelper.getStorePathIndex(defaultMessageStore.getMessageStoreConfig().getStorePathRootDir());
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：把消息存放到索引文件中的方法
     */
    public void buildIndex(DispatchRequest req) {
        //尝试得到一个可用的索引文件
        IndexFile indexFile = retryGetAndCreateIndexFile();
        if (indexFile != null) {
            //成功获取到了索引文件之后，得到该索引文件存储的最后一条消息的物理偏移量，也就是这条消息在CommitLog文件中的全局偏移量
            long endPhyOffset = indexFile.getEndPhyOffset();
            DispatchRequest msg = req;
            //得到要存储的消息的主题
            String topic = msg.getTopic();
            //得到消息的key集合
            String keys = msg.getKeys();
            //判断当前要存储的消息在CommitLog文件中的全局偏移量是否小于索引文件的最新消息全局偏移量
            //如果小于则意味着这条消息过期了，不用存储，直接退出当前方法即可
            if (msg.getCommitLogOffset() < endPhyOffset) {
                return;
            }
            //得到消息的事务类型
            final int tranType = MessageSysFlag.getTransactionValue(msg.getSysFlag());
            //根据事务类型决定是否构建索引
            switch (tranType) {
                case MessageSysFlag.TRANSACTION_NOT_TYPE:
                case MessageSysFlag.TRANSACTION_PREPARED_TYPE:
                case MessageSysFlag.TRANSACTION_COMMIT_TYPE:
                    break;
                //以上三种类型消息都会正常存储消息
                //事务回滚消息则不存储，直接退出当前方法
                case MessageSysFlag.TRANSACTION_ROLLBACK_TYPE:
                    return;
            }
            //判断消息的唯一键是否不为空，这里可以看到，不止消息的业务key会被写入IndexFile文件中
            //唯一key也会被写入IndexFile文件中，这也就意味着，根据消息唯一key，也可以立刻查询到该消息
            if (req.getUniqKey() != null) {
                //不为空则使用消息唯一键和主题构建key，然后把消息存储索引文件
                indexFile = putKey(indexFile, msg, buildKey(topic, req.getUniqKey()));
                if (indexFile == null) {
                    //存储失败则记录错误日志
                    LOGGER.error("putKey error commitlog {} uniqkey {}", req.getCommitLogOffset(), req.getUniqKey());
                    return;
                }
            }
            //判断消息是否拥有key
            if (keys != null && keys.length() > 0) {
                //如果有则分割key字符串，得到key数组
                String[] keyset = keys.split(MessageConst.KEY_SEPARATOR);
                //遍历所有key
                for (int i = 0; i < keyset.length; i++) {
                    //得到当前便利的key
                    String key = keyset[i];
                    //判断key是否有效
                    if (key.length() > 0) {
                        //使用主题和key构建新的key，然后把消息存储到索引文件中
                        indexFile = putKey(indexFile, msg, buildKey(topic, key));
                        if (indexFile == null) {
                            //存储失败则记录错误日志
                            LOGGER.error("putKey error commitlog {} uniqkey {}", req.getCommitLogOffset(), req.getUniqKey());
                            return;
                        }
                    }
                }
            }
        } else {//没有获取可以存储消息的索引文件则记录错误日志
            LOGGER.error("build index error, stop building index");
        }
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：把消息存放到索引文件中的方法
     */
    private IndexFile putKey(IndexFile indexFile, DispatchRequest msg, String idxKey) {
        //在这里把消息放到索引文件中
        for (boolean ok = indexFile.putKey(idxKey, msg.getCommitLogOffset(), msg.getStoreTimestamp()); !ok; ) {
            //存放失败则记录文件已满的日志信息
            LOGGER.warn("Index file [" + indexFile.getFileName() + "] is full, trying to create another one");
            //尝试获取或创建新的索引文件
            indexFile = retryGetAndCreateIndexFile();
            //新的索引文件创建失败则直接返回null
            if (null == indexFile) {
                return null;
            }
            //再次存储消息到索引文件中，再次失败会再次循环
            ok = indexFile.putKey(idxKey, msg.getCommitLogOffset(), msg.getStoreTimestamp());
        }
        //存储成功则返回索引文件本身
        return indexFile;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：重新获取或者创建新的索引文件的方法
     */
    public IndexFile retryGetAndCreateIndexFile() {
        IndexFile indexFile = null;
        //在循环中创建索引文件，循环次数为最大重试次数
        for (int times = 0; null == indexFile && times < MAX_TRY_IDX_CREATE; times++) {
            //获取最新索引文件，获取失败则创建新的索引文件
            indexFile = this.getAndCreateLastIndexFile();
            //获取成功直接退出循环
            if (null != indexFile) {
                break;
            }
            try {
                //获取失败则记录尝试创建索引文件次数的日志信息
                LOGGER.info("Tried to create index file " + times + " times");
                //等待1秒后再次尝试
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                LOGGER.error("Interrupted", e);
            }
        }
        //循环结束仍没有成功创建索引文件
        if (null == indexFile) {
            //那就给消息存储引擎设置索引文件状态错误的标志
            this.defaultMessageStore.getRunningFlags().makeIndexFileError();
            LOGGER.error("Mark index file cannot build flag");
        }
        return indexFile;
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：获取最新索引文件，获取失败则创建新的索引文件的方法
     */
    public IndexFile getAndCreateLastIndexFile() {
        //记录当前得到的索引文件的变量
        IndexFile indexFile = null;
        //记录上一个索引文件的变量
        IndexFile prevIndexFile = null;
        //记录上一个索引文件的结束物理偏移量
        long lastUpdateEndPhyOffset = 0;
        //记录上一个索引文件存储最后消息的时间戳
        long lastUpdateIndexTimestamp = 0;
        {
            //获取读锁
            this.readWriteLock.readLock().lock();
            //判断索引文件集合是否不为空
            if (!this.indexFileList.isEmpty()) {
                //如果不为空则先获取最后一个索引文件
                IndexFile tmp = this.indexFileList.get(this.indexFileList.size() - 1);
                //判断最后一个索引文件是否写满了
                if (!tmp.isWriteFull()) {
                    //没有写满则可以直接返回
                    indexFile = tmp;
                } else {
                    //如果写满了，则要创建新的索引文件，这里得到旧的索引文件的的结束物理偏移量和存储最后消息的时间戳
                    lastUpdateEndPhyOffset = tmp.getEndPhyOffset();
                    lastUpdateIndexTimestamp = tmp.getEndTimestamp();
                    //记录旧的索引问文件
                    prevIndexFile = tmp;
                }
            }
            //释放读锁
            this.readWriteLock.readLock().unlock();
        }
        if (indexFile == null) {
            try {
                //得到要创建的新的索引文件名称
                String fileName = this.storePath + File.separator + UtilAll.timeMillisToHumanString(System.currentTimeMillis());
                //创建新的索引文件，索引文件的起始物理偏移量和起始时间戳要根据上一个文件的结束物理偏移量和存储最后消息的时间戳来初始化
                //保证索引文件存储数据的连续性
                indexFile = new IndexFile(fileName, this.hashSlotNum, this.indexNum, lastUpdateEndPhyOffset, lastUpdateIndexTimestamp);
                //得到写锁
                this.readWriteLock.writeLock().lock();
                //把新创建的索引文件加入到集合中
                this.indexFileList.add(indexFile);
            } catch (Exception e) {
                LOGGER.error("getLastIndexFile exception ", e);
            } finally {
                //释放写锁
                this.readWriteLock.writeLock().unlock();
            }
            if (indexFile != null) {
                //索引文件创建成功了，则需要把上一个索引文件的数据刷新到硬盘
                //这里得到上一个索引文件
                final IndexFile flushThisFile = prevIndexFile;
                //创建新的线程
                Thread flushThread = new Thread(new AbstractBrokerRunnable(defaultMessageStore.getBrokerConfig()) {
                    @Override
                    public void run0() {
                        //在新线程中执行索引文件刷新数据的操作
                        IndexService.this.flush(flushThisFile);
                    }
                }, "FlushIndexFileThread");
                //设置线程为守护线程
                flushThread.setDaemon(true);
                //启动刷盘线程
                flushThread.start();
            }
        }
        //返回创建的新文件，创建失败则返回null
        return indexFile;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：把索引文件数据刷新到硬盘的方法
     */
    public void flush(final IndexFile f) {
        if (null == f) {
            return;
        }
        long indexMsgTimestamp = 0;
        //判断文件是否写满
        if (f.isWriteFull()) {
            indexMsgTimestamp = f.getEndTimestamp();
        }//在这里执行刷新操作
        f.flush();
        if (indexMsgTimestamp > 0) {
            this.defaultMessageStore.getStoreCheckpoint().setIndexMsgTimestamp(indexMsgTimestamp);
            this.defaultMessageStore.getStoreCheckpoint().flush();
        }
    }


    //启动索引文件服务的方法
    public void start() {
       //源码中该方法就是空方法
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：关闭索引服务的方法
     */
    public void shutdown() {
        try {
            this.readWriteLock.writeLock().lock();
            for (IndexFile f : this.indexFileList) {
                try {
                    f.shutdown();
                } catch (Exception e) {
                    LOGGER.error("shutdown " + f.getFileName() + " exception", e);
                }
            }
            this.indexFileList.clear();
        } catch (Exception e) {
            LOGGER.error("shutdown exception", e);
        } finally {
            this.readWriteLock.writeLock().unlock();
        }
    }

    //其他内容暂时省略
}
```

```java
package org.apache.rocketmq.store.index;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/7/14
 * @方法描述：索引文件实现类
 */
public class IndexFile {

    private static final Logger log = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //每个哈希槽的大小
    private static int hashSlotSize = 4;

    //消息索引的大小，实际上就是索引文件存储消息key的存储单元大小
    //一共是20个字节
    //┌───────────────┬───────────────────────────────┬───────────────┬───────────────┐
    //│ Key HashCode  │ Physical Offset   │ Time Diff │ Next Index Pos│
    //│ (4 Bytes)     │ (8 Bytes)         │ (4 Bytes) │ (4 Bytes) │
    //├───────────────┴───────────────────────────────┴───────────────┴───────────────┤
    //从上图可以看到，前4个字节存储的是消息的key的哈希值，后面8个字节是这条消息在CommitLog文件中的全局偏移量，后面4个字节是这条消息
    //存储的时间和索引文件中第一条消息存储时间的差值，如果差值小于0则意味着该索引条目无效
    //最后4个字节存储的是哈希槽中上一条消息的索引，现在大家可能还不清楚这一切是什么意思，别着急，往下看到putKey方法就全明白了
    private static int indexSize = 20;

    //哈希槽存储的无效索引
    private static int invalidIndex = 0;

    //哈希槽总数量，默认是5000000，也就是五百万个
    private final int hashSlotNum;

    //索引文件可以存储的索引条目数量，默认是2千万个
    private final int indexNum;

    //当前索引文件的容量，这个容量就等于索引文件头大小+所有哈希槽大小+存储的所有索引条目大小
    private final int fileTotalSize;

    //内存映射文件
    private final MappedFile mappedFile;

    //内存映射缓冲区
    private final MappedByteBuffer mappedByteBuffer;

    //索引文件头
    private final IndexHeader indexHeader;


    //构造方法
    public IndexFile(final String fileName, final int hashSlotNum, final int indexNum,
                     final long endPhyOffset, final long endTimestamp) throws IOException {
        //在这里计算索引文件的总大小，总大小就是文件头大小+所有哈希槽大小+存储的所有索引条目大小
        this.fileTotalSize = IndexHeader.INDEX_HEADER_SIZE + (hashSlotNum * hashSlotSize) + (indexNum * indexSize);
        //创建内存映射文件
        this.mappedFile = new DefaultMappedFile(fileName, fileTotalSize);
        //得到内存映射缓冲区
        this.mappedByteBuffer = this.mappedFile.getMappedByteBuffer();
        //得到哈希槽数量
        this.hashSlotNum = hashSlotNum;
        //得到索引条目总数量
        this.indexNum = indexNum;
        ByteBuffer byteBuffer = this.mappedByteBuffer.slice();
        //创建文件头，在刷新数据的时候会先把文件头的数据刷新到文件中，然后才是后面的所有数据
        this.indexHeader = new IndexHeader(byteBuffer);
        if (endPhyOffset > 0) {
            //在创建新的索引文件时，如果这个索引文件并不是文件队列中的第一个文件，则需要获取前一个索引文件的末尾物理偏移量
            //因为索引文件存储的消息的物理偏移量是递增的，所以当前索引文件的开始物理偏移量就是前一个索引文件的结束物理偏移量
            //所谓开始偏移量就是当前索引文件存储的第一条消息在CommitLog文件中的全局偏移量
            this.indexHeader.setBeginPhyOffset(endPhyOffset);
            this.indexHeader.setEndPhyOffset(endPhyOffset);
        }
        if (endTimestamp > 0) {
            //设置新的索引文件的开始存储消息的时间戳，大家可以看到，不管是上面的物理偏移量还是存储消息时间戳
            //都是设置到文件头中，这就表示索引文件头中持有了索引文件的元数据
            this.indexHeader.setBeginTimestamp(endTimestamp);
            this.indexHeader.setEndTimestamp(endTimestamp);
        }
    }




    //终止服务的方法
    public void shutdown() {
        //这里可以看到，在关闭索引服务之前会把索引文件的数据刷新到硬盘
        this.flush();
        UtilAll.cleanBuffer(this.mappedByteBuffer);
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：刷新索引文件数据到本地硬盘的操作
     */
    public void flush() {
        long beginTime = System.currentTimeMillis();
        //得到资源锁
        if (this.mappedFile.hold()) {
            //先把文件头的数据更新到索引文件缓冲区中
            this.indexHeader.updateByteBuffer();
            //在这里执行刷盘操作
            this.mappedByteBuffer.force();
            //释放资源锁
            this.mappedFile.release();
            log.info("flush index file elapsed time(ms) " + (System.currentTimeMillis() - beginTime));
        }
    }


    //判断索引文件是否写满的方法
    public boolean isWriteFull() {
        return this.indexHeader.getIndexCount() >= this.indexNum;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：向索引文件存放数据的方法，方法参数key表示用户为消息定义的key，phyOffset表示消息在在CommitLog文件中的全局偏移量，storeTimestamp表示消息的存储时间戳
     */
    public boolean putKey(final String key, final long phyOffset, final long storeTimestamp) {
        //判断当前索引文件是否已经写满了，当前文件存储的消息条目数量就存储在文件头中
        //如果没写满，才执行下面的操作，写满就返回false
        if (this.indexHeader.getIndexCount() < this.indexNum) {
            //计算消息key的哈希值
            int keyHash = indexKeyHashMethod(key);
            //哈希值和哈希槽总数取模得到要存储消息索引的哈希槽的位置，所谓消息索引就是要存储的这条消息在索引文件的索引区中的位置
            int slotPos = keyHash % this.hashSlotNum;
            //slotPos * hashSlotSize得到的是刚才定位到的哈希槽索引在哈希槽区的偏移量
            //再加上文件头的大小就得到了哈希槽位置在索引文件中的具体偏移量
            int absSlotPos = IndexHeader.INDEX_HEADER_SIZE + slotPos * hashSlotSize;
            try {//根据这个偏移量从缓冲区中得到这个哈希槽目前存储的文件索引
                //这里我要解释一下，假如有两个消息的key的哈希值一样了，这就意味着发生了哈希冲突，那么就会以链表的方式来存储数据
                //大家想象一下hashmap存储数据的结构即可，这里就会根据得到的值判断当前哈希槽是否存储了有效数据
                int slotValue = this.mappedByteBuffer.getInt(absSlotPos);
                if (slotValue <= invalidIndex || slotValue > this.indexHeader.getIndexCount()) {
                    //如果存储的数据无效则把哈希槽置置为无效
                    //如果有效那么刚才得到的slotValue就是之前已经存储在索引文件的消息的索引值
                    slotValue = invalidIndex;
                }//计算消息存储时间与索引文件开始存储消息时间的差值
                long timeDiff = storeTimestamp - this.indexHeader.getBeginTimestamp();
                //转换为毫秒
                timeDiff = timeDiff / 1000;
                //调整时间差边界
                if (this.indexHeader.getBeginTimestamp() <= 0) {
                    timeDiff = 0;
                } else if (timeDiff > Integer.MAX_VALUE) {
                    timeDiff = Integer.MAX_VALUE;
                } else if (timeDiff < 0) {
                    timeDiff = 0;
                }
                //这里就是文件头大小+哈希槽总大小+当前已经存储的索引条目的总大小，这里得到的就是要存储的消息索引条目在索引文件中的起始偏移量
                int absIndexPos = IndexHeader.INDEX_HEADER_SIZE + this.hashSlotNum * hashSlotSize + this.indexHeader.getIndexCount() * indexSize;
                //从起始偏移量开始存储数据，先把消息key的哈希值写入缓冲区
                this.mappedByteBuffer.putInt(absIndexPos, keyHash);
                //再写入消息在CommitLog文件中的全局偏移量
                this.mappedByteBuffer.putLong(absIndexPos + 4, phyOffset);
                //再写入消息的存储时间差
                this.mappedByteBuffer.putInt(absIndexPos + 4 + 8, (int) timeDiff);
                //这里一步非常关键，这里把哈希槽存储的上一条消息的索引位置写入了当前消息条目中
                //这一以来，只要根据哈希槽存储的现在的消息索引，就能定位到现在要查询的消息，而找到了现在要查询的条目，就可以根据最后四个字节
                //定位到key哈希值一致的上一条消息的索引位置，就可以找到上一条key哈希值相同的消息，这样一来就构成了一个完整的链表
                this.mappedByteBuffer.putInt(absIndexPos + 4 + 8 + 4, slotValue);
                //在这里把当前消息定位到的哈希槽的值更新了，更新得值就是当前消息在索引文件中的索引，也就是当前消息在索引文件的索引区是第几条消息的信息
                this.mappedByteBuffer.putInt(absSlotPos, this.indexHeader.getIndexCount());
                if (this.indexHeader.getIndexCount() <= 1) {
                    //如果目前要写入消息的索引文件中还没有数据，则将索引条目的起始物理偏移量设置为当前消息的CommitLog文件的全局偏移量
                    //注意，因为indexCount初始化就是1，所以当indexHeader.getIndexCount() <= 1，说明索引文件中并没有数据
                    this.indexHeader.setBeginPhyOffset(phyOffset);
                    //消息存储的起始时间也设为当前消息的存储时间
                    this.indexHeader.setBeginTimestamp(storeTimestamp);
                }
                if (invalidIndex == slotValue) {
                    //如果哈希槽值为空，增加哈希槽使用数
                    this.indexHeader.incHashSlotCount();
                }//在这里增加文件头记录的索引文件存储的消息条目数
                this.indexHeader.incIndexCount();
                //把当前存储消息在CommitLog文件的全局偏移量设置到文件头中
                this.indexHeader.setEndPhyOffset(phyOffset);
                //更新文件头最新消息的存储时间
                this.indexHeader.setEndTimestamp(storeTimestamp);
                return true;
            } catch (Exception e) {
                log.error("putKey exception, Key: " + key + " KeyHashCode: " + key.hashCode(), e);
            }
        } else {
            log.warn("Over index file capacity: index count = " + this.indexHeader.getIndexCount()
                    + "; index max num = " + this.indexNum);
        }
        return false;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：计算key的哈希值的方法
     */
    public int indexKeyHashMethod(final String key) {
        int keyHash = key.hashCode();
        int keyHashPositive = Math.abs(keyHash);
        if (keyHashPositive < 0) {
            keyHashPositive = 0;
        }
        return keyHashPositive;
    }


    public long getBeginTimestamp() {
        return this.indexHeader.getBeginTimestamp();
    }


    public long getEndTimestamp() {
        return this.indexHeader.getEndTimestamp();
    }


    public long getEndPhyOffset() {
        return this.indexHeader.getEndPhyOffset();
    }


    //判断指定时间范围内是否有索引条目的方法
    public boolean isTimeMatched(final long begin, final long end) {
        boolean result = begin < this.indexHeader.getBeginTimestamp() && end > this.indexHeader.getEndTimestamp();
        result = result || (begin >= this.indexHeader.getBeginTimestamp() && begin <= this.indexHeader.getEndTimestamp());
        result = result || (end >= this.indexHeader.getBeginTimestamp() && end <= this.indexHeader.getEndTimestamp());
        return result;
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：从索引文件中查询指定key的方法，该方法会返回一个集合，集合中存储的就是相同key的消息在的CommitLog文件中的全局偏移量
     */
    public void selectPhyOffset(final List<Long> phyOffsets, final String key, final int maxNum, final long begin, final long end) {
        //得到文件资源锁
        if (this.mappedFile.hold()) {
            //计算key的哈希值
            int keyHash = indexKeyHashMethod(key);
            //得到对应的哈希槽位置
            int slotPos = keyHash % this.hashSlotNum;
            //得到哈希槽在索引文件中的偏移量
            int absSlotPos = IndexHeader.INDEX_HEADER_SIZE + slotPos * hashSlotSize;
            try {//得到哈希槽位置存储的索引值，这个索引值就是要查询的消息在索引文件索引区的索引
                int slotValue = this.mappedByteBuffer.getInt(absSlotPos);
                //判断刚才得到的索引值是否有效
                if (slotValue <= invalidIndex || slotValue > this.indexHeader.getIndexCount()
                        || this.indexHeader.getIndexCount() <= 1) {
                } else {//有效则开始获取对应的消息，这里之所以循环获取，是考虑有链表的情况，即一个key对应多个索引值
                    for (int nextIndexToRead = slotValue; ; ) {
                        //如果找到的条目数超过了阈值，则退出循环，不再继续寻找对应的消息了
                        if (phyOffsets.size() >= maxNum) {
                            break;
                        }//得到当前要查找的消息在索引文件中的偏移量
                        int absIndexPos = IndexHeader.INDEX_HEADER_SIZE + this.hashSlotNum * hashSlotSize + nextIndexToRead * indexSize;
                        //根据偏移量的到消息key的哈希值
                        int keyHashRead = this.mappedByteBuffer.getInt(absIndexPos);
                        //得到消息在CommitLog文件中的全局偏移量
                        long phyOffsetRead = this.mappedByteBuffer.getLong(absIndexPos + 4);
                        //得到消息存储的时间差
                        long timeDiff = this.mappedByteBuffer.getInt(absIndexPos + 4 + 8);
                        //得到上一个key的哈希值相同的消息索引位置
                        int prevIndexRead = this.mappedByteBuffer.getInt(absIndexPos + 4 + 8 + 4);
                        if (timeDiff < 0) {
                            //时间差小于0则退出循环
                            break;
                        }
                        timeDiff *= 1000L;
                        //计算当前查找到的消息的实际存储时间
                        long timeRead = this.indexHeader.getBeginTimestamp() + timeDiff;
                        //判断消息存储时间是否在指定的时间范围之内
                        boolean timeMatched = timeRead >= begin && timeRead <= end;
                        //如果符合要求则把消息在CommitLog文件中的全局偏移量添加到结果集中
                        if (keyHash == keyHashRead && timeMatched) {
                            phyOffsets.add(phyOffsetRead);
                        }//然后判断当前消息记录的上一条消息的索引是否有效
                        if (prevIndexRead <= invalidIndex
                                || prevIndexRead > this.indexHeader.getIndexCount()
                                || prevIndexRead == nextIndexToRead || timeRead < begin) {
                            break;
                        }//有效则更新索引位置，进入下一次循环，查找下一条消息
                        nextIndexToRead = prevIndexRead;
                    }
                }
            } catch (Exception e) {
                log.error("selectPhyOffset exception ", e);
            } finally {
                this.mappedFile.release();
            }
        }
    }
}
```
