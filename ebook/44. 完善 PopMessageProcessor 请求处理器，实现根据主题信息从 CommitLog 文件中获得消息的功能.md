## 继续重构 PopMessageProcessor 请求处理器


根据我们之前的分析，消费者客户端最终想要从 Broker 节点获得消息时，肯定要首先到消费偏移量管理器中获取当前消费组下，目标消费队列的最新消费偏移量。要执行这个操作肯定就要知道消费者客户端所属的消费组信息，订阅主题以及目标队列 Id，而这些信息恰好已经获得了，所以在 popMsgFromQueue() 方法中，我认为首先就应该先从消费偏移量管理器中查询目标队列的最新消费偏移量，具体操作我已经实现了，请看下面代码块。

```java
        long offset;

                this.brokerController.getMessageStore().getMinOffsetInQueue(topic, queueId) <= 0 &&

                this.brokerController.getMessageStore().checkInMemByConsumeOffset(topic, queueId, 0, 1)) {

            //如果是第一次消费队列中的消息，那在我们的程序中，就会在这里返回消费队列初始偏移量
            offset = 0;

            //这个消费队列中存储的消息的最大偏移量，当然，这里返回的是消息最大偏移量/消息单元的值
            offset = this.brokerController.getMessageStore().getMaxOffsetInQueue(topic, queueId) - 1;
            if (offset < 0) {
                offset = 0;
            }
        }

            //所以先更新到管理器中，当然，等消费者客户端从队列获取了消息之后，还会再次更新消费偏移量
            this.brokerController.getConsumerOffsetManager().commitOffset("getPopOffset", group, topic, queueId, offset);
        }
        return offset;
    }
```

从上面代码块中可以看到，到消费偏移量管理器中获取目标队列消费偏移量的操作并不复杂，其实就是看看目标队列是否有没有被消费过，如果已经被消费了，那就直接获取它最新的消费偏移量继续消费即可，如果没有被任何消费者客户端消费过，那就要初始化目标队列的消费偏移量，也就是从偏移量为 0 的位置开始消费，这个逻辑展示的应该很清楚了，大家可以自己品味品味。



好了，现在消费者客户端已经从 ConsumerOffsetManager 消费偏移量管理器中得到了目标队列的最新消费偏移量，那接下来只需要从该位置开始消费即可，这也是常规逻辑，我相信每一位朋友都能顺其自然地想到。当然，我相信执行到这里，大家肯定也能意识到，**在获取了目标队列地消费偏移量之后，接下来就该去队列中获取消息了，这个时候，显然就要争抢队列同步锁了**，只有争抢到了同步锁之后，才能到目标队列中获取消息。**如果争抢锁失败了，那就没什么可说的了，只能直接退出当前方法，在外层方法中执行下一次循环，去另外的目标队列中获取消息；当然，如果争抢队列锁成功，在我看来，那也不能直接到目标队列中获取消息，而是应该先看一看消费者客户端获取到的消息数量是否已经到达阈值了，到达阈值也只能直接退出当前方法**，这两个逻辑理解起来不难吧？如果还有一点要强调的话，那就是不管消费者客户端是否成功争抢到队列锁，是否成功获取到了消息，总之退出 popMsgFromQueue() 方法的时候，需要把目标消费队列中剩余的可消费的消息数量返回，这个返回值至关重要，等后面实现长轮询功能的时候大家就清楚了，现在先对此有一些印象即可。接下来，我就先把刚才分析的内容落实到代码层面，给大家看看 popMsgFromQueue() 方法前面的部分内容，请看下面代码块。

## 重构 DefaultMessageStore 和 ConsumeQueue


其实程序实现到这里基本上就没什么难度了，可能大家觉得我在开玩笑，好像根本都没有实现什么呢，怎么突然就说新功能的实现没难度了呢？明明现在才刚刚触及到核心功能啊，之前所执行的操作不是参数校验就是保证并发安全，根本就没从消费队列中获取任何消息啊。我知道大家肯定会有这样的困惑，但我还是坚持自己刚才的观点，接下来要实现的功能确实没有一点难度了，虽然要编写的代码可能还会多一点，但和之前以前，更多的内容也都是和一些检验操作有关。请大家想想，**当程序执行 DefaultMessageStore 消息存储引擎的 getMessage() 方法时，是不是已经知道了要获取的消息所属主题以及队列 Id，那直接根据这个获得对应的消费队列不就行了，也就是获得对应的 ConsumeQueue 消费队列对象**，这个可以理解吧？除此之外，**在外层方法中也已经得到了该消费队列最新的消费偏移量，也就是说，直接从这个位置开始获取后面的消息就行了，当然，获取消息之后，还要根据每一条消息封装的全局偏移量和消息大小到 CommitLog 文件中得到消息本身的内容**。这些操作实现起来也没什么难度吧？如果说有一点值得注意的话，**那就是在从消费队列中获取消息时，需要直接使用早就构建好的消息过滤器过滤消息**，大家可别忘了，消费队列中存储的消息还封装了消息的 tag 信息呢，这一点也可以理解吧？这样一来，消息就被提前过滤好了，那么直接使用过滤后的消费队列中的消息，去 CommitLog 文件中得到消息本身的内容了。我相信这些逻辑对大家来说都很容易理解，在代码层面上也很容易实现，确实没什么难度可言。



当然，以上分析的都是在获取消息时要执行的最核心的操作，除了这些核心操作，还有一些额外要执行的操作，**那就是校验从 ConsumerOffsetManager 消费偏移量管理器中得到的目标队列的消费偏移量是否正确，不正确的话则需要修正，然后重新消费**。这句话其实也很容易理解，我可以马上给大家举一个具体的例子，就比如说消费者从 ConsumerOffsetManager 偏移量管理器中得到的目标队列的消费偏移量是 3，那乘以消息单元大小之后，就意味着消费者要从消费队列偏移量为第 60 字节的内容开始消费，但是，在消费的时候却发现目标消费队列中根本就没有消息，也就是说最大消息偏移量为 0，或者是目标队列的最小有效偏移量为 100，也就是说 100 字节之前的消息都已经失效了，那这个时候是不是就要根据消费队列的实际内容来修正客户端要消费的偏移量了？这些逻辑可以理解吧？如果大家理解了这些逻辑，那 DefaultMessageStore 消息存储引擎的 getMessage() 方法就可以先实现成下面这样，请看下面代码块。

```java
                //设置消费偏移量太小状态
```

```java
    //单个内存映射文件的大小
    private final int mappedFileSize;

    //内存映射文件队列
    private final MappedFileQueue mappedFileQueue;


    //省略该类其他内容


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * @方法描述：从指定位置得到该位置之后的消息数据缓冲区的方法

    public SelectMappedBufferResult getIndexBuffer(final long startIndex) {
        //得到内存映射文件的大小
        int mappedFileSize = this.mappedFileSize;
        //得到指定位置在消费队列中对应的消息偏移量
        long offset = startIndex * CQ_STORE_UNIT_SIZE;
        //判断消息偏移量是否合法
        if (offset >= this.getMinLogicOffset()) {
            //合法则根据偏移量得到该偏移量对应的内存映射文件
            MappedFile mappedFile = this.mappedFileQueue.findMappedFileByOffset(offset);

        }
        return null;
```

为了实现这个功能，首先我想先定义一个新的类，因为消费队列中每一条消息都封装了三个重要的信息，**那么我定义的这个类的对象就可以封装一条消息的内容，比如说我可以给这个类定义三个成员变量，分别用来封装消息在 CommitLog 中的全局偏移量，完整消息的大小，以及消息的 tag 信息，这样分析下来，那我就可以把这个类定义为 CqUnit，表示消息单元，每一个 CqUnit 对象都可以封装消费队列中的一条消息**，具体内容请看下面代码块。

好了，现在 CqUnit 类也定义完毕了，那接下来应该怎么做呢？很简单，之前我们不是已经在 ConsumeQueue 消费队列中得到了执行偏移量之后的内存缓冲区吗？**那接下来就可以在 ConsumeQueue 内部定义具体解析这块内存缓冲区中消息的方法，解析出一条消息就创建一个 CqUnit 对象，把消息内容封装到 CqUnit 对象中，最后对外返回一个存储了 CqUnit 对象的集合即可**。这样一来，外层方法得到了存储 CqUnit 对象的集合，只需要遍历该集合，就可以直接从每一个 CqUnit 对象中得到每一条消息封装的具体内容，这样一来，外层方法要执行的操作就大大简化了。很好，要实现的操作确实越来越简单了，接下来我就把解析 ConsumeQueue 消费队列内存缓冲区的内容展示给大家，在实现这部分的内容时，我也是直接仿照源码，**在 ConsumeQueue 类中定义了一个内部类，内部类的对象其实就是一个迭代器对象，最终以迭代器的形式把一批 CqUnit 对象返回给外层方法了**，具体内容请看下面代码块。

```java

/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @方法描述：消费队列文件对象
 */
public class ConsumeQueue implements ConsumeQueueInterface, FileQueueLifeCycle {

    private static final Logger log = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //消费队列内存映射文件存储的每条消息的字节，也就是存储单元为20字节
    //前8字节为物理偏移量，后4字节为消息长度，后8字节为消息的Tag哈希值
    public static final int CQ_STORE_UNIT_SIZE = 20;

    //消息tag标签在存储单元中的偏移量为12字节
    public static final int MSG_TAG_OFFSET_INDEX = 12;

    private static final Logger LOG_ERROR = LoggerFactory.getLogger(LoggerName.STORE_ERROR_LOGGER_NAME);

    //单个内存映射文件的大小
    private final int mappedFileSize;

    //内存映射文件队列
    private final MappedFileQueue mappedFileQueue;


    //省略该类其他内容



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：从指定位置开始迭代ConsumeQueue中的消息单元的方法
     */
    @Override
    public ReferredIterator<CqUnit> iterateFrom(long startIndex, int count) {
        return iterateFrom(startIndex);
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：从指定位置开始迭代ConsumeQueue中的消息单元的方法
     */
    @Override
    public ReferredIterator<CqUnit> iterateFrom(long startOffset) {
        //从指定偏移量开始，获取之后所有消息的缓冲区
        SelectMappedBufferResult sbr = getIndexBuffer(startOffset);
        if (sbr == null) {
            return null;
        }
        //返回一个ConsumeQueueIterator对象，用于遍历ConsumeQueue中的消息单元
        //大家一定要去DefaultMappedFile类的selectMappedBuffer()方法中，查看一下SelectMappedBufferResult中的每个成员变量代表什么意思
        //这一点非常关键
        return new ConsumeQueueIterator(sbr);
    }

    

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：从指定位置得到该位置之后的消息数据缓冲区的方法
     */
    public SelectMappedBufferResult getIndexBuffer(final long startIndex) {
        //得到内存映射文件的大小
        int mappedFileSize = this.mappedFileSize;
        //得到指定位置在消费队列中对应的消息偏移量
        long offset = startIndex * CQ_STORE_UNIT_SIZE;
        //判断消息偏移量是否合法
        if (offset >= this.getMinLogicOffset()) {
            //合法则根据偏移量得到该偏移量对应的内存映射文件
            MappedFile mappedFile = this.mappedFileQueue.findMappedFileByOffset(offset);
            if (mappedFile != null) {
                //成功找到该文件则返回该文件内对应位置的缓存，offset % mappedFileSize计算的是消息偏移量在内存映射文件内的相对偏移量
                return mappedFile.selectMappedBuffer((int) (offset % mappedFileSize));
            }
        }
        return null;
    }



    //新定义的内部类，该类的对象就是一个迭代器

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：这个内部类的对象就是用来封装ConsumeQueue中消息单元的迭代器
     */
    private class ConsumeQueueIterator implements ReferredIterator<CqUnit> {

        //存储了指定偏移量之后消息的缓冲区，注意这个缓冲区并不包含所有消息，而是某个MappedFile内存映射文件指定偏移量之后的所有内容
        private SelectMappedBufferResult sbr;
        //记录当前sbr缓冲区的初始位置，这个初始位置大家要梳理清楚，其实是SelectMappedBufferResult对应的内存映射文件消息被消费到的位置
        //因为消息队列下可能有多个内存映射文件，比如说当前这个缓冲区的起始偏移量是10，而消息消费到了该缓冲区偏移量5的位置
        //现在要消费5之后的所有消息，那么这个relativePos成员变量就会被5赋值
        private int relativePos = 0;

        //构造方法
        //大家一定要去DefaultMappedFile类的selectMappedBuffer()方法中查看一下每个值具体代表什么
        public ConsumeQueueIterator(SelectMappedBufferResult sbr) {
            this.sbr = sbr;
            if (sbr != null && sbr.getByteBuffer() != null) {
                relativePos = sbr.getByteBuffer().position();
            }
        }



        //判断是否还有下一个消息单元的方法
        @Override
        public boolean hasNext() {
            if (sbr == null || sbr.getByteBuffer() == null) {
                return false;
            }//其实就是判断缓冲区内是否还有剩余数据
            return sbr.getByteBuffer().hasRemaining();
        }


        /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
         * @author：陈清风扬，个人微信号：chenqingfengyangjj。
         * @方法描述：迭代对象的核心方法，获取下一个消费单元的方法
         */
        @Override
        public CqUnit next() {
            //没有下一个消息单元直接返回null
            if (!hasNext()) {
                return null;
            }
            //如果有消息单元，那就把该消息单元在消费对类中的偏移量计算出来，注意，这里计算的是当前消息在消费队列中的偏移量
            //并不是消息在所属的内存映射文件中的偏移量，一个消费队列可以有多个内存映射文件存储数据
            //这一点大家要梳理清楚
            long queueOffset = (sbr.getStartOffset() + sbr.getByteBuffer().position() - relativePos) / CQ_STORE_UNIT_SIZE;
            //把消息内容封装到CqUnit对象中，到此为止，一个CqUnit对象就封装了消息在消费队列中的偏移量
            //也封装了这条消息在CommitLog文件中的全局偏移量、消息大小，消息tag哈希值
            CqUnit cqUnit = new CqUnit(queueOffset,
                    sbr.getByteBuffer().getLong(),
                    sbr.getByteBuffer().getInt(),
                    sbr.getByteBuffer().getLong());
            return cqUnit;
        }


        @Override
        public void remove() {
            throw new UnsupportedOperationException("remove");
        }


        @Override
        public void release() {
            if (sbr != null) {
                sbr.release();
                sbr = null;
            }
        }


        /**
         * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
         * @author：陈清风扬，个人微信号：chenqingfengyangjj。
         * @方法描述：得到迭代对象中下一个消息单元的方法
         */
        @Override
        public CqUnit nextAndRelease() {
            try {
                return next();
            } finally {
                //释放缓冲区资源
                release();
            }
        }
    }

    //省略该类其他内容
}
```

从上面代码块中可以看到，**在解析 ConsumeQueue 消费队列指定缓冲区中消息内容的时候，直接创建了一个 ConsumeQueueIterator 迭代器对象，如果外层方法得到了这个迭代器对象就可以调用迭代器的 hasNext() 方法判断是否还有下一条消息，如果存在下一条消息，那就可以调用迭代器的 next() 方法得到一个 CqUnit 消息单元对象，而这个消息单元对象就封装了解析完毕的消息内容**，这个逻辑大家应该可以理解吧？



好了，上面功能都实现了之后，接下来就可以完成我们的终极目标了，那就是根据从 CqUnit 对象中解析出来的消息内容到 CommitLog 文件中得到完整的消息，当然，在获取真正消息之前还可以使用消息过滤器过滤消息，只有符合 tag 信息的消息才能被执行后续操作，从 CommitLog 中得到了指定的消息之后，就可以把消息返回给消费者客户端了，只要我们实现了后续的这些功能，那么消费者从 Broker 节点的消息存储引擎中查询并获取消息的功能就算是实现了，那接下来我就把刚才分析的内容落实到代码层面，也就是说，我们要继续完善  DefaultMessageStore 类的 getMessage() 方法。



之前我们已经实现了部分 getMessage() 方法，在该方法中，执行了一系列对消费偏移量校验修正的操作，这一切的前提是消费者从消费管理器中得到的消费偏移量并不正确，所以需要校正。那当消费者从消费偏移量管理器中得到的目标队列的消费偏移量是正确的，那这个时候显然就可以直接从目标队列中获取消息了。这个时候，**是不是只要调用 ConsumeQueue 消费队列的 iterateFrom() 方法，就可以得到指定消费偏移量之后的所有内容了？当然，这些内容肯定是以迭代器对象的形式返回给外层方法**。那封装了要消费的消息内容的迭代器都得到了，**那接下来是不是就可以在循环中判断迭代器内部是否还有消息，如果有消息就可以执行跌倒器的 next() 方法，得到封装消息具体内容的 CqUnit 对象**；好了，现在封装一条消息具体内容的 CqUnit 对象也得到了，**那接下来就可以使用消息过滤器过滤 CqUnit 对象封装的消息，判断二者持有的 tag 是否一致，一致则可以去 CommitLog 文件中获得完整消息**。这就是根据一条消费队列中的消息获取对应完整消息的全流程，程序只需要在迭代器循环中不断执行这个操作，直到消息全部获取完毕，或者获取的消息数量达到了阈值，这时候就可以结束循环了。大家可以仔细品味品味这个逻辑，当然，我肯定已经把这部分内容对应的代码编写完毕了，请看下面代码块。

```java
    private boolean estimateInMemByCommitOffset(long offsetPy, long maxOffsetPy) {
        //这个方法的逻辑其实非常简单，this.messageStoreConfig.getAccessMessageInMemoryMaxRatio() / 100.0得到的就是
        //配置给rocketmq程序可使用的内存比，如果这个比例为百分之40，就意味着rocketmq可以使用的内存占据总的物理内存的百分之四十
        //StoreUtil.TOTAL_PHYSICAL_MEMORY_SIZE就是总的物理内容，二者相乘得到的就是rocketmq可以使用的字节总数
        long memory = (long) (StoreUtil.TOTAL_PHYSICAL_MEMORY_SIZE * (this.messageStoreConfig.getAccessMessageInMemoryMaxRatio() / 100.0));
        //这里maxOffsetPy就是commitlog文件存储的最大消息的偏移量
        //offsetPy就是指定偏移量，二者做减法得到的就是从指定偏移量到最大偏移量之间的字节数
        //这些字节可能就是接下来要访问的字节，如果这些字节小于rocketmq可用的字节总数，那就意味着这些字节可能还在内存中
        //就可以从内存中访问，这个逻辑也很简单，因为越在commitlog文件中越往后的消息肯定越晚到来，越晚存储
        //每当有消息到来的时候都会先被写入到pagecache缓存中，如果缓存不够肯定会把旧的消息先落盘
        //这样一来，越是后面存储的消息，越可能存放在内存中，大家想明白了这个逻辑，就懂了这个方法的作用了
        return (maxOffsetPy - offsetPy) <= memory;
    }
```
