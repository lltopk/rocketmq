在上一章我们分析任意延迟时间的定时消息功能的实现思路时，已经明确了一点：如果 Broker 节点接收到的这条消息是延迟消息，那就要在节点内部自动减少该消息的延迟时间，然后把消息投递到系统内置的延迟消息主题中。等到消息的延迟时间到期了，才会把这条消息重新投递到它真正的主题消费队列中。并且我们已经决定了，要用时间轮来管理所有的延迟消息，而时间轮的精度被我们设定为了 1 秒，也就是说，以秒为单位的话，这个时间轮可以调度任意一个时刻的定时任务。很好，那按照我们对时间轮的了解，接下来要做的事就很简单了：**既然时间轮是以具体的时间刻度来调度定时任务，指针每指向一个新的时刻，就要把这个时刻对应的所有定时任务都处理了，而我们之前也说了，每一个延迟消息被重新投递的操作就可以包装成一个定时任务，那么接下来我们只需要根据延迟消息的延迟时间计算出这个消息要被定位到时间轮的哪个刻度上，然后把着定时任务放到该刻度的槽位中不就行了**？这个逻辑可以理解吧？



很好，要做的事情已经明确了，接下来就可以开始执行了。其实一点也不复杂，所有延迟消息都会被 Broker 节点存储到系统内置的延迟消息主题队列中，那么我们只要从延迟消息主题的消费队列中不断获取消息，根据消息的延迟时间计算对应定时任务在时间轮中的槽位，然后把它放到时间轮中，这样不就行了吗？至于时间轮怎么执行定时任务，这个以后再分析。



那好，现在就有一个新的问题了，要怎么执行刚才分析的操作呢？很显然，这时候就要创建一个新的线程，让这个线程来干活了。也就是说，**我们要启动一个新的线程，让这个线程不断从延迟消息主题下的消费队列中查询消息，然后再把重新投递这条消息的操作封装成定时任务，把定时任务存放到时间轮的对应槽位中**。这个逻辑非常简单，好像不需要我们特别关注，按照简单的流程编写代码即可。但是，要我说在这个简单的操作中，仍然有一些可以细化的操作。就比如说，往常我们使用时间轮的时候，尤其是在 Netty 中使用时间轮，每一个任务的延迟时间都是我们定义的，每一个任务的执行逻辑也都是我们定义的，各个定时任务的执行逻辑可能并不相同，所以这个时候最好的方式就是把每一个定时任务放到时间轮的槽位中，当然，这么说也许不太恰当。实际上时间轮的每一个槽位可能都有一个对应的队列，这个队列可能是链表结构，我们只需要把定时任务放到对应槽位的任务队列中即可。如果大家对 Netty 时间轮的内容还有印象，我相信大家就会理解这一点。



好了，那回到我们目前要实现的功能，和 Netty 的时间轮不一样，延迟消息定时任务的逻辑已经非常清晰了，并且，每一个延迟消息对应的定时任务的逻辑应该都是一样的，都是把消息重新投递到它真正主题的消费队列中。既然是这样，那在我看来，我们就没必要再给每一个延迟消息定义什么定时任务了，而是可以把定时任务抽取出来，定义成一个公共的方法，只要等到消息的延迟时间到期了，程序执行这个方法，把这条消息重新投递到它的原始主题消费队列中，这不就行了吗？如果是这样的话，**那么当线程从延迟主题消费队列中不断查询到消息后，并不需要在为这条消息定义定时任务了，而是可以直接把这条消息放到时间轮对应的槽位中，时间轮的指针指向了哪个刻度，就可以执行定义好的公共方法，把这个刻度槽位的所有消息重新投到原始主题的消费队列中**，这个逻辑理解起来并不困难吧？



拿出了刚才的一点小重构，我们还可以对线程执行的操作进行什么优化呢？我想大家应该也注意到了，虽然我们还没有把时间轮真正定义出来，但通过刚才的分析，我们也能清楚地发现，**新启动的线程在处理延迟消息时，既要负责消息读取工作，也要负责消息写入工作。所谓消息读取就是把消息从延迟消息主题的消费队列中获取消息，有可能还需要把消息加载到内存；而消息写入指的就是把延迟消息提交给时间轮**。一个线程负责两种类型的工作也不是不可以，但面对这种情况，**更通用的做法就是引入一个新的队列，作为数据的缓存区，然后把线程的读写操作解耦**。仔细想想，这是不是更像一个生产者消费者模型？线程不断把新的延迟消息交给时间轮处理，而只有到了指定时间之后，时间轮中的消息才会被消费，这也就意味着时间轮中的消息可能并不会被实时消费，消息堆积得多了，这对时间轮来说也是一种考验。如果时间轮中堆积的消息多了，处理不过来了，显然就不能再接收新的消息，那么线程也就不能再提交消息，自然也要阻塞等待，线程不能工作，那延迟消息主题中的消息就不能加载到本地，这就是读写不解耦造成的影响。这个逻辑可以理解吧？



而按照通用的模板，**这个时候我们就可以定义两个线程，然后再引入一个新的队列。一个线程专门负责从延迟消息主题的消费队列中获取消息，然后把消息提交给新队列，另一个线程专门负责从队列中获取消息，把消息提交给时间轮**。这样一来，读写操作不就解耦了吗？而通过新引入的这个队列，还可以进一步优化延消息主题下消息的加载操作，在这种情况下，就算时间轮中数据满了，只要新引入的队列还有空间，那就可以继续把延迟主题下的消息加载到内存，以便后续直接使用。当然，除了这些好处，引入新的线程和队列还有一个最大的好处，那就是线程的职责分离了，各个线程只需要执行自己的操作，维护自己的操作，逻辑拆分得更仔细，不用再乱成一团了。



好了，既然决定要定义两个线程，把操作拆分一下，同时引入一个新的队列，就按照这么来吧。那接下来请大家思考一下，新引入的这个队列要存储什么呢？是存储消息本身吗？还是存储被包装过的消息？从延迟消息主题中不断获取延迟消息的线程其实没什么可分析的，因为这个线程要执行的操作非常简单，就是从消费队列中查询消息，然后把消息放到新引入的队列中。那就直接把消息本身放到新引入的队列中吗？还有一个问题，这里的消息指的究竟是什么消息呢？仅仅是从消费队列中得到消息呢？还是说是根据消费队列中的关键信息，从 CommitLog 文件中得到的消息呢？这里是一个小细节，很容易被大家忽略。我从源码得到的答案是，**读取消息的线程会根据消息队列中消息的关键信息，查询到 CommitLog 文件中这条消息原本的内容**，原因很简单，**在消费队列中存储的消息信息只包含消息在 CommitLog 文件中的全局偏移量，消息完整大小，消息 tag 的哈希值，并没有消息的延迟时间信息，而在后面处理延迟消息，把消息放到时间轮中时，会用到消息的延迟时间计算消息所在刻度，这么分析下来，显然应该得到消息原本的内容**。那么这是不是就意味着新引入的队列存储的就是原本消息的内容呢？也就是一条条 MessageExt 消息？源码中也不是这么做的，实际上，在源码中定义了一个 TimerRequest 类，新引入的队列中存储的就是 TimerRequest 对象，而 TimerRequest 对象就是对消息完整内容做了一层包装，就像下面代码块展示的这样，请看下面代码块。

```java
public class TimerRequest {

    //消息在CommitLog文件中的全局偏移量
    private final long offsetPy;
    //消息的完整大小
    private final int sizePy;
    //消息的延迟时间
    private final long delayTime;
    //请求如对时间
    private long enqueueTime;
    //消息完整的内容
    private MessageExt msg;


    public TimerRequest(long offsetPy, int sizePy, long delayTime, long enqueueTime) {
        this(offsetPy, sizePy, delayTime, enqueueTime, null);
    }

    public TimerRequest(long offsetPy, int sizePy, long delayTime, long enqueueTime, MessageExt msg) {
        this.offsetPy = offsetPy;
        this.sizePy = sizePy;
        this.delayTime = delayTime;
        this.enqueueTime = enqueueTime;
        this.msg = msg;
    }


    //省略其他get、set方法

}
```

好了，要往新队列中存储的对象明确了，那接下来就把新队列和负责读操作的线程也定义出来吧，这些其实都很好定义，队列就直接使用 JDK 的 BlockingQueue 原生队列即可，而线程就更简单了，直接让一个类继承 ServiceThread 类，这个类的对象就是一个线程，比如我们可以把这个线程定义为 TimerEnqueueGetService，这个线程对象就会把延迟消息主题下的消息都存放到我们刚才定义的队列中。而这些内容都可以定义在 TimerMessageStore 定时消息存储器中，所以接下来就请大家看一下初步构建的 TimerMessageStore 类，请看下面代码块。

```java
package org.apache.rocketmq.store.timer;



/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/10/31
 * @方法描述：定时消息存储引擎
 */
public class TimerMessageStore {


    private static final Logger LOGGER = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //表示当前定时消息存储器得运行状态，分别为初始化状态，运行状态，暂停状态，关闭状态
    public static final int INITIAL = 0, RUNNING = 1, HAULT = 2, SHUTDOWN = 3;

    //定时消息存储器默认状态
    private volatile int state = INITIAL;

    //队列容量
    public static final int DEFAULT_CAPACITY = 1024;

    //定时消息主题信息，其实就是系统内置的延迟消息主题名称
    public static final String TIMER_TOPIC = TopicValidator.SYSTEM_TOPIC_PREFIX + "wheel_timer";

    //定时消息主题下消费队列当前被消费到的偏移量
    protected volatile long currQueueOffset;
    
    //这个就是我们新引入的队列，被包装后的延迟消息就要被存放到该队列中
    protected final BlockingQueue<TimerRequest> enqueuePutQueue;

    //从延迟队列主题中读取数据的线程对象
    private TimerEnqueueGetService enqueueGetService;

    //当前Broker节点的最新角色，注意，并不是只有主节点才能执行定时任务调度操作
    //大家一定要搞清楚，所谓的定时任务调度其实就是把延迟消息重新投递到原始主题下而已
    //如果从节点自己不执行这个操作，它是无法从主节点同步数据的，一旦主节点宕机，从节点代理主节点
    //从节点没有执行定时任务调度操作，那么从节点就无法正常提供消息被延迟消费服务，所以从节点自己也得执行定时任务调度操作
    private volatile BrokerRole lastBrokerRole = BrokerRole.SLAVE;

    private final MessageStore messageStore;

    this.storeConfig = storeConfig;

    //构造方法
    public TimerMessageStore(final MessageStore messageStore, final MessageStoreConfig storeConfig) throws IOException {

        this.messageStore = messageStore;
        this.storeConfig = storeConfig;
        //给当前Broker节点赋值，在我们的程序中，当前Broker节点肯定是主节点
        this.lastBrokerRole = storeConfig.getBrokerRole();
        enqueuePutQueue = new LinkedBlockingDeque<>(DEFAULT_CAPACITY);
    }

    
    //初始化定时消息存储器的方法
    public void initService() {
        //在这里把读操作线程对象创建了
        enqueueGetService = new TimerEnqueueGetService();
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：加载定时消息存储器的方法，该方法会在Broker节点启动的过程中被调用
     * 我就不在文章中展示BrokerController对象调用当前方法的内容了，大家阅读我提供的第二十六版本代码就能看到了
     */
    public boolean load() {
        this.initService();
        return true;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：启动定时消息存储器的方法，该方法也会在BrokerController对象中调用，我就不再展示了
     */
    public void start() {

        enqueueGetService.start();
    }


    //以下就是TimerEnqueueGetService线程类，该类是TimerMessageStore的内部类

    
    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：定时消息入队服务组件，所谓入队服务组件，就是把消息队列中的定时消息放到队列中，之后，这些消息就会被存储到时间轮中等待被投递
     */
    public class TimerEnqueueGetService extends ServiceThread {

        @Override
        public String getServiceName() {
            return getServiceThreadName() + this.getClass().getSimpleName();
        }


        @Override
        public void run() {
            TimerMessageStore.LOGGER.info(this.getServiceName() + " service start");
            //判断服务是否停止工作
            while (!this.isStopped()) {
                try {
                    //在这里执行消息入队操作，队列Id为0这一点大家应该都清楚了，因为在时间轮主题中只有一个队列
                    //并且这个队列的Id就是0，这是写死的
                    if (!TimerMessageStore.this.enqueue(0)) {
                        //如果没有需要入队的消息，那么这个线程就休息一会
                        waitForRunning(100L * precisionMs / 1000);
                    }
                } catch (Throwable e) {
                    TimerMessageStore.LOGGER.error("Error occurred in " + getServiceName(), e);
                }
            }
            TimerMessageStore.LOGGER.info(this.getServiceName() + " service end");
        }
    }




    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：将定时消息主题下消费队列中的消息入队的方法
     */
    public boolean enqueue(int queueId) {
       
        //判断当前节点是否可以执行消息入队操作
        //当前节点是主节点才能执行该操作，如果是从节点也可以执行
        //但是必须保证定时任务主题下消费队列的消费进度必须小于主节点的进度才行
        //该方法内容非常简单，我就不在文章中展开了
        if (!isRunningEnqueue()) {
            return false;
        }

        //根据消费队列主题和队列Id得到具体的消费队列
        ConsumeQueueInterface cq = this.messageStore.getConsumeQueue(TIMER_TOPIC, queueId);
        if (null == cq) {
            //找不到队列则返回false，退出当前方法
            return false;
        }

        
        //得到消费队列之后，判断一下消费队列最小的可消费进度
        //currQueueOffset代表定时消息主题下消费队列被当前组件消费到的数据偏移量，这一点大家可别忘了
        //currQueueOffset小于消费队列最小的可消费进度，那就意味着currQueueOffset成员变量没有及时更新，这个消费队列消费偏移量已经是旧的了
        //要消费的消息已经过期了，接下来要更新当前队列的消费偏移量
        if (currQueueOffset < cq.getMinOffsetInQueue()) {
            LOGGER.warn("Timer currQueueOffset:{} is smaller than minOffsetInQueue:{}",
                    currQueueOffset, cq.getMinOffsetInQueue());
            currQueueOffset = cq.getMinOffsetInQueue();
        }

        //得到延迟消息主题消费队列的消费进度
        long offset = currQueueOffset;
        ReferredIterator<CqUnit> iterator = null;
        try {
            //从指定偏移量开始消费队列中的消息，得到消息迭代器对象
            iterator = cq.iterateFrom(offset);
            if (null == iterator) {
                return false;
            }

            //记录消费的消息数量
            int i = 0;
            //迭代消息，开始消费消息
            while (iterator.hasNext()) {
                //增加消息数量计数
                i++;
                try {
                    //得到一个消息单元，这个消息单元中封装了消息在CommitLog文件中的全局偏移量和大小信息
                    CqUnit cqUnit = iterator.next();
                    //得到该消息在CommitLog中的全局偏移量
                    long offsetPy = cqUnit.getPos();
                    //得到该消息在CommitLog中的大小
                    int sizePy = cqUnit.getSize();
                    //得到消息的tag哈希值，注意，这里仅仅是读取，并没有真的使用
                    cqUnit.getTagsCode();
                    //根据消息的全局偏移量和大小从CommitLog中获取完整的消息
                    MessageExt msgExt = getMessageByCommitOffset(offsetPy, sizePy);
                    //判断是否成功获取消息
                    if (null == msgExt) {
                        //这里是统计失败信息的操作，我给省略了
                    } else {
                        //从消息本身的内容中得到消息要被定时投递的精准时间
                        long delayedTime = Long.parseLong(msgExt.getProperty(TIMER_OUT_MS));
                        //得到消息在消费队列中的偏移量，注意，这里的偏移量并不是具体的字节偏移量
                        //而是数量偏移量，这个偏移量乘以消息单元大小，才能得到具体的字节偏移量
                        msgExt.setQueueOffset(offset + i);
                        
                        //以下就是TimerRequest对象入队的具体操作
                        
                        //创建TimerRequest对象，该对象封装了这条消息的核心信息，而这个TimerRequest对象，就会被存储到enqueuePutQueue队列中
                        //等待消息被存储到时间轮
                        TimerRequest timerRequest = new TimerRequest(offsetPy, sizePy, delayedTime, System.currentTimeMillis(), msgExt);
                        //在这里执行TimerRequest对象入队操作，也就是消息入队操作
                        //最多阻塞三秒等待
                        while (!enqueuePutQueue.offer(timerRequest, 3, TimeUnit.SECONDS)) {
                            //每次失败则判断消息是否可以入队
                            if (!isRunningEnqueue()) {
                                //不能入队则返回失败
                                return false;
                            }
                        }
                    }
                } catch (Exception e) {
                    //捕捉异常的内容我就省略了
                }
                //更新消费队列的消费偏移量，进入下一次循环
                currQueueOffset = offset + i;
            }
            //这里在上面的循环结束之后，又更新了一次消费队列的最新消费偏移量
            //这是要保证程序异常退出上面的循环时，消费队列的消费偏移量仍然能够被正确更新
            currQueueOffset = offset + i;
            //返回是否有消息入队的结果
            return i > 0;
        } catch (Exception e) {
            LOGGER.error("Unknown exception in enqueuing", e);
        } finally {
            if (iterator != null) {
                //在这里释放资源
                iterator.release();
            }
        }
        return false;
    }
}
```

好了，现在时间轮的时间变量也定义完毕了，接下来总该定义时间轮本身的功能了吧？别急，眼下还有一些别的问题要讨论。请大家想一想，从名字上来看，时间轮就是一个轮，也就是一个圆圈，既然是圆圈，那这就意味着它肯定是循环使用的。这也就是说，时间轮写满了一圈数据，等到要再要写新的数据时，就得从头开始写了。这么说可能还是有些模糊，那我们就来点实际的，假如我们把时间轮定义好了，这个时间轮有 7 个槽位，精度是 1 秒，那这个时间轮就是调度当前时间之后 7 秒内的所有定时任务；但现在有一个定时任务要在第 8 秒执行，按照时间轮循环的原理来说，这个任务是不是就要放到时间轮刻度 1 的位置了？那问题就来了，假如当前时间轮刚要调度刻度 1 对应的任务，这么一来不就把第 8 秒的任务也调度了吗？这显然是一个错误，那这个问题该怎么解决呢？



Netty 的时间轮是这么解决的，它给每一个要调度的定时任务定义了一个额外的属性，那就是圈数，当定时任务被放到时间轮时，会根据定时任务的延迟时间计算它在时间轮中的位置，如果定时任务延迟时间超过了时间轮的时间总量，这就意味着这个定时任务要在时间轮下一圈才能被调度执行，如果超过了两圈，则把这个定时任务的圈数设置为 2，时间轮每过一圈，定时任务的圈数就减 1，直到可以被当圈执行。这个逻辑可以理解吧？很好，那回到我们要实现的处理所有延迟消息的时间轮中，这个时间轮肯定也会遇到这种情况，那该怎么解决这个问题呢？



其实有一个最简单的手段，那就是禁止向时间轮提交超过时间轮时间总量的延迟消息，比如说整个时间轮只能处理延迟 7 秒以内的消息，那么提交消息的时候，就不能提交 延迟 7 秒的消息。这么做可以吧？当然可以，但在 RocketMq 源码中并不是这么做的，它也是仿照了 Netty 的做法，**那就是给提交给时间轮的消息新定义了一个属性，那就是消息状态。如果消息状态是默认，就表示消息可以直接被处理，如果消息状态是滚动，这就意味着在本次调度中不应该处理这条消息，而是应该看情况，等下次，或者下下次等等时机再处理消息**。这个逻辑应该不难理解吧？那这个消息的新属性我也定义好了，就定义在了 TimerRequest 类中，请看下面代码块。

因为时间轮只能接收最大延迟时间为 3 天的消息，那么一开始时间轮就接收了 3 天之内的延迟消息，然后随着系统时间流逝，时间轮指针向前推移。终于，第一天的消息被处理完了，而随着第一天过去，那延迟到第四天的消息就可以提交到时间轮了，这一点可以理解吧？好了，这样分析下去，那当时间走完前三天，延迟到第六天的消息就可以被提交到时间轮了，这个时候已经整整过去三天了。很好，到了第四天显然就可以把延迟到第七天的消息提交到时间轮了，对吧？但是，已经过去三天了，而在 RocketMq 中，假如我们给消息设置的过期时间就是 3 天，那么生产者生产的这一批消息就已经过期了，已经被处理的消息不用关心，但那些没有被提价到时间轮的也已经被过期删除了，这个时候又该怎么办呢？
