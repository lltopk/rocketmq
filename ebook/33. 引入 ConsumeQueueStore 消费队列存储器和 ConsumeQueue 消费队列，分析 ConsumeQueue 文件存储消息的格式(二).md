

## 完善 ConsumeQueue 消费队列和 ConsumeQueueStore 消费队列管理器


我能想到的第一个问题就是，当消息被重放的时候，这些重放消息会被存储到 ConsumeQueue 消费队列的文件中，而这个过程会用到内存映射机制，但是除了内存映射机制，在之前实现消息存储到 CommitLog 文件夹的功能时，我们还实现了内存级别的读写分离功能，那现在问题来了，**在把重放消息写入到 ConsumeQueue 消费队列中时，可以启用内存级别的读写分离功能吗**？



在第一个问题之后，我又想到了第二个问题，那就是当重放消息都被写入到主题文件的缓冲区之后，该怎么刷新到本地硬盘中呢？根据之前存储消息到 CommitLog 文件夹功能的实现思路，我们已经知道了，只要缓冲区的消息要被刷新到本地硬盘，不管消息是粗放到对外内存缓冲区还是内存映射缓冲区，这些消息被刷新到本地时都要调用 DefaultMappedFile 内存映射文件对象的 flush() 方法，确切地说，是直接调用 MappedFileQueue 内存映射文件管理器的 flush() 方法。那么现在要把 ConsumeQueue 消费队列缓冲区中的数据刷新到本地持久化了，这个时候应该执行什么方法呢？因为 ConsumeQueue 对象持有了 MappedFileQueue 内存映射文件管理器，那这样一来，**是不是应该直接在 ConsumeQueue 对象内部调用 MappedFileQueue 内存映射文件管理器的 flush() 方法执行数据刷新操作呢**？如果是这样的话，显然就应该给 ConsumeQueue 消费队列也定义一个 flush() 方法，但如果是这样的话，我们已经知道了，ConsumeQueue 消费队列会被 ConsumeQueueStore 消费队列管理器管理，那么 ConsumeQueueStore 消费队列管理器需要定义 flush() 方法吗？这是我想到的第二个问题。



相比于前两个问题，第三个问题就更重要一些了，在目前的消息队列框架中，我们已经知道了，一个主题会对应一个 ConsumeQueue 消费队列对象，假如程序中存在多个主题，那么在 Broker 节点内部，就会为多个主题创建对应的 ConsumeQueue 消费队列对象。了解了这一点之后，我现在要提出的问题是：**在消息队列程序内部，一个指定的主题下可能会存在多个 ConsumeQueue 消费队列吗**？我之所以提出这个问题，原因也很简单，因为很多时候，生产者生产的消息是没有顺序可言的，也不要求按照顺序生产消息，这就意味着消费者客户端消费消息的时候也不需要按照顺序消费，只需要尽快把消息消费完毕即可。如果是这样的话，那假如有多个消费者客户端同时到 Broker 节点消费消息，并且这些消费者客户端消费的都是同一个主题下的消息，比如说这个主题就是 TestTopic<font style="color:rgb(28, 30, 33);background-color:rgb(250, 250, 250);">，</font>而这个时候在 Broker 节点内部，这个 TestTopic 主题显然只对应着一个 ConsumeQueue 消费队列，这就意味着多个消费者客户端都要访问同一个 ConsumeQueue 消费队列，到这个队列中消费消息。这个逻辑大家可以理解吧？当然，这个逻辑本身肯定没什么问题，完全正确。我想说的是，在这个流程的基础上，可以对程序执行什么重构操作，以便提高多个消费者客户端消费消息的效率呢？



我首先想到的就是既然有多个消费者客户端同时消费同一个主题下的消息，而现在只有一个 ConsumeQueue 消费队列可以被多个消费者客户端访问，**那为了提高程序执行效率，就可以为该主题，也就是 TestTopic 主题定义多个 ConsumeQueue 消费队列呀，当执行消息重放操作的时候，就可以把消息重放到这些队列中。这样一来，当多个消费者客户端消费消息的时候，不就可以消费多个消费队列中的消息了**？这样不就提高程序执行效率了吗？



大家可能不清楚这究竟是怎么回事，可能还有些疑问，就比如说，就算给某个主题提供了多个 ConsumeQueue 消费队列，多个消费者客户端可以共同消费这些队列中的消息，当然，一个客户端只能同时访问一个 ConsumeQueue 消费队列；这种方式虽然可以提高消息被消费的速度，但是当多个消费者客户端从各自访问的 ConsumeQueue 消费队列中消费了消息，最后还是要根据消息的关键信息到 CommitLog 文件夹中查询消息的真正内容，如果是这样的话，显然就是多个消费者客户端会同时访问 CommitLog 文件夹中的内容，那这种情况不会出现并发问题吗？实际上并不会，原因很简单，**因为只要被写入到 CommitLog 文件夹中的数据根本不会被修改，消息只是不断被追加到 CommitLog 文件夹中，在 CommitLog 文件夹中的数据只会越来越多，而原有的数据并不会被修改，消费者客户端到 CommitLog 文件夹中所做的也只是读取数据而已，所以就算出现并发读取数据的情况，也不会出现并发问题**。这个逻辑应该很容易理解吧？



那这样分析下来之后，我想大家应该也认同了这个观点，**那就是确实可以给一个主题定义多个 ConsumeQueue 消费队列，只要不是顺序消费的场景，那么多个 ConsumeQueue 消费队列中的消息确实可以被多个消费者客户端同时消费**，很好，那现在新的问题就来了，**怎么给一个主题定义多个 ConsumeQueue 消费队列呢？应该按照什么规则定义呢？而为一个主题定义了多个 ConsumeQueue 消费队列之后，那消息怎么被重放到主题下的多个 ConsumeQueue 消费队列中呢**？



当我终于提出以上几个问题之后，接下来的内容就变得简单了，而且接下来要实现得功能就会和之前 Proxy 节点中执行的某个操作联系起来了。实际上是这样的，大家应该还记得当生产者客户端生产了消息之后，会把消息发送给 Proxy 节点，而 Proxy 节点又会把消息转发给对应的 Broker 节点。在这个过程中，Proxy 节点执行了一个非常重要的操作，那就是根据消息所属的主题信息，得到了该主题下所有可以路由的消息队列，然后使用负载均衡功能选择了一个具体的目标队列，当这个队列被选出来之后，队列所属的 Broker 节点的网络地址也就确定了，而目标队列的队列 Id 也就确定了。这个流程大家应该都还有印象吧？假如我们给一个 Broker 节点创建了一个 <font style="color:rgb(28, 30, 33);background-color:rgb(250, 250, 250);">TestTopic 主题，然后给这个主题定义配置信息时，定义了 8 个写队列和 8 个读队列，那么当 Proxy 节点为消息选择 TestTopic 主题的路由队列时，就有 8 个写队列可以选择，这不就是一个主题下有多个消息队列的情况吗？</font>

<font style="color:rgb(28, 30, 33);background-color:rgb(250, 250, 250);"></font>

**<font style="color:rgb(28, 30, 33);background-color:rgb(250, 250, 250);">来到 Broker 节点内部，当存储 TestTopic 主题下的重放消息时，如果根据该主题的配置信息，也就是 8 个读队列数量，也为该主题定义 8 个 </font>****ConsumeQueue 消费队列对象，那这样一来，这个主题下不就拥有 8 个 ConsumeQueue 消费队列了吗？重放消息就可以被存放到该主题下的 8 个消费队列中了**。这个逻辑理解起来应该也不难吧？至于重放消息依据何种策略存放到这 8 个 ConsumeQueue 消费队列中，这就更简单了，**写队列 和读队列的队列 Id 是一一对应的**。就**比如说在 Proxy 节点选中了队列 Id 为 1 的目标队列，那么当 Broker 节点接收到消息后，在重放消息的时候，就可以根据消息信息中携带的目标队列 Id，查找对应 Id 的 ConsumeQueue 消费队列，如果 Broker 节点内部还没有创建对应 Id 的 ConsumeQueue 消费队列，那就创建 ConsumeQueue 对象，然后存储重放消息即可**。大家可以品味品味这个逻辑，总之，这样分析完毕之后，**我们也确实清楚了一个主题下是可以存在多个 ConsumeQueue 消费队列对象，并且每一个 ConsumeQueue 消费队列都拥有各自的队列 Id**，那这个时候，主题和 ConsumeQueue 消费队列的映射关系就要稍微改变一下了，就可以重构成下面这样，请看下面代码块。

好了，新的映射关系定义完毕了，那么接下来就该重构一下 ConsumeQueueStore 类，然后把 ConsumeQueueStore 消费队列管理器的 findOrCreateConsumeQueue() 方法真正实现了，其实这个方法的实现逻辑非常简单，**就是根据指定主题和队列 Id 查询消费队列，如果存在消费队列就直接返回，不存在则创建对应的消费队列然后返回即可**。接下来就请大家看一下我重构完毕的 ConsumeQueueStore 类，请看下面代码块。

```java
package org.apache.rocketmq.store.queue;




/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/6/29
 * @方法描述：消费队列管理器
 */
public class ConsumeQueueStore {

    protected static final Logger log = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    protected final DefaultMessageStore messageStore;

    protected final MessageStoreConfig messageStoreConfig;

    //消费队列集合，每一个主题都对应这个一个消费队列集合
    //key就是主题名称，value就是该主题下的所有消息队列，这个value的key就是消费队列Id，value就是对应的ConsumeQueue消费队列对象
    protected final ConcurrentMap<String/* topic */, ConcurrentMap<Integer/* queueId */, ConsumeQueueInterface>> consumeQueueTable;


    public ConsumeQueueStore(DefaultMessageStore messageStore) {
        this.messageStore = messageStore;
        this.messageStoreConfig = messageStore.getMessageStoreConfig();
        this.consumeQueueTable = new ConcurrentHashMap<>(32);
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：根据指定Id和主题查找或者创建消费队列的方法
     */
    @Override
    public ConsumeQueueInterface findOrCreateConsumeQueue(String topic, int queueId) {
        //先从父类的consumeQueueTable表中获取主题对应的队列映射表，表的key是队列Id，value是消费队列本身
        ConcurrentMap<Integer, ConsumeQueueInterface> map = consumeQueueTable.get(topic);
        if (null == map) {
            //如果该主题的映射表不存在，则创建新的映射表
            ConcurrentMap<Integer, ConsumeQueueInterface> newMap = new ConcurrentHashMap<>(128);
            //把新创建的映射表存放到consumeQueueTable表中
            ConcurrentMap<Integer, ConsumeQueueInterface> oldMap = consumeQueueTable.putIfAbsent(topic, newMap);
            if (oldMap != null) {
                //如果映射表已经存在，就会返回已经存在的映射表，使用这个表即可
                map = oldMap;
            } else {
                //否则使用新创建的映射表
                map = newMap;
            }
        }
        //从映射表中获取指定队列Id的消费队列
        ConsumeQueueInterface logic = map.get(queueId);
        //如果消费队列已经存在则直接返回
        if (logic != null) {
            return logic;
        }
        //不存在则意味着要创建新的消费队列
        ConsumeQueueInterface newLogic;
        //得到当前主题的配置信息，从配置信息中可以得到该主题对应的消费队列的具体类型
        Optional<TopicConfig> topicConfig = this.messageStore.getTopicConfig(topic);
        //根据消费队列类型创建对应的消费队列
        if (Objects.equals(CQType.BatchCQ, QueueTypeUtils.getCQType(topicConfig))) {
            //如果是批量消费队列类型，创建BatchConsumeQueue对象
            //批量消息暂时不必关注，大家忽略这个分支即可
            newLogic = new BatchConsumeQueue(
                    topic,
                    queueId,
                    getStorePathBatchConsumeQueue(this.messageStoreConfig.getStorePathRootDir()),
                    this.messageStoreConfig.getMapperFileSizeBatchConsumeQueue(),
                    this.messageStore);
        } else {
            //否则创建普通消费队列对象
            newLogic = new ConsumeQueue(
                    topic,
                    queueId,
                    getStorePathConsumeQueue(this.messageStoreConfig.getStorePathRootDir()),
                    this.messageStoreConfig.getMappedFileSizeConsumeQueue(),
                    this.messageStore);
        }
        //将新创建的消费队列放入映射表
        ConsumeQueueInterface oldLogic = map.putIfAbsent(queueId, newLogic);
        //确定最终返回的消费队列
        if (oldLogic != null) {
            //如果已存在消费队列则使用已经存在的
            logic = oldLogic;
        } else {
            //否则使用新创建的消费队列
            logic = newLogic;
        }
        //返回找到或创建的消费队列
        return logic;
    }
}
```

上面代码块的内容都很简单，所以我就不再重复讲解了，到此为止，我刚才提出的三个问题中的第三个问题就被解决完毕了，那剩下的两个问题就简单多了，我就不再为大家仔细分析了，就直接展示源码中的实现思路吧，在把重放消息存放到 ConsumeQueue 消费队列中的时候需要开启内存读写分离功能吗？答案是不需要；那应该给 ConsumeQueue 消费队列和 ConsumeQueueStore 消费队列管理器定义 flush() 方法吗？答案是需要，并且定义的方法内容都很简单，**ConsumeQueue 的 flush() 方法只不过是是进一步调用了内存映射文件管理器的 flush() 方法，而 ConsumeQueueStore 消费队列管理器只不过是调用了被选中的要执行刷新操作的 ConsumeQueue 消息队列的 flush() 方法**。接下来我就根据这些实现思路，把重构完毕的 ConsumeQueue 类为大家展示一下，当然，我之所以想再次展示 ConsumeQueue 类，是因为在上面的代码块中，在 ConsumeQueueStore 消费队列管理器的 findOrCreateConsumeQueue() 方法中创建 ConsumeQueue 消费队列对象时，执行了该对象的构造方法，而我并没有为大家真正展示 ConsumeQueue 类的构造方法，因为之前还没有为 ConsumeQueue 引入队列 Id 的概念，现在这个概念引入了，就可以为 ConsumeQueue 类定义构造方法了，具体内容请看下面代码块。

package org.apache.rocketmq.store;




/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @方法描述：消费队列文件对象，可以看到，这个类实现了ConsumeQueueInterface接口
 */
public class ConsumeQueue implements ConsumeQueueInterface {


    private static final Logger log = LoggerFactory.getLogger(LoggerName.STORE_LOGGER_NAME);

    //消费队列内存映射文件存储的每条消息的字节，也就是存储单元为20字节
    //前8字节为物理偏移量，后4字节为消息长度，后8字节为消息的Tag哈希值
    public static final int CQ_STORE_UNIT_SIZE = 20;

    //消息tag标签在存储单元中的偏移量为12字节
    public static final int MSG_TAG_OFFSET_INDEX = 12;

    private static final Logger LOG_ERROR = LoggerFactory.getLogger(LoggerName.STORE_ERROR_LOGGER_NAME);

    //消息存储引擎
    private final MessageStore messageStore;

    //内存映射文件队列
    private final MappedFileQueue mappedFileQueue;

    //当前消费队列存储消息所属的主题信息
    private final String topic;

    //当前消费队列的队列Id
    private final int queueId;

    //存储消息的缓冲区对象，其实是这样的，当消息重放的时候，会先把消息的关键信息写入到这个缓冲区中
    //然后再把内容从这个缓冲区存储到内存映射文件中，至于为什么这么做，原因也很简单，那就是先对消息按照固定格式编码
    //编码完毕之后，就可以直接把消息写入到pagecache中了
    private final ByteBuffer byteBufferIndex;

    //ConsumeQueue消费队列文件的存储路径
    private final String storePath;

    //单个内存映射文件的大小
    private final int mappedFileSize;

    //消费队列映射文件中的最大消息物理偏移量，注意这个最大偏移量指的是消息队列文件中
    //存储的最新的消息在CommitLog文件中的全局偏移量，这个偏移量是消息的结尾偏移量
    //所谓结尾偏移量就是消息结尾的全局偏移量，比如说一条消息有5个字节，它在CommitLog文件中
    //的全局偏移量是200，表示是从200字节的位置开始存储这条消息，消息总大小为5字节
    //那么消息的结尾偏移量就是205字节，这就是当前成员变量表示的含义，一会大家就知道是怎么回事了
    private long maxPhysicOffset = -1;


    //构造方法
    public ConsumeQueue(
            final String topic,
            final int queueId,
            final String storePath,
            final int mappedFileSize,
            final MessageStore messageStore) {
        this.storePath = storePath;
        this.mappedFileSize = mappedFileSize;
        this.messageStore = messageStore;
        this.topic = topic;
        this.queueId = queueId;
        String queueDir = this.storePath
                + File.separator + topic
                + File.separator + queueId;
        //在这里可以看到，创建MappedFileQueue内存映射文件管理器对象了
        this.mappedFileQueue = new MappedFileQueue(queueDir, mappedFileSize, null);
        this.byteBufferIndex = ByteBuffer.allocate(CQ_STORE_UNIT_SIZE);
    }




    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：将ConsumeQueue消费队列的数据刷新到磁盘的方法
     */
    @Override
    public boolean flush(final int flushLeastPages) {
        //调用映射文件队列的flush方法，刷新指定页数的数据
        boolean result = this.mappedFileQueue.flush(flushLeastPages);
        return result;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * @方法描述：该方法就是把消息真正重放到消费队列中的方法，该方法在文章中做了简化
     * 但实际上源码和我提供的第十五版本中的内容也不难，无非就是添加了一点消息偏移量范围的合法校验操作
     */

        //该方法的内容暂时省略
    }

}

从上面代码块可以看到，我们对 ConsumeQueue 类的重构非常简单，无非就是添加了一个 flush() 方法，该方法的内容非常少，就是在刷新消费队列数据的时候，直接调用了内存映射文件管理器的 flush() 方法刷新即可，这没什么可讲的，大家肯定都清楚是怎么回事了。还有一点需要注意的就是，在我们给 ConsumeQueue 类定义的构造方法中，创建 MappedFileQueue 内存映射文件管理器的时候执行了这行代码：new MappedFileQueue(queueDir, mappedFileSize, null)，可以看到，在执行 MappedFileQueue 对象的构造方法时并没有给第三个方法参数传参，而从我们之前章节中可以知道，第三个方法参数实际上要传入一个 AllocateMappedFileService 内存映射文件分配器，这个内存映射文件分配器就是用来创建内存映射文件对象的，而该分配器内部还持有了临时存储池，如果程序启动了内存读写分离功能，就会使用临时存储池给内存映射文件分配缓冲区，这些流程大家应该还很清楚。但现在的情况是，**ConsumeQueue 消费队列对象持有的 MappedFileQueue 内存映射文件管理器并没有获得内存映射文件分配器，这就意味着这个 MappedFileQueue 内存映射文件对象根本就不能使用临时存储池，那它显然也就不可能给新创建的内存映射文件对象分配对外缓冲区，那内存读写分离功能肯定也就无法派上用场，当 MappedFileQueue 内存映射文件管理器内部创建新的 DefaultMappedFile 内存映射文件对象时，会直接调用 DefaultMappedFile 对象的构造方法创建**。所以，从这一点上就能看出来，当重放消息被存放到 ConsumeQueue 消费队列中的时候并不会使用内存读写分离功能，大家清楚这其中的逻辑即可。

                //否则使用新创建的映射表
                map = newMap;

        Optional<TopicConfig> topicConfig = this.messageStore.getTopicConfig(topic);

            newLogic = new BatchConsumeQueue(
                    topic,
                    queueId,
                    getStorePathBatchConsumeQueue(this.messageStoreConfig.getStorePathRootDir()),
                    this.messageStoreConfig.getMapperFileSizeBatchConsumeQueue(),
                    this.messageStore);
        } else {
            //否则创建普通消费队列对象
            newLogic = new ConsumeQueue(
                    topic,
                    queueId,
                    getStorePathConsumeQueue(this.messageStoreConfig.getStorePathRootDir()),
                    this.messageStoreConfig.getMappedFileSizeConsumeQueue(),
                    this.messageStore);
        }
        //将新创建的消费队列放入映射表
        ConsumeQueueInterface oldLogic = map.putIfAbsent(queueId, newLogic);
        //确定最终返回的消费队列
        if (oldLogic != null) {
            //如果已存在消费队列则使用已经存在的
            logic = oldLogic;
        } else {
            //否则使用新创建的消费队列
            logic = newLogic;
        }
        //返回找到或创建的消费队列
        return logic;
    }
}

上面图片只展示了 4 个队列文件夹，这一点可能会让大家觉得有些困惑，为什么少了 4 个队列文件夹呢？而且队列文件夹并不是从队列 1 开始的，这是因为 Proxy 节点在选中目标队列的时候有一个随机性，大家可以回顾一下之前的内容，**在 Proxy 节点刚开始轮询目标队列的时候有一个随机初始索引值，这样可以避免不同 Proxy 节点转发消息给 Broker 节点时在同一时间都被轮询到同一目标队列的情况出现，否则就会导致服务器压力骤增**。所以在刚开始可能并不会直接选择队列 Id 为 1 的目标队列来接收消息。而之所以缺少了 4 个队列，**是因为 Broker 节点并不会一开始就根据主题配置信息把某个主题下的所有消费队列文件夹都创建完毕，而是每接收到消息，根据消息携带的目标队列 Id 判断有没有为其创建对应的消费队列，如果没有，那这个时候才会真正创建消费对类对象，本地文件夹也才会被创建出来**。而在我为大家提供的第十五版本代码中，我测试的时候让生产者客户端发送了 4 次消息给 Broker 节点，Proxy 节点轮询了 4 次目标队列，所以 Broker 节点内部在接收到消息后就会把这 4 个队列 Id 对应的消费队列创建出来，因此大家才看到了本地存在的四个文件夹。大家在阅读第十五版本代码的过程中可以多让生产者客户端发送几次消息，看看本地队列文件夹会不会创建完整。好了，这些内容解释完毕之后，接下来就给大家展示一下队列文件夹中存放的本地文件，请看下面图片。

<img src="https://cdn.nlark.com/yuque/0/2025/jpeg/26725125/1757231424966-c8a3d8ac-439c-4d8a-8ffa-098d7eb74140.jpeg" width="873" title="" crop="0,0,1,1" id="u1cb5df6a" class="ne-image">

可以看到，本地文件仍然是使用存储消息的起始偏移量作为文件名称，重放消息就会被存放到这些文件中。如果第一个文件存满了，就会创建第二个本地文件，继续存储新的重放消息。到此为止，和 ConsumeQueueStore 类以及 ConsumeQueue 类相关的内容就讲解得差不多了，我相信以上这些内容大家也都掌握了，毕竟都非常简单，没什么难度。如果以上内容大家都掌握了，那么现在我想做一件事，那就是在实现并多次重构了 ConsumeQueueStore 类和 ConsumeQueue 类之后，在程序现有的功能上，我想为大家再次梳理、分析一下目前的 Broker 节点接收到生产消息后要执行的操作流程，我认为目前的流程是这样的：**当 Broker 节点接收到 Proxy 节点转发过来的生产消息之后，会先执行存储生产消息的操作，这个时候消息就会被交给消息存储引擎处理，然后被写入到 CommitLog 的文件缓冲区中，最终被持久化到本地文件中；而在这个过程中，程序内部会启动一个后台线程，这个后台线程会一直监测 CommitLog 的文件缓冲区中是否被写入了新的消息，只要有新消息到达，那么这个后台线程就会解析新消息，把新消息的关键信息，也就是消息在 CommitLog 文件夹中的全局偏移量、消息总大小，以及消息携带的 tag 标签信息都解析出来，这些信息就会组成一条重放消息；当然，在这个过程中新消息被轮询时选择的目标队列 Id 以及消息所属主题信息也会被解析出来，只不过这个 Id 以及主题信息并不是重放消息的内容，接下来，后台线程就会把这条重放消息写入到 ConsumeQueue 消费队列的内存缓冲区中。那在执行这个操作的时候，后台线程就会根据解析出来的消息所属的队列 Id 和主题信息从 ConsumeQueueStore 消费队列管理器中查找对应的 ConsumeQueue 消费队列，如果找到了消费队列直接返回该 ConsumeQueue 对象即可，如果没有找到，那就为这个主题和队列 Id 创建一个 ConsumeQueue 对象，然后返回这个对象；最后，就可以把重放消息存放到 ConsumeQueue 对象中了，消息就会被写入 ConsumeQueue 对应的内存映射文件缓冲区，最后被操作系统刷新到本地文件**。这就是 Broker 节点存储一条生产消息的完整流程，大家可以仔细品味品味这其中的逻辑。



当然，到目前为止，我们也只是把 ConsumeQueueStore 类和 ConsumeQueue 类实现并重构了，我们也已经知道，**只要调用 ConsumeQueue 对象的 putMessagePositionInfo() 方法，就可以把重放消息按照规定好的编码格式写入到对应主题和队列 Id 的 ConsumeQueue 消息队列内存映射缓冲区中，最终被刷新到本地文件**。但只实现了这些内容还不够，因为真正干活的后台线程并没有被定义呢？至于后台线程如何去 CommitLog 文件的缓冲区解析每一条消息，这个功能我们也没实现呢，看到这里，我相信大家肯定也意识到了，接下来我们的任务就是要围绕着后台线程所做的工作来展开了，实现诸多相关功能，最终实现完整的消息重放功能。
