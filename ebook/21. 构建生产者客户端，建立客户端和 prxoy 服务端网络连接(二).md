

## 实现生产者客户端启动功能


上一章结尾我为大家总结了目前生产者客户端存在的一些问题，我相信大家都还有印象，所以我就不再重复那些问题了，当然，我现在要做的也不是立刻解决哪些问题，我想请大家先别急，还是回到上一章最后一小节遗留的那个问题，也就是 **ProducerImpl 对象怎么被创建？ProducerImpl 对象的 startUp() 方法什么时候会被调用呢**？我希望我们能先从这个问题入手，看看在解决这个问题的过程中，生产者客户端会发生哪些变化。



也许有朋友会对此感到好奇，好奇我为什么要从 ProducerImpl 生产者实例的创建时机和启动时机入手，我想给大家简单解释一下，因为从我们目前构建的生产者客户端来说，只要创建了 ProducerImpl 对象，就意味着得到了生产者客户端，而只要调用了 ProducerImpl 对象的 startUp() 方法，就意味着启动了生产者客户端，就可以使用生产者客户端的各个功能，和服务端进行通信了。这个逻辑大家肯定都已经非常熟悉了，所以现在我们只需要把 ProducerImpl 生产者实例创建出来，然后调用它的 startUp() 方法启动生产者客户端即可。



但是，请大家思考一下，创建 ProducerImpl 生产者实例并不是什么复杂的操作，调用它的构造方法就能创造，这一点大家也应该没有异议吧？那我们就能直接创建 ProducerImpl 生产者实例吗？显然不能这么做，因为创建 ProducerImpl 对象只是最后一步，在创建它之前需要把一切准备工作都完成了才行。请大家回顾一下在实现 Nacos 框架的时候，我们创建 Nacos 客户端之前做了什么工作？是不是把客户端配置信息对象准备完毕了？还有什么故障转移组件也准备完毕了？总之我们准备好了很多组件，最后才执行客户端对象的构造方法，把 Nacos 客户端创建出来。那回到目前正在为消息队列构建的生产者客户端，我们已经知道创建 ProducerImpl 对象就是最后一个步骤，该对象创建完毕就意味着生产者客户端创建完毕了，所以在这个对象创建之前，别的组件我们还不清楚，但是配置信息对象肯定要准备好吧？



而一旦要准备配置信息对象，那么可访问的服务端网络地址啊，主题信息啊，超时时间，失败重试次数等等信息就都可以被封装起来了，这样一来，上一章结尾我提出的几个问题也就被解决一些了。当然还有一些比较复杂的问题没有解决，比如生产者客户端向 Proxy 服务端查询路由信息的功能该怎么实现，我会在本篇文章的后半部分为大家实现这些功能。好了，闲话少说，既然提到了生产者客户端的配置信息对象，那么这个配置信息对象该怎么定义呢？反正要封装的配置信息已经清楚了，**也许我们可以直接定义一个名为 ProducerSettings 类，这个类就可以当作生产者客户端的配置信息类**，刚才我们列举的生产者客户端的配置信息都可以定义在该类中。这个也很好理解吧？但在 RocketMq 框架源码中并不是这么做的，**在源码中除了定义了一个 ProducerSettings 类，还定义了一个 ClientSettings 配置信息类，并且 ProducerSettings 类是 ClientSettings 的子类**。这么做的原因也很简单，**因为生产者客户端和消费者客户端本来就有一些公共的配置属性，所以就在程序中为二者定义了一个公共父类，也就是 ClientSettings 类，这个类中封装的都是生产者和消费者客户端的公共配置信息，子类中才封装了各自独有的配置信息**。比如说生产者客户端要向存储引擎发送生产的消息，那么每次可以发送消息的最大大小就是一个很关键的配置信息，这个配置信息就被定义在了 ProducerSettings 类中。看到这里大家应该也能意识到，**其实上一章我们引入的 ClientImpl 客户端对象肯定也是一个公共父类，生产者和消费者客户端都会用到这个类，只不过生产者客户端会创建 ProducerImpl 对象，消费者客户端创建的则是与它对应的消费者实例**。这些内容我就先不展开了，后面总会为大家一一实现。现在，我就仿照 RocketMq 源码，为我们自己的消息队列框架引入 ProducerSettings 类和 ClientSettings 类。

```java
package org.apache.rocketmq.client.java.retry;


/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2025/6/10
 * @方法描述：客户端发送请求失败之后的重试策略，每次请求失败重新发送请求时，等待的时间会按照指数递增，直到达到最大退避时间，也就是最大的等待时间
 * 到达最大的等待时间后，这个时间就不再会增加了。这么做的原因是，如果连续失败的请求，每次重试间隔时间太短，可能会导致服务端无法处理这些请求，从而导致服务端压力过大，甚至崩溃
 * 其实就是为了减轻系统压力的
 */
public class ExponentialBackoffRetryPolicy implements RetryPolicy {

    //失败重试次数
    private final int maxAttempts;

    //初始退避时间，也就是请求第一次重试时要等待的时间
    private final Duration initialBackoff;

    //最大退避时间
    private final Duration maxBackoff;

    //退避指数，也就是每次重试间隔时间会乘以这个数
    private final double backoffMultiplier;

    //构造方法
    public ExponentialBackoffRetryPolicy(int maxAttempts, Duration initialBackoff, Duration maxBackoff,
                                         double backoffMultiplier) {
        this.maxAttempts = maxAttempts;
        this.initialBackoff = initialBackoff;
        this.maxBackoff = maxBackoff;
        this.backoffMultiplier = backoffMultiplier;
    }

    //创建一个立即重试策略对象的方法，之所以是立即充实策略，是因为重试策略的initialBackoff和maxBackoff都为Duration.ZERO
    //退避指数为1
    public static ExponentialBackoffRetryPolicy immediatelyRetryPolicy(int maxAttempts) {
        return new ExponentialBackoffRetryPolicy(maxAttempts, Duration.ZERO, Duration.ZERO, 1);
    }


    @Override
    public int getMaxAttempts() {
        return maxAttempts;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：计算下一次请求重试要等待的时间的方法，参数attempt表示当前尝试的次数
     */
    @Override
    public Duration getNextAttemptDelay(int attempt) {
        checkArgument(attempt > 0, "attempt must be positive");
        double delayNanos = Math.min(initialBackoff.toNanos() * Math.pow(backoffMultiplier,
                1.0 * (attempt - 1)), maxBackoff.toNanos());
        if (delayNanos <= 0) {
            return Duration.ZERO;
        }
        return Duration.ofNanos((long) delayNanos);
    }


    //该类的其他内容暂时省略
}
```

好了朋友们，现在生产者客户端要使用的配置信息类也定义完毕了，**并且我还引入了一个 ExponentialBackoffRetryPolicy 请求失败重试策略类**，这些类的内容都很简单，而且也很常见，所以我就不再重复讲解了。现在前置工作准备完毕，接下来我们只需要把配置信息对象也创建好，设置好用户自己定义的配置参数，那就可以执行最后一步，也就是创建 ProducerImpl 生产者实例，然后启动生产者客户端了。在我们自己开发的消息队列框架中，我们确实可以这么做，但只要大家简单看一看 RocketMq 框架的源码，就会发现在源码中并不是这么做的，接下来就让我为大家简单展示一下 RocketMq 的部分源码，大家可以看看在源码中的这些操作和我们预想的有什么不同。实际上是这样的，**在 RocketMq 源码中定义了一个 ClientServiceProviderImpl 类**，这个类的对象就是一个客户端服务提供器，具体内容请看下面代码块。

```java
/**
```

```java
public class ProducerBuilderImpl implements ProducerBuilder {

    //封装生产者客户端配置信息的成员变量

    //发送消息的最大失败重试次数

    //构造方法
    public ProducerBuilderImpl() {
        
    }

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：设置客户端配置信息的方法
     */
    @Override
    public ProducerBuilder setClientConfiguration(ClientConfiguration clientConfiguration) {
        this.clientConfiguration = checkNotNull(clientConfiguration, "clientConfiguration should not be null");
        return this;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：设置要发送消息的Topic主题的方法
     */
    @Override
    public ProducerBuilder setTopics(String... topics) {
        //对每一个主题信息进行非空校验
        final Set<String> set = Arrays.stream(topics).peek(topic -> checkNotNull(topic, "topic should not be null"))
                //对每一个主题进行格式规范校验

                .collect(Collectors.toSet());
        this.topics.addAll(set);
        return this;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     */
    @Override
    public ProducerBuilder setMaxAttempts(int maxAttempts) {
        checkArgument(maxAttempts > 0, "maxAttempts should be positive");
        this.maxAttempts = maxAttempts;
        return this;
    }

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：构建生产者客户端对象的方法
     */
    @Override
    public Producer build() {
        checkNotNull(clientConfiguration, "clientConfiguration has not been set yet");
        //在这里创建了生产者客户端对象，可以看到，这里调用的ProducerImpl的构造方法已经和我们上一章实现的并不一致了
        //所以很快我们就要根据这个构造方法重构ProducerImpl类
        final ProducerImpl producer = new ProducerImpl(clientConfiguration, topics, maxAttempts);
        //在这里启动了生产者客户端对象
        producer.startUp();
        return producer;
    }
}
```

好了朋友们，现在这个 ProducerBuilderImpl 生产者实例构建器的内容也展示完毕了，**在这个类的 build() 方法中，大家可以看到，就是在该方法中创建了 ProducerImpl() 生产者实例，然后调用了 ProducerImpl 对象的 startUp() 方法，真正启动了生产者客户端**。所以说，**现在我们只需要创建 ProducerBuilderImpl 生产者构建器，然后调用该构建器的 build() 方法，就可以创建并启动生产者客户端**，这个逻辑大家可以理解吧？



如果以上逻辑大家都能理解，那接下来我们肯定会忍不住思考，已经展示了 RocketMq 源码中的一些内容了，怎么还没轮到客户端需要的配置信息类登场呢？ProducerSettings 和 ClientSettings 这两个配置信息类不仅还没出现，**反而是在 ProducerBuilderImpl 构建器类中出现了一个 ClientConfiguration 类型的成员变量，这个类从名字上看更符合客户端配置信息类的意思，并且我们还可以在 ProducerBuilderImpl 类的 build() 方法中看见，在创建 ProducerImpl 生产者实例对象的时候还用到了这个 ClientConfiguration 客户端配置信息对象**。这是怎么回事呢？难道在 RocketMq 源码中，ClientConfiguration 才是封装客户端配置信息的对象吗？其实并不是这样，实际上 ClientConfiguration 类的内容非常简单，在源码中主要封装了访问服务端时要用到的密钥安全认证信息，除此之外也没什么作用了，我把该类的具体内容展示在下面了，请看下面代码块。

```java
package org.apache.rocketmq.client.apis;


public class ClientConfiguration {
    
    private final String endpoints;

    //会话凭证提供者，这个里面就封装了accessKey和secretKey信息
    private final SessionCredentialsProvider sessionCredentialsProvider;

    //请求超时时间，默认3秒
    private final Duration requestTimeout = Duration.ofSeconds(3);

   
    ClientConfiguration(String endpoints, SessionCredentialsProvider sessionCredentialsProvider,
                        Duration requestTimeout) {
        this.endpoints = endpoints;
        this.sessionCredentialsProvider = sessionCredentialsProvider;
        this.requestTimeout = requestTimeout;
    }

   
    public static ClientConfigurationBuilder newBuilder() {
        return new ClientConfigurationBuilder();
    }

    
    public String getEndpoints() {
        return endpoints;
    }

    public void setEndpoints(String endpoints) {
        this.endpoints = endpoints;
    }

  
    public Optional<SessionCredentialsProvider> getCredentialsProvider() {
        return null == sessionCredentialsProvider ? Optional.empty() : Optional.of(sessionCredentialsProvider);
    }

    
    public Duration getRequestTimeout() {
        return requestTimeout;
    }
}
```

## 实现生产者客户端查询指定主题路由信息功能


我们都知道，生产者客户端最核心的功能就是生产消息，把消息发送给消息存储引擎，如果说得更确切一些，那就是在 RocketMq 5.0 版本之前，生产者客户端会把生产的消息直接发送给可路由的 Broker 节点，Broker 节点的存储引擎会存储消息；而在 5.0 之后的版本，因为引入了 Proxy 模块，所以生产者客户端会先把消息发送给 Proxy 节点，然后由 Proxy 模块把消息转发给对应的 Broker 节点。**如果我们使用的是 5.0 之前的 RocketMq 框架，那么确实很有必要为生产者客户端实现查询指定主题路由信息的功能，只有这样，生产者客户端才知道指定主题下的消息要路由发送给哪个 Broker 节点；并且在 5.0 版本之前的程序中，生产者客户端需要直接访问 Namesrv 服务端，才能查询到指定主题下可路由的 Broker 节点信息，而生产者和消费者得到了可路由的节点信息后，还会直接和这些 Broker 节点都建立网络连接，之后就会直接访问这些可路由的 Broker 节点**。但在引入了 Proxy 模块之后，一切变得不同了，我之前也跟大家解释过，**Proxy 模块就是生产者和消费者客户端的代理，在 5.0 之后的 RocketMq 程序中，Proxy 节点在启动的时候就会从 Namesrv 服务端获取程序内所有 Broker 节点的信息**，这一功能在之前的代码中也实现了；**生产者和消费者客户端并不会直接访问 Namesrv 服务端查询指定主题的路由信息，而是访问 Proxy 节点，从 Proxy 节点获取指定主题的路由信息，如果 Proxy 节点没有对应的信息，那么 Proxy 节点就会访问 Namesrv 服务端，根据客户端想要查询的主题信息获得对应的路由信息，然后再返回给客户端**，这些都是我们之前实现的功能。在这种情况下，**生产者和消费者客户端不会再直接访问 Namesrv 和可以路由的 Broker 节点了，而是直接和 Proxy 节点建立网络连接，所有请求都会发送给 Proxy 节点，让 Proxy 节点转发给对应的节点**。



如果大家还记得我们之前为 Proxy 模块实现的所有功能，那肯定也还记得，**当 Proxy 模块把指定主题路由信息返回给客户端的时候，会用 Proxy 模块自己的网络地址替换掉可路由的 Broker 节点的网络地址，因为 Proxy 模块的出现就是为了简化客户端功能，以至于连负载均衡的操作也不必在生产者和消费者客户端内进行了。如果生产者客户端想把生产的消息发送给 Broker 节点，那么生产者客户端就会把消息先发送给 Proxy 节点，Proxy 会在内部找到这条消息可路由的节点信息，然后为这条消息做负载均衡，选择合适的 Broker 节点，把消息发送给被选中的目标 Broker 节点，等目标 Broker 节点接收到消息之后，就可以存储消息了**。这本来是后面要实现的功能，但现在简单讲解一些也没关系，我相信就算不看代码，大家也都能理解其中的逻辑。如果大家理解了这一部分逻辑，那肯定会对一个问题感到困惑，既然生产者客户端只和 Proxy 服务端进行通信，Proxy 会为生产者客户端代理一切操作，那么这样看起来，在 5.0 之后的 RocketMq 程序中，**生产者客户端似乎根本没必要从 Proxy 服务端查询指定主题可路由的 Broker 节点信息，因为就算查询了，返回来的 Broker 节点的网络地址也被替换成 Proxy 服务端的网络地址了**，只有这样，生产者客户端在生产消息时，才能直接把消息发送给 Proxy 节点，而生产者客户端已经知道 Proxy 节点的网络地址了，之前展示的测试类中已经印证这一点了，那生产者客户端生产消息时，直接把消息发送给 Proxy 节点服务端不就行了吗？还查询指定主题的路由信息干什么呢？这么理解没有问题吧？



这么理解当然没问题，但是，看待问题要全面一些，如果我们只关注可路由的 Broker 节点的网络地址被替换成了 Proxy 服务端的网络地址，只从这个角度考虑的话，那么生产者客户端确实没必要查询指定主题的路由信息了，反正每个请求都会发送给 Proxy 节点，Proxy 节点会代理操作。但与此同时我们还要看到，**指定主题的路由信息并不只是包含可路由的 Broker 节点的网络地址，除此之外还包含了 Broker 节点的重要信息，客户端还能根据返回的信息得到 Broker 集群的信息，因为返回给生产者客户端的路由信息包含了 Broker 组的主节点和从节点的所有信息，总之客户端得到的可路由的节点信息非常丰富，我们不能只把视野局限在可路由的节点的网络地址上**。如果从这个角度来分析，那么生产者客户端当然需要从 Proxy 服务端查询指定主题的路由信息。当然，坦诚地说，我目前还没在 5.2.0 版本的源码中看到客户端使用这些路由信息执行了什么操作，因为很多重要操作都是在 Proxy 模块执行的：比如负载均衡，故障转移等等。也许是目前源码还不太完善，这些功能是为以后的某些功能做铺垫，源码还会进一步迭代，也许吧，到时候就清楚了，现在还是回到眼前的事情上，接下来，就让我为大家实现生产者客户端查询指定主题路由信息功能。

```java
    private ListenableFuture<TopicRouteData> fetchTopicRoute0(final String topic) {
        try {
            //创建主题资源对象，把主题信息封装到资源对象中
            Resource topicResource = Resource.newBuilder().setName(topic).build();
            //创建查询主题路由信息请求

            //生成客户端签名对象

            //在这里使用客户端管理器把请求发送给服务端
            final ListenableFuture<RpcInvocation<QueryRouteResponse>> future =
                    //我把重构之后的客户端管理器的queryRoute()方法也展示在当前代码块中了，大家可以看一看
                    clientManager.queryRoute(endpoints, metadata, request, clientConfiguration.getRequestTimeout());
            //当服务端给客户端回复了响应之后，也就是上面操作返回的future被设置为完成状态之后，下面定义的回调方法就会被执行了
            return Futures.transformAsync(future, invocation -> {
                //得到服务端回复的响应，这里从一个Invocation对象中得到Proxy服务端回复的响应
                //至于Invocation对象为什么会封装响应，往下看大家就清楚了，在RpcClientImpl类的queryRoute()方法中，大家会得到答案
                //我把RpcClientImpl类重构之后的queryRoute()方法也展示在当前代码块中了
                final QueryRouteResponse response = invocation.getResponse();
                //得到请求Id
                final String requestId = invocation.getContext().getRequestId();
                //得到响应状态
                final Status status = response.getStatus();
                //得到状态描述信息
                final String statusMessage = status.getMessage();
                //得到状态码
                final Code code = status.getCode();
                //得到状态码的值
                final int codeNumber = code.getNumber();
                //根据状态码的值执行不同操作
                switch (code) {
                    case OK:
                        //如果状态码正常，就什么也不做
                        break;
                    case BAD_REQUEST:
                    case ILLEGAL_ACCESS_POINT:
                    case ILLEGAL_TOPIC:
                    case CLIENT_ID_REQUIRED:
                        //如果状态码为请求错误，或者参数错误、非法访问、非法主题、缺少客户端Id等等
                        //则在这里抛出对应的异常
                        throw new BadRequestException(codeNumber, requestId, statusMessage);
                    case NOT_FOUND:
                    case TOPIC_NOT_FOUND:
                        //如果状态码为为资源不存在、主题不存在，抛出NotFoundException异常
                        throw new NotFoundException(codeNumber, requestId, statusMessage);
                    case TOO_MANY_REQUESTS:
                        //执行到这里意味着状态码是请求过多，服务端限流
                        throw new TooManyRequestsException(codeNumber, requestId, statusMessage);
                    case INTERNAL_ERROR:
                    case INTERNAL_SERVER_ERROR:
                        //执行到这里意味着状态码为服务端内部错误
                        throw new InternalErrorException(codeNumber, requestId, statusMessage);
                    case PROXY_TIMEOUT:
                        //执行到这里意味着状态码为代理超时
                        throw new ProxyTimeoutException(codeNumber, requestId, statusMessage);
                    default:
                        //意义未明确的状态码
                        throw new UnsupportedException(codeNumber, requestId, statusMessage);
                }
                //从响应中获取服务端返回的消息队列列表
                final List<MessageQueue> messageQueuesList = response.getMessageQueuesList();
                //创建一个包含消息队列列表的TopicRouteData对象
                final TopicRouteData topicRouteData = new TopicRouteData(messageQueuesList);
                //返回包含主题路由数据的，并且状态为已完成的future对象
                return Futures.immediateFuture(topicRouteData);
            }, MoreExecutors.directExecutor());
        } catch (Throwable t) {
            return Futures.immediateFailedFuture(t);
        }
    }
```

## 实现生产者客户端心跳检测功能


要想实现生产者客户端心跳检测功能，我们首先就得考虑生产者客户端应该向什么节点执行心跳检测操作，也就是向什么节点发送心跳请求。在上一小节我们已经讨论过了，在 5.0 之后的 RocketMq 框架中，**生产者客户端是不会再直接和 Namesrv、Broker 节点建立网络连接了，客户端只会直接访问 Proxy 节点，那显然生产者客户端肯定要向 Proxy 服务端发送心跳请求，执行心跳检测操作**。既然是心跳检测操作，毫无疑问，肯定是用定时任务来执行的，那这个定时任务应该定义在哪里呢？具体定义什么操作呢？



在 RoketMq 源码中是这么做的，**这个定时任务就被定义在了 ClientManagerImpl 客户端管理器的 startUp() 方法中，也就是说生产者客户端启动的时候，心跳检测定时任务就会被提交了；至于定时任务要执行什么操作，这就更简单了，那就是直接向客户端能够访问的所有 Proxy 节点发送心跳请求即可，成功接收到响应则意味着心跳检测成功**。这些操作都很简单，所以我们直接仿照源码来实现即可，接下来就请大家看一下我重构之后的 ClientManagerImpl 客户端管理器，请看下面代码块。

```java
public abstract class AbstractIdleService implements Service {

    //省略该类其他内容

    private final Service delegate = new DelegateService();


    private final class DelegateService extends AbstractService {
        @Override
        protected final void doStart() {
          MoreExecutors.renamingDecorator(executor(), threadNameSupplier)
              .execute(
                  new Runnable() {
                    @Override
                    public void run() {
                      try {
                        startUp();
                        notifyStarted();
                      } catch (Throwable t) {
                        notifyFailed(t);
                      }
                    }
                  });
        }

        @Override
        protected final void doStop() {
          MoreExecutors.renamingDecorator(executor(), threadNameSupplier)
              .execute(

                        notifyStopped();
                      } catch (Throwable t) {
                        notifyFailed(t);
                      }
                    }
                  });
```
