

## 引入 NettyRemotingAbstract 类

从上面代码块中可以看出，我给 NettyRemotingServer 类定义了一个 processorTable 成员变量用来存放注册到 Namesrv 服务端内部的请求处理器，既然这些请求处理器要被 Namesrv 服务端使用，所以这个功能就直接在 NettyRemotingServer 类中实现了，也就是直接在服务端内部实现了。这么实现当然没有问题，但现在我有个新的问题想问问大家，如果我们要实现 Namesrv 客户端，其实就是使用 Netty 构建一个客户端，并且这个客户端可以向 Namesrv 服务端发送 RemotingCommand 请求进行通信，那这个客户端该怎么实现呢？我知道这会突然提出这个问题确实有点莫名其妙，但还是请大家简单思考一下，该怎么使用 Netty 构建一个客户端。



如果让我自己使用 Netty 构建一个可以和 Namesrv 通信的客户端，我的做法非常简单，只要模仿 NettyRemotingServer 就行。**既然服务端被定义为 NettyRemotingServer ，那客户端就定义为 NettyRemotingClient 吧，再给 Netty 构建的客户端定义一个配置类封装配置信息，可以把这个配置类定义为 NettyClientConfig 类；接下来就是真正构建客户端了吧？Netty 构建客户端要用到 Bootstrap 启动器对象，还要使用 IO 事件循环组 EventLoopGroup 对象，还要给客户端 Channel 的 Pipeline 设置各种处理器，编解码器、IdleStateHandler 空闲检测处理器等等**；当客户端和服务端的连接断开的时候，不仅服务端会感知到，客户端本身也会感知到，服务端使用连接管理器组件管理连接，客户端当然也可以使用连接管理器管理连接，**所以还可以把我定义好的客户端使用的 NettyConnectManageHandler 连接管理器设置到 Pipeline 中**；除此之外，我们肯定也都清楚，Netty 构建的客户端和服务端是通过 Channel 通信的，而 Channel 具备全双工通信能力，也就是说客户端可以主动给服务端发送请求消息，服务端也可以主动给客户端发送请求消息，所以 Netty 构建的客户端当然也应该再定义一个 IO 事件处理器专门处理服务端发送过来的消息，然后把这个 IO 事件处理器设置到 Pipeline 中，**我就把这个 IO 事件处理器的名称定义为 NettyClientHandler 吧**。以上分析的内容应该都能理解吧？这是 Netty 最基础的使用方式了，当然，为了从模式上完全模仿我们之前实现的 NettyRemotingServer 类，**在定义 NettyRemotingClient 类的时候，我们可以给 NettyRemotingClient 类也定义一个 start() 启动方法，然后把刚才分析的那些内容都定义在 start() 方法中**，就像下面代码块展示的这样，请看下面代码块。

```java
package org.apache.rocketmq.remoting.netty;


//这个类在第二版本代码中并没有展示，这里只是为了在文章中使用，所以为大家展示一下该类的部分代码
//实际上这个类还有很多内容，等后面版本代码就会为大家实现了
public class NettyRemotingClient{


    //Netty构建的客户端的启动引导对象
    private final Bootstrap bootstrap = new Bootstrap();

    //Worker事件循环组
    private final EventLoopGroup eventLoopGroupWorker;

    //Netty客户端配置信息对象
    private final NettyClientConfig nettyClientConfig;


    public void start() {

        //配置Netty客户端的引导对象
        //设置Worker事件循环组
        Bootstrap handler = this.bootstrap.group(this.eventLoopGroupWorker)
                //设置Channel类型为NioSocketChannel
                .channel(NioSocketChannel.class)
                //设置TCP_NODELAY选项，禁用Nagle算法，这在NettyRemotingServer中已经见过了
                .option(ChannelOption.TCP_NODELAY, true)
                //设置长连接的心跳机制
                .option(ChannelOption.SO_KEEPALIVE, false)
                //设置连接超时时间
                .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, nettyClientConfig.getConnectTimeoutMillis())
                //为channel设置Pipeline
                .handler(new ChannelInitializer<SocketChannel>() {
                    @Override
                    public void initChannel(SocketChannel ch) throws Exception {
                        //向channel的Pipeline中添加各种Handler
                        ch.pipeline().addLast(
                                //判断Netty客户端是否禁用工作了，如果没有禁用，那就使用默认的事件循环组执行这些Handler中的方法
                                nettyClientConfig.isDisableNettyWorkerGroup() ? null : defaultEventExecutorGroup,
                                //添加编码器到Pipeline中
                                new NettyEncoder(),
                                //添加解码器到Pipeline中
                                new NettyDecoder(),
                                //添加空闲状态处理器到Pipeline中
                                new IdleStateHandler(0, 0, nettyClientConfig.getClientChannelMaxIdleTimeSeconds()),
                                //添加连接管理器到Pipeline中
                                new NettyConnectManageHandler(),
                                //添加客户端处理器到Pipeline中，客户端处理器会处理客户端接收到的请求或者响应
                                new NettyClientHandler());
                    }
                });



        //从客户端配置信息对象中得到配置的缓冲区大小，设置客户端发送缓冲区的大小
        if (nettyClientConfig.getClientSocketSndBufSize() > 0) {
            LOGGER.info("client set SO_SNDBUF to {}", nettyClientConfig.getClientSocketSndBufSize());
            handler.option(ChannelOption.SO_SNDBUF, nettyClientConfig.getClientSocketSndBufSize());
        }
        //从客户端配置信息对象中得到配置的缓冲区大小，设置客户端接收缓冲区的大小
        if (nettyClientConfig.getClientSocketRcvBufSize() > 0) {
            LOGGER.info("client set SO_RCVBUF to {}", nettyClientConfig.getClientSocketRcvBufSize());
            handler.option(ChannelOption.SO_RCVBUF, nettyClientConfig.getClientSocketRcvBufSize());
        }

        //设置客户端写缓冲区高低水位线
        if (nettyClientConfig.getWriteBufferLowWaterMark() > 0 && nettyClientConfig.getWriteBufferHighWaterMark() > 0) {
            LOGGER.info("client set netty WRITE_BUFFER_WATER_MARK to {},{}",
                    nettyClientConfig.getWriteBufferLowWaterMark(), nettyClientConfig.getWriteBufferHighWaterMark());
            handler.option(ChannelOption.WRITE_BUFFER_WATER_MARK, new WriteBufferWaterMark(
                    nettyClientConfig.getWriteBufferLowWaterMark(), nettyClientConfig.getWriteBufferHighWaterMark()));
        }
        //根据配置信息判断客户端是否启用了池化的内存分配功能
        if (nettyClientConfig.isClientPooledByteBufAllocatorEnable()) {
            //如果启用了则设置池化内存分配器
            handler.option(ChannelOption.ALLOCATOR, PooledByteBufAllocator.DEFAULT);
        }

        //连接服务端的代码我就省略了

        
    }
}
```

上面代码块的内容非常简单，和上一章实现完毕的 NettyRemotingServer 类中的部分内容几乎完全一致，所以我就不再重复讲解了，熟悉 Netty 的朋友应该都能看懂上面代码块的逻辑。总之，现在我们已经定义完毕了一个 Netty 构建的客户端，这个客户端还可以和 Namesrv 服务端进行通信，虽然我没有把具体的通信方法定义出来，大家明白我的意思就行。很好，文章进行到这里，看起来好像已经离题很远了，因为我一开始是想跟大家分析上一章实现的 Namesrv 服务端功能存在的五个方面的缺陷。大家先别急，还是请先思考一个问题，在上面代码块中，我向 Netty 构建的客户端中设置了 IO 事件处理器 NettyClientHandler，虽然我没有真的把这个处理器实现出来，但是通过对上一章为 Namesrv 服务端实现的 IO 事件处理器的了解，大家应该也很清楚这个 NettyClientHandler 处理器的功能。**它肯定会处理来自服务端的请求，并且也会根据服务端发送过来的请求类型，找到对应的处理请求的处理器，然后使用处理器处理请求**，这一点我相信大家都可以理解吧？



如果大家理解了这一点，那现在问题就来了，显然客户端也会定义自己的请求处理器，请求处理器会专门处理某种类型的请求，我们先不必关心服务端会向客户端发送什么请求，也没必要关心客户端应该定义什么请求处理器，现在请大家想一想，不管客户端要定义什么请求处理器，这些处理器肯定也要注册到客户端内部吧？就像 Namesrv 服务端把要用到的各种请求处理器注册到自己内部，客户端也应该这么做请求处理器才能派上用场，这一点也可以理解吧？那么客户端怎么把请求处理器注册到自己内部呢？**如果还是要模仿 NettyRemotingServer 类的话，那就应该在 NettyRemotingClient 类中也定义注册请求处理器的方法**，就像下面代码块展示的这样，请看下面代码块。

上面代码块中的逻辑也很简单，但我们的重点并不是关注其内部逻辑，我想看到这里大家应该也意识到了，Netty 构建的客户端和服务端在很多功能上都是相同的，既然功能是相同的，客户端和服务端都要实现相应的功能，**那最好的方式就是为 NettyRemotingClient 客户端和 NettyRemotingServer 服务端定义一个抽象父类，把公共内容都定义在父类中，比如说在注册请求处理器这个功能中，就可以把存储请求处理器的 processorTable 成员变量定义在抽象父类中**。使用抽象类重构客户端和服务端代码，我分析的逻辑应该足够清晰了吧？如果大家理解了这个逻辑，**那么接下来我就可以为大家总结之前实现的 Namesrv 功能的第一个缺陷了：**

**1 那就是客户端和服务端的公共功能没有定义到抽象父类中，只要是客户端和服务端相同的功能都可以定义在抽象父类中，不同的功能可以也可以把方法先定义在抽象父类中，子类们各自实现不同的方法逻辑**。



很好，到此为止我就终于把这个简单的知识点分析完毕了，接下来就可以真正引入 Netty 构建的客户端和服务端的抽象父类了，从标题就能看出来，**我把这个抽象父类定义为了 NettyRemotingAbstract**，那么这个 NettyRemotingAbstract 类中应该定义什么内容呢？**客户端、服务端存储请求处理器的 processorTable 成员变量显然应该定义到这个 NettyRemotingAbstract 类中**，那除此之外还可以定义什么内容呢？刚才我在实现 Netty 构建的客户端时为大家简单分析过了，客户端和服务端使用 Channel 通信，而 Channel 是可以全双工通信，这也就意味着客户端可以主动向服务端发送通信请求，与此同时，服务端也可以主动向客户端发送通信请求，既然是这样的话，**那么发送请求显然就是客户端和服务端的公共功能了，那发送请求的方法就可以定义在 NettyRemotingAbstract 抽象父类中**。而通常来说，**发送请求的方式有三种，一种是同步发送请求，一种是异步发送请求，一种是发送单向请求。同步发送请求和异步发送请求的区别是异步发送请求可以定义响应回调方法，请求发送出去后就不关心了，接收到响应后执行事先定义完毕的回调方法；至于单向发送请求就更简单了，单向请求不关心响应，也就是说假如客户端向服务端发送了单向请求，那么服务端不必对这个请求回复响应**。好了，这几种请求也分析完毕之后，接下来就让我为大家展示一下初步定义完毕的 NettyRemotingAbstract 类，请看下面代码块。

## 引入信号量机制


信号量机制是新引入的概念，接下来就让我先为大家解释一下信号量机制是什么。当客户端和服务端进行通信的时候，不管是谁想谁发送请求，只要是没有对可以发送的请求数量进行限制，那么这两端就可以一直发送消息。比如说在某一个时刻，服务端要向多个客户端发送成百上千个请求，这也就意味着服务端内部要创建非常多的请求对象，还要执行发送请求的操作，**我们先不说大量请求发送时创建那么多请求对象会占用多少内存，会不会造成内存溢出，假如内存够用的话，发送请求的写缓冲区就那么点，这么多请求要全部发送出去，肯定会造成后面的请求发送超时**，这不是我们想看到的情况。为**了避免出现这种情况，提高服务端或者客户端发送请求的效率，我们就需要对客户端、服务端在同一时间能够发送的请求数量做一个限制**。比如说就定义一个数值，客户端和服务端在同一时刻能够发送的请求数量是 256 个，只要在某个时刻双端发送请求数量达到 256 个了，那么就不能再发送消息。这个逻辑大家应该可以理解吧？如果大家都理解了这个逻辑，那接下来我们就可以实现对应的功能了，怎么才能给服务端或者客户端发送请求的数量定义一个限制呢？定义了这个限制之后，又该怎么让这个限制发挥作用呢？这时候就轮到信号量机制登场了，**因为定义的客户端、服务端在某个时刻可以发送的最大请求数就是信号量**。



其实信号量就是一个数值，在代码中，我就可以用 int 整数来定义，定义这个数值非常简单，关键是如何让它发挥作用。**如果大家对 JDK 并发包下的内容都很熟悉，那肯定是在在 JDK 的 concurrent 包下有一个 Semaphore 类，这个类的对象就是一个信号量**。说是信号量，其实它就是一个计数器，如果我们创建了一个 Semaphore 对象，就像下面代码块展示的这样，请看下面代码块。

```java

//timeoutMillis是获取超时时间，返回值表示是否获取成功
//如果获取成功，那么Semaphore中的许可数量就会变成255

boolean acquired = semaphore.tryAcquire(timeoutMillis, TimeUnit.MILLISECONDS);

        this.semaphore = semaphore;

            }
        }
    }

        return semaphore;
    }
```

**4 如果大家理解了第三点的内容，那现在就有一个新的问题，如果服务端或者是客户端成功把请求发送给了对方，但是迟迟接收不到响应？这个时候发送请求之前获得的信号量许可证该怎么释放呢？也就是说请求发送成功了，但一直没有接收到响应，难道就不释放信号量许可证了吗**？



以上四点就是上面代码块中存在的问题，也就是我们目前实现的 NettyRemotingAbstract 类的缺陷。要想解决上面四个问题，那就要寻找一个突破口，**而这个突破口就是我早就想跟大家说明的目前实现的 Namesrv 服务端存在的第二方面的缺陷：**

**2 我们并没有为 Namesrv 服务端构建完善的响应体系，这就导致我们无法顺利实现很多功能。响应体系一旦构建完毕，也就是说响应对象定义好了，请求和响应一一对应的方式也实现完毕了，回复响应的方法也定义好了，扫描过期响应的功能也实现了，那以上的问题就全部都可以解决了**。



所以接下来我们就要先回到 Namesrv 服务端的功能上，先为它实现了完善的响应体系，然后才能回过头重构 NettyRemotingAbstract 类，解决这个类中发送请求时遇到的所有问题。但是我不得不说一句，要为 Namesrv 实现的响应体系内容很多，这一章的内容已经够多了，所以只能放到下一章讲解。



大家可能也发现了，第二版本代码内容对应的文章有点多，而且我实现各个功能的速度也不是很快，我想为大家谈谈我的感受，然后解释一下我为什么这么做：在我看来，实现一个框架的过程本来就比较复杂，在实现的过程中总是一个问题引出另一个问题，一个功能依赖另一个功能。各个模块和体系并不一定都是完全独立的，更多的情况是它们彼此依赖，协同工作。我们现在为 Namesrv 实现的通信组件是最基础的组件，也是最重要的组件，之后的业务功能，业务逻辑能否顺利执行，都要依赖目前实现的通信组件。原因很简单，业务往来肯定要发送消息吧，那就必须用到通信组件。
