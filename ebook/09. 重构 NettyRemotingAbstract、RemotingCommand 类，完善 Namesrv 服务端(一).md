```java
package org.apache.rocketmq.remoting.protocol;


/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2024/12/27
 * @方法描述：Remoting协议中封装网络数据的对象，RocketMq框架内部通信时，请求体和响应体都是由这个类的对象来表示的
 * 目前我们只关注如何封装请求体
 */
public class RemotingCommand {

    //当前消息如果是请求，那么这个成员变量就是请求码，代表请求的请求类型
    //否则就是响应码
    private int code;

    //请求或响应有效消息体
    private byte[] body;

    //这个标志位就是用来计算当前消息是请求消息还是响应消息的
    //flag为1时，当前对象就是响应对象，为0时就是请求对象
    //为2时则为单向请求对象
    private int flag = 0;

    //因为RemotingCommand即可表示请求也可以表示响应
    //在处理RemotingCommand消息的时候要先判断接收到的RemotingCommand是请求还是响应
    //而这个成员变量就是用来设置当前RemotingCommand是请求还是响应
    private static final int RPC_TYPE = 0;

    //下面这个算是一个扩展，大家可以看一看，我就不在文章中详细讲解了
    //用来计算当前RPC操作是否为单向RPC操作
    private static final int RPC_ONEWAY = 1;

    //生成唯一请求Id的成员变量
    private static AtomicInteger requestId = new AtomicInteger(0);

    //请求唯一标识，这里可以看出来每创建一个RemotingCommand对象的时候
    //请求的唯一Id就已经被赋值了，并且请求Id是唯一递增的
    private int opaque = requestId.getAndIncrement();

    //受保护的构造方法，防止在该类之外直接实例化RemotingCommand对象
    protected RemotingCommand() {
        
    }


    //设置消息为响应类型的方法
    public void markResponseType() {
         //这里我要解释一下，因为RPC_TYPE是0
        //这里和1做位运算得到的还是1
        int bits = 1 << RPC_TYPE;
        //1又和flag做位运算，这里就相当于把1赋值给flag
        this.flag |= bits;
    }

    //判断当前消息是否为响应消息
    public boolean isResponseType() {
        //这里作位运算得到的还是1
        int bits = 1 << RPC_TYPE;
        //this.flag & bits得到的是1，bits也是1
        //所以，只要调用markResponseType()方法，就会把flag设置为1
        //那么当前对象就代表响应对象
        //其实本质上还是判断flag是0还是1来决定消息是请求还是响应，只不过运用位运算做了一点扩展
        //让flag还可以表示单向消息了
        return (this.flag & bits) == bits;
    }


    //标记当前消息为单向消息，如果是单项消息则不用回复响应
    public void markOnewayRPC() {
        int bits = 1 << RPC_ONEWAY;
        this.flag |= bits;
    }


    //判断当前消息是否为单向消息
    public boolean isOnewayRPC() {
        int bits = 1 << RPC_ONEWAY;
        return (this.flag & bits) == bits;
    }
    

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @date:2024/12/28
     * @方法描述：创建请求对象的方法，在第二版本代码中，该方法在NettyCLient测试类中被调用了
     */
    public static RemotingCommand createRequestCommand(int code) {
        //创建RemotingCommand对象的时候，请求ID就已经被赋值了
        RemotingCommand cmd = new RemotingCommand();
        //设置请求类型码
        cmd.setCode(code);
        return cmd;
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @date:2024/12/28
     * @方法描述：创建响应对象的方法

    public static RemotingCommand createResponseCommand(int code) {
        RemotingCommand cmd = new RemotingCommand();
        //设置当前对象为响应对象
        cmd.markResponseType();
        //设置响应码
        cmd.setCode(code);
        return cmd;
    }
```

好了，在阅读完了上面的代码块之后，我相信大家肯定都回忆起来了，目前 Namesrv 服务端接收到的客户端消息就会由 NettyServerHandler 处理器的 channelRead0 方法处理，这个逻辑应该非常清晰了，而且也非常简单。从代码逻辑上看，这部分内容确实不用重构，但是按照我们对 Netty 框架的理解，或者说对 Netty 构建的服务器的理解，我相信每一位朋友都想重构这部分的代码，原因很简单：**目前 Namesrv 服务端对所有客户端发送的消息的接收和处理都是由 Netty 服务器自己的单线程执行器处理的**。这一点大家都能理解吧？当 Netty 构建的服务端接收到消息后，就会在单线程执行器中回调 NettyServerHandler 处理器的 channelRead0 方法，让该方法处理接收到的消息，因此 channelRead0 方法也是被 Netty 的单线程执行器执行的，既然 channelRead0 是由 Netty 单线程执行器执行的，那么 channelRead0 方法内部的所有操作，也都是由 Netty 的单线程执行器执行的，而 channelRead0 方法内部执行的所有操作，其实都属于 RocketMq 框架的业务操作了。这么一来的话，**也就意味着 Netty 构建的服务器内部的单线程执行器不仅要负责接收客户端发送过来的消息，还要负责处理这些消息，执行和 RocketMq 相关的业务操作**。这当然不是我们想看到的情况，**我们希望的是 Netty 构建的服务器只负责消息的接收和发送，而和 RocketMq 相关的业务操作，应该由 RocketMq 自己的线程来执行，如果 Netty 的单线程执行器把这两者全负责了，那么接收和发送消息的效率肯定就会受到影响，这也正是 Namesrv 目前存在的第三个严重缺陷**！这样分析下来，那我们肯定希望对 NettyServerHandler 处理器的 channelRead0 方法进行一番重构：**也许我们可以再定义一个业务线程池，然后在 channelRead0 方法中把接收到的客户端消息交给业务线程池处理，这样一来执行 channelRead0 方法的 Netty 单线程执行器只需要把客户端消息提交给业务线程池就可以返回了，也就可以执行其他任务了**。这个逻辑应该也很容易理解吧？



如果上面的逻辑大家都理解了，那接下来我们就可以分析一下，要为 RocketMq 的 Namesrv 新定义的业务线程池，应该定义在哪里了。也许大家的第一想法就是把这个业务线程池定义在 NettyRemotingAbstract 类中，也就是给 NettyRemotingAbstract 类定义一个新的线程池成员变量，然后在 NettyRemotingAbstract 类的 processMessageReceived() 方法中使用这个线程池，也就是说，让 Netty 的单线程执行器在执行 processMessageReceived() 方法的时候把消息交给 Mq 的业务线程池处理。这么做当然没有问题，但实际上我们还可以更细致一点。接下来就让我为大家解释一下，所谓的细致指的是什么。



如果大家还记得之前的内容，那大家肯定知道，在我们已经构建好的 Namesrv 服务端中，定义了一个 RequestCode 类，这个类中定义了一些请求码，就像下面代码块展示的这样，请看下面代码块。

上面代码块中展示的请求码其实就代表请求类型，而当客户端向服务端发送请求的时候，就会把请求类型封装到 RemotingCommand 对象中，这样一来，Namesrv 服务端接收到请求之后，就可以根据请求类型找到对应的请求处理器，然后使用请求处理器处理请求即可。当然，**我们也早就为 Namesrv 定义好了两个请求处理器，一个是 DefaultRequestProcessor 请求处理器，另一个是 ClientRequestProcessor 请求处理器。其中 ClientRequestProcessor 请求处理器只处理 GET_ROUTEINFO_BY_TOPIC 类型的请求，而 DefaultRequestProcessor 请求处理器则负责处理其他的所有类型的请求**。这些内容大家应该还有印象吧？



如果大家还记得这些内容，那接下来就很好说了，既然刚才我们说为 Namesrv 定义业务线程池的时候要更细致一点，**那我们不妨就为每一个请求处理器都定义一个线程池，这样一来，每一个请求处理器都可以使用自己的业务线程池处理请求，彼此互不干扰，专心自己的工作即可**。如果是这样的话，那么 Namesrv 服务端处理请求的逻辑就变成了这样：**当 Namesrv 接收到客户端发送过来的请求时，也就是当 Netty 单线程执行器调用了 NettyServerHandler 处理器的 channelRead0() 方法后，只需要在后续执行的操作中，根据接收到的请求的类型找到对应的请求处理器，然后得到这个处理器的业务线程池，最后再把请求提交给业务线程池处理即可**。这么重构之后，Netty 的单线程执行器就只负责接收请求，把请求提交给对应的业务线程池，至于请求如何被处理，Netty 的单线程执行器就不必关心了。好了，如果这个逻辑大家都理解了，那接下来我们就可以为 Namesrv 的两个请求处理器分别定义业务线程池了。

在目前的 Namesrv 服务端中，接收到的客户端请求最终会被 NettyRemotingAbstract 类的 processRequestCommand() 方法处理，在该方法中，会根据请求的类型得到具体的请求处理器，然后使用请求处理器处理请求，但刚才我们已经为每一个请求处理器定义了对应的业务线程池，**这个时候我们就可以根据接收到的请求的类型从 processorTable 表中找到对应的 Pair 对象，然后从 Pair 对象中得到具体的请求处理器和对应的业务线程池，接着把请求提交给业务线程池处理即可**。当然，这么说肯定不太准确，**因为请求肯定是被请求处理器处理的，所以确切地说，应该把请求处理器处理请求的操作封装成一个 Runnable，然后把这个任务提交给业务线程池执行**。所以，NettyRemotingAbstract 类的 processRequestCommand() 方法最终应该被重构成下面这样，请看下面代码块。

```java
package org.apache.rocketmq.remoting.netty;


/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2024/12/25
 * @方法描述：Netty服务器的抽象父类，在第一版本代码中，这个类的内容非常简单，在第二版本代码中，这个类就会被填充非常多的内容，实际上netty服务端处理接收到的请求的核心逻辑，就全部定义在了当前类中，第二版本代码大家就全清楚了
 */
public abstract class NettyRemotingAbstract {

    //省略部分内容 

    //请求码和封装了与请求对应的请求处理器、执行器的Pair对象的映射表
    protected final HashMap<Integer/* request code */, Pair<NettyRequestProcessor, ExecutorService>> processorTable = new HashMap<>(64);

    //默认请求处理器和执行器的映射表
    protected Pair<NettyRequestProcessor, ExecutorService> defaultRequestProcessorPair;


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @date:2024/12/27
     * @方法描述：处理请求的方法
     */
    public void processRequestCommand(final ChannelHandlerContext ctx, final RemotingCommand cmd) {

        //根据请求码从处理器表中得到封装了处理该请求处理器的Pair对象
        final Pair<NettyRequestProcessor, ExecutorService> matched = this.processorTable.get(cmd.getCode());
        //判断是否从处理器表中得到了对应的Pair对象
        final Pair<NettyRequestProcessor, ExecutorService> pair = null == matched ? this.defaultRequestProcessorPair : matched;
        //得到请求的唯一Id
        final int opaque = cmd.getOpaque();
        if (pair == null) {
            //如果没有找到处理该请求的处理器，那就直接回复给客户端一个不支持该请求的响应
            String error = " request type " + cmd.getCode() + " not supported";
            //创建响应对象，回复不支持该请求的响应码
            final RemotingCommand response =RemotingCommand.createResponseCommand(RemotingSysResponseCode.REQUEST_CODE_NOT_SUPPORTED, error);
            //设置响应唯一Id
            response.setOpaque(opaque);
            //用channel回复响应
            writeResponse(ctx.channel(), cmd, response);
            log.error(RemotingHelper.parseChannelRemoteAddr(ctx.channel()) + error);
            return;
        }

        
        //执行到这里意味着找到了处理该请求的处理器，但这个时候并不用直接处理请求，因为Namesrv要接收的请求太多了，可能有很多客户端都向Namesrv发送了同一类型的请求
        //直接就让该请求的处理器处理的话，显然有点忙不过来，所以这个时候就可以把处理该请求的操作封装成一个任务，然后把任务提交到请求处理器处理请求的执行器任务队列中
        //等待执行器依次处理即可，这里就是把处理请求的操作封装成了一个任务
        Runnable run = buildProcessRequestHandler(ctx, cmd, pair, opaque);


        try {
            //pair中存储了请求处理器和该请求处理器要处理请求的执行器，这里就是把任务对象提交给执行器的任务队列了
            pair.getObject2().submit(run);
        } catch (RejectedExecutionException e) {
            //如果触发线程池的拒绝策略，说明线程池任务队列满了
            //回复客户端系统繁忙的响应
            final RemotingCommand response = RemotingCommand.createResponseCommand(RemotingSysResponseCode.SYSTEM_BUSY,
                    "[OVERLOAD]system busy, start flow control for a while");
            //设置响应Id
            response.setOpaque(opaque);
            //回复客户端响应
            writeResponse(ctx.channel(), cmd, response);
        } catch (Throwable e) {
            //忽略异常，这里在源码中并不是真的忽略异常
            //而是记录相关信息到性能检测组件中，但在我们的代码中还没有引入性能检测组件，所以我就直接把这里的代码注释了
        }
        
    }





    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @date:2024/12/28
     * @方法描述：把处理请求的操作封装成了任务的方法，在文章中，我对该方法做了简化
     */
    private Runnable buildProcessRequestHandler(ChannelHandlerContext ctx, RemotingCommand cmd,
                                                Pair<NettyRequestProcessor, ExecutorService> pair, int opaque) {
        //直接返回一个Runnable对象
        return () -> {
            RemotingCommand response;
            try {
                //在这里获得请求处理器，然后使用请求处理器处理接收到的请求
                response = pair.getObject1().processRequest(ctx, cmd);
            } catch (AbortProcessException e) {
                response = RemotingCommand.createResponseCommand(e.getResponseCode(), e.getErrorMessage());
                response.setOpaque(opaque);
                writeResponse(ctx.channel(), cmd, response);
            }
        };
    }
    

    

    //省略部分代码

}
```

上面代码块中的注释非常详细，所以我也就不再为大家重复讲解其中的逻辑了。总之，到此为止，我们就为 Namesrv 服务端成功引入了业务线程池，让 Netty 的单线程执行器可以专心接收请求，而 RocketMq 的业务逻辑，则让业务线程池处理即可。当然，看到这里肯定有朋友会提出一个问题，**那就是目前我们只是给 Namesrv 的两个请求处理器定义的对应的业务线程池，这让 Netty 的单线程执行器不必再关注业务上的任何操作，但是 Namesrv 服务端接收到响应的操作并没有被重构，这也就意味着 Netty 的单线程执行器还需要处理接收到的响应**，这显然和我们预想的不太一样。我把目前 Namesrv 服务端处理响应的相关代码也搬运到这里了，请看下面代码块。

```java
                default:

     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * 和请求对应的ResponseFuture对象中，并且还会执行ResponseFuture内部定义完毕的回调方法

        final int opaque = cmd.getOpaque();

        final ResponseFuture responseFuture = responseTable.get(opaque);

            if (responseFuture.getInvokeCallback() != null) {

                responseFuture.executeInvokeCallback();

            //没有从响应表中找到对应的ResponseFuture对象，就记录告警日志，这时候很可能就是响应到达的太晚了，请求已经过期被丢弃了
            log.warn("receive response, cmd={}, but not matched any request, address={}", cmd, RemotingHelper.parseChannelRemoteAddr(ctx.channel()));
        }
    }
```

很简单，首先肯定是要明确消息的内容，也就是说，我们必须先确定客户端与服务端通信的过程中，发送的每一条消息的内容是什么。按照我们之前实现的内容来看，客户端与服务端通信的消息非常简洁，如果是请求消息，那么消息就只包含请求码和请求体；如果是响应消息，那么消息就只包含响应码和响应体，看起来确实非常简洁，没有多少内容。但现在我们要仿照 RocketMq 源码完善通信协议了，这时候就应该看看在 RocketMq 源码中，Namesrv 客户端与服务端通信的消息内容是怎么定义的了。



既然谈到了 RocketMq 源码，那现在我终于可以跟大家直接挑明了，实际上在 RocketMq 源码中，客户端与服务端发送通信消息时，并不只是把请求码、请求体或响应码、响应体封装到 RemotingCommand 消息对象中，实际上会把请求头、请求体或者响应头、响应体封装到 RemotingCommand 消息对象中，然后再把消息对象发送给对方。看到这里，大家肯定会有疑惑，请求头和响应头是什么呢？接下来就让我给大家解释一下，实际上在 RocketMq 源码中，为每一种请求都定义了一个专门的请求头对象，**比如说在第二版本代码的测试类中，客户端想从 Namesrv 服务端获取指定主题下的路由信息，那客户端肯定就会给 Namesrv 服务端发送一个 RequestCode.GET_ROUTEINFO_BY_TOPIC 类型的请求，这个类型的请求就是根据主题信息获得对应的路由信息的**。既然是这样，那么 Namesrv 服务端肯定就需要知道客户端想获得哪个主题下的路由信息吧？**而对应的主题信息就会被封装到与 RequestCode.GET_ROUTEINFO_BY_TOPIC 请求类型对应的请求头中，然后把请求头封装到 RemotingCommand 对象中，再把 RemotingCommand 消息对象发送给服务端即可**。我把第二版本代码的测试类给大家展示一下，大家就清楚了，请看下面代码块。
