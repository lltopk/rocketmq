大家肯定已经很熟悉上面代码块中的内容了，我在上一章结尾为大家简单总结了一下上面代码块中存在的四个问题，当时总结得可能有些啰嗦，现在我把那四个问题又精简了一下，再次展示给大家：

**1 目前实现的发送请求的方法，没有对请求发送失败、或者异常情况的处理。**

**2 在 RocketMq 源码中，发送的请求接收到响应后，就可以释放对应的信号量许可证；但假如成功发送的请求一直没有接收到响应，获取的信号量许可证该怎么释放呢？**

**3 响应对象还没有定义，不管是客户端还是服务端，发送请求后都无法接收响应，那响应对象该如何定义呢？**

可以看到，我把上一章提出的四个问题简化成三个问题了，其实就是把第二和第三个问题合并了。要想解决这几个问题，**我们就要继续完善正在构建的 Namesrv 服务端，也就是要为 Namesrv 服务端构建完善的响应体系**。当然，这个响应体系不仅仅可以在 Namesrv 服务端内部使用，在后面章节实现的客户端中，也会使用这个响应体系。那么 Namesrv 服务端的响应体系应该怎么构建呢？或者说一个完善的相应体系该怎么构建呢？还是老样子，我也总结好了几点，想从这几个方面来构建：

**1 首先肯定要把响应对象定义出来，也就是响应体，响应体可以承载真正的响应信息，客户端服务端才能真正通信，才能知道发送的请求，以及请求要执行的操作是否成功了，如果失败了，那么失败原因，或者说响应失败码就可以通过响应传递给发送请求的一方，让发送请求放可以调整后续操作。**

**2 因为请求和响应对象是一一对应的，响应对象定义完毕之后，必须要和请求建立一一对应的关系，这样发送方法才能知道接收到的响应对应的是哪个请求。**

**3 响应定义完毕了，和请求一一对应的关系也建立完毕了，接下来就可以定义回复响应的方法了，把响应回复给发送请求的那一方。**

**4 最后要实现的其实算是一个兜底功能，因为在程序运行的过程中很可能会出现这样一种情况，那就是请求发送成功了，但迟迟没有接收到响应，这个时候就可以在后台启动一个定时任务线程，定时扫描哪些请求还没有接收到响应，然后再执行相关操作即可**。

根据以上四个要点，我们就可以立刻构建一个功能完善的响应体系，如果大家理解了这部分逻辑，那接下来我们就可以按顺序一一实现上面四个要点对应的功能了。

当然，在 RocketMq 源码中并不是使用 int 整数的值来判断当前 RemotingCommand 对象表示请求还是响应，而是使用了位运算，但核心原理和我刚才分析的没什么区别，接下来我把仿照 RocketMq 源码重构之后的 RemotingCommand 类展示一下，请看下面代码块。

```java

/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

 * 目前我们只关注如何封装请求体
 */
public class RemotingCommand {

    //当前消息如果是请求，那么这个成员变量就是请求码，代表请求的请求类型
    //否则就是响应码
    private int code;

    //请求或响应有效消息体
    private byte[] body;

    //这个标志位就是用来计算当前消息是请求消息还是响应消息的
    //flag为1时，当前对象就是响应对象，为0时就是请求对象
    //为2时则为单向请求对象
    private int flag = 0;

    //因为RemotingCommand即可表示请求也可以表示响应
    //在处理RemotingCommand消息的时候要先判断接收到的RemotingCommand是请求还是响应
    //而这个成员变量就是用来设置当前RemotingCommand是请求还是响应
    private static final int RPC_TYPE = 0;

    //下面这个算是一个扩展，大家可以看一看，我就不在文章中详细讲解了
    //用来计算当前RPC操作是否为单向RPC操作
    private static final int RPC_ONEWAY = 1;


    //设置消息为响应类型的方法
    public void markResponseType() {
         //这里我要解释一下，因为RPC_TYPE是0
        //这里和1做位运算得到的还是1
        int bits = 1 << RPC_TYPE;
        //1又和flag做位运算，这里就相当于把1赋值给flag
        this.flag |= bits;
    }

    //判断当前消息是否为响应消息
    public boolean isResponseType() {
        //这里作位运算得到的还是1
        int bits = 1 << RPC_TYPE;
        //this.flag & bits得到的是1，bits也是1
        //所以，只要调用markResponseType()方法，就会把flag设置为1
        //那么当前对象就代表响应对象
        //其实本质上还是判断flag是0还是1来决定消息是请求还是响应，只不过运用位运算做了一点扩展
        //让flag还可以表示单向消息了
        return (this.flag & bits) == bits;
    }


    //标记当前消息为单向消息，如果是单项消息则不用回复响应
    public void markOnewayRPC() {
        int bits = 1 << RPC_ONEWAY;
        this.flag |= bits;
    }


    //判断当前消息是否为单向消息
    public boolean isOnewayRPC() {
        int bits = 1 << RPC_ONEWAY;
        return (this.flag & bits) == bits;
    }


    //其他get、set方法省略
}
```

好了，上面代码块展示的就是重构之后的 RemotingCommand 类，当然，只是暂时重构成这样，接下来还会继续重构。但在继续重构之前先让我们仔细观察一下目前的 RemotingCommand 类，目前的 RemotingCommand 类中包含了多个成员变量，其中 code 成员变量可以表示请求类型或者响应码，body 成员变量可以表示请求或者响应的有效体，flag 成员变量可以表示当前 RemotingCommand 对象是否为请求对象和响应对象。很好，这次重构完毕的 RemotingCommand 类显然很符合我们的期望，现在这个 RemotingCommand 类的对象已经可以即表示请求对象，又能表示响应对象了。这也意味着之前我提出的四个要点中的第一个要点对应的功能已经实现完毕了。好了，**接下来我们就要实现第二个要点对应的功能了，那就是为请求和响应建立一一对应的关系**，那这个功能该怎么实现呢？



现在我能想到的就是被应用的最广泛，也是最简单的一种方式：**那就是给请求和响应都定义一个唯一 Id，确切地说，是给每一个请求都定义一个唯一 Id，而收到请求的一方在回复响应时，把请求的唯一 Id 设置给响应。发送请求的一方就可以通过接收到响应的 Id 找到与之对应的请求了，只要请求和响应的 Id 一致，就意味着请求和响应是一对**。这个逻辑并不难理解吧？当然，可能有朋友会问为什么非要实现请求与响应一一对应的关系呢？简单来说，如果你设计的程序发送请求的操作是完全同步的，发送请求的线程在发送了请求之后什么也不做，一直等待接收到响应后再开始继续工作，处理响应，那这种情况下就算没有给请求和响应定义一一对应的 Id，接收到的响应肯定和请求是一对。但是，在我们应用的众多框架中，**更有可能出现的情况是发送请求时会采取异步发送的方式**，也就是说把请求发送出去后发送请求的线程就紧接着去忙别的事了，不会一直干等着响应到来(**当然，也有可能使用伪异步方式发送请求，RocketMq 中就是这样，一会我就为大家解释**)。所以，等响应真正到来的时候，发送请求的线程就需要根据接收到的响应的 Id 找到与之对应的请求，找到对应的请求之后就可以执行真正有用的操作了，比如说释放信号量对象的许可证，或者是执行对应的回调方法，这种操作在 RPC 远程调用中非常常见吧？总而言之，**只有明确知道请求是和接收到的响应一一对应的，才能知道这次请求的结果，才能执行后续的操作**。这个逻辑应该也不难理解吧？



好了，我们分析了一大堆，那么应该怎么实现请求和响应一一对应的功能呢？或者说，怎么给请求和响应定义唯一 Id 呢**？在我们实现的请求响应体系中，请求和响应是用同一个对象表示的，也就是 RemotingCommand 对象，那就直接给这个 RemotingCommand 类定义一个 Id 成员变量好了，就使用 int 整数来表示这个唯一 Id。然后我再定义一个 AtomicInteger 原子对象成员变量，并且还要把这个成员变量定义为静态的，这样一来，就可以每创建一个 RemotingCommand 对象，就让 AtomicInteger 成员变量自增得到一个整数，然后把整数分配给 Id 成员变量，那所有请求的 Id 肯定都是唯一的了。而请求的 Id 会赋值给响应对象的 Id 成员变量，那么响应对象的 Id 肯定也是唯一的，并且和请求一一对应**。接下来我们就可以按照这个思路继续重构 RemotingCommand 类，代码我已经写好了，并且我还把创建 RemotingCommand 请求对象和响应对象的方法都展示在下面代码块中了，请看下面代码块。

## 引入 ResponseFuture 类


按照我们之前的分析，**接收到响应后需要执行释放信号量许可证的操作，当然，如果发送请求时还定义了收到响应时要被执行的回调方法，那么现在响应已经回复了，回调方法也应该被执行**。那么这一切该怎么执行呢？我们根本无法得到要执行的回调方法，也无法得到要被释放的信号量对象啊？并且之前我还跟大家分析了，需要建立响应和请求一一对应的关系，现在看来就算建立了这个响应也没什么用啊，我们只能接收到响应，除此之外，似乎什么也得不到。至少在 processResponseCommand() 方法中除了响应什么也得不到。如果，**我是说如果在程序发送请求的时候，创建一个新的对象，比如说就定义一个 ResponseFuture 对象，这个对象把为该请求申请的信号量对象许可证和需要回调的方法都封装了，然后再把该 ResponseFuture 对象存储起来，可以存储到一个 Map 中，Map 的 key 就是与 ResponseFuture 对象对应的请求的唯一 Id，value 就是 ResponseFuture 对象本身，那么接收到响应的时候，就可以通过唯一 Id 从 Map 中找到这个对象，之后就可以从 ResponseFuture 中得到回调方法和要释放的信号量，再执行对应操作即可**。这个 ResponseFuture 对象可以定义成下面这样，请看下面代码块。

```java
 * @方法描述：该类的对象就是用来封装响应的对象，每一个请求都会对应一个ResponseFuture对象，用来判断发送的请求是否超时

public class ResponseFuture {
    
   
    //唯一Id，一个响应要和一个请求对象，发送请求的时候会生成请求Id
    //在发送请求的时候会创建一个ResponseFuture对象，这个对象会封装接收到的响应，并且会用请求Id给该对象的opaque成员变量赋值
    private final int opaque;
   
    //收到响应后要回调的方法
    private final InvokeCallback invokeCallback;

        this.invokeCallback = invokeCallback;
        this.timeoutMillis = timeoutMillis;
        this.once = once;

     /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * @方法描述：在该方法中，接收到响应后的回调方法会被回调

    public void executeInvokeCallback() {
        //得到响应对象
        RemotingCommand response = getResponseCommand();
        //在这里执行回调方法即可
        invokeCallback.operationSucceed(response);
        //该方法其他内容省略
    }

    public void release() {

            this.once.release();
        }
    }

    }
```

看完了 ResponseFuture 类的内容之后，我相信每一位朋友都明白我的意图了，**我们只需要在程序发送请求的时候创建一个 ResponseFuture 对象，然后把该对象存放到 Map 中即可。而这个 Map 就是我为 NettyRemotingAbstract 类新定义的成员变量，processResponseCommand() 方法也定义在了 NettyRemotingAbstract 类中，这样一来，processResponseCommand() 方法在处理响应的时候就可以直接从 Map 成员变量中根据响应唯一 Id 获得对应的 ResponseFuture 对象，然后执行后续操作**。接下来请大家在阅读一下我重构完毕的 NettyRemotingAbstract 类，请看下面代码块。

```java
package org.apache.rocketmq.remoting.netty;


/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
 * @author：陈清风扬，个人微信号：chenqingfengyangjj。
 * @date:2024/12/25
 * @方法描述：Netty服务器的抽象父类，在第一版本代码中，这个类的内容非常简单，在第二版本代码中，这个类就会被填充非常多的内容，实际上netty服务端处理接收到的请求的核心逻辑，就全部定义在了当前类中，第二版本代码大家就全清楚了
 */
public abstract class NettyRemotingAbstract {

     
    //单向请求信号量
    protected final Semaphore semaphoreOneway;

    //异步请求信号量，同步请求也会从这个信号量对象中获取许可证
    //也就是说，这个信号量对象会被同步请求、异步请求共用
    protected final Semaphore semaphoreAsync;

    //key是请求码，也就是请求类型，value就是对应的请求处理器
    protected final HashMap<Integer/* request code */, NettyRequestProcessor> processorTable = new HashMap<>(64);

    //默认请求处理器
    protected NettyRequestProcessor defaultRequestProcessorPair;

    //这个就是响应表，每发送一个请求就要创建一个ResponseFuture对象，用来接收与这个请求对应的响应
    //接收到响应并处理响应的时候，就会用到这个响应表，响应表的key就是请求和响应共享的唯一Id
    protected final ConcurrentMap<Integer /* opaque */, ResponseFuture> responseTable = new ConcurrentHashMap<>(256);


    //省略其他内容

    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @date:2024/12/28
     * @方法描述：发送请求的方法
     */
    protected CompletableFuture<ResponseFuture> invoke0(final Channel channel, final RemotingCommand request, final long timeoutMillis) {

        //得到请求发送操作开始执行的时间
        long beginStartTime = System.currentTimeMillis();

        //尝试在指定时间获取异步发送请求的信号量指标，这里之所以设置这个信号量，是希望可以把服务器内发送请求的数量控制在一定范围之内
        //防止请求发送过多导致服务器内部资源被过度挤占，如果没有获取到信号量，就停止发送请求
        boolean acquired = this.semaphoreAsync.tryAcquire(timeoutMillis, TimeUnit.MILLISECONDS);

        if (acquired) {
            //执行到这里就意味着成功获得到信号量了，也就意味着可以成功发送本次请求
            //那就把这个信号量封装到SemaphoreReleaseOnlyOnce对象中，这么做的用意也很简单，就是防止同意信号量被多次释放
            //这次申请到的信号量只被释放一次
            final SemaphoreReleaseOnlyOnce once = new SemaphoreReleaseOnlyOnce(this.semaphoreAsync);
            //得到从操作开始到当前的消耗时间，获取信号量也许会消耗一部分时间
            long costTime = System.currentTimeMillis() - beginStartTime;
            //得到的这个操作消耗时间和请求超时时间对比一下，如果请求超时时间小于操作消耗时间，说明执行发送请求的操作早就超过请求超时时间了
            //这时候也就没必要继续发送请求了
            if (timeoutMillis < costTime) {
                //释放信号量
                once.release();
                //这里暂时返回null，后面再次重构当前方法的时候，再返回CompletableFuture对象
                return null;
            }

            //创建一个ResponseFuture对象，并且设置了请求超时时间，以及响应回调对象，信号量对象
            final ResponseFuture responseFuture = new ResponseFuture(opaque,
                    new InvokeCallback() {

                        //该方法会在请求——响应全流程结束之后被回调
                        @Override
                        public void operationComplete(ResponseFuture responseFuture) {
                            //该方暂不实现
                        }

                        //该方法会在该请求成功接收到响应后被回调
                        @Override
                        public void operationSucceed(RemotingCommand response) {
                            //该方暂不实现
                        }

                        //该方法会在获取响应失败时被回调
                        @Override
                        public void operationFail(Throwable throwable) {
                            ///该方暂不实现
                        }
                        //注意，这里把响应超时时间，信号量对象设置到ResponseFuture对象中了
                    }, timeoutMillis - costTime, once);

            
            //把ResponseFuture存储到响应表中
            this.responseTable.put(opaque, responseFuture);
            
            //在这里把请求发送出去了，请大家想一想，请求成功发送了，那么信号量对象应该在哪里被释放呢？
            channel.writeAndFlush(request);
            //这里暂时返回null，后面再次重构当前方法的时候，再返回CompletableFuture对象
            return null;

            //实际上，这个方法我已经定义不下去了，因为存在太多问题了，大家先看一看，然后让我为大家分析一下。
            
        }else {
            //执行到这里意味着没有成功获得到信号量，暂时写成直接返回null
            //等待后面重构
            return null;
        }
    }


     /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @date:2024/12/28
     * @方法描述：处理接收到的响应的方法，该方法在文章中被简化了，具体内容可以看我提供的第二版本代码
     */
    public void processResponseCommand(ChannelHandlerContext ctx, RemotingCommand cmd) {
        //先获得响应的唯一Id
        final int opaque = cmd.getOpaque();
        //从响应表中得到对应的ResponseFuture对象
        final ResponseFuture responseFuture = responseTable.get(opaque);
        
        if (responseFuture != null) {
            //如果ResponseFuture对象不为null，就把接收到的响应设置到ResponseFuture对象中
            //方便ResponseFuture对象内部的回调方法使用
            responseFuture.setResponseCommand(cmd);
            
            //到这时候响应也接收到了，也就可以把ResponseFuture对象从响应表中移除了，避免对与ResponseFuture对象对应的请求产生请求超时的误判
            responseTable.remove(opaque);
            //判断ResponseFuture对象中是否设置了回调方法
            if (responseFuture.getInvokeCallback() != null) {
                //如果设置了，这个时候就可以执行回调方法了
                responseFuture.executeInvokeCallback();
                //释放ResponseFuture对象内部的信号量资源
                responseFuture.release();
            } else {
                //如果没有设置回调方法，释放ResponseFuture对象内部的信号量资源即可
                //表示一次请求响应全流程结束了
                responseFuture.release();
            }
        } else {
            //没有从响应表中找到对应的ResponseFuture对象，就记录告警日志，这时候很可能就是响应到达的太晚了，请求已经过期被丢弃了
            log.warn("receive response, cmd={}, but not matched any request, address={}", cmd, RemotingHelper.parseChannelRemoteAddr(ctx.channel()));
        }
    }


    //省略其他内容

}
```
