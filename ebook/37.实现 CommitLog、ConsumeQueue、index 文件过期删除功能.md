## 实现 CommitLog 文件过期删除功能


其实文件过期删除的功能实现起来很简单，没什么可分析的，按照 RocketMq 源码中的设定，只要本地存在超过 72 小时的文件就算过期文件，这就意味着这些本地文件可以被删除了，当然，这个过期行为只限定在了 CommitLog 文件中；并且这也并不是说只要文件一过期就可以被立即删除了，实际上删除文件的操作可能并不会立刻执行，通常来说，要等待每天凌晨 4 点，程序内部才会把已经过期的本地文件删除了。这么分析下来，总结一句话那就是：**对于 CommitLog 本地文件来说，只要有文件存在超过 72 小时，那么在每条凌晨 4 点，程序内部就可以执行删除对应过期文件的操作**。当然，**还有一点大家肯定也能想到了，即然本地文件都删除了，那对应的内存映射文件对象，也就是 DefaultMappedFile 对象肯定要被释放了**，这一点想必大家也都能理解吧？既然是这样，那对于过期 CommitLog 文件功能的实现，我们就可以直接在程序内部启动一个定时任务，那就开启一个定时任务，定期执行操作，然后在任务中判断哪些本地文件最后一次修改到当前系统时间过去 72 小时不就行了吗？当然，还得判断当前时间是不是凌晨 4 点，如果是凌晨 4 点，那就可以执行 CommitLog 过期本地文件删除的操作。这个逻辑大家都可以理解吧？



删除过期 CommitLog 文件的定时任务被我就定义为 CleanCommitLogService 了，它是 DefaultMessageStore 的内部类，CleanCommitLogService 类的对象定义了定时任务要执行的操作，这个 CleanCommitLogService 对象会在 DefaultMessageStore 构造方法中被创建，然后被 DefaultMessageStore 默认消息存储引擎的定时任务执行器定时执行，就像下面代码块展示的这样，请看下面代码块。

从上面代码块中可以看到，在 DefaultMessageStore 默认消息存储引擎启动的时候，就在 start() 方法中启动了 CommitLog 文件过期删除定时任务，这个定时任务每 10 秒会执行一次，任务一旦开始执行，CleanCommitLogService 对象的 run() 方法就会被执行，而在 run() 方法中，删除 CommitLog 过期文件的 deleteExpiredFiles() 方法就会被调用，当然，目前我们还没有真的实现该方法，但该方法具体的实现思路我刚才已经为大家分析过了，所以这个 deleteExpiredFiles() 方法首先起来也很简单。



而根据我们刚才的分析，只需要在 deleteExpiredFiles() 方法中判断当前系统时间是不是凌晨 4 点，如果是凌晨 4 点，那就可以执行 CommitLog 过期文件删除操作了，而执行的时候，肯定需要调用 CommitLog 对象的 deleteExpiredFile() 方法，因为要删除的是 CommitLog 文件夹中的过期文件，那操作 CommitLog 文件夹的肯定是 CommitLog 对象呀，然后再判断 CommitLog 文件夹中的哪些文件是过期的，过期文件删除即可，最后把删除的过期文件对应的内存映射文件对象释放了，那么 CommitLog 过期文件删除操作就算执行完毕了。这个逻辑大家可以理解吧？



我相信以上流程理解起来应该没什么问题，但我要补充的一点是，**实际上在 RocketMq 源码中还执行了一个额外的判断，那就是判断存储本地文件的硬盘的利用率是否超过了阈值，如果超过了阈值，那也要立即执行一次过期文件删除操作，而不必等到凌晨 4 点才执行。原因很简单，假如本地硬盘快没空间了，已经无法再存储新的数据了，那肯定要把过期数据删除了，好腾出新空间存储数据呀**。所以，我们也要仿照 RocketMq 源码，在我们自己的消息队列框架中也实现这个功能，**而且我们要像源码那样定义两个本地空间利用率阈值，这两个阈值分为两个等级，低等级的就是普通阈值，比如说本地硬盘利用率超过 85% 了，这时候就需要立刻执行一次本地过期文件删除操作；而高等级的阈值会被设置到 90%，如果本地硬盘利用率超过 90% 了，那这个时候不仅会立即执行删除过期文件的操作，还会把 DefaultMessageStore 消息存储引擎设置为已写满状态，这样一来消息存储引擎就不会再接收并存储新到来的生产消息了**。这两个阈值的作用大家也要理解清楚。

```java
        private void deleteExpiredFiles() {
            //记录过期文件数量的变量
            int deleteCount = 0;
            //从配置信息对象中得到CommitLog文件的最大保存时间，这里得到的就是72小时，这意味着CommitLog文件最多保存72个小时
            long fileReservedTime = DefaultMessageStore.this.getMessageStoreConfig().getFileReservedTime();
            //得到过期文件删除操作的执行间隔
            int deletePhysicFilesInterval = DefaultMessageStore.this.getMessageStoreConfig().getDeleteCommitLogFilesInterval();
            //得到销毁内存映射文件操作的等待时间
            int destroyMappedFileIntervalForcibly = DefaultMessageStore.this.getMessageStoreConfig().getDestroyMapedFileIntervalForcibly();
            //得到单次可以删除的过期文件的最大数量
            int deleteFileBatchMax = DefaultMessageStore.this.getMessageStoreConfig().getDeleteFileBatchMax();
            //判断是否到达预设的删除时间点，这个预设时间点就是凌晨4点
            boolean isTimeUp = this.isTimeToDelete();
            //判断本地硬盘的使用率是否超过了阈值
            boolean isUsageExceedsThreshold = this.isSpaceToDelete();
            //判断是否要手动触发删除过期文件操作，这里可以看到，只要manualDeleteFileSeveralTimes的值大于0了，就意味着要手动触发删除过期文件的操作
            boolean isManualDelete = this.manualDeleteFileSeveralTimes > 0;
            //满足以上任意一个条件，就可以执行过期文件删除操作
            if (isTimeUp || isUsageExceedsThreshold || isManualDelete) {
                //如果是手动删除，则递减手动删除次数计数器
                //表示可以手动删除的次数减1，还剩下19次
                if (isManualDelete) {
                    this.manualDeleteFileSeveralTimes--;
                }
                //判断是否需要立刻清理过期文件
                boolean cleanAtOnce = DefaultMessageStore.this.getMessageStoreConfig().isCleanFileForciblyEnable() && this.cleanImmediately;

                        isTimeUp,
                        isUsageExceedsThreshold,
                        manualDeleteFileSeveralTimes,
                        cleanAtOnce,
                        deleteFileBatchMax);

                //执行过期文件删除操作

                }
            }
        }

            //存放水位线到达阈值的路径的集合
            Set<String> fullStorePath = new HashSet<>();
            //初始化最小物理磁盘使用率为100%
            double minPhysicRatio = 100;
            //记录使用率最低的文件存储路径
            String minStorePath = null;
            //遍历所有物理存储路径进行硬盘空间使用率检查
            for (String storePathPhysic : storePaths) {
                //得到当前文件所在硬盘的使用率
                double physicRatio = UtilAll.getDiskPartitionSpaceUsedPercent(storePathPhysic);
                if (minPhysicRatio > physicRatio) {
                    //更新最小硬盘使用率信息
                    minPhysicRatio = physicRatio;
                    //更新使用率最小的文件路径信息
                    minStorePath = storePathPhysic;
                }
                //如果当前硬盘空间使用率超过阈值
                if (physicRatio > getDiskSpaceCleanForciblyRatio()) {
                    //则记录文件路径
                    fullStorePath.add(storePathPhysic);
                }
            }
            //把需要强制清理的文件路径设置到CommitLog对象中
            DefaultMessageStore.this.commitLog.setFullStorePaths(fullStorePath);
            //判断最低使用率是否超过警告水位线
            if (minPhysicRatio > getDiskSpaceWarningLevelRatio()) {
                //超过了则设置消息存储引擎为硬盘写满状态
                //注意，这里先返回了之前的状态，然后再更新了状态
                boolean diskFull = DefaultMessageStore.this.runningFlags.getAndMakeDiskFull();
                if (diskFull) {
                    //记录消息引擎状态改变日志
                    DefaultMessageStore.LOGGER.error("physic disk maybe full soon " + minPhysicRatio +
                            ", so mark disk full, storePathPhysic=" + minStorePath);
                }
                //更新立即清理标志并返回需要清理的标志
                cleanImmediately = true;
                return true;
            }
            //判断最低使用率是否超过强制清理水位线
            else if (minPhysicRatio > getDiskSpaceCleanForciblyRatio()) {
                //超过则设置立即清理标志
                //这里可能会有些朋友困惑，为什么只以硬盘空间最低使用率来判断呢？如果有更高的硬盘空间使用率，但是不用这个更高的使用率判断

                cleanImmediately = true;
                return true;

            if (logicsRatio > getDiskSpaceWarningLevelRatio()) {

                cleanImmediately = true;
                return true;
            }

            else {
                //更新消息引擎状态为健康状态
                boolean diskOK = DefaultMessageStore.this.runningFlags.getAndMakeDiskOK();
                //如果状态发生改变，并且之前是硬盘写满状态，那么就在这里记录相关日志信息
                if (!diskOK) {
                    DefaultMessageStore.LOGGER.info("logics disk space OK " + logicsRatio + ", so mark disk ok");
                }
            }


            //以下是考虑到数据在硬盘多备份的情况，如果没有使用对备份数据功能，那下面的操作其实可以忽略

            //比如一个硬盘空间是2T，那么就可1T用来存储数据，1T用来做备份，那么这个1T的数据，就会占用2T的硬盘空间
            //这里得到的就是数据备份数量
            int replicasPerPartition = DefaultMessageStore.this.getMessageStoreConfig().getReplicasPerDiskPartition();
            if (replicasPerPartition <= 1) {
                //执行到这里就意味着数据只有一份，并没有做备份
                //在这里判断硬盘空间使用率是否异常，小于0意味着检测错误，大于阈值意味着要执行清理操作
                if (minPhysicRatio < 0 || minPhysicRatio > ratio) {
                    DefaultMessageStore.LOGGER.info("commitLog disk maybe full soon, so reclaim space, " + minPhysicRatio);
                    return true;
                }
                //判断消费队列数据硬盘空间使用率是否异常
                if (logicsRatio < 0 || logicsRatio > ratio) {
                    DefaultMessageStore.LOGGER.info("consumeQueue disk maybe full soon, so reclaim space, " + logicsRatio);
                    return true;
                }//执行到这里意味着剩余空间充足，无需执行文件删除操作

                //总数据大小/分配到的空间大小，得到一份数据的硬盘空间利用率
                double logicalRatio = 1.0 * majorFileSize / partitionLogicalSize;
                //利用率超过阈值的话就需要执行过期文件清理操作
                if (logicalRatio > DefaultMessageStore.this.getMessageStoreConfig().getLogicalDiskSpaceCleanForciblyThreshold()) {
                    DefaultMessageStore.LOGGER.info("Logical disk usage {} exceeds logical disk space clean forcibly threshold {}, forcibly: {}",
                            logicalRatio, minPhysicRatio, cleanImmediately);
                    cleanImmediately = true;
                    return true;

                }

                boolean isUsageExceedsThreshold = logicalRatio > ratio;
                if (isUsageExceedsThreshold) {
                    DefaultMessageStore.LOGGER.info("Logical disk usage {} exceeds clean threshold {}, forcibly: {}",
                            logicalRatio, ratio, cleanImmediately);
                }
                return isUsageExceedsThreshold;
            }
        }
```

```java
/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
```

```java
 * @date:2025/6/29
 * @方法描述：内存映射文件管理器
 */
public class MappedFileQueue implements Swappable {

    //省略该类其他内容

    //存放所有内存映射文件对象的集合
    protected final CopyOnWriteArrayList<MappedFile> mappedFiles = new CopyOnWriteArrayList<>();



     /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：得到当前内存映射文件队列的拷贝数据
     */
    protected Object[] copyMappedFiles(final int reservedMappedFiles) {
        Object[] mfs;
        if (this.mappedFiles.size() <= reservedMappedFiles) {
            return null;
        }
        mfs = this.mappedFiles.toArray();
        return mfs;
    }


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：内存映射文件队列启动时的自检方法，就是看看各个内存映射文件是否是连续的
     */
    public void checkSelf() {
        //创建副本数据
        List<MappedFile> mappedFiles = new ArrayList<>(this.mappedFiles);
        if (!mappedFiles.isEmpty()) {
            Iterator<MappedFile> iterator = mappedFiles.iterator();
            MappedFile pre = null;
            //遍历所有内存映射文件
            while (iterator.hasNext()) {
                MappedFile cur = iterator.next();
                //下面就是当前文件和上一个文件偏移量做对比的操作
                if (pre != null) {
                    //计算当前文件与上一个文件的偏移量差，如果偏移量差不是单个内存映射文件的大小
                    //则意味着文件可能被损坏了
                    if (cur.getFileFromOffset() - pre.getFileFromOffset() != this.mappedFileSize){
                        //记录错误日志
                        LOG_ERROR.error("[BUG]The mappedFile queue's data is damaged, the adjacent mappedFile's offset don't match. pre file {}, cur file {}",
                                pre.getFileName(), cur.getFileName());
                    }
                }//把当前文件赋值给上一个文件，进入下一次循环，使用上一个文件和即将得到的当前文件做对比
                pre = cur;
            }
        }
    }

    
    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：根据过期时间删除过期内存映射文件的方法
     * expiredTime是文件过期时间，超过这个时间的文件将被视为过期，可以被删除
     * deleteFilesInterval是删除文件的时间间隔
     * intervalForcibly是内存映射文件强制销毁的等待时间
     * cleanImmediately为是否立即清理的标志
     * deleteFileBatchMax为单次可以删除的最大文件数量
     */
    public int deleteExpiredFileByTime(final long expiredTime, final int deleteFilesInterval, final long intervalForcibly, final boolean cleanImmediately, final int deleteFileBatchMax) {
        //得到当前映射文件队列的快照，避免在遍历过程中集合被修改导致并发问题，参数0表示从第一个文件开始复制整个队列
        Object[] mfs = this.copyMappedFiles(0);
        //如果映射文件数组为空，则直接返回0，表示没有删除任何文件
        if (null == mfs)
            return 0;
        //得到数组中最后一个映射文件的索引，这里得到最后一个文件的索引其实为了在后序遍历的时候避开最后一个文件
        //因为最后一个文件通常意味着最新的被写入数据的文件，这个文件肯定不会被删除，要删除也是从倒数第二个文件开始删除
        int mfsLength = mfs.length - 1;
        //记录最后成功删除的文件数量
        int deleteCount = 0;
        //创建集合，存储待删除的映射文件对象
        List<MappedFile> files = new ArrayList<>();
        //记录跳过的文件数量，用于日志记录，表示有多少文件因为未过期而被跳过
        int skipFileNum = 0;
        //再次检查映射文件数组是否为空
        if (null != mfs) {
            //不为空则执行自检操作，确保文件队列状态正常，数据连续
            checkSelf();
            //遍历映射文件数组，从最早的文件开始判断，直到倒数第二个文件
            for (int i = 0; i < mfsLength; i++) {
                //得到当前遍历到的映射文件对象
                MappedFile mappedFile = (MappedFile) mfs[i];
                //计算当前内存映射文件的最大存活时间
                long liveMaxTimestamp = mappedFile.getLastModifiedTimestamp() + expiredTime;
                //判断该文件是否过期了，或者是否需要立即清理
                if (System.currentTimeMillis() >= liveMaxTimestamp || cleanImmediately) {
                    //如果之前有跳过的文件，记录日志
                    if (skipFileNum > 0) {
                        log.info("Delete CommitLog {} but skip {} files", mappedFile.getFileName(), skipFileNum);
                        //重置跳过文件计数器
                        skipFileNum = 0;
                    }
                    //在这里执行销毁映射文件的操作，传入强制等待时间
                    //这里我要强调一下，这里销毁内存映射文件，就会把该文件设置为不可用状态了
                    //然后急哦关闭该文件的文件通道
                    if (mappedFile.destroy(intervalForcibly)) {
                        //销毁成功则把该文件添加到待删除列表
                        files.add(mappedFile);
                        //增加删除计数
                        deleteCount++;
                        //判断是否达到单次可以删除的最大文件数量
                        //如果达到则停止循环
                        if (files.size() >= deleteFileBatchMax) {
                            break;
                        }
                        //如果设置了文件删除间隔并且还有更多文件需要遍历处理
                        if (deleteFilesInterval > 0 && (i + 1) < mfsLength) {
                            try { //则在这里休眠指定时间，控制删除速率，减轻IO压力
                                Thread.sleep(deleteFilesInterval);
                            } catch (InterruptedException e) {

                            }
                        }
                    } else {
                        //执行到这里意味着文件销毁失败，那就直接退出循环，因为mq默认按照文件顺序删除文件，如果当前文件不能删除，那后续文件也不能被删除
                        break;
                    }
                } else {
                    //如果文件尚未过期，那就增加跳过计数并退出循环
                    //因为mq中文件是按时间顺序组织的，如果当前文件未过期，那后面的文件也不会过期
                    skipFileNum++;
                    break;
                }
            }
        }
        //在这里执行最终删除内存映射文件的操作，之前执行的是内存映射文件销毁操作，并没有真正从文件队列中删除对应的文件对象呢
        deleteExpiredFile(files);
        //返回成功删除的文件数量
        return deleteCount;
    }



    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：从内存映射文件集合中删除指定内存映射文件的方法
     */
    void deleteExpiredFile(List<MappedFile> files) {
        if (!files.isEmpty()) {
            Iterator<MappedFile> iterator = files.iterator();
            while (iterator.hasNext()) {
                MappedFile cur = iterator.next();
                //如果文件队列中不包含当前遍历到的文件
                if (!this.mappedFiles.contains(cur)) {
                    //从待删除列表移除非活跃文件
                    iterator.remove();
                    log.info("This mappedFile {} is not contained by mappedFiles, so skip it.", cur.getFileName());
                }
            }
            try {//在这里执行批量删除操作
                if (!this.mappedFiles.removeAll(files)) {
                    //删除失败记录错误日志
                    log.error("deleteExpiredFile remove failed.");
                }
            } catch (Exception e) {
                log.error("deleteExpiredFile has exception.", e);
            }
        }
    }
```

## 实现 ConsumeQueue、index 文件过期删除功能


好了，CommitLog 过期文件删除功能实现之后，我相信大家都在等着我继续实现 ConsumeQueue、index 文件过期删除功能，而这也正是我接下来要做的。实际上 ConsumeQueue、index 文件过期删除功能实现起来也非常简单，同样是定义一个定时任务，然后在定时任务中执行删除过期文件的操作即可，这个逻辑和刚才实现的 CommitLog 过期文件删除的逻辑没什么区别。但是，我想说的是，**这两个过期文件删除的功能并不是完全一样，最本质的区别就是 ConsumeQueue、index 过期文件的删除并不是根据时间来判断的，而是根据 CommitLog 文件中的最小数据偏移量来判断的**。这句话可能让大家感到困惑，接下来请听我解释一下。



现在我们都知道了，ConsumeQueue、index 文件中的数据都是根据 CommitLog 文件中构建来的，是因为 CommitLog 文件中被写入了新的数据，为了消费者客户端能尽快消费消息，定位到消息，所以我们才异步构建了 ConsumeQueue、index 文件，尤其是异步构建的 ConsumeQueue 文件，和 CommitLog 文件夹中的数据耦合非常紧密，因为消费者完全是根据 ConsumeQueue 文件中的重放消息去消费 CommitLog 文件夹中的消息的。假如说消费者从 ConsumeQueue 文件中得到了一条重放消息，结果这条重放消息存储的消息全局偏移量在 CommitLog 文件夹中并没有对应的数据，这不就出问题了吗？**所以当 ConsumeQueue、index 文件过期删除的时候，必须严格按照 CommitLog 文件夹中最小数据偏移量来删除**。就比如说，经**过一次过期文件删除之后，CommitLog 文件夹中存储的第一条消息对应的全局偏移量是 200 字节，这也就意味着前 200 字节的消息都已经过期删除了，也不必再被查询到和被消费了，那这个时候就可以使用这个 200 全局偏移量为界限，到 ConsumeQueue、index 文件中判断，因为这两个文件中的消息都封装着各自的全局偏移量信息，只要 ConsumeQueue、index 某个本地文件中存储的最后一条消息对应的全局偏移量是小于 200 字节，那么整个文件就可以被删除了，因为上消费队列中的数据和 index 文件中的数据也都是按顺序存放的，它们内部的重放消息封装的全局偏移量也都是递增的，如果消费队列某个文件中最后一条重放消息，对应的全局偏移量已经过期了，也就是小于 CommitLog 文件中数据的最小全局偏移量，那么这个消费队列文件中的所有数据肯定也都是过期的，可以被删除了，**大家要梳理清楚这个逻辑。



如果以上逻辑大家都理解了，那接下来我们就可以定义 ConsumeQueue、index 文件过期删除的定时任务对象了，这个对象被我定义为了 CleanConsumeQueueService，也是默认消息存储引擎的内部类，创建和启动的逻辑和 CleanCommitLogService 一致，那接下来，就请大家看一下 CleanConsumeQueueService 类的具体内容，请看下面代码块。

```java
    public void checkSelf() {
        //创建副本数据
        List<MappedFile> mappedFiles = new ArrayList<>(this.mappedFiles);
        if (!mappedFiles.isEmpty()) {
            Iterator<MappedFile> iterator = mappedFiles.iterator();
            MappedFile pre = null;
            //遍历所有内存映射文件
            while (iterator.hasNext()) {
                MappedFile cur = iterator.next();
                //下面就是当前文件和上一个文件偏移量做对比的操作
                if (pre != null) {
                    //计算当前文件与上一个文件的偏移量差，如果偏移量差不是单个内存映射文件的大小
                    //则意味着文件可能被损坏了
                    if (cur.getFileFromOffset() - pre.getFileFromOffset() != this.mappedFileSize){

                        LOG_ERROR.error("[BUG]The mappedFile queue's data is damaged, the adjacent mappedFile's offset don't match. pre file {}, cur file {}",
                                pre.getFileName(), cur.getFileName());
                    }
                }//把当前文件赋值给上一个文件，进入下一次循环，使用上一个文件和即将得到的当前文件做对比
                pre = cur;
            }
        }
    }

     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

     * deleteFilesInterval是删除文件的时间间隔
     * intervalForcibly是内存映射文件强制销毁的等待时间
     * cleanImmediately为是否立即清理的标志
     * deleteFileBatchMax为单次可以删除的最大文件数量
     */
    public int deleteExpiredFileByTime(final long expiredTime, final int deleteFilesInterval, final long intervalForcibly, final boolean cleanImmediately, final int deleteFileBatchMax) {
        //得到当前映射文件队列的快照，避免在遍历过程中集合被修改导致并发问题，参数0表示从第一个文件开始复制整个队列
        Object[] mfs = this.copyMappedFiles(0);
        //如果映射文件数组为空，则直接返回0，表示没有删除任何文件
        if (null == mfs)
            return 0;
        //得到数组中最后一个映射文件的索引，这里得到最后一个文件的索引其实为了在后序遍历的时候避开最后一个文件
        //因为最后一个文件通常意味着最新的被写入数据的文件，这个文件肯定不会被删除，要删除也是从倒数第二个文件开始删除
        int mfsLength = mfs.length - 1;
        //记录最后成功删除的文件数量
        int deleteCount = 0;
        //创建集合，存储待删除的映射文件对象
        List<MappedFile> files = new ArrayList<>();
        //记录跳过的文件数量，用于日志记录，表示有多少文件因为未过期而被跳过
        int skipFileNum = 0;
        //再次检查映射文件数组是否为空
        if (null != mfs) {
            //不为空则执行自检操作，确保文件队列状态正常，数据连续
            checkSelf();
            //遍历映射文件数组，从最早的文件开始判断，直到倒数第二个文件
            for (int i = 0; i < mfsLength; i++) {
                //得到当前遍历到的映射文件对象
                MappedFile mappedFile = (MappedFile) mfs[i];
                //计算当前内存映射文件的最大存活时间
                long liveMaxTimestamp = mappedFile.getLastModifiedTimestamp() + expiredTime;
                //判断该文件是否过期了，或者是否需要立即清理
                if (System.currentTimeMillis() >= liveMaxTimestamp || cleanImmediately) {
                    //如果之前有跳过的文件，记录日志
                    if (skipFileNum > 0) {
                        log.info("Delete CommitLog {} but skip {} files", mappedFile.getFileName(), skipFileNum);
                        //重置跳过文件计数器
                        skipFileNum = 0;
                    }
                    //在这里执行销毁映射文件的操作，传入强制等待时间
                    //这里我要强调一下，这里销毁内存映射文件，就会把该文件设置为不可用状态了
                    //然后关闭该文件的文件通道
                    if (mappedFile.destroy(intervalForcibly)) {
                        //销毁成功则把该文件添加到待删除列表
                        files.add(mappedFile);
                        //增加删除计数
                        deleteCount++;
                        //判断是否达到单次可以删除的最大文件数量
                        //如果达到则停止循环
                        if (files.size() >= deleteFileBatchMax) {
                            break;
                        }
                        //如果设置了文件删除间隔并且还有更多文件需要遍历处理
                        if (deleteFilesInterval > 0 && (i + 1) < mfsLength) {
                            try { //则在这里休眠指定时间，控制删除速率，减轻IO压力
                                Thread.sleep(deleteFilesInterval);
                            } catch (InterruptedException e) {

                            }
                        }
                    } else {
                        //执行到这里意味着文件销毁失败，那就直接退出循环，因为mq默认按照文件顺序删除文件，如果当前文件不能删除，那后续文件也不能被删除
                        break;
                    }
                } else {
                    //如果文件尚未过期，那就增加跳过计数并退出循环
                    //因为mq中文件是按时间顺序组织的，如果当前文件未过期，那后面的文件也不会过期
                    skipFileNum++;
                    break;
                }
            }
        }
        //在这里执行最终删除内存映射文件的操作，之前执行的是内存映射文件销毁操作，并没有真正从文件队列中删除对应的文件对象呢
        deleteExpiredFile(files);
        //返回成功删除的文件数量
        return deleteCount;
    }

    //这里我还要再多说一句，实际上消费队列中的数据和index文件中的数据也都是顺序存放的
    //它们内部的重放消息封装的全局偏移量也都是递增的，如果消费队列某个文件中最后一条重放消息

    //那么这个消费队列文件中的所有数据肯定也都是过期的，可以被删除了，大家要梳理清楚这个逻辑


    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：根据CommitLog文件中最小消息偏移量删除对应过期数据的方法，该方法删除的是消息队列过期文件，该方法中的部分逻辑和上面方法相同，送我就不添加详细注释了
     */
    public int deleteExpiredFileByOffset(long offset, int unitSize) {
        //得到当前映射文件队列的快照，避免在遍历过程中集合被修改导致并发问题，参数0表示从第一个文件开始复制整个队列
        Object[] mfs = this.copyMappedFiles(0);

        int deleteCount = 0;
        //判断内存映射文件数组是否为空
        if (null != mfs) {
            //得到最后一个文件的索引
            int mfsLength = mfs.length - 1;
            //遍历映射文件数组
            for (int i = 0; i < mfsLength; i++) {
                //初始化文件销毁标志
                boolean destroy = false;
                //得到当前遍历到的映射文件对象
                MappedFile mappedFile = (MappedFile) mfs[i];
                //从文件的末尾位置减去unitSize，unitSize是消费队列存储单元，从文件末尾减去存储单元，得到的就是该文件存储的最后一条消息的起始偏移量
                //然后得到这条消息对应的文件缓冲区对象
                SelectMappedBufferResult result = mappedFile.selectMappedBuffer(this.mappedFileSize - unitSize);
                //如果成功获取到缓冲区结果
                if (result != null) {
                    //就从缓冲区中读取这条消息封装的在CommitLog文件中的消息的全局偏移量
                    long maxOffsetInLogicQueue = result.getByteBuffer().getLong();
                    //释放缓冲区资源，避免内存泄漏

                    //如果小于，则意味着该文件中的所有消息都已经被消费，可以被销毁
                    //这里可以看到，消费队列数据删除的时候，也是按文件整体删除的
                    //只要这个文件中的数据都过期了，就把文件都删除了，并不是说哪一条消息过期了
                    //就删除这一条消息，那样的话太麻烦了
                    destroy = maxOffsetInLogicQueue < offset;
                    //如果文件可以被销毁，则记录日志信息
                    if (destroy) {
                        log.info("physic min offset " + offset + ", logics in current mappedFile max offset " + maxOffsetInLogicQueue + ", delete it");
                    }
                }
                else if (!mappedFile.isAvailable()) {
                    //执行到这里意味着没有得到对应的缓冲区结果对象，并且当前遍历的内存映射文件不可用
                    //那就记录警告日志，并尝试销毁这个挂起的消费队列文件
                    log.warn("Found a hanged consume queue file, attempting to delete it.");
                    //在这里标记当前文件可销毁标志
                    destroy = true;
                }
                else {
                    //执行到这里意味着没有成功获取缓冲区结果对象，但文件又是可用的
                    //这时候就记录告警日志，表示这种情况理论上不会发生
                    log.warn("this being not executed forever.");
                    //退出循环
                    break;
                }
                //如果当前遍历的文件是可销毁的，并且也销毁成功了
                if (destroy && mappedFile.destroy(1000 * 60)) {
                    //销毁成功，则把文件添加到待删除列表
                    files.add(mappedFile);
                    //增加文件删除计数
                    deleteCount++;
                } else {
                    //执行到这里意味着文件销毁失败，那就直接退出循环，因为mq默认按照文件顺序删除文件，如果当前文件不能删除，那后续文件也不能被删除
                    break;
                }
            }
        }

        deleteExpiredFile(files);
        //返回成功删除的文件数量
        return deleteCount;
    }

        if (!files.isEmpty()) {
            Iterator<MappedFile> iterator = files.iterator();
            while (iterator.hasNext()) {
                MappedFile cur = iterator.next();
```

请大家仔细思考一下，从上面代码块中我们已经知道了，在删除 ConsumeQueue 消费队列过期数据的时候，也是按照文件为单元来删除的，虽然我们会有一个阈值标准，也就是以 CommitLog 文件中最小数据偏移量为标准判断 ConsumeQueue 文件中哪些数据过期了，但是我们并不会真的去对比 ConsumeQueue 消费队列每一个文件中每一条数据，判断这个重放消息是否过期，如果过期就删除。如果真的这么做显然就太麻烦了，**我们所做的只是对比 ConsumeQueue 消费队列的每一个文件，看看文件存储的最后一条重放消息封装的全局偏移量是否小于 CommitLog 的最小数据偏移量，如果小于那么就意味着这个 ConsumeQueue 本地文件可以删除了**。这个流程大家肯定都很清楚了。



很好，如果大家都理解了以上流程，那现在就会出现一种情况，因为在删除 ConsumeQueue 过期文件的时候并不会精确到每一条重放消息，而是以文件为基本单元删除，那这个时候就可能会出现一种情况：**那就是在某个 ConsumeQueue 消费队列的本地文件中，这个文件存储的重放消息有一部分是过期的，有一部分是没有过期的**，**那当消费者客户端消费消息的时候，就可能访问到 ConsumeQueue 消费队列中已经过期的重放消息，然后根据重放消息封装的消息全局偏移量去 CommitLog 中查询指定消息，肯定就查询不到了，因为这个消息已经被过期删除了**。大家可以品味品味这个逻辑。



如果大家不明白上面的情况究竟是怎么回事，那么接下来请看看我为大家展示的一个示例：假如现在某个主题、Id 的 ConsumeQueue 消费队列下有三个本地文件，文件 1 中存储的重放消息对应的 CommitLog 全局偏移量范围为 101～300 字节；文件二中存储的重放消息对应的 CommitLog 全局偏移量范围为 301～500 字节；文件三中存储的重放消息对应的 CommitLog 全局偏移量范围为 501～700 字节；某个时刻程序内部对 CommitLog 文件执行了过期数据删除操作，在删除完毕之后，CommitLog 中最小数据全局偏移量变成了 401 字节，这也就意味着假如消费者客户端要到 Broker 节点消费消息，只能从 CommitLog 全局偏移量为 401 字节的位置开始消费消息，而之前的消息都因为过期被删除了。很好，再对 CommitLog 文件执行了过期删除操作之后，得到了目前 CommitLog 中最小数据起始偏移量为 401 字节，这个就是要对 ConsumeQueue 消费队列文件进行数据过期删除时做判断的阈值，那程序很快就对 ConsumeQueue 消费对类文件执行了数据过期删除操作，对比之后发现，ConsumeQueue 消费队列下的三个本地文件中，只有文件 1 可以被删除，虽然文件二中的部分重放消息已经过期了，但是文件二存储的最后一条重放消息对应的全局偏移量大于 401，这也就意味着这条重放消息对应的 CommitLog 中的消息还没有过期，可以被消费者客户端正常消费，因此 ConsumeQueue 消费队列下的文件二并不能被删除，文件二都不能被删除，那文件三肯定就更不能被删除了。那既然 ConsumeQueue 消费队列的第二个文件不能被删除，这就意味着有一部分过期消息对应的 CommitLog 全局偏移量还可以被消费者客户端得到，那消费者客户端使用这些过期消息的全局偏移量去 CommitLog 中消费消息，显然无法得到真正的消息，这不就出问题了吗？大家可以仔细思考思考，梳理清楚这种情况出现的原因。



很好，如果现在大家都了解了以上这种情况出现的原因，也知道这种情况的存在是一个 bug，那我们接下来要做的就是要解决这个 bug。那这个 bug 该如何解决呢？其实方法非常简单，**那就是给 ConsumeQueue 类再定义一个 minLogicOffset 成员变量**，**这个成员变量记录的是消费者客户端到 ConsumeQueue 消费队列中消费消息时，可以消费的最小重放消息的偏移量**。我知道仅凭刚才的文字，大家可能仍然不理解这个新的成员变量的作用，这么关系，还是回到刚才的示例，ConsumeQueue 消费队列下有三个本地文件，这三个本地文件存储的重放消息的整体范围是从 101～700，也就是说当消费者客户端到 ConsumeQueue 消费队列中获取重放消息时，就可以从 ConsumeQueue 消费队列偏移量为 101 的位置开始消费消息，每得到一条重放消息，再根据重放消息封装的全局偏移量到 CommitLog 中查询具体消息即可。**但现在 CommitLog 过期文件删除之后，消费者只能从 CommitLog 文件全局偏移量为 401 的位置开始真正消费消息，那如果我们要是能够确定，全局偏移量 401 的消息在 ConsumeQueue 消费队列文件中对应哪一条重放消息不就行了吗**？比如说经过对比查询之后，发现在 ConsumeQueue 消费队列第二个文件的偏移量为 60 的重放消息，封装的 CommitLog 全局消息偏移量为 401，那这也就意味着，当消费者客户端到 ConsumeQueue 消费队列中消费消息时，只需要直接从第二个本地文件偏移量为 60 的位置开始读取重放消息，那么在这之后消费到的消息都是没有过期的，都是可以正常消费的，**这个 60 偏移量，就是要赋值给 ConsumeQueue 类的 minLogicOffset 成员变量**！



现在大家应该清楚了 ConsumeQueue 类的 minLogicOffset 成员变量的作用是什么了吧？虽然我们目前还不会真正用到 ConsumeQueue 类的 minLogicOffset 成员变量，等后面实现消费者客户端消费消息功能时才会用到它，但大家提前了解一下对理解目前程序的运行流程很有帮助。注意，我再强调一下，**这个 ConsumeQueue 类的 minLogicOffset 成员变量表示的是重放消息在 ConsumeQueue 消费队列中的偏移量，也就是消费者客户端可以消费的最早的重放消息的偏移量，并不是消息在 CommitLog 中的全局偏移量，这一点大家一定要梳理清楚；而 minLogicOffset 成员变量对应的重放消息封装的全局偏移量，这个全局偏移量对应的 CommitLog 中的消息，就是消费者客户端可以消费的最早的没有过期的消息，之前的消息全部被过期删除了**。大家一定要梳理清楚这个逻辑。



好了，在理解了以上内容之后，那我们要解决刚才的 bug，只需要在 ConsumeQueue 消费队列每次执行了文件过期删除操作之后，根据 CommitLog 文件的最小全局偏移量给 minLogicOffset 成员变量赋值不就行了？也就是说在每次对 ConsumeQueue 消费队列每次执行了文件过期删除操作之后，根据 CommitLog 文件的最小全局偏移量确定在 ConsumeQueue 消费队列文件中对应哪一条重放消息即可。那这个操作该怎么实现呢？非常简单，在执行了过期文件删除之后，肯定只会在 ConsumeQueue 消费队列的新第一个本地文件中存在新旧数据同时存在的情况，原因很简单，如果新的第一个本地文件中的数据都是旧的，那肯定就会被删除了；**所以我们只需要使用 CommitLog 文件的最小全局偏移量去 ConsumeQueue 消费队列的第一个本地文件中确定哪一条重放消息封装的全局偏移量和 CommitLog 文件的最小全局偏移量相等即可，确定了重放消息之后，就可以得到重放消息在 ConsumeQueue 消费队列中的偏移量，然后把这个偏移量赋值给 minLogicOffset 即可**。这样一来，**等消费者到 ConsumeQueue 消费队列中消费重放消息时，只需要从 minLogicOffset 位置开始消费即可，这个时候消费者客户端最终得到的消息都是合法消息，没有一条消息是过期的**。现在大家应该清楚这个流程了吧？而至于怎么去 ConsumeQueue 消费队列的第一个文件中对比，这就更简单了，直接使用二分法查找对比即可，更多细节我就不再展开了，接下来请大家看看重构之后的 ConsumeQueue 类的内容，就全都明白了，请看下面代码块。

```java
package org.apache.rocketmq.store;




/**
 * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。

 */
public class ConsumeQueue implements ConsumeQueueInterface, FileQueueLifeCycle {


    //省略该类其他内容

    //内存映射文件队列
    private final MappedFileQueue mappedFileQueue;

    //消费队列映射文件中消息的最小偏移量

     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：删除过期ConsumeQueue文件的方法
     */
    @Override
    public int deleteExpiredFile(long offset) {
        int cnt = this.mappedFileQueue.deleteExpiredFileByOffset(offset, CQ_STORE_UNIT_SIZE);
        //校正消费队列的最小有效偏移量，确保不会访问已删除的CommitLog数据
        this.correctMinOffset(offset);
        return cnt;
    }




    /**
     * @课程描述:从零带你写框架系列中的课程，整个系列包含netty，xxl-job，rocketmq，nacos，sofajraft，spring，springboot，disruptor，编译器，虚拟机等等。
     * @author：陈清风扬，个人微信号：chenqingfengyangjj。
     * @方法描述：调整ConsumeQueue的最小偏移量的方法，确保消费者消费消息时不会访问已删除的CommitLog数据，minCommitLogOffset方法参数是CommitLog文件中的最小有效偏移量
     */
    @Override
    public void correctMinOffset(long minCommitLogOffset) {
        //在前十五个版本代码中并没有用到这个方法，因此我也没有机会给大家分析minLogicOffset成员变量的具体作用
        //大家光看注释可能并不知道这个成员变量的真正作用。当然，我还是要说一句，就算我现在给大家把这个成员变量的具体作用分析完毕了
        //在第十六版本代码中，也用不到这个成员变量，当消费者客户端消费消息的时候，这个成员变量才会派上用场，但这不妨碍我们提前了解这个
        //成员变量的具体作用。简而言之：minLogicOffset成员变量就是ConsumeQueue中第一条有效的消息的逻辑偏移量，换句话说，这个最小偏移量对应的CommitLog文件中的消息其实就是消费者可以从CommitLog文件中消费的第一条消息
        //了解了这个概念之后，请大家思考一个问题，假如CommitLog文件队列中可以消费的第一条消息的偏移量是500，而消费队列中的minLogicOffset最小偏移量是40，这个40对应的CommitLog文件中的消息的全局偏移量为400
        //那当消费者从消费队列消费消息时，直接根据minLogicOffset最小偏移量获取可消费的第一条消息，结果这个消息对应的CommitLog全局偏移量是400，但是CommitLog文件过期删除之后，最小消息偏移量是500
        //那消费者肯定就没办法从CommitLog文件中得到要消费的消息，因为这个消息已经过期了，所以应该定期对消费队列的最小偏移量进行更新，也就是定期执行当前方法
        //保证消费队列的最小偏移量指向的是CommitLog文件中的有效消息，而当前方法中传进来的参数就是CommitLog文件中最小有效消息的偏移量
        //消费队列只需要根据这个CommitLog最小有效消息偏移量校准自己的最小偏移量，就可以保证消费队列的最小偏移量指向CommitLog文件中的有效消息了
        //现在请大家掌握了这些信息，就可以阅读下面的代码内容了

        //判断消费队列是否处于废弃状态，最小偏移量大于等于映射文件的最大偏移量，就意味着消费队列的内存映射文件中已经没有数据可以消费了
        if (minLogicOffset >= mappedFileQueue.getMaxOffset()) {
            //记录信息日志，表明当前主题和队列Id的ConsumeQueue不包含有效条目
            log.info("ConsumeQueue[Topic={}, queue-id={}] contains no valid entries", topic, queueId);
            //推出当前方法
            return;
        }


        
        //得到内存映射队列中的最后一个映射文件
        MappedFile lastMappedFile = this.mappedFileQueue.getLastMappedFile();
        //如果最后一个映射文件不存在，就意味着内存映射队列中没有文件，退出当前方法即可
        if (null == lastMappedFile) {
            return;
        }
        SelectMappedBufferResult lastRecord = null;
        try {
            //得到最后一个内存映射文件的可读字节位置
            int maxReadablePosition = lastMappedFile.getReadPosition();
            //最后字节的可读位置减去存储单元，得到的就是内存映射文件队列中最后一个内存映射文件存储的最后一条消息
            lastRecord = lastMappedFile.selectMappedBuffer(maxReadablePosition - ConsumeQueue.CQ_STORE_UNIT_SIZE, ConsumeQueue.CQ_STORE_UNIT_SIZE);
            if (null != lastRecord) {
                //成功获取到了最后一条记录的缓冲区结果对象后，就得到这条记录对应的缓冲区
                ByteBuffer buffer = lastRecord.getByteBuffer();
                //消费队列中每个数据的前八个字节就是这条消息在CommitLog文件中的全局偏移量
                //得到这条消费队列消息对应的CommitLog文件的全局偏移量
                long commitLogOffset = buffer.getLong();
                if (commitLogOffset < minCommitLogOffset) {
                    //如果最后一个文件最后一条条消息对应的CommitLog文件偏移量小于最小提交日志偏移量
                    //这就意味着消费队列存储的所有消息对应的CommitLog文件的偏移量都是过期了的，CommitLog文件早就把这些消息删除了
                    //这个时候只需要更新消息队列的最小偏移量即可，即使当前的消费队列中没有任何有效的条目，也要保留已知的最大消费偏移量。让minLogicOffset指向一个未来的槽位。
                    // Keep the largest known consume offset, even if this consume-queue contains no valid entries at
                    // all. Let minLogicOffset point to a future slot.
                    this.minLogicOffset = lastMappedFile.getFileFromOffset() + maxReadablePosition;
                    //记录信息日志，表明ConsumeQueue不包含有效条目，并且分配了新的最小偏移量
                    log.info("ConsumeQueue[topic={}, queue-id={}] contains no valid entries. Min-offset is assigned as: {}.",
                            topic, queueId, getMinOffsetInQueue());
                    //推出当前方法
                    return;
                }
            }
        } finally {
            //如果最后一条记录结果缓冲区不为null
            if (null != lastRecord) {
                //在这里释放缓冲区资源
                lastRecord.release();
            }
        }


        
        //执行到这里意味着最后一个内存映射文件存储的最后一条消息对应的CommitLog文件消息的偏移量大于方法传进来的offset，比如说现在方法传进来的CommitLog文件的最小偏移量是500
        //消费队列最后一个内存映射文件最后一条消息对应的CommitLog全局偏移量是700，这个时候就要从前面的内存映射文件找到对应的消息，也就是从第一个内存映射文件中查找
        MappedFile mappedFile = this.mappedFileQueue.getFirstMappedFile();
        long minExtAddr = 1;
        if (mappedFile != null) {
            //如果得到了第一个内存映射文件，就从之前的最小逻辑偏移量开始搜索。通常一个消费队列文件包含300,000条消息数据
            // Search from previous min logical offset. Typically, a consume queue file segment contains 300,000 entries
            // searching from previous position saves significant amount of comparisons and IOs
            boolean intact = true; // Assume previous value is still valid
            //假如内存映射队列的第一个文件的起始位置是200字节，而minLogicOffset最小逻辑偏移量是100字节
            //注意minLogicOffset也是重放消息在消费队列中的偏移量，所以这两个数值可以直接做计算
            //如果是这样的话，那么二者的差值肯定是小于0的
            long start = this.minLogicOffset - mappedFile.getFileFromOffset();
            if (start < 0) {
                //如果二者差值小于0，那就把intact更新为false，表示内存映射文件的数据不完整
                //这一点大家可以理解吧？消费者才消费到100字节，结果内存映射起始数据偏移量为200字节
                //这就意味着中间肯定有数据丢失
                //标记为不完整，表示之前的值可能无效
                intact = false;
                //设置开始位置为0，所谓开始位置，就是从第一个内存映射文件中读取数据的位置
                //这里就是从文件首位置开始读取的意思
                start = 0;
            }
            
            //如果二者的差值大于0，比如说内存映射队列的第一个文件的起始位置是200字节，而minLogicOffset最小逻辑偏移量是300字节
            //那二者的差值100就是minLogicOffset在第一个内存映射文件中的相对偏移量，从这里开始读取数据，就可以直接判断minLogicOffset对应的消息的全局偏移量是否大于等于方法参数minCommitLogOffset了
            //这里判断了一下start > mappedFile.getReadPosition()，mappedFile.getReadPosition()可读位置也许是存储消息的最大偏移量，也许是文件末尾，文件已经写满了
            //不管怎么样，这都意味着minLogicOffset的在第一个内存映射文件中的相对偏移量超过了第一个内存映射文件mappedFile.getReadPosition()最大可读位置
            //这就意味着mappedFile文件中已经没有可以被消费的数据了，但这个文件没有被删除，所以要在这里记录错误日志
            if (start > mappedFile.getReadPosition()) {
                //记录错误日志，表明ConsumeQueue文件应该已经被删除，但实际上仍存在
                log.error("[Bug][InconsistentState] ConsumeQueue file {} should have been deleted",
                        mappedFile.getFileName());
                //推出当前方法
                return;
            }


            
            //接下来就可以从刚才定义的开始位置读取数据了，这个开始位置就是minLogicOffset在第一个内存映射文件中的相对偏移量
            //这里返回了封装了start位置之后所有数据内容的结果缓冲区
            SelectMappedBufferResult result = mappedFile.selectMappedBuffer((int) start);
            //如果没能成功获取结果缓冲区，这种情况也不是没可能发生，如果minLogicOffset是900，而内存映射队列的第一个文件的起始位置是200字节
            //二者差值是700，也就是说要从第一个内存映射文件700位置读取数据，但是第一个内存映射文件总大小也才500，这个时候肯定就得到不对应的缓冲区结果了
            //这其实也意味着第一个内存映射文件的数据是过期的，应该被删除了
            if (result == null) {
                //记录警告日志
                log.warn("[Bug] Failed to scan consume queue entries from file on correcting min offset: {}",
                        mappedFile.getFileName());
                return;
            }
            try {
                //执行到这里意味着得到了结果缓冲区
                //判断结果缓冲区是否没有有效的消息数据
                if (result.getSize() == 0) {
                    log.debug("ConsumeQueue[topic={}, queue-id={}] contains no valid entries", topic, queueId);
                    //退出当前方法，因为没有有效的消息需要处理
                    return;
                }
                //得到结果缓冲区的切片
                ByteBuffer buffer = result.getByteBuffer().slice();
                //得到minLogicOffset对应的消息在CommitLog文件中的全局偏移量
                long commitLogOffset = buffer.getLong();
                //如果intact为true，这就意味着当前校验的内存映射文件的数据是完整的，并且minLogicOffset对应的消息在CommitLog文件中的全局偏移量大于或等于CommitLog文件最小偏移量
                //这就意味着从当前队列的第一个内存映射文件的minLogicOffset位置开始消费消息，是可以消费到CommitLog文件中的有效消息，那这个时候就可以什么都不做，直接退出当前方法即可
                if (intact && commitLogOffset >= minCommitLogOffset) {
                    //记录信息日志
                    log.info("Abort correction as previous min-offset points to {}, which is greater than {}",
                            commitLogOffset, minCommitLogOffset);
                    //退出方法，因为一切都很完美不需要进行进一步的校正
                    return;
                }




                
                //执行到这里就意味着minLogicOffset对应的消息在CommitLog文件中的全局偏移量小于方法参数commitLogOffset，那现在就出现了一种情况，也就是说在第一个内存映射文件中
                //minLogicOffset位置消息在CommitLog文件中的全局偏移量是过期的，而内存映射文件最后存储的消息对应的CommitLog文件全局偏移量可能是没有过期的，是有效的
                //那接下来就要使用二分法，查找具体在第一个内存映射文件中的哪条消息对应的CommitLog文件全局偏移量正好大于或者等于方法参数commitLogOffset，只有找到了这个消费队列消息的位置
                //然后把这个位置赋值给minLogicOffset，这样一来消费者消费消息的时候才能得到CommitLog文件中的有效消息
                //接下来就是具体的二分法的操作了
                //初始化二分查找的低端索引为0
                int low = 0;
                //初始化二分查找的高端索引为映射缓冲区的大小减去一个存储单元大小
                //得到的就是第一个内存映射文件存储的最后一条数据的起始偏移量
                int high = result.getSize() - ConsumeQueue.CQ_STORE_UNIT_SIZE;
                //开始无限循环，执行二分查找
                while (true) {
                    //如果高端索引与低端索引的差值小于等于一个存储单元大小，意味着查到了文件末尾，退出循环即可
                    if (high - low <= ConsumeQueue.CQ_STORE_UNIT_SIZE) {
                        break;
                    }
                    //计算中间位置，确保其为存储单元的对齐位置
                    int mid = (low + high) / 2 / ConsumeQueue.CQ_STORE_UNIT_SIZE * ConsumeQueue.CQ_STORE_UNIT_SIZE;
                    //设置缓冲区的位置到中间位置，准备读取该位置的数据
                    buffer.position(mid);
                    //从缓冲区中读取这条消息对应的CommitLog文件的全局偏移量
                    commitLogOffset = buffer.getLong();
                    //如果读取到的消息对应的CommitLog文件的全局偏移量大于方法参数
                    if (commitLogOffset > minCommitLogOffset) {
                        //这个时候就可以将高端索引调整为中间位置，缩小搜索范围到左半部分
                        high = mid;
                    }
                    //如果读取到的消息对应的CommitLog文件的全局偏移量等于方法参数
                    else if (commitLogOffset == minCommitLogOffset) {
                        //这个时候就可以将低端索引和高端索引都调整为中间位置，意味着找到目标位置，可以结束二分查询了
                        low = mid;
                        high = mid;
                        break;
                    }
                    //如果读取到的消息对应的CommitLog文件的全局偏移量小于方法参数
                    else {
                        //这个时候就可以低端索引调整为中间位置，缩小搜索范围到右半部分
                        low = mid;
                    }
                }
                //遍历低端索引到高端索引之间的最后一条或两条消息数据
                for (int i = low; i <= high; i += ConsumeQueue.CQ_STORE_UNIT_SIZE) {
                    //设置缓冲区的位置到当前索引位置，准备读取数据
                    buffer.position(i);
                    //从缓冲区中读取物理偏移量
                    long offsetPy = buffer.getLong();
                    //如果读取到的消息对应的CommitLog文件的全局偏移量大于等于方法参数
                    if (offsetPy >= minCommitLogOffset) {
                        //这个时候就终于可以更新minLogicOffset为映射文件的起始偏移量加上起始位置和当前索引的值了
                        //这个位置就是最新的有效消息的位置，消费者只要从消费队列中读取这个位置，就能得到CommitLog文件中的有效消息
                        this.minLogicOffset = mappedFile.getFileFromOffset() + start + i;
                        //记录日志信息
                        log.info("Compute logical min offset: {}, topic: {}, queueId: {}", this.getMinOffsetInQueue(), this.topic, this.queueId);
                        //跳出循环，因为已经找到有效minLogicOffset偏移量了
                        break;
                    }
                }
            } catch (Exception e) {
                log.error("Exception thrown when correctMinOffset", e);
            } finally {
                //释放缓冲区对象
                result.release();
            }
        }
    }

}
```
